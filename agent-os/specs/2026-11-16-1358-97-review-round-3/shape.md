### R3-2: Decide whether a deferred item ships a mitigation from a signal that is not its free text

- **Mitigation (ships now, Plan Task 2):** `NOTHING_SHIPS` in `workflows/redline-loop.js` reads `none`, `n/a`, `nothing`, `nothing ships`, `nothing ships now` or `no mitigation` followed by its reason after a full stop, a semicolon, a colon or a spaced dash as no mitigation, so the wordings this round found no longer demand a commit; a comma or a word still goes on into what ships.
- **Title:** Decide whether a deferred item ships a mitigation from a signal that is not its free text
- **What was found:** Redline decides whether a deferred item ships a mitigation from the words of its free-text `mitigation` field: `hasMitigation` in `workflows/redline-loop.js` reads an empty string and a list of phrases (`none`, `n/a`, `nothing`, `nothing ships`, `nothing ships now`, `no mitigation`, alone, with a note in parentheses, or with their reason after a full stop, a semicolon, a colon or a spaced dash) as nothing, and any other text as a mitigation. When an agent says that nothing ships in other words, such as `No code ships in this pull request.`, the item is read as shipping one: the gate demands a commit naming it, the plan has no task for it, and the round stops at the check after its repair, the same way on every resume.
- **Why it is not fixed here:** The pull request that added deferred items reads "no mitigation" from the field's words, in one function, the same way everywhere (decision 35 of the #95 spec), and its first review round kept that reading and declined a field of its own for this change; the round that found the remaining wordings widened the list of phrases instead, so a reading that rests on another signal changes how that spec defines a deferral that ships nothing and is weighed on its own.
- **The fix proposed:** Have the shaper and the resolve agent state whether a deferral ships something as a field of its own (for example a required `ships` boolean beside `mitigation`), asked for in the template and the agent files, and have `hasMitigation` read it, keeping the words for the reply only; or, short of a new field, have the gate demand a deferral's commit only when the round planned a task with files for it, so a wording the list misses costs a mis-worded reply, never a stopped round. Pin a deferral worded `No code ships in this pull request.` with no task, which must end its round with no commit demanded.

### R3-3: Keep code as written in a drafted issue's multi-line body fields

- **Mitigation (ships now, Plan Task 3):** the shape, reshape and resolve prompts in `workflows/redline-loop.js` ask for each drafted issue's `found`, `why` and `fullFix` as one paragraph with no line break and code in inline code spans, and `issueDraft`'s comment and `docs/running.md` say a code span stays as written only in a field with no line break.
- **Title:** Keep code as written in a drafted issue's multi-line body fields
- **What was found:** Redline composes a deferred item's GitHub issue from the shaper's fields and passes `found`, `why` and `fullFix` each through `postedText` as one text (`issueDraft` in `workflows/redline-loop.js`). Under #87's rule in `textParts`, a text holding a newline is escaped whole, its code spans included, so a field written over several lines, or holding a fenced code block, files code such as `if ($a < $b && $c)` and a `@param` tag as `if ($a &lt; $b &amp;&amp; $c)` and `@&#8288;param`, which GitHub shows literally inside code. With `defer to print` the same escaped body is what the session prints for pasting into another tracker.
- **Why it is not fixed here:** The rule that escapes a text with a newline whole is #87's and is shared by every text Redline posts, and #88 tracks a rule for multi-line markdown with code fences in comments and replies. A rule that splits a body by Markdown block has to be checked against GitHub's renderer before it is used, as #87's triggers were, and the review round that found this had no way to run that check, so it asked the agents to write each field as one paragraph instead.
- **The fix proposed:** Escape a drafted issue's body fields by Markdown block, with the rule #88 settles for multi-line markdown or one of its own: leave a fenced code block as written, escape the prose around it, and keep each paragraph's code spans as written, with every construct checked once through `gh api markdown -f mode=gfm` on invented text and recorded. Then pin in `tests/loop-test.mjs` a `found` holding a fenced block with `<`, `&` and `@param`, filed unchanged while the prose around it is escaped.
