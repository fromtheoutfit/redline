# Decide whether a deferred item ships a mitigation from a signal that is not its free text

Redline decides whether a deferred item ships a mitigation from the words of its free-text `mitigation` field: `hasMitigation` in `workflows/redline-loop.js` reads an empty string and a list of phrases (`none`, `n/a`, `nothing`, `nothing ships`, `nothing ships now`, `no mitigation`, alone, with a note in parentheses, or with their reason after a full stop, a semicolon, a colon or a spaced dash) as nothing, and any other text as a mitigation. When an agent says that nothing ships in other words, such as `No code ships in this pull request.`, the item is read as shipping one: the gate demands a commit naming it, the plan has no task for it, and the round stops at the check after its repair, the same way on every resume.

- **Where:** `workflows/redline-loop.js:771`
- **Why it is not fixed in #97:** The pull request that added deferred items reads "no mitigation" from the field's words, in one function, the same way everywhere (decision 35 of the #95 spec), and its first review round kept that reading and declined a field of its own for this change; the round that found the remaining wordings widened the list of phrases instead, so a reading that rests on another signal changes how that spec defines a deferral that ships nothing and is weighed on its own.
- **Proposed fix:** Have the shaper and the resolve agent state whether a deferral ships something as a field of its own (for example a required `ships` boolean beside `mitigation`), asked for in the template and the agent files, and have `hasMitigation` read it, keeping the words for the reply only; or, short of a new field, have the gate demand a deferral's commit only when the round planned a task with files for it, so a wording the list misses costs a mis-worded reply, never a stopped round. Pin a deferral worded `No code ships in this pull request.` with no task, which must end its round with no commit demanded.
