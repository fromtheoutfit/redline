## scripts/guard

# The guard

`scripts/redline-guard.sh` is a default-deny allowlist per role, and every change to it is proven by a row in `tests/guard-cases.tsv`.

- The table at the top of the script is the policy: one line per role, its command groups and its write prefixes, both literal. A command a role newly needs is a new member of a group, never a looser parse
- Default deny: a command the classifier cannot place is refused. `bash` only as `bash -c <string>`, checked recursively; interpreters (`python3`, `node`, `php -r`), `gh`, `curl`, `eval`, `source` and `sudo` are refused for every role. The guard reads only the subcommand word after `redline-gh.sh`, never a query or a body, so a GraphQL mutation reaches GitHub only through a wrapper subcommand (`resolve-threads`, the github role's by `gh-all`): a `tests/guard-cases.tsv` row pins the raw `gh api graphql` form as refused to the github role, and the mutation's text is pinned by a `tests/gh-test.sh` case, not by the guard (#39)
- Write targets are checked, not only command names: redirections, `tee`, `sed -i`, `mv`, `cp`, `rm`, `mkdir`, `touch`, `git add` paths, `find -exec` and process substitutions all go through `writable()`
- Redline never edits Redline: the plugin's directory, `.claude/redline/`, `.claude/redline*.json`, `.claude/settings*.json` and the `.claude/{agents,workflows,skills}/redline*` copies are refused for every role, and so is a write that would take a directory holding one of them along (`rm -rf .claude`)
- When the repository is the plugin (its checkout loaded in place, Redline reviewing itself), the plugin's source is repository content under the roles' usual prefixes, except `scripts/redline-guard.sh` and `hooks/hooks.json`: the guard that vets the run is changed by a person, never by a Redline role (#4). A finding there is deferred, mitigated by a pinned `tests/guard-cases.tsv` row or a Known limits line, and a person makes the change after the run (#5, R1-1). The same holds for a finding whose fix needs `.claude/redline/checks.sh` restamped, which no role may write: one that changes the gate's backticked text, or how `scripts/redline-gate.sh` computes the hash or writes the stamp line. It is deferred with a Known limits line, and a person makes the change and restamps (#7, R1-1, R1-2). A finding whose fix touches `scripts/checks-template.sh` below its header, or changes the text `redline-setup.sh checks` writes into this repository's `checks.sh` (its header, the template version line, the check block), is deferred the same way: the setup test's last cases regenerate `checks.sh` from `checks.json` and compare it with the committed file, and no role may regenerate it, so such a fix leaves the gate red. The round records the intended lines in its Deferred entry, mitigated by a Known limits line, and a person makes the change, regenerates `checks.sh` and restamps after the run (#7, R1-14; #12, R1-1). `checks.sh` is generated from `.claude/redline/checks.json`, which no role may write either: a finding whose fix changes a check is deferred the same way, and a person edits `checks.json`, regenerates and restamps (#6)
- Protected paths are compared case-folded: the default macOS volume is case-insensitive, so `Scripts/redline-guard.sh` is the guard. Folding only ever refuses more; the prefix checks and the self-hosted test stay as spelled, which fails closed (#5, R1-4)
- What the guard allows it also approves (`permissionDecision: allow`), so a role never meets a permission prompt for a vetted command and the shared `settings.json` carries no git write rule
- Every change to the guard adds or changes a row in `tests/guard-cases.tsv` in the same commit, with the `agent_type` Claude Code sends, beside a row for the neighbouring decision that must not change (`allow Write REPO/scripts/redline-guard.sh` in an ordinary repository, next to the self-hosted `deny`)
- An agent's prompt tells it the shape of a command the guard accepts: no `$`, no backticks, no process substitution, one command per call, redirection only into the temp directory. When a prompt and the table disagree, the table wins and the prompt is fixed
- A Redline role is identified by `agent_type` alone (`redline:redline-<role>`, or `redline-<role>` for a copy under `.claude/agents/`); anything else, the main session included, leaves the guard inert with no output, with one exception: a Bash call that is one of the plugin's own scripts by real path (`redline-gh.sh`, `redline-prefs.sh`, `redline-gate.sh check`, `redline-setup.sh version`), the repository's `checks.sh`, or read-only git is approved for any session, so the shared allow list carries no `Bash(/*/scripts/…)` rule that a script of the same name at any path an agent could write would match, and a reason for such a session is inert, never a deny, so the permission prompt decides (#50)
- A guard denial is a sentence a person can act on: which file or command, which rule, and for the self-hosted files, who changes them
- A repository's ask rules (`askRules[].when.paths` in `.claude/redline.json`, #49) add to the refused set for every role: the guard reads the file at each call, refuses a write under a rule's globs naming the rule and its reason, refuses a write to a directory that holds a rule's root (`rm -rf config`, or a pattern whose literal prefix is the root or above it), resolves the target through symlinks first (always, a missing parent included, so a link under the temp directory that points into a match is refused), and fails closed on a malformed list, refusing every write until a person fixes the file. The glob dialect (`**` across segments, `*` and `?` inside one, a slashless pattern at any depth, a leading slash anchoring, a trailing slash taking the directory) is one function in the guard and one in the workflow, pinned by the same cases on both sides; `tests/guard-test.sh` prepares the fixture repositories the rows need under `~/.cache/redline/` on every run
- A Bash write target holding `*`, `?`, `[` or `{` is refused for every role unless it is under the temp directory: the guard checks paths, not patterns, and expanding the pattern at check time is not a fix, since a pattern that matches nothing when the hook runs can match a file an earlier command in the same call creates. The literal prefix still goes through the protected and ask-rule checks first, so the specific reason wins where it applies, and the refusal names the protected file or rule the pattern could reach. A tool's `file_path` is literal and never cut (#53, closing #52 R1-1)
- Read-only git is vetted by flag, for every role and the main session: `--output`, `-O`/`--open-files-in-pager` and `--ext-diff` on a read subcommand, every `-c`/`--config-env` (a configuration key can name a program: `diff.external`, `core.pager`, `core.fsmonitor`, `gpg.program`, `filter.*.clean`), `--exec-path`, and every `GIT_*` or `PAGER` environment prefix are refused outright; no key list is kept, since nothing legitimate uses them and a list would need keeping (#50)

## scripts/bash-conventions

# Bash scripts

Every script under `scripts/` is its own documentation and talks to the workflow in JSON.

- Every script starts `#!/usr/bin/env bash` and `set -euo pipefail` (`redline-gh.sh`, `redline-guard.sh`, `redline-prefs.sh`, `redline-gate.sh`, `redline-setup.sh`, `checks-template.sh`). The test harnesses use `set -uo pipefail` instead, because one failing case must not stop the table
- A script a workflow reads emits exactly one JSON object on stdout and everything else on stderr: `checks.sh` logs through `log()` to stderr and prints the envelope last; `redline-prefs.sh resolve` and the read subcommands of `redline-gh.sh` print JSON and nothing else
- `bash -n` reads its first file and treats the rest as arguments; check several with `ls <glob> | xargs -n1 bash -n` (#5, R1-3)
- Usage errors exit 2 with a one-line reason on stderr. A check that fails exits 1. A script whose exit code is an answer (`redline-gh.sh has-review`: 0, 1 or 2) says so in its header
- A wrapper that runs another script for a role (`redline-background.sh` around `checks.sh`) passes the wrapped script's stdout and stderr through unchanged, and its documented exit codes (0, 1 and 2 for `checks.sh`), so the role reads the result as it would the script's own, and takes the codes above them for its own answers (3 still running, 4 past the limit, 5 no result), stated in its header. Any other code the wrapped script exits with (a command failing under its `set -e`, a signal) is the wrapper's no-result answer with a line naming the code, never passed through: a passed-through 3 reads as still running and loops the role (#41, R1-3). A result the wrapper keeps under a label the workflow reuses is read once: the wait that returns it removes the label's files, so a wait that runs before the next start has cleared them cannot return the earlier run's result (#41, R1-2). It runs one fixed script, never a command it is given, so the guard admits it by subcommand (#40)
- The header comment is the documentation, in this order: what the script is, usage, environment variables, the output contract, the exit codes. The README quotes from it rather than restating it. A field added to `checks.sh`'s JSON, or a limit changed in it (`run_check` in `scripts/checks-template.sh`), updates the README's output contract in the same change, and a flag that reports a cut is set by every limit that can cut (#7, R1-14). `checks.sh`'s whole JSON stays bounded however many checks fail: the failing checks share one output budget, split evenly among them in a final pass after every check has run, never consumed in run order, because the checker may not Read a result that spills to a file (#7, R1-13)
- A change to what a subcommand selects or prints rewords every description of it in the same commit, found by searching for the old phrase across `README.md`, `skills/` and `agents/` rather than by editing only the `redline-gh.sh` table row that quotes the header: R1-3 changed which review body `human-review` takes and updated the header, the README's `redline-gh.sh` row and the revise skill, and left the README's paragraph on `/redline:redline-revise <pr> review` describing the old selection (#38, R2-1)
- A subcommand added to `redline-gh.sh` or `redline-prefs.sh` is added to the guard's groups in the same change (`GH_READ` for a read subcommand; `gh-all` already covers a write one), and the agent or skill that calls it names the exact spelling
- A script only a skill calls (`redline-prefs.sh`, `redline-gate.sh`, `redline-setup.sh`) needs no guard group: the guard's default deny refuses it to every role, and `tests/guard-cases.tsv` rows pin it as the skill's (#6); when one of its subcommands is reserved for a person, its rule in the shared allow list (`templates/settings.allow.json`, and the repository's `.claude/settings.json`) names only the subcommand the skill runs unprompted (`Bash(/*/scripts/redline-gate.sh check *)`), so the reserved one stays behind the permission prompt (#7, R1-9); `redline-setup.sh`'s writing subcommands have no allow-list rule, and the permission prompt is the person's confirmation (#6), while `version`, which writes nothing and which `/redline:redline`'s precheck runs at every launch, once had the one narrow rule, `Bash(/*/scripts/redline-setup.sh version *)`, on the pattern of `redline-gate.sh check`'s (#12, R1-8); since #50 the allow list carries no script path rule at all (a `Bash(/*/scripts/…)` rule matched a script of that name at any path an agent could write), and the guard approves the one unprompted subcommand (`redline-gate.sh check`, `redline-setup.sh version`) for the main session by real path, so the reserved ones stay behind the permission prompt
- A generator that writes a file from a template (`redline-setup.sh checks` from `checks-template.sh`) splices by anchor lines and exits 1 naming a missing one, so the template and the generator cannot drift apart silently, and its output is deterministic: the same input gives the same bytes, and nothing is written when they are unchanged (#6). It validates every input field it writes, not only the commands: a field that lands in a comment is a single line, and one that lands inside quotes holds no character that would end or expand them, so a bad `checks.json` exits 2 rather than writing a `checks.sh` that runs a stray line (#12, R1-6)
- A script that edits a person's file (`.gitignore`, `shape-spec.md`, `settings.json`) preserves the file's line endings and a byte-order mark (`settings.json` refuses a byte-order mark instead, exit 2, as its header says), writes only when the bytes change and reports `changed: false` otherwise, so a rerun can say nothing drifted; a JSON file is compared with `jq -S`, since a CLI that rewrites it (`claude plugin install`) reorders keys and that is not drift (#6)
- A merge into a person's JSON file keeps every value already there, adds only what is missing, and reports each kept value that differs from the template (`conflicts`) rather than overwriting it (#12, R1-3, R1-4); every subcommand that writes takes `--dry-run`, which prints the same JSON with `written: false` and creates nothing, not even the target's directory (#12, R1-2)
- A rerun over a file the script wrote earlier changes only the values the script derives from its inputs (`config` updates `checker` and `checkerStallMs` in place, keeping the file's formatting) and keeps every other value as the person's, the ones the person chose at setup included (`reviewer`), listing each that differs from the template under `differs` without changing it; `--force` is the full reset to the template (#12, R1-5)
- A rerun's `differs` lists drift from the template, never the person's own additions: `config_differs` ignores a key only the person writes (`askRules`), so a rerun does not report the rules as values to reset (#49)
- A validator that shares its messages with another (`ask_rules_fault` in `redline-setup.sh`, `rule_fault` in the guard, the workflow's launch check) shares its tests too: a key's presence (`has("paths")`), never a non-null value, so `{"paths": null}` gets the shared message instead of passing, and a list's elements are filtered to objects (`objects`) before a field of each is read, so a non-object element gets `not an object` and exit 2 instead of jq's own error and exit 5 under `set -e` (#52, R1-2), and a pattern is matched against the whole string, `\A...\z` in jq: jq's `$` also matches before a final newline, so `^[a-z][a-z0-9-]*$` passed the id `"a\n"`, which the guard's `fullmatch` and the workflow's `/^...$/` refuse, and setup wrote a list that then stopped every run (#52, R2-1)
- A flag that replaces a list a rerun otherwise keeps (`config --ask-rules`) clears it with `[]`, and the skill that calls it passes `[]` when the person removes every entry: without the flag the old list stays, so "with none, omit the flag" left a removed list enforced (#52, R1-3)
- A jq program that holds a quote goes in a quoted heredoc (`prog="$(cat <<'JQ' ... JQ)"`, then `jq "$prog"`), never in a bash single-quoted string: `ask_rules_fault` first wrote `'\($r.id)'` inside `jq -r '...'`, which ended the bash string at the first quote and failed `bash -n` (#49)
- Python inside a script is `python3 -I -c "$PYTHON"` with the standard library only, fed on stdin; it writes no file beside the script
- A path the script receives is made absolute once (`cd "$(dirname "$path")" && pwd`) and used as is; the repository is `git rev-parse --show-toplevel`, never a walk from `$PWD`
- A path compared with `git rev-parse --show-toplevel` is made physical first (`pwd -P`): git prints the physical path, and on macOS `/var` is `/private/var`, so a logical path never matches its prefix (#6)
- A header printed by `-h|--help` is printed with `sed -n '2,/^$/p'`, never a numeric range, which rots on every header edit (#6)
- A script that chooses which part of a file to hash refuses when more than one part qualifies, naming each by line, rather than taking the first: a silent switch moves the hash onto the wrong text and every later check passes against it (#7, R1-6)
- Never print a token, a header or an environment dump; `redline-gh.sh` leaves authentication to `gh`
- `jq` reads and writes every JSON value; no hand-built JSON strings in bash
- A JSON value that grows with the pull request (the anchor positions of `place`, megabytes on a 336-file PR) reaches `jq` through `--slurpfile` or `--rawfile` from a temp file, never `--argjson`, which puts it on the command line and fails with "Argument list too long" (#33)
- `redline-gh.sh` never calls `gh pr diff` or `gh pr view --json files`: the first refuses a PR over 300 files, the second stops at 100, so the paginated files endpoint (`gh api --paginate --slurp`, gh 2.48.0 or newer, which the script names when an older gh rejects the flag) is the one source of the file list, the diff and the anchor positions (#33)
- A read subcommand whose answer is a number (`last-round`) prints it as a bare JSON number, `0` for none; one whose answer is yes or no (`has-review`) uses the exit code
- GraphQL in `redline-gh.sh` is two fixed strings (`THREADS_QUERY`, `RESOLVE_MUTATION`), parameterised by `-F` variables only (`owner`, `name`, `number`, `endCursor`; `threadId`) and never built from an argument; `gh api graphql --paginate --slurp` follows `pageInfo` through `$endCursor` into one array of pages, and gh fills `{owner}` and `{repo}` in `-F` values as it does in an endpoint. A write subcommand that reads first (`resolve-threads` reads the threads, then sends one mutation per thread) exits 2 when the read fails and 1 when a mutation does, after the ones already sent, as its header says (#39)
- A GitHub login a selector names is matched case-folded (`ascii_downcase` on both sides of the comparison), since GitHub treats logins case-insensitively, and a skill takes the login it writes as an owner from the script's output, never from the text as typed (#38, R1-2)
- Every script runs under Apple's bash 3.2 with BSD tools (the macOS CI leg pins `/bin/bash`) and under bash 5 with GNU tools (Ubuntu), so bash 4 features (`declare -A`, `mapfile`, `${x,,}`) and GNU-only flags stay out; shellcheck covers `scripts/*.sh`, `tests/*.sh` and the generated `checks.sh` at severity warning, set by `-S warning` on the workflow's command, required, and every code `.shellcheckrc` disables names the line that needs it (#17). `.shellcheckrc` holds no severity: shellcheck 0.11.0 ignores a `severity=` key there and honours `-S`, so a severity in the rc file reads as set and is not (#47, R1-2)
- A workflow `run:` block whose exit status rides on a pipe opens with `set -euo pipefail`, as a script does: GitHub runs a step with no `shell:` as `bash -e`, without pipefail, so the advisory shellcheck step's `shellcheck ... | sed ...` exited with sed's status and passed on every finding, and on a runner with no shellcheck (#47, R1-1)
- An allow entry a template drops is added to `templates/settings.retired.json` in the same change, so `redline-setup.sh settings` can report it under `stale` in a repository set up earlier and remove it with `--remove-stale`; a merge never removes on its own, and a person's own entry is never stale, since only the retired list is consulted (#50)
- A change to `scripts/checks-template.sh` below its header bumps its `# redline-template:` version line, which is how a set-up repository is told to rerun setup (`redline-setup.sh version` exits 1, the launch precheck warns); a fix left at the old version reaches only fresh setups (#50)

## testing/tests

# Tests

Seven harnesses, no framework, each runnable alone, and all of them through `.claude/redline/checks.sh --baseline`.

- `tests/guard-test.sh` over `tests/guard-cases.tsv`: every row is the hook input Claude Code would send (`agent_type`, tool, command or path) and the decision expected. A `# @cwd PLUGIN` line sends the rows after it from the checkout, where the repository is the plugin. About 60 ms a row; 350 rows on 2026-10-21
- `node tests/loop-test.mjs`: `workflows/redline-loop.js` under scripted `agent()` and `parallel()`; it asserts which agents ran, in what order, with what prompt text, and what the script returned. No model, no GitHub, no repository. Its human-pass scenario proves the H ids, the reviewer and the author as owners, the final nit pass as a Redline round and the summary comment in place of the handoff (#36). Its thread-sweep scenario proves the selection (fixed, deferred and decided findings with a reply posted; never a body finding, a dropped one or a teammate's thread), the handoff line, a skipped thread left open with its reason, a thread already resolved in neither count (#45, R1-3), and the absence of the sweep on a dry run, `no push`, a capped run, a hand-off and `review only` (#39). Its carry-forward scenario proves the two prompt lists, the review body headings, the carried-forward and resolved replies in the earlier threads, the sweep ids and the handoff's Earlier rounds section, and that the loop carries a finding the reviewer did not account for (#35), that a review with no carry-forward list clears a `carriedFrom`, that a fallback carry is numbered after a gap in the reviewer's ids, that an earlier thread is swept when its carrying finding sits in the review body, and that a finding an earlier run carried is named by its new id (#46). It also proves that a carried finding the reviewer marks known by a Redline id is still carried, and that one an issue tracks stays known, with its earlier thread answered `carried forward as R2-1; already tracked in #41` from both the revise pass and a round with no revise pass, and left open (#46, R1-2)
- A loop-test mock answers as the real agent would for the run's settings (the post mock returns no comments in a dry run), or the path the setting changes goes untested (#34, R1-7; #37, R1-1)
- A loop-test scenario scripts the checker's result shape per call (a passing gate with a stray `error`, a failing gate, an unreadable result, a baseline that cannot be read, a structural misread the workflow overrides beside the run-level reason that still stops, #55, and what the stop record keeps after the override, #56, R1-1), as it scripts the reviewer's findings, so the stop and the repair paths are both asserted (#9)
- A fix for a value one call site mishandled is pinned at a second call site too, so the test proves the rule and not only the site: #42's fix covered nine checks and scripted `'""'` at one, so a revert at the other eight stayed green (#43, R1-1)
- `tests/prefs-test.sh`: the merge rules of `scripts/redline-prefs.sh`, in a throwaway repository under the temp directory
- `tests/gate-test.sh` over `tests/gate-fixtures/`: the gate parser and the stamp of `scripts/redline-gate.sh`, on one synthetic `shape-spec.md` per gate shape seen so far, mutated with `sed` and `awk` in the temp directory; the fixture hashes are pinned inline, and the last case checks this checkout's own stamp (#6)
- `tests/setup-test.sh` over `tests/setup-fixtures/`: the subcommands of `scripts/redline-setup.sh`, on a settings file with other keys, a bare `shape-spec.md` and a Laravel-shaped `checks.json`, in the temp directory; its last cases regenerate this checkout's own `checks.sh` from its committed `.claude/redline/checks.json`, stamp it and compare, and prove a regenerate over the committed file is a no-op (#6)
- `tests/gh-test.sh` over `tests/gh-fixtures/`: the read subcommands of `scripts/redline-gh.sh` that a large pull request exercises (`files`, `diff`, `place`, `last-round`, `has-review`) and the human-review ingest (`human-review`, `last-human-review`, on a PR with a teammate's submitted review, their single comment, their reply inside a Redline thread and the author's hand reply; #36; a thread two teammates share, under a Redline reply that names the one comment it answered; #38, R1-1; a review body a Redline human review comment answered, beside an older open one and a teammate's comment that quotes the header without the marker; #38, R1-3) and the thread sweep (`threads`, `resolve-threads`, on a PR's review threads over two GraphQL pages: a Redline thread with its reply, one a teammate replied in after Redline, one a teammate opened, one already resolved, one with no reply yet; #39; one with a teammate's comment between Redline's comment and its reply, which stays open; #45, R1-2) and the prior-findings read (`prior-findings`, on PR 14: one finding per disposition, a body finding answered by an issue comment, a teammate's reply that is not a disposition, an Already tracked line that is not a finding, and a round that carried an earlier finding; #35), against a fake `gh` first on PATH that serves the fixtures by endpoint (an array of pages for `--paginate --slurp`, a `--jq` filter applied with the real jq), refuses `gh pr diff` as GitHub does over 300 files, refuses every write except the one `gh api graphql` call, whose query it serves from the fixture pages and whose mutation it appends to a log the cases read, pinning which threads were resolved and the mutation's text byte for byte (#39), and plays an older gh that rejects `--slurp`; nothing reaches GitHub (#33)
- `tests/background-test.sh`: `start` and `wait` of `scripts/redline-background.sh` against a stub `checks.sh` in a throwaway repository with its own `TMPDIR`: results passed through as printed (exit 0, 1 and 2), still running, past the limit, a run that died or never started, a rerun under the same label with its wait sent at once, a result read once (#41, R1-2), a gate exit outside 0, 1 and 2 reported as no result (#41, R1-3); `REDLINE_BACKGROUND_POLL` shortens the waits (#40)
- A harness that polls for a file the script under test writes bounds the poll (`within <seconds> <test>`), so a red run, where the script is missing, fails the case instead of hanging the table (#40). A harness never waits for a precondition the role cannot wait for: `background-test.sh` waited for the old result to vanish before calling `wait`, which hid the race the role's back-to-back calls hit (#41, R1-2)
- A fixture is made large enough to hit the limit it guards: the gh harness's 150 small files passed while Losers League #778 (336 files, a 1.8 MB diff) overflowed the command line, so it also carries a 60,000-line patch (#33)
- The ask rules (#49) are proven in four harnesses: `tests/guard-test.sh` prepares two fixture repositories under `~/.cache/redline/` on every run (a rules file with a paths, an any-depth and a prose rule, files, a symlink inside the repository and one under `/tmp` into it; a malformed list), switched to by `# @cwd ASKRULES` and `# @cwd ASKRULESBAD`, and reads an optional fifth column the deny reason must contain, so a row pins the rule named and not only the decision, and pins the wildcard operands as refused, naming the rule each could reach (#52, R1-1; #53); `tests/loop-test.mjs` scripts the shaper's `files` and `askRule` per finding and proves the forced ask, the autopilot `left`, the review mark, the injected list, the handoff section, the open threads, the refused override, the no-rules prompt identity and a human pass's `none` on a rule-covered file left as `none` (#52, R1-4); `tests/setup-test.sh` proves the `config --ask-rules` round trip, an empty list clearing an existing one (#52, R1-3), every validation message (a null `paths` or `prose` and a non-object rule before an object included, #52, R1-2; an id ending in a newline, #52, R2-1) and the `composer.json` suggestions on a Craft and a Laravel fixture; `tests/gh-test.sh` proves the stripped finding-line tail and the `left` reply on PR 14's R2-3
- A change that touches a tested surface adds a case in the same commit: a guard row, a loop check, a prefs case, a gate case or a setup case, and a row beside it for the neighbouring decision that must not change
- A comparison of two command outputs passes when both are empty, so a harness pins at least one output against a literal before it compares outputs with each other (#6); a check that two outputs differ also requires each side to be a well-formed value, since the empty output of a failed command differs from everything (#7, R1-10)
- A case named for a boundary asserts the boundary itself: one that says it checks a header's last line matches the last non-blank line of the output, not text a few lines before it, or a cut between the two still passes (#34, R2-1)
- `.claude/redline/checks.sh` carries the gate stamp (`# redline-gate:`); a change to the backticked text of the gate list in `shape-spec.md`, or to how `scripts/redline-gate.sh` computes the hash or writes the stamp line, restamps it in the same commit, and the gate test's last case proves it (#6; #7, R1-1). `checks.sh` is generated: a change to a check edits `.claude/redline/checks.json` and regenerates with `scripts/redline-setup.sh checks .claude/redline/checks.json .claude/redline/checks.sh` in the same commit, never a hand edit, and the setup test's last cases prove the two agree (#6)
- A bug fix lands red before green: the case that reproduces it is added first and seen to fail, then the fix
- The tests write only under the temp directory and `~/.cache/redline/`, never into the checkout; a fixture copy is changed with `sed ... > <copy>` (or `awk`) in the temp directory, never `sed -i`, whose argument differs between BSD and GNU sed (#12, R1-9)
- A stand-in checkout (a copy of the working tree made to prove a rerun or a fresh setup) goes outside the temp directory: the guard's `TMP` prefix lets every role write there, so the guard test's write rows show false allows from a checkout under it (#6)
- The gate records its baseline time in `.claude/redline/checks.sh`'s header; a test that doubles it says why in its own header
- The gate runs in CI (`.github/workflows/gate.yml`) on every push to a pull request and to `main`, on Ubuntu and macOS, as the checker runs it (`checks.sh --baseline`), then `redline-gate.sh check`, `redline-setup.sh version` and a clean-tree check; the workflow adds no check of its own, so a new gate step is an edit to `checks.json`, and a harness that fails on one OS is fixed on that OS, never skipped or weakened in the workflow (#17)
- A main-session row uses `-` as the agent and expects `allow` for the plugin's scripts by real path, the repository's `checks.sh` and read-only git, and `inert` for everything else (a copy under `/tmp`, a reserved subcommand, a refused flag, a pipe into another command), never `deny` (#50)
- A version case derives the older and newer versions from the template's own `# redline-template:` line (`TV`, `TN` in `tests/setup-test.sh`), never spelling them, so a template bump changes no test (#50)

## process/docs-gate

# Docs gate

Every spec names the README and template changes it needs, so a public reader is never behind the code.

- Gate step 10 in `.claude/commands/agent-os/shape-spec.md`: for each file added or altered under `scripts/`, `skills/`, `agents/`, `templates/`, `workflows/`, `hooks/` or `.claude-plugin/`, and for each new config key, subcommand, allow rule or exit code, the plan names the README section (and template, if any) and either the commit that updated it or "no reader-facing change" with the reason
- A plan that cannot name the section adds one; the entry then names the new section
- The entries are written at shaping time, one per touched file, in `plan.md`: in the task that touches the file (as point 7 of the unattended section has a Redline shaper write them) or together under one Docs entries heading (as the #13 spec did); either placement meets this rule, and the gate confirms each names its commit or its reason (#51, R1-2)
- No commit exists at shaping time: a plan's entry names the README section (and template) its task updates, or the reason there is no reader-facing change, and its commit is that task's own, named in `plan.md`'s As built when it lands and confirmed at the gate. The plan approver checks the section or the reason only: its check 8 first asked for the commit too, which no reshape could supply, so a plan written as point 7 says could be bounced until the run ran out of adjustments (#51, R1-3)
- The README names a gate step by its title, never by its number: the numbers move whenever a step is inserted before them (#40 moved the retrospective from 9 to 10, #13 from 10 to 11), and a gate edit touches no directory this step lists, so no Docs entry would flag the stale number (#51, R1-1)
- In a Redline run the shaper writes them from the unattended section's point 7, so the round's commits carry the README edit; the plan approver bounces a plan missing one; the reviewer reports a change with no entry as a nit with the fix "update section X of the README"
- A prose step whose text holds a backticked span is inside the stamp: adding this step moved the hash, and the restamp went in the same commit (#13)
- Point 7 of the unattended section keeps its "Steps … stay as written" sentence first on its line and says "gate step" in lower case after it: `redline-setup.sh unattended` reads the fill-ins back by leftmost match, so an earlier capital "Step" on that line would be read as the fill-in (#13)

## process/standards-retrospective

# Standards retrospective

Every spec ends by asking what it taught, mechanically, and the answer lands in a standard or is recorded as "no changes".

- Gate step 11 in `.claude/commands/agent-os/shape-spec.md`: list every Decision in `shape.md`, every deviation in `plan.md`'s As built, and every check that went red and was fixed by learning something; classify each as already in a standard, missing, or contradicting one
- Approved edits land in their own commit, separate from the spec's code. Code that enforces a new rule (a guard-cases row, a loop-test check) follows in its own commit with the case proving a violation fails
- In a Redline run the shaper proposes the edits under `## Standards retrospective (proposed)` in `shape.md`, the standards approver approves the list, and the implementer applies it in one commit
- When nothing changes, `shape.md` records "Standards retrospective: no changes" under Decisions, so the absence is deliberate and visible
- A standards edit keeps the file's headings: they diff empty against `main` unless the spec names the section it adds, renames or removes
- `index.yml` lists every standard and nothing else; a new file is added to it in the same commit, alphabetised by folder and file

## prompts/attribution

# Attribution

Redline labels its own work as Redline and never as a model or a vendor.

- `Redline round N` review titles, the `redline:` commit prefix, the `Redline handoff` comment and `decided by: redline` are a tool's name and are allowed everywhere
- No `Co-Authored-By`, no "Generated with", no model or vendor name in a commit message, PR body, review, reply, issue, spec file or standard. The guard refuses a commit message that carries one (`ATTRIBUTION` in `scripts/redline-guard.sh`), after stripping path spellings such as `.claude/` and `CLAUDE.md`
- A repository's CLAUDE.md gets the paragraph from `templates/claude-md-git-sentence.md`, so a model reading its no-attribution rule does not take Redline's label for attribution
- This repository's own commits, issues and specs follow the same rule; the plugin manifest names its author, who is a person
- An agent prompt never says which model is running; a role is named by what it does (reviewer, shaper, checker)
