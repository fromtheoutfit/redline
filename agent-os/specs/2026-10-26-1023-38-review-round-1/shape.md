## Decisions

- **R1-1 · decided.** Tie a Redline reply to the comments it actually answered.
  - **Question.** How should a Redline reply be tied to the comments it answered?
  - **Story.** Two teammates review the PR. Marc leaves a comment on a line. Sam replies under it, from a review of his own, asking for a null check, and later Marc adds "also rename baz" in the same thread. You run Redline over Marc's first review. It fixes the rename and replies in that thread. Then you run it for Sam (`review @sam`) or for the newest review (`review latest`). Redline says there is nothing to revise and stops: it counts every comment posted before its reply in that thread as answered, whoever wrote it. Sam's null check and Marc's follow-up are never fixed or answered, and nothing tells you. The PR's own advice for several reviewers, one pass per review, is the path that loses them. (Why a person: spec assumption.)
  - **Options.** (1) **Name the comments in the reply** (recommended). Every human-pass reply ends with a hidden line `<!-- redline:answers <ids> -->` listing the comment ids it answers (each finding's `commentId`; with R1-4's merged reply, every finding in that thread). `human-review` counts a comment as answered only when a Redline reply in its thread lists its id, and keeps today's thread rule for a reply without the line (a Redline round's reply, or a human-pass reply posted before this change). Cost: `replyEntry()` in `workflows/redline-loop.js`, the filter and header in `scripts/redline-gh.sh`, the `human-review` row in `README.md`, a new PR 11 fixture in `tests/gh-fixtures/` with `tests/gh-test.sh` cases, and one loop check. About 20 lines of code, all in files this PR already changes. Effect: a pass answers exactly the comments it took in; afterwards `review @sam` lists 911 and `review @marcamos` lists 912. (2) **Read the earlier records.** The skill reads the committed `human-review-<m>.json` records on the branch and treats as answered only the comment ids an earlier pass ingested and replied to. Cost: a skill-side filter or a new script argument, coupling the wrapper or the skill to the spec folder layout, and a pass that stopped at a hand-off has a record but no reply. Effect: correct for passes run from this branch, blind to a record not yet committed. (3) **Document it.** A Known limits line in `README.md`: a pass's reply counts every earlier comment in its thread as answered, so a comment left in someone else's thread is handled by hand. Cost: one line. Effect: the gap stays, but the author knows to check shared threads.
  - **Recommendation.** Name the comments in the reply: it ties each reply to exactly what it answered, stays inside this PR's files, and keeps today's rule as the fallback for replies that predate it.
  - **Decision (2026-10-26).** Option chosen: **Name the comments in the reply.** The author has each human-pass reply list, in a hidden line, the comment ids it answers, and counts a comment as answered only when a reply in its thread names it, with the thread rule kept for replies that don't have the line, so a later pass over another reviewer's review still finds the comments left in a shared thread.
  - **Planned as** `plan.md`, Task 5.
  Decided by: @michaelfromtheoutfit
- **R1-2 · fix.** Match the login case-folded in both places `@login` selects. Downcase the selector once where `$pick` is built (`{kind: "login", login: ($selector[1:] | ascii_downcase)}`), and compare `(.login | ascii_downcase)` and `((.user.login // "") | ascii_downcase)` against it. The skill takes the reviewer login from the script's output (`body.user` when `body` is not null, else `comments[0].user`), never the typed text. The script header and the README row say the match ignores case. A gh-test case pins `@MarcAmos` against the literal `@marcamos` result. Likelihood and impact: it needs a login typed in a different case from GitHub's spelling. That is easy to do with a mixed-case login, and when it fires the pass stops with "nothing to revise" while the teammate's comments stay open. It is visible, but it misleads. Cost: three `ascii_downcase` edits in one jq filter, one sentence in the skill, two documentation phrases and one gh-test case, all in the PR's diff. Proportionate.
  Decided by: redline
- **R1-3 · decided.** Detect an already-answered review body, and decide which body @login takes.
  - **Question.** How should an answered review body be detected, and should `@login` reach a body older than the newest?
  - **Story.** Marc's review has three inline comments and a general note in its body ("the empty case needs a test somewhere"). Redline fixes all four and answers the note with a PR comment. A day later you run `review latest`, or `review @marcamos`, again to pick up anything new. Nothing is new, but Redline does not stop. The script never checks whether a review's body was answered, so it hands the old note back as a new finding, H2-1. The shaper re-plans work that is already done. If it marks the note a fix there is nothing to commit, so the gate fails with "no commit names H2-1" and the pass stops; otherwise a second PR comment answers the same note again. Separately, `review @marcamos` only ever looks at Marc's newest review body, so an older note of his is never picked up by login. (Why a person: spec assumption.)
  - **Options.** (1) **Name the review in the reply, newest unanswered body** (recommended when R1-1 is answered "Name the comments in the reply"). The body finding's PR comment names its review: the header becomes `**H1-4** · from review 7 by @marcamos`, in `passOf()`'s `bodyHeader` and `bodyHeaderHint`. `human-review` also reads the PR's issue comments, as `last-human-review` already does, and treats a body as answered when a Redline human review comment names its review. `@login` takes the newest body that is still unanswered, so a pass still takes one body, as the spec chose. Cost: `scripts/redline-gh.sh` (one more paginated read and the filter), `passOf()` in `workflows/redline-loop.js`, `tests/gh-test.sh` with a fixture issue comment, one loop check, and `README.md`. About 25 lines, in files this PR already changes. Effect: a second pass over an answered review stops with "nothing to revise", and an older unanswered body by the same login surfaces on the next pass. (2) **Name the review, every open body.** As option 1, and `@login` takes every unanswered body by that login, each as its own finding. Cost: option 1 plus an output-contract change (`body` becomes a list) carried through the skill, the `human-review-<n>.json` record and the workflow's `revise.body`; roughly double. Effect: one pass picks up every general note a teammate left. (3) **Read the earlier records** (pairs with R1-1's option 2). A body counts as answered when an earlier committed `human-review-<m>.json` names its review under `body` and that pass's summary file exists. Cost: a skill-side check with the same coupling to the spec folder layout. Effect: as option 1, for passes run from this branch. (4) **Document it.** A Known limits line in `README.md`: a review body is ingested on every pass that selects its review, so when it is already done, answer its call with no change. Cost: one line. Effect: the repeat stays, and the author handles it each time.
  - **Recommendation.** Name the review in the reply and take the newest unanswered body. It uses the same idea as R1-1's recommended answer, keeps one body per pass as the spec chose, and lets the "nothing to revise" stop fire.
  - **Depends on** R1-1: the detection should use the same mechanism as the answer there (a reply that names what it answered, or the committed records).
  - **Decision (2026-10-26).** Option chosen: **Name the review in the reply, newest unanswered body.** The author has the body reply name the review it answers, makes human-review skip a body whose review a Redline human-review comment already names, and keeps one body per pass (the newest one not yet answered), so a repeat pass over an answered review stops with nothing to revise and an older note comes up on the next pass.
  - **Planned as** `plan.md`, Task 6.
  Decided by: @michaelfromtheoutfit
- **R1-4 · fix.** In a human review pass, the reply entries that share a non-zero `comment_id` merge into one. The merged entry keeps the first finding's id as `finding`, lists every id under `findings`, and keeps the shared `comment_id` and route. Its file is `human-review-<n>-reply-<ids joined by ->.md`. Its body opens `Redline human review <n>:` and gives each finding's outcome on its own `**H<n>-<k>**:` line, with each line's owner as today. A Redline round never merges (each finding has its own root), so its prompts stay byte-identical. The human push prompt and `agents/redline-github.md` say one entry may answer several findings of one thread and is still one reply. Likelihood and impact: a teammate who adds a follow-up in their own thread, or a reply inside a Redline thread next to their own comment, is ordinary GitHub use. `review @login` selects both, and the reviewer reproduced the pair on the s2 fixtures. When it fires, one finding's outcome never reaches its thread, or two replies land against the run's own rule, and the summary says every comment was answered. Cost: one helper of about 20 lines and one call site in `workflows/redline-loop.js`, one sentence in the human push prompt and one in `agents/redline-github.md`, and two loop checks, all in the PR's diff. Proportionate.
  Decided by: redline
- **R1-5 · fix.** A plan approval is keyed by the pass. `passOf()` gains `planKey`: the round number for a Redline round, `h<n>` for a human review pass. `revise()` checks `approvedPlans.includes(pass.planKey)`, and `handoffResult()` adds `passOf(record).planKey` to `approveWith.approvedPlans`. The `approvedPlans` parse keeps numbers as today and also keeps strings of the form `h<n>`. The result's relaunch `how` text, the comment above the parse and `skills/redline/SKILL.md:167` say a human review pass is approved as `h<n>`. Three loop checks: the existing human plan-dial run returns `{"approvedPlans":["h1"]}`; with `firstRound: 1`, `approvedPlans: [1]` still stops after `shape h1`; and `approvedPlans: ["h1"]` stops after `shape r1` with `{"approvedPlans":["h1",1]}`. Likelihood and impact: it needs the plan dial, a pass number equal to `firstRound` (a human pass on a PR Redline never reviewed, or one whose only Redline rounds are earlier passes' nit passes) and a nit pass that finds a correctness bug. That is rare, but when it fires the plan dial's promise ("After shaping, every round", `README.md:81`) is silently broken: a fix is shaped, implemented and pushed without the person seeing its dispositions. Cost: about eight lines in `workflows/redline-loop.js`, one phrase in `skills/redline/SKILL.md`, and three loop checks, all in the PR's diff. Existing numeric `approvedPlans` stay valid. Proportionate.
  Decided by: redline
