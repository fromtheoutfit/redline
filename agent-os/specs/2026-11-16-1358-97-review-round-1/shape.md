## Deferred

### R1-4: Check that GitHub Issues are on before a run files deferred items to GitHub

- **Mitigation (ships now, Plan Task 3):** `docs/contract.md`'s `deferTo` row and `docs/running.md`'s "Where a draft goes" each say that `github` needs GitHub Issues turned on in the repository, and that a repository with Issues off, or one that tracks its work in another tracker, sets `spec` or `print`.
- **Title:** Check that GitHub Issues are on before a run files deferred items to GitHub
- **What was found:** With `deferTo` set to `github`, the default, Redline files each deferred item during the run with `redline-gh.sh defer issue`, which runs `gh issue list` and then `gh issue create`. Nothing checks first that the repository has GitHub Issues turned on, and the installed `gh` carries the error text "the '%s' repository has disabled issues", so on such a repository filing is expected to fail. If it does, the round stops at stage `defer` after the gate has passed and before the push: its commits stay local and no reply is posted. A resume relaunches with the same `deferTo` and stops the same way, and a fresh run with `defer to spec` is stopped by the precheck while HEAD is ahead of the pull request. The docs say that `github` needs Issues turned on, but nothing enforces it.
- **Why it is not fixed here:** What `gh issue list` and `gh issue create` do on a repository with Issues off (exit code and message) has not been measured, and no Redline role can run `gh` to measure it; the check also adds a read to the launch path, across `redline-gh.sh`'s output contract, the skill's launch steps and their tests, which the review round that found it could not plan without that measurement. The docs sentence shipped in its place.
- **The fix proposed:** First measure what `gh issue list --state all --search x` and `gh issue create` do on a repository with Issues off, and record it. Then, when `deferTo` is `github` and the run posts, read the repository's `hasIssuesEnabled` at launch (`gh repo view --json hasIssuesEnabled`, through a `redline-gh.sh` read subcommand) and stop the launch with one line naming `defer to spec` and `defer to print`, the way `redline-prefs.sh` already stops on an unknown `deferTo` instead of falling back. So that a round already stopped at `defer` is not stuck, have `redline-gh.sh defer issue` record the item as a draft and say so when `gh` reports that the repository has disabled issues, so the reply names the draft's path and a resume moves on.
