## Decisions

- **R1-1 · fix.** The exit-2 rule comes first everywhere a usage error could be read as unreadable output. In `stopReason()`, the `out.exit === 2` test moves above the `out.status === 'result_unreadable'` block. In `agents/redline-checker.md`, the exit-2 rule becomes the step before the `result_unreadable` step. The `checkerPrompt` sentence gains that a usage error (exit 2) is `status` `read` with `result` null. A new section 9 case scripts the shape the prompt steers to today (`exit: 2`, `status: 'result_unreadable'`, `reason: 'not_json'`) and asserts the exit-2 message. A second check pins the prompt sentence. Likelihood and impact: a usage error needs a bad snapshot path or a malformed snapshot, which is rare, and when it happens the run already stops with no repair pass and the stderr text in the message. Only the named cause is wrong, which misleads the person about where to look. Cost: about three lines moved in `workflows/redline-loop.js`, one sentence extended, the agent file's steps 3 and 4 reordered, and two loop-test checks. All three files are in the PR's diff, with no new helper. Proportionate.
  Decided by: redline
- **R1-2 · fix.** The spilled cause reads `see emit_checks in ${pluginRoot}/scripts/checks-template.sh`. The section 9 assertion at `tests/loop-test.mjs:472` expects `emit_checks in /p/scripts/checks-template.sh` (`baseArgs.pluginRoot` is `/p`, line 131). Likelihood and impact: low. It shows only on a spilled result, and `emit_checks` already caps the output (#7), but when it fires the person gets a path that does not exist in their repository. Cost: one template literal and one assertion, both in the PR's diff. Proportionate.
  Decided by: redline
- **R1-3 · fix, decided: Text never decides.** Should the checker's stray text fail a round whose only failures were already failing at baseline?
  - **What the person saw (the shaper's story, as returned).** A teammate runs Redline on a repository where one check already fails before the run starts, say a flaky browser test. The round's fixes break nothing new, so by the README's Baseline rule the round should pass, and it does when the checker leaves its error field empty. But the checker sometimes writes a note anyway, such as 'checks.sh exited 1'. The loop then counts that note as a failure reason, because checks.sh reported ok false. It sends the implementer a repair pass with nothing to fix, then stops at check. Nothing is pushed, no replies go out and there is no handoff. That is the same dead end this PR was written to remove after PR #34's round 2, and it hits only repositories that carry a known failure. The #9 spec states two rules: text is a reason on a failing gate, and only failing checks and git-block findings get a repair pass. In this case they disagree, so which one wins is your call. (Why a person: spec assumption.)
  - **Options as returned.** (1) **Text never decides** (recommended): about six lines moved in `judge()` in `workflows/redline-loop.js`, two section 9 checks in `tests/loop-test.mjs` (the reviewer's baseline scenario and a neighbour with a new failure plus text), one sentence in `README.md:226`, and the `workflow/agents.md` bullet reworded through the retrospective; the verdict comes only from the checks, the git block and the exit fallback, with baseline failures allowed, and checker text is a warning on a round that passes and extra context on one that fails. (2) **Document it**: one sentence each in `README.md` and `agent-os/standards/workflow/agents.md`; behaviour unchanged, and a repository with baseline failures can still lose a whole round to stray checker text. (3) **Accept**: nothing; the #9 spec's ok/exit rule stands as written and the edge stays undocumented. Shaper's recommendation: "Text never decides: it is a small change inside the PR's own files, matches the README's Baseline rule and the 'only failing checks and git-block findings are repaired' rule, and closes the last path by which text the implementer cannot change ends a run."
  - **Decision (2026-10-26).** Option chosen: Text never decides. The checker’s error text is never a verdict input. Verdicts come from checks[].exit against the baseline, the git block, and the gate’s exit code; text is carried as a warning or as detail on a failure the data already established.
  - **Planned as** `plan.md`, Task 4.
  Decided by: @michaelfromtheoutfit
