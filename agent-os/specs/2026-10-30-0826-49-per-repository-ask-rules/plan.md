## Context

The shaper decides `ask` from a fixed list of reasons. Every repository has things a person is always brought in for (Craft project config under `config/project/**`, migrations, billing logic, user-facing copy); today those live in a person's head, so Vestmark runs `review only` by hand. This spec lets a repository declare them in `.claude/redline.json` as `askRules`, enforces path rules twice (the guard refuses the write; the workflow forces the disposition), has the shaper and plan approver judge prose rules from an injected list, marks such findings in the review, leaves them to the person in the handoff, and has setup ask for them.

## Decisions (the prompt's thirteen, as amended while shaping)

1. `askRules` as specified. Validation (shared wording for the skill, the script and the guard): `id` matches `[a-z][a-z0-9-]*` and is unique; `when` has exactly one of `paths` (a non-empty list of non-empty strings, no `!`, no `[`) or `prose` (a non-empty string); `reason` is one non-empty line. Absent or `[]` is today's behaviour.
2. As specified, with one shape: a rule-matched finding gets outcome kind **`left`** (left to the person), never `fixed`/`deferred`. Guided: the person's answer is recorded with `decided by: @login`; the options are the person's to carry out outside the run ("Make the change by hand after the run", "Accept, no change"), since the guard would refuse the write anyway. Autopilot: `decided by: redline (autopilot)`, no task, no commit, recorded under Deferred with `mitigation: none (repository rule <id>)` and the shaper's recommendation as the full fix. A plan-dial override to `fix`/`defer` on a rule-matched finding is refused with a warning.
3. Paths rules enforced in the guard and in the workflow, with **one glob dialect in both** (Python and JS, pinned by the same cases): matched case-folded against the repository-relative path (`/`-separated); `**` spans segments (`config/project/**` matches everything below; `**/foo` matches `foo` at any depth); `*` and `?` stay inside a segment; a pattern with no `/` (a trailing one aside) matches at any depth; a leading `/` only anchors (stripped); a trailing `/` matches the directory and everything in it. No negation, no classes. The guard also refuses a **directory target that holds a rule's root** (`rm -rf config`, or `sed -i … config/project/*.yaml` cut at `*`): a target that is an ancestor of the pattern's literal leading segments. Symlinks: the target is always realpathed (non-strict), and `REPO` is realpathed for the relative path, so `cfg -> config/project` and `/tmp/link -> <repo>/config/project` both refuse. Malformed `askRules` make the guard refuse every write by a role, naming the fault (fail closed).
4. Prose rules judged by the shaper and the plan approver from `args.askRules`, injected by the workflow. The `why_human` value `repository rule <id>` is listed in the shaper's agent file, the unattended template and this repository's copy (outside the gate, no restamp); the schema's enum is built from the rules.
5. The forcing point is `forceAskRules(record, pass, inScope, shaped)` in `workflows/redline-loop.js`, named in a comment as the function #25's numeric limits share.
6. **Answered 2026-10-30:** the reviewer gets the rule list too and tags `askRule: "<id>"` (advisory; the shaper applies the rules and the forcing point wins). **Answered:** the mark is both the finding line's last tail ` · yours under rule <id>` and an inline-comment sentence; `redline-gh.sh prior-findings` strips the tail, and one gh-test fixture line pins it.
7. Handoff: a `### Left to you (repository rules)` section (every rule-matched finding of the run: id, title, rule id, reason, owner), the Deferred line variant for autopilot entries, and the threads line naming them as left open with reason `repository rule <id>`. `humanSummary` gains a "left to you under repository rules" part.
8. Setup: `redline-setup.sh suggest-ask-rules <repoRoot>` (new, read-only) prints the stack suggestions from `composer.json` (`craftcms/cms` → `config/project/**`; `laravel/framework` → `database/migrations/*`), so the Craft suggestion is testable; `config --ask-rules <file.json>` validates and writes the list (jq rewrite of the file when it is new or differs; reported under `updated.askRules`); without the flag an existing list is kept and printed under `askRules`; `config_differs` ignores `askRules`. The skill asks in step 7 after the reviewer question and, on a rerun, shows the list and keeps it.
9. Kept: the guard refuses `.claude/redline.json`; the rules file stays a person's.
10. Tests as specified, plus: guard-test gets a fixture repository and an optional fifth column (a substring the deny reason must contain); gh-test gets one case for the tail and the `left` classification.
11. README: "Ask rules" subsection under Settings, "Set up a repository" item 2 names the key, the `redline-setup.sh` table gains the flag and the subcommand, the guard section names the rule refusal, Known limits names the gaps the guard cannot close (writes through `xargs`, build tools, `find -exec` on files).
12. **Answered 2026-10-30: ship both.** Tasks are ordered so the paths half (Tasks 2-6) is a working state before the prose half (Task 7).
13. Done when as specified; the end-to-end check is in the Verification section.
14. (New) In a human review pass a rule-matched comment follows the same path (`ask` to the author; `left` on autopilot). The checker's allowed list is unchanged: a PR file under a rule stays allowed, which is why the guard is the second enforcement.
15. (New) The skill's precheck validates `askRules` by reading the file (five fields, no script) and stops with one line naming the bad rule; `args.askRules` is the list (`[]` when absent).
