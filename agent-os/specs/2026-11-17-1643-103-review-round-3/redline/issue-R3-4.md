# Read a reshape's change to the task of a deferral the person or autopilot decided

When the person or the autopilot decides a finding in a Redline round (a disposition override, or an answer to a judgment call), the workflow reads the task the round planned for it from the resolve agent's `tasks` alone: `resolvedTasks` in `workflows/redline-loop.js`, which only `resolveWith` adds to and which `plannedFiles` and `isDeferral` read. A reshape after a bounced plan rewrites `plan.md` and returns every finding's `files`, but it runs no resolve unless it raises a new call, so when the plan approver bounces such a deferral's mitigation task and the reshape changes or removes that task, the list is never updated. The plan approver's next pass and the implementer are then shown the files of the task as first planned (`effectiveDispositions`), and the planned-but-unbuilt warning can name files the plan no longer holds. An approver that holds the list to the plan, as rule 1 of `agents/redline-plan-approver.md` asks, can bounce the same plan until `maxPlanAdjustments` and stop the round at approve, and for a judgment call answered with a deferral in empty words whose task the reshape removed, `isDeferral` still sees a planned task, so the check demands a commit for it and the round stops at check.

- **Where:** `workflows/redline-loop.js:3810`
- **Why it is not fixed in #103:** Reading a decided finding's task from the resolve agent's tasks and no other list is the split #97 made and pull request #103 kept on purpose, and the base branch's `isDeferral` and check demand already read those tasks across reshapes, so the gap predates that pull request, which only added readers where it shows. Seeing a reshape's edit means deciding whether a reshape may change a decided finding's task at all, a change to the contract between the reshape and the resolve agent: the workflow drops a reshape's deferred entry and disposition for a decided finding on purpose, so its `files` for one cannot simply be trusted, and that choice belongs in its own spec. The failure needs a decided deferral with a planned mitigation, a bounce on that task and a reshape that changes it, and its cost is a resumable stop or a warning that names stale files, never a wrong commit or reply.
- **Proposed fix:** Keep, for each decided finding, the files of its task as last planned: set from a resolve's `tasks` for the ids that resolve applied, and replaced after each reshape by the reshape's own `files` for a decided finding whose decision makes it a deferral (a `defer` override, or a call whose resolve entry stands), so that `plannedFiles`, and `isDeferral` through it, read the newest plan; the other design is to tell the reshape that a decided finding's task keeps the files the resolve agent gave it and to record an adjustment that needs others as not applied, which keeps the split and ends such a bounce at a stop for the person. Pin either with a loop case: an override to defer whose resolve plans `app/x.php`, a bounced plan, and a reshape that lists no files for it, then check what the second plan approver call is shown (`files: []` under the first design) and that a reshape listing the same files leaves it unchanged.
