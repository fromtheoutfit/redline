# Standards for issue #81: pin the relaunch script, the Finish rule

The following standards apply to this work.

---

## workflow/replay

# Replay

A relaunch replays every agent before the stopping point from cache, so every prompt before that point is byte-identical between the first launch and the relaunch.

- Nothing before a stopping point reads the clock: the launch timestamp is `args.launchedAt`, the spec folder name is derived from it, and `Date.now()` and `new Date()` do not appear in `workflows/redline-loop.js`
- Decisions, approved plans and selected findings enter the workflow only after the prompt they answer (`args.decisions` after shaping, `args.approvedPlans` for the plan dial, `args.selected` for the review dial); a prompt before that point never mentions them
- A plan approval is keyed by the pass, not by a bare round number: `passOf(record).planKey` is a Redline round's number, or `h<n>` for a human review pass, since a human pass and its final nit pass can carry the same number (#38, R1-5)
- The skill relaunches with byte-identical `args` plus only what the stop asked for, and `resumeFromRunId` set to the run id it recorded at launch. A run the harness stopped is relaunched the same way with nothing added
- A prompt names its inputs by path (`<specFolder>/redline/round-1-findings.json`), not by content, wherever the content can change between launches
- The GitHub agent never posts a round-N review when one already exists on the PR (`redline-gh.sh has-review`), so a fresh run after a lost session cannot double-post
- The first round number enters through `args.firstRound`: the skill reads the highest posted round with `redline-gh.sh last-round` before the launch and passes the next one, and the workflow never asks GitHub for it, since the answer changes as soon as the run posts (#33; #10, round numbering). A human review pass's number enters the same way, through `args.revise.n` from `redline-gh.sh last-human-review`, with the ingested comments as `args.revise.findings` (#36)
- The findings of the PR's earlier Redline rounds and their dispositions enter through `args.priorFindings`: the skill reads them with `redline-gh.sh prior-findings` after `last-round` and passes the list, and the workflow never reads the threads itself, since the run's own carried-forward replies change them (#35)
- Finish's thread sweep is the one place the workflow asks GitHub for state that changes as the run posts (which threads are open, and who spoke last in them), and it sits after every stopping point, so no prompt a relaunch replays depends on it (#39)
- A per-repository list the prompts need (`askRules`, #49) enters through `args` at launch, read by the skill from `.claude/redline.json`, and is injected by appending to an existing interpolation, empty when there is none, so a repository without one keeps byte-identical prompts; the loop test proves it by comparing every prompt of a run with no key against one with `[]`
- A dial that turns a pass off keeps every prompt byte-identical to the run before the pass existed: `coverage off` reaches the workflow as `models.coverage` null, the coverage call and the candidates block exist only when a pass ran, and the loop test proves it by running every pre-existing scenario under the off value, so every earlier check holds unchanged (#79)
- `tests/loop-test.mjs` proves the rule: its relaunch scenarios assert that the prompts before the stopping point equal the first launch's, and a change that breaks that fails there before it reaches a PR
- A resume after an error changes exactly one prompt: `run()` appends a resume line to the agent label the error result's `resumeFrom` names (`args.resume`), so every prompt before it replays and that agent and all after rerun; a cached result the script rejected replays unchanged on a plain relaunch, which is why the line exists. A hand commit's paths join `approvedPaths` at that label, never at startup, so the cached snapshot prompt stays byte-identical (#10)
- On an interactive relaunch the harness relays the person's last typed message to every agent with precedence over its task; an `AskUserQuestion` pick is not relayed and a headless session relays nothing. The skill relaunches only from `relaunch` typed alone or a line holding only a Redline command, a namespaced form (`/redline:redline`, `/redline:redline-review`, `/redline:redline-revise`) or a short alias (`/redline`, `/redline-revise`) a repository's `.claude/commands/` provides, and `RUN_LINE` names both lines and every form (#60, #44; #63, R1-4)

## workflow/agents

# Agents

One role per file under `agents/`, loaded as `redline:redline-<role>`, with its model and its denied tools in the frontmatter.

- Frontmatter carries `model` (overridden per call from `.claude/redline.json`) and `disallowedTools` as whole tools. Per-command limits are the guard's job: `Bash(git push *)` in `disallowedTools` would remove all of Bash, and a plugin agent's own `hooks` are ignored
- A prompt opens with "This is a Redline agent run on pull request #N" and names the plugin's README path for the git rules. The agent file holds the role; the workflow's prompt holds the round's inputs
- The reviewer, the shaper, both approvers and the checker return JSON, not prose, and the workflow reads fields, never text (the coverage pass's relay of a skill's text is the one exception, below). The checker's pass or fail comes from `checks.sh`'s JSON: each check's `exit` against the baseline, the exit code and the git block (`unexpected_files`, `uncommitted`, `commits`), never `ok` and never the checker's error text (#37, R1-3)
- An agent file's return block is one JSON object with each key once. A key two operations fill with different types (the GitHub agent's `skipped`: post-review's `already posted` string, resolve-threads' `[{id, reason}]` list) appears once, and a sentence under the block says what each operation puts there. Each call's schema in the workflow carries the type that call accepts (#45, R1-1)
- Judgment calls are returned, never decided: a shaper that cannot settle a question from the code returns it as `ask` with a story, options and a recommendation. The person decides in their session, or autopilot takes the recommendation and says so, except for a finding a repository ask rule covers, which autopilot leaves to the person with the rule as its reason (#49)
- A finding a repository ask rule covers (#49) has its own outcome kind, `left`: never `fixed` or `deferred`, so no commit is demanded, its thread stays open for the person, a human pass's refusal of `defer` is never tripped, and its reply opens `left to the author under repository rule <id>`, which `redline-gh.sh prior-findings` reads as the disposition `left`. One function in the workflow (`forceAskRules`) applies the rules after every shape and reshape, whatever `fix`, `defer` or `ask` the shaper returned (a human pass's `none`, a comment that asks for nothing, is left as it is, since there is no change to leave to the person; #52, R1-4): a paths rule on the finding's file and on the `files` the shaper lists for its task, a prose rule by the shaper's `askRule` tag; the reviewer's tag is advisory and only marks the review. A later numeric limit (#25) forces there too
- Every decision carries its owner, in `shape.md`, in each finding's reply and in the handoff comment: `decided by: redline`, `decided by: @<login>` (the login `redline-gh.sh login` prints), `decided by: redline (autopilot)`, or `decided by: @<reviewer login>` for a change a teammate's review asked for and a human review pass made as asked (#36)
- A human review pass (`/redline:redline-revise <pr> review <selector>`) sorts a teammate's comment into `fix` (theirs: the shaper returns `decidedBy: "reviewer"` and the workflow maps it to their login), `ask` (the author's) or `none` (asks for nothing), never `defer`: nothing a teammate asked for is deferred by Redline on its own, and the author chooses a mitigation at the hand-off if they want one. The workflow refuses the other pass's values at `shape`. Every label, reply file, title and log line of a pass comes from one descriptor (`passOf` in `workflows/redline-loop.js`), so a Redline round's prompts stay byte-identical to what they were before human passes existed, and the loop test proves it (#36)
- A role's prompt names only the commands the guard allows it, in the exact spelling the guard accepts (`<plugin>/scripts/redline-gh.sh diff <pr>`, `vendor/bin/pest <file>`)
- A message the run shows the person names a plugin file by its absolute path from `pluginRoot`, as a prompt names a plugin script (`${pluginRoot}/scripts/redline-gh.sh`): the person reads it from the repository under review, where a path relative to the plugin does not exist (#37, R1-2)
- A message the run shows the person says when it fires in the words of the decision behind it, so a fix that widens or narrows the condition rewords the message and the loop checks that pin it in the same commit: R1-3 let the checker-text warning fire on a round whose gate exited 1, and it still said 'on a passing gate' next to 'still failing, as at baseline' (#37, R2-1)
- A decision that changes a rule a prompt states is applied everywhere the prompt and the role's agent file state the old rule, found by searching both for the rule's own words (`never re-raise`, the example values), not only in the sentence the finding quoted: R2-1's reopen changed the candidates block and two paragraphs of the agent file but left the handled-list header and the `knownAs` example saying a fixed match is never re-raised (#80, R3-3); and a prompt sentence that invites more text into a field the workflow parses (a coverage ref) is checked, in the same change, against every parse of that field, so the prompt keeps the text out of the field or after the parsed token and the parse reads past it: R1-4 kept a partly tracked candidate's issue out of a `finding` ref, which the workflow matches by id alone, and R4-1 had a `duplicate` ref open with the index or the id, a note after it, and widened the target parse, anchored at both ends, to read a leading index token (#86, R1-4, R4-1)
- An agent whose words reach GitHub in a comment or a reply says so in its file. The reviewer, the shaper, the resolve agent and the implementer each carry the sentence: 'An identifier that begins with `@` (a decorator, a directive, a docblock tag) is always written in backticks, because a bare `@word` notifies a GitHub account.' The loop test pins it in each file. The workflow neutralises the finder's and the verifier's short fields itself, but a comment's description, a reply, a mitigation or a commit subject is posted as written. The GitHub agent writes none of its own text, so its file does not carry the sentence. A new role whose text is posted gains it too (#87).
- A body the GitHub agent writes with the Write tool, byte for byte, holds no invisible character the post depends on: nothing compares the file it writes with the workflow's text, so a character it drops goes unseen. Such a character is written as a numeric character reference GitHub decodes, as `postedText` writes the word joiner as `&#8288;`, and the loop test checks that the post and handoff prompts hold no raw joiner (the #87 follow-up spec)
- Haiku for the roles that move files and post (github, checker); Opus for the ones that read code (reviewer, plan approver); the revise model is picked at launch and saved per person
- A role that finds a problem with its own instructions (a command the guard refuses, a file that does not exist) reports it in its JSON rather than working around it
- A sentence that says what keeps a change out of a run, in the README, `CLAUDE.md`, a standard or a prompt, credits a role only with a check its prompt carries, read in that prompt before the sentence is written: #65's R1-3 correction credited the plan approver with keeping the guard and hook files out of a cached-mode plan, while its file-scope check names the loaded plugin's directory, which is then the cache, and the claim reached four files before R2-1 removed it (#65, R2-1)
- A degraded result is data, not an error: the GitHub agent returns a posted review with no inline comment as `posted` true with every finding in `movedToBody`, the workflow records a warning, and `error` is reserved for an operation that failed. The workflow does not take an agent's `error` on trust in either direction: an `error` on a review that is posted, has a review id and accounts for every finding (inline or in `movedToBody`) is recorded as a warning and the run continues, while one on a result that fails that check still stops the run (#33: a review with every finding in the body ended the run at `post`; #34, R1-8; #9)
- Every agent's `error` is normalized once, as `run()` returns the result: `""`, `''` and `null` are empty and the text is trimmed, so a call site reads `.error` as it is, and a new call cannot stop a run on `'""'` as Losers League #790 did at Finish. The run record's `detail.checker` keeps the normalized text, beside the status, reason and partial result #9 keeps it for (#42; #43, R1-1)
- An agent that could not read what it was asked to relay returns a distinct status (the checker's `result_unreadable`, with a reason from a fixed set) and whatever it did get, never a partial object that looks like a failing result. The workflow stops on that status, and on any result the implementer cannot change (no result, exit 2, no git block), naming the cause and the fix; it sends to repair only failing checks and git-block findings. The checker's `error` is text and never a verdict input: the verdict comes from each check's `exit` against the baseline, the git block and the gate's exit code, and the text is a warning on a round that passes (a round whose only failing checks were failing at baseline included) or detail added to a failure the data already established; `""`, `''` and `null` as its text are empty, by the normalization in the bullet above (#9; #34 round 2; #37, R1-3). A usage error (exit 2) prints no JSON, so the checker's instructions and `stopReason()` test it before the unreadable status it would otherwise fall under: a specific case comes before the general rule, in the agent's steps and in the workflow's check order (#37, R1-1). Two causes with two different fixes are two reasons, since the message is what the person acts on: a foreground run the Bash tool moved to the background is `backgrounded` (re-record the baseline), not `spilled` (cap the output) (#40). A reason that claims something the workflow can check from the JSON it holds (`not_json`, `no_git_block`) is checked: when the result is one object with a `checks` array and a `git` key, the workflow reads it and records the misread as a warning naming the reason, since a Haiku checker read `git: null` as a missing key and stopped #54 at baseline. A reason about where the output went (`spilled`, `backgrounded`, `no_result`) stops as before: the JSON cannot refute it (#55). The run record's `detail.checker` then holds the copy the workflow read (`status` `read`, `reason` empty), and the warning is where the checker's own reason is kept; a change that rewrites a result before a call site stores it rewords every sentence that says what the record keeps, as #55 left the README saying `detail.checker` kept whatever the checker returned (#56, R1-1)
- A role never ends its turn to wait on a background task: a subagent's background task is killed when the agent gives its final response, and Claude Code blocks a long foreground `sleep`. A gate the recorded baseline says will not fit in one foreground Bash call (over 480 s of `args.baselineSeconds`, or none recorded) runs through `redline-background.sh`: `start` with `run_in_background`, then `wait` in the foreground, again while it exits 3, each call under the tool's 600 s cap and the stall window. The stall watchdog restarts only a silent agent and every wait is activity, so the wait's own `--limit` (the stall window in seconds) is what bounds a hung gate (#40)
- A check that something was already posted looks for text only that post carries. `redline-gh.sh pr-comments` prints review bodies and issue comments together, so a body finding's marker, which the review body also holds, proves nothing; the reply's own `from the Redline round N review body` line does; and it prints no URL or id, so a prompt whose duplicate check finds the post asks the agent to report it posted (`posted` true) with an empty `comment_url`, never for a field the script cannot give: a request for one leaves the agent to report the post missing or set `error` (#34, R1-1; #59, R2-1)
- A reply names what it answers, in a line only that reply carries: a human review pass's thread reply ends with a hidden `<!-- redline:answers <ids> -->` listing its findings' comment ids, and `redline-gh.sh human-review` counts a comment as answered only when a Redline reply in its thread names it. A Redline reply without the line (a Redline round's, or a human-pass reply posted before the line existed) answers every comment before it in its thread, the fallback that keeps older replies valid. Counting by thread alone lost a second teammate's comment and a follow-up left in a shared thread (#38, R1-1)
- A finding an earlier round recorded is not one it dispositioned. The evidence of a disposition is the Redline reply answering the finding (`fixed`, `deferred`, `decided`, `dropped`, or `carried` by a later round; a later run's `resolved; first reported as` reply reads as `fixed`, since it is Redline's own claim that the code no longer has the bug, not a decision a person made, so a coverage candidate that still reproduces it reopens it as one that still reproduces a fixed finding does, #80, R4-3), never `shape.md`, which a hand-off never relaunched leaves reading `Decided by: redline` on fixes never made; a finding with no reply, or a `not changed` one, is carried forward: a finding of the current round with `carriedFrom`, re-verified against the head and never copied, listed under its own heading in the review body, replied to in its earlier thread and swept with it, and named in the handoff. The reviewer accounts for every carry-forward id as carried or resolved, and the workflow carries what it did not account for, with a warning, rather than dropping it. The duplicate check for a reply is a reply opening with this pass's title, so an earlier round's reply in a carried finding's thread is not one (#35). Only the run's first round carries: a `carriedFrom` on any review with no carry-forward list (a re-review, a final nit pass, a first round with no earlier findings) is cleared with a warning, since the history block shows later reviewers the carried ids (#46, R1-1). An earlier thread is swept on its own reply when the finding that carries it sits in the review body, which has no thread to reply in (#46, R1-4). The handoff names an earlier finding by its disposition before its reply text: one a later round's line already carried reads `carried forward as R2-2 in round 2`, whatever its own thread's last reply says (#46, R1-5). A carried finding is never known by a Redline id: a `knownAs` naming one is cleared with a warning and the finding is carried. One naming an issue or a teammate's comment keeps the author's choice to track it there: the finding stays under Already tracked with `first reported as R1-2` on its line, unshaped, and its earlier thread is answered `carried forward as R2-1; already tracked in #41 · decided by: redline` and left open as `already tracked`. That reply is what the next run reads as carried, so the finding is neither set aside unanswered nor raised again (#46, R1-2)
- An id the workflow mints beside the reviewer's is numbered after the highest in use, never by count: a reviewer's ids can skip a number, and every record of a run (comment ids, dispositions, outcomes, reply ids, the carried map) is keyed by id (#46, R1-3). When the workflow renames an id the reviewer returned, every ref to it in the same result (a coverage `finding` or `duplicate` entry) is renamed with it before anything reads the refs, or the entry looks like one naming no finding (#80, R2-3)
- An answered review body is found the same way: a human review pass's body reply is an issue comment whose header line names the review (`**H<n>-<k>** · from review <id> by @<login>`), and `redline-gh.sh human-review` reads the PR's issue comments back and never takes a body whose review such a comment names, so a repeat pass over an answered review stops with nothing to revise. A pass still takes one body, the newest of the selection's that is not yet answered, so an older note comes up on the next pass (#38, R1-3)
- A reply's route comes from whether a review is on GitHub, never from a missing thread id alone: a thread id replies in the thread, a body finding of a posted review gets an issue comment behind its marker, and a dry run or an unposted review writes the reply file and posts nothing (#34, R1-7). A dry run routes every reply file-only whatever threads exist, since a teammate's threads are real even then (#36)
- A thread gets one reply per pass. In a human review pass two open comments of one thread (a teammate's comment and their own follow-up) are two findings with one thread root, so their replies merge into one that opens with the pass's title and gives each finding's outcome on its own `**H<n>-<k>**:` line; the GitHub agent never replies twice in one thread (#38, R1-4)
- Finish resolves the threads Redline opened for the findings it settled, and never a human's (#39). The workflow picks, the GitHub agent calls, as with the run-record commit: the workflow lists each settled finding's inline comment id and reply id (`record.commentIds`, and `record.replyIds` kept from the agent's `replies[].reply_id`, which the loop dropped before), the agent runs the one `resolve-threads` line it is given, and the script resolves only a thread every comment of which is in the list, so a thread a teammate opened or commented in, wherever the comment sits, is skipped with a reason, which is a result and not an error (#45, R1-2). Redline posts from the author's login, so its comments are told by id, never by author. Settled is fixed, deferred or decided with the reply posted; a dropped finding stays open as the person's pick, and a body finding has no thread. The sweep runs after the PR description and before the handoff comment or the human summary, so the comment reports it (`Resolved n threads; m left open: <ids and why>`). A thread already resolved when the sweep runs (resolved by hand before Finish) is in neither count, since the line reports what this sweep resolved and what is still open (#45, R1-3). A capped run, a dry run and a `no push` run sweep nothing, and the line is absent when no Redline thread exists
- A count a skill or prompt needs comes from a command that prints the number (`git diff --shortstat`, `jq length`), never from counting printed lines by eye (#34, R1-5)
- An error result names the agent label that caused the stop (`resumeFrom`), and the skill writes a marker through `redline-prefs.sh run save`; a resume is the person's choice at the next launch, never a retry by the skill or the workflow, and a `gather` error is not resumable (#10)
- The workflow checks a result before it acts on it: the shaper's spec folder is listed by the GitHub agent's read-only `spec-status` operation, an `ask` must have its judgment call, except, on a reshape, one the round already decided, since the reshape returns only the calls still pending or newly raised (#61, R1-2), and an unusable result is a stage error with `resumeFrom` naming the agent to rerun, never a synthetic judgment call; the one call the workflow writes is the repository-rule ask (#57)
- A workflow subagent never has the Agent tool (`agent()` has no `tools` option and the default workflow agent denies it), so a skill it invokes runs its recipe without a fan-out. The skill runs as a foreground fork with the caller's tools and output contract: a `schema` on the agent that calls the Skill tool, role or not, can make the fork call StructuredOutput itself and leave the caller with `Skill execution completed` (spike #72's reviewer-role probe, then #79's second corpus run on a default agent after the same script got through on the first; it is not deterministic), and the run record counts the calling agent only (two tool calls), so a skill pass is a plain workflow agent with no schema, measured from the fork's transcript under `subagents/` (spike #72, #79). Its text is the one thing the workflow reads as text: the skill's own documented contract, one fenced json array of findings; an array none of whose entries carries the contract's fields is not that contract, and stops the round as recipe drift rather than passing as blank candidates (#80, R1-3), and two fixed marker lines the prompt asks for (`coverage: skill denied`, `coverage: skill absent`), each read at the start of any line with leading backticks or quotes allowed, since an agent copies the prompt's formatting, and only when no fenced list in the skill's shape was found, so a skill result that quotes a marker is still the list (#80, R2-2), each a cause the workflow turns into a stage error at the pass's own label; anything else in the text is ignored. The effort word is always passed, since without one the skill reuses the level typed last on the machine (#79)
- The coverage pass is the finder and the reviewer the verifier (#79): the built-in `code-review` skill runs over the whole pull request at the round's head on every whole-PR and fix-diff round, since it is stochastic and attends to what moved, so each pass is a sample and the manual loop it replaces ran one per round. The reviewer verifies its candidates and runs no discovery pass of its own over the PR; it keeps the checks its prompt names by rule (scheduled and queued overlap, the Docs nit, the Version nit) and the fix-diff recheck, and accounts for every candidate with one of a fixed set of outcomes (`finding`, `forThePerson`, `duplicate`, `settled`, `known`, `refuted`, `outside`, `disproportionate`). The finder never returns an empty list, so the verifier's collapse is the run's stop rule: the prompt defines new (not collapsed into a finding already reported, settled in an earlier round, carried, or tracked elsewhere); `fixed` is the one disposition a candidate may reopen: a candidate that matches an earlier finding marked fixed but that the verifier reproduces or traces at the round's head is new, reported as a finding of this round with the earlier id named, so a fix that did not fully land keeps the run going under `maxRounds`, while a re-sampled finding the fix did close no longer reproduces and settles (#80, R2-1); a reopened finding carries no `knownAs`, since the workflow counts a finding with one as already tracked and a round of those confirms nothing new, and every sentence the verifier reads states the reopen rule, the handled-list header of an earlier run's findings included, which names the exception only when the pass ran, so a `coverage off` prompt is as before (#80, R3-3); a `decided` finding stays settled whatever its commits, since an applied decision is often a deliberate keep or mitigation: a candidate that still reproduces one goes under For the person naming the earlier id and is accounted for as `forThePerson`, never as a finding, so the run still ends (#80, R3-4), the run ends when a round confirms no new correctness finding, and the workflow lists an unaccounted candidate under For the person as reported, with a warning, the mirror of carry-forward. Two guards keep the finder's wider net out of the plan: a candidate anchored outside the diff is never a finding, and one that needs implausible conditions to bite is disproportionate and dropped with that word. What the verifier would not act on but a person should see goes under `### For the person`, no id, never shaped, carried into the handoff, and never read back as a finding, since `redline-gh.sh prior-findings` reads only lines that open with a finding id. The verifier is shown the PR's earlier runs' handled findings on every round that ran a coverage pass, not only on the whole-PR round, since the pass samples the whole PR at every head and can re-sample a finding an earlier run deferred or decided; the carry-forward list stays on the first round (#80, R1-2). The count sentence counts a candidate where the round puts it. Under `correctness only`, a nit reported from a candidate is `forThePerson` and listed there, whether or not it carries a `knownAs`. Otherwise a finding listed under Already tracked is `known`. A `finding` entry whose ref names no finding of the round is listed under For the person as reported, like an unaccounted candidate. The findings file keeps the candidate list beside the accounting its indexes point into (#80, R1-4, R1-5)
- The verifier's rules from the #817 rerun (#85). An issue or a teammate's comment that tracks only part of a candidate leaves the remainder to be judged as its own candidate: one caused in the diff is a finding naming the issue, `knownAs` empty, accounted for as `finding`, unless another rule puts it elsewhere as it would any candidate (a collapse, a refutation, the disproportionate rule, or For the person for a removed guard or a candidate plausible but not reproduced), so a neighbouring issue never decides where a remainder goes (#86, R2-1); a partly tracked candidate is accounted for by what its remainder became, with the issue named in the finding's description, the For the person line or another outcome's ref, never in a `finding` ref, which the workflow matches by id alone (#86, R1-4), `known` being for one tracked whole; two candidates are not one because one issue's title fits both. A refutation answers the candidate's claim, and its ref states that claim and the evidence against it; evidence for a neighbouring claim, or a comment or docblock stating intent, does not refute, and such a candidate goes under For the person. A guard this pull request removed is never disproportionate: a candidate the base branch handled and the PR stopped handling goes under For the person naming the removed line. Every candidate that is neither a finding nor a For the person entry is listed after For the person in the set-aside block, under its own heading `### Candidates set aside (N)` (in the handoff, `### Candidates set aside in round <n> (N)`), a collapsed `<details>` whose summary is `Collapsed, already tracked or dropped`, by one rule (`LISTED_ELSEWHERE`), never a list of outcomes, so an outcome added later is listed too, and the rule reads the accounting after `accountCoverage`, which accounts for a candidate behind an Already tracked finding as `known`, so that candidate is in the block too, its ref the finding's id and the issue (#86, R5-3); "dropped" means `refuted`, `outside` or `disproportionate` and nothing wider. One line each, with the candidate's own file, line and summary, whole, so a refutation that answers another claim shows as a mismatch, then the outcome and the ref (`no reason given`, with a warning, when none): a `known` line names the issue, and a `duplicate` of another candidate's index also gives that candidate's place and outcome, and the finding's id when that candidate became a finding, which the block does not list (#86, R5-4), so a duplicate of a dropped or tracked candidate cannot hide: the accounting sentence, in the verify prompt and the agent file, has a duplicate's ref open with the index of the candidate or the id of the finding it collapses into, anything meant for the reader after it, and the workflow reads the target from a leading index token (`3`, `candidate 3` or `index 3`, any case) whatever follows it, so a note after the index keeps the target (#86, R4-1); nothing set aside, no block. Every finder and verifier field the review body and the handoff post (the block's lines; finding, For the person, Already tracked and Resolved lines; the summary; the handoff's decision and Earlier rounds lines), and an inline comment's title, go through one function, `postedText`, with fields that share a line read as one text. Outside code spans, `&` then `<` are escaped, and `&#8288;`, the word joiner (U+2060) as a numeric character reference, follows each `@` before an ASCII letter or digit, so no tag ends the block or bolds the body and no `@word` notifies; GitHub decodes it, and outside a code span it shows nothing (the #87 follow-up spec). Spans are read as GitHub pairs backtick runs and left as written, unless the text holds `](`, `][`, `://`, `www.` (any case), a backslash before a backtick, a carriage return or a newline; such a text is escaped whole, and a backslash anywhere else, as in a namespace, changes no pairing and is no trigger (#89, R3-3). The workflow's own mentions, and shaper, person and implementer text, are posted as written. A comment's description and proposed fix, and every reply, are a known gap (#88). A title `prior-findings` reads back is decoded once at intake by `readBack`, the exact inverse over the same `textParts`: it strips the workflow's `@&#8288;` before it decodes `&lt;` and `&amp;`, so a reference the finder typed reads back as typed and a carried title is escaped once (#87; the #87 follow-up spec). The handoff carries the block of the last round that ran the pass, naming it; earlier rounds' blocks stay in their own bodies (the #85 follow-up spec). The line is built by `personLine`, as a For the person line is, so it opens with the backticked place, never a finding id, and `redline-gh.sh prior-findings` never reads it back (#86, R1-3)

## scripts/bash-conventions

# Bash scripts

Every script under `scripts/` is its own documentation and talks to the workflow in JSON.

- Every script starts `#!/usr/bin/env bash` and `set -euo pipefail` (`redline-gh.sh`, `redline-guard.sh`, `redline-prefs.sh`, `redline-gate.sh`, `redline-setup.sh`, `checks-template.sh`). The test harnesses use `set -uo pipefail` instead, because one failing case must not stop the table
- A script a workflow reads emits exactly one JSON object on stdout and everything else on stderr: `checks.sh` logs through `log()` to stderr and prints the envelope last; `redline-prefs.sh resolve` and every `redline-gh.sh` read subcommand whose header says JSON print JSON and nothing else; a subcommand a role reads as text says what it prints instead (`diff` a unified diff, `pr-comments` and `issues-search` text), and one whose answer is yes or no (`has-review`) prints nothing and answers by exit code (#71, R1-6)
- `bash -n` reads its first file and treats the rest as arguments; check several with `ls <glob> | xargs -n1 bash -n` (#5, R1-3)
- Usage errors exit 2 with a one-line reason on stderr. A check that fails exits 1. A script whose exit code is an answer (`redline-gh.sh has-review`: 0, 1 or 2) says so in its header
- A wrapper that runs another script for a role (`redline-background.sh` around `checks.sh`) passes the wrapped script's stdout and stderr through unchanged, and its documented exit codes (0, 1 and 2 for `checks.sh`), so the role reads the result as it would the script's own, and takes the codes above them for its own answers (3 still running, 4 past the limit, 5 no result), stated in its header. Any other code the wrapped script exits with (a command failing under its `set -e`, a signal) is the wrapper's no-result answer with a line naming the code, never passed through: a passed-through 3 reads as still running and loops the role (#41, R1-3). A result the wrapper keeps under a label the workflow reuses is read once: the wait that returns it removes the label's files, so a wait that runs before the next start has cleared them cannot return the earlier run's result (#41, R1-2). It runs one fixed script, never a command it is given, so the guard admits it by subcommand (#40)
- The header comment is the documentation, in this order: what the script is, usage, environment variables, the output contract, the exit codes. `docs/scripts.md` quotes it verbatim and `docs/contract.md` carries the output contract, so a header change updates `docs/scripts.md` in the same commit (#14). A field added to `checks.sh`'s JSON, or a limit changed in it (`run_check` in `scripts/checks-template.sh`), updates `docs/contract.md`'s output contract in the same change, and a flag that reports a cut is set by every limit that can cut (#7, R1-14). `checks.sh`'s whole JSON stays bounded however many checks fail: the failing checks share one output budget, split evenly among them in a final pass after every check has run, never consumed in run order, because the checker may not Read a result that spills to a file (#7, R1-13)
- A change to what a subcommand selects or prints rewords every description of it in the same commit, found by searching for the old phrase across `README.md`, `docs/`, `skills/` and `agents/` rather than by editing only the `redline-gh.sh` table row that quotes the header: R1-3 changed which review body `human-review` takes and updated the header, the README's `redline-gh.sh` row and the revise skill, and left the README's paragraph on `/redline:redline-revise <pr> review` describing the old selection (#38, R2-1)
- A subcommand added to `redline-gh.sh` or `redline-prefs.sh` is added to the guard's groups in the same change (`GH_READ` for a read subcommand; `gh-all` already covers a write one), and the agent or skill that calls it names the exact spelling
- A script only a skill calls (`redline-prefs.sh`, `redline-gate.sh`, `redline-setup.sh`) needs no guard group: the guard's default deny refuses it to every role, and `tests/guard-cases.tsv` rows pin it as the skill's (#6); when one of its subcommands is reserved for a person, its rule in the shared allow list (`templates/settings.allow.json`, and the repository's `.claude/settings.json`) names only the subcommand the skill runs unprompted (`Bash(/*/scripts/redline-gate.sh check *)`), so the reserved one stays behind the permission prompt (#7, R1-9); `redline-setup.sh`'s writing subcommands have no allow-list rule, and the permission prompt is the person's confirmation (#6), while `version`, which writes nothing and which `/redline:redline`'s precheck runs at every launch, once had the one narrow rule, `Bash(/*/scripts/redline-setup.sh version *)`, on the pattern of `redline-gate.sh check`'s (#12, R1-8); since #50 the allow list carries no script path rule at all (a `Bash(/*/scripts/…)` rule matched a script of that name at any path an agent could write), and the guard approves the one unprompted subcommand (`redline-gate.sh check`, `redline-setup.sh version`) for the main session by real path, so the reserved ones stay behind the permission prompt
- A generator that writes a file from a template (`redline-setup.sh checks` from `checks-template.sh`) splices by anchor lines and exits 1 naming a missing one, so the template and the generator cannot drift apart silently, and its output is deterministic: the same input gives the same bytes, and nothing is written when they are unchanged (#6). It validates every input field it writes, not only the commands: a field that lands in a comment is a single line, and one that lands inside quotes holds no character that would end or expand them, so a bad `checks.json` exits 2 rather than writing a `checks.sh` that runs a stray line (#12, R1-6)
- A script that edits a person's file (`.gitignore`, `shape-spec.md`, `settings.json`) preserves the file's line endings and a byte-order mark (`settings.json` refuses a byte-order mark instead, exit 2, as its header says), writes only when the bytes change and reports `changed: false` otherwise, so a rerun can say nothing drifted; a JSON file is compared with `jq -S`, since a CLI that rewrites it (`claude plugin install`) reorders keys and that is not drift (#6)
- A merge into a person's JSON file keeps every value already there, adds only what is missing, and reports each kept value that differs from the template (`conflicts`) rather than overwriting it (#12, R1-3, R1-4); every subcommand that writes takes `--dry-run`, which prints the same JSON with `written: false` and creates nothing, not even the target's directory (#12, R1-2)
- A rerun over a file the script wrote earlier changes only the values the script derives from its inputs (`config` updates `checker` and `checkerStallMs` in place, keeping the file's formatting) and keeps every other value as the person's, the ones the person chose at setup included (`reviewer`), listing each that differs from the template under `differs` without changing it; `--force` is the full reset to the template (#12, R1-5)
- A rerun's `differs` lists drift from the template, never the person's own additions: `config_differs` ignores a key only the person writes (`askRules`), so a rerun does not report the rules as values to reset (#49)
- A validator that shares its messages with another (`ask_rules_fault` in `redline-setup.sh`, `rule_fault` in the guard, the workflow's launch check) shares its tests too: a key's presence (`has("paths")`), never a non-null value, so `{"paths": null}` gets the shared message instead of passing, and a list's elements are filtered to objects (`objects`) before a field of each is read, so a non-object element gets `not an object` and exit 2 instead of jq's own error and exit 5 under `set -e` (#52, R1-2), and a pattern is matched against the whole string, `\A...\z` in jq: jq's `$` also matches before a final newline, so `^[a-z][a-z0-9-]*$` passed the id `"a\n"`, which the guard's `fullmatch` and the workflow's `/^...$/` refuse, and setup wrote a list that then stopped every run (#52, R2-1)
- A flag that replaces a list a rerun otherwise keeps (`config --ask-rules`) clears it with `[]`, and the skill that calls it passes `[]` when the person removes every entry: without the flag the old list stays, so "with none, omit the flag" left a removed list enforced (#52, R1-3)
- A jq program that holds a quote goes in a quoted heredoc (`prog="$(cat <<'JQ' ... JQ)"`, then `jq "$prog"`), never in a bash single-quoted string: `ask_rules_fault` first wrote `'\($r.id)'` inside `jq -r '...'`, which ended the bash string at the first quote and failed `bash -n` (#49)
- Python inside a script is `python3 -I -c "$PYTHON"` with the standard library only, fed on stdin; it writes no file beside the script
- A path the script receives is made absolute once (`cd "$(dirname "$path")" && pwd`) and used as is; the repository is `git rev-parse --show-toplevel`, never a walk from `$PWD`
- A path compared with `git rev-parse --show-toplevel` is made physical first (`pwd -P`): git prints the physical path, and on macOS `/var` is `/private/var`, so a logical path never matches its prefix (#6)
- A header printed by `-h|--help` is printed with `sed -n '2,/^$/p'`, never a numeric range, which rots on every header edit (#6)
- A script that chooses which part of a file to hash refuses when more than one part qualifies, naming each by line, rather than taking the first: a silent switch moves the hash onto the wrong text and every later check passes against it (#7, R1-6)
- Never print a token, a header or an environment dump; `redline-gh.sh` leaves authentication to `gh`
- `jq` reads and writes every JSON value; no hand-built JSON strings in bash
- A JSON value that grows with the pull request (the anchor positions of `place`, megabytes on a 336-file PR) reaches `jq` through `--slurpfile` or `--rawfile` from a temp file, never `--argjson`, which puts it on the command line and fails with "Argument list too long" (#33)
- `redline-gh.sh` never calls `gh pr diff` or `gh pr view --json files`: the first refuses a PR over 300 files, the second stops at 100, so the paginated files endpoint (`gh api --paginate --slurp`, gh 2.48.0 or newer, which the script names when an older gh rejects the flag) is the one source of the file list, the diff and the anchor positions (#33)
- A read subcommand whose answer is a number (`last-round`) prints it as a bare JSON number, `0` for none; one whose answer is yes or no (`has-review`) uses the exit code
- GraphQL in `redline-gh.sh` is two fixed strings (`THREADS_QUERY`, `RESOLVE_MUTATION`), parameterised by `-F` variables only (`owner`, `name`, `number`, `endCursor`; `threadId`) and never built from an argument; `gh api graphql --paginate --slurp` follows `pageInfo` through `$endCursor` into one array of pages, and gh fills `{owner}` and `{repo}` in `-F` values as it does in an endpoint. A write subcommand that reads first (`resolve-threads` reads the threads, then sends one mutation per thread) exits 2 when the read fails and 1 when a mutation does, after the ones already sent, as its header says (#39)
- A GitHub login a selector names is matched case-folded (`ascii_downcase` on both sides of the comparison), since GitHub treats logins case-insensitively, and a skill takes the login it writes as an owner from the script's output, never from the text as typed (#38, R1-2)
- Every script runs under Apple's bash 3.2 with BSD tools (the macOS CI leg pins `/bin/bash`) and under bash 5 with GNU tools (Ubuntu), so bash 4 features (`declare -A`, `mapfile`, `${x,,}`) and GNU-only flags stay out; shellcheck covers `scripts/*.sh`, `tests/*.sh` and the generated `checks.sh` at severity warning, set by `-S warning` on the workflow's command, required, and every code `.shellcheckrc` disables names the line that needs it (#17). `.shellcheckrc` holds no severity: shellcheck 0.11.0 ignores a `severity=` key there and honours `-S`, so a severity in the rc file reads as set and is not (#47, R1-2)
- A workflow `run:` block whose exit status rides on a pipe opens with `set -euo pipefail`, as a script does: GitHub runs a step with no `shell:` as `bash -e`, without pipefail, so the advisory shellcheck step's `shellcheck ... | sed ...` exited with sed's status and passed on every finding, and on a runner with no shellcheck (#47, R1-1)
- An allow entry a template drops is added to `templates/settings.retired.json` in the same change, so `redline-setup.sh settings` can report it under `stale` in a repository set up earlier and remove it with `--remove-stale`; a merge never removes on its own, and a person's own entry is never stale, since only the retired list is consulted (#50)
- A change to `scripts/checks-template.sh` below its header bumps its `# redline-template:` version line, which is how a set-up repository is told to rerun setup (`redline-setup.sh version` exits 1, the launch precheck warns); a fix left at the old version reaches only fresh setups (#50)
- A template whose body a repository copies (`templates/shape-spec-unattended.md`) carries a version marker in the body (`<!-- redline-unattended: vN -->`, the section's first line); a body change bumps it and freezes the previous file under `templates/history/shape-spec-unattended.v<N-1>.md` in the same commit, and pins the new body's sha256 in `tests/setup-test.sh` (#64, R1-2), since an installed plugin has no git history to show from; a rerun merges three ways (the frozen base at the section's version, the repository's copy, the current template), every side with the wanted fill-ins applied first so fill-in phrases never conflict, keeping hand edits and deletions, merging a same-length hunk line by line (adjacent lines changed on different sides: Chalkboard's hand-edited story line beside the `why_human` line #49 changed), and asking on a line changed differently on both sides (`--pick <n>=ours|theirs`); that line alone is the conflict, so a pick never settles the lines beside it (#64, R1-1); a hunk is split line by line only when its lines line up, every base line anchored on a side sitting at its own offset there, so a deletion and an addition inside one hunk stay one conflict and a pick never writes a line twice or drops one (#64, R2-1); a section with no marker is matched to the nearest body and reported as guessed; the marker is bumped alone only on `--keep`, so the launch keeps warning otherwise (#15)
- A read-only subcommand the launch precheck runs takes the repository root and answers every contract question in one call (`redline-setup.sh version <repoRoot>`: `checks.sh`, the unattended section, `settings.json`), since the guard approves the main session by subcommand word (`version`) and a read-only flag on a writing subcommand (`unattended --version`, `settings --dry-run`) would stop at the permission prompt on every launch (#15)
- A prompt, skill or workflow sets no variable prefix on a command other than `REDLINE_OCTANE=1` or a gate variable the repository's `checks.json` declares, puts no wrapper (`time`, `env`, `timeout`) in front of a script, uses no shell keyword, and runs git from the repository root: the guard refuses every other prefix, every keyword and git away from the root for the roles, and approves the main session only for the bare command word of a script, `checks.sh` or read-only git (#54)
- A role without the read group lists files with `git -C <repo> grep --no-index -l -e '' -- <paths>` and tests a heading with `-e '^## ...'`: `git grep` is git-read, `ls` and `grep` are not (#57)
- A reader that bootstraps a hand-written file (`redline-setup.sh read-checks`) accepts the hand-written spellings the generator replaced, not only the generator's own: the gate file with or without `steps m to n`, `ALWAYS_ALLOWED` or the git block's hard-coded `printf` list, `ENV=<name>` with or without `(default …)` on the line; and a header line that shows a command prints it as a person types it, since the escaping belongs to the `run_check` line alone; a pattern that skips past a field the generator wrote accepts every character the field's validator lets through, so the reader's optional `(default …)` tail is `\(default .*\)` to the line's last `)`, never `[^)]*`, since a default may hold a parenthesis (#18; #62, R1-1)
- A file setup writes verbatim from a template (`redline-setup.sh command`, the alias command files under `.claude/commands/`) carries a marker line naming the template, and a rerun compares bytes: equal is `unchanged`, different with the marker is `differs` (exit 1, the unified diff in the JSON, `--force` rewrites), and a file of that name without the marker is a person's own, `foreign`, never written whatever the flags (#44); setup's step for such a file branches on what step 1's inventory found for that file (absent, Redline's or a person's own), never on fresh setup versus rerun, since a fresh setup can find one already there (#63, R1-2)

## scripts/guard

# The guard

`scripts/redline-guard.sh` is a default-deny allowlist per role, and every change to it is proven by a row in `tests/guard-cases.tsv`.

- The table at the top of the script is the policy: one line per role, its command groups and its write prefixes, both literal. A command a role newly needs is a new member of a group, never a looser parse
- Default deny: a command the classifier cannot place is refused. `bash` only as `bash -c <string>`, checked recursively; interpreters (`python3`, `node`, `php -r`), `gh`, `curl`, `eval`, `source` and `sudo` are refused for every role. The guard reads only the subcommand word after `redline-gh.sh`, never a query or a body, so a GraphQL mutation reaches GitHub only through a wrapper subcommand (`resolve-threads`, the github role's by `gh-all`): a `tests/guard-cases.tsv` row pins the raw `gh api graphql` form as refused to the github role, and the mutation's text is pinned by a `tests/gh-test.sh` case, not by the guard (#39)
- Write targets are checked, not only command names: redirections, `tee`, `sed -i`, `mv`, `cp`, `rm`, `mkdir`, `touch`, `git add` paths, `find -exec` and process substitutions all go through `writable()`
- Redline never edits Redline: the plugin's directory, `.claude/redline/`, `.claude/redline*.json`, `.claude/settings*.json` and the `.claude/{agents,workflows,skills}/redline*` copies are refused for every role, and so is a write that would take a directory holding one of them along (`rm -rf .claude`)
- When the repository is the plugin (its checkout loaded in place, Redline reviewing itself), the plugin's source is repository content under the roles' usual prefixes, except `scripts/redline-guard.sh` and `hooks/hooks.json`: the guard that vets the run is changed by a person, never by a Redline role (#4). Loaded from a cached release, the guard treats the checkout as an ordinary repository, and only point 11 of the unattended section keeps the two files out of a plan; the plan approver has no check that names them (#65, R1-3, R2-1). A finding there is deferred, mitigated by a pinned `tests/guard-cases.tsv` row or a Known limits line, and a person makes the change after the run (#5, R1-1). The same holds for a finding whose fix needs `.claude/redline/checks.sh` restamped, which no role may write: one that changes the gate's backticked text, or how `scripts/redline-gate.sh` computes the hash or writes the stamp line. It is deferred with a Known limits line, and a person makes the change and restamps (#7, R1-1, R1-2). A finding whose fix touches `scripts/checks-template.sh` below its header, or changes the text `redline-setup.sh checks` writes into this repository's `checks.sh` (its header, the template version line, the check block), is deferred the same way: the setup test's last cases regenerate `checks.sh` from `checks.json` and compare it with the committed file, and no role may regenerate it, so such a fix leaves the gate red. The round records the intended lines in its Deferred entry, mitigated by a Known limits line, and a person makes the change, regenerates `checks.sh` and restamps after the run (#7, R1-14; #12, R1-1). `checks.sh` is generated from `.claude/redline/checks.json`, which no role may write either: a finding whose fix changes a check is deferred the same way, and a person edits `checks.json`, regenerates and restamps (#6)
- Protected paths are compared case-folded: the default macOS volume is case-insensitive, so `Scripts/redline-guard.sh` is the guard. Folding only ever refuses more; the prefix checks and the self-hosted test stay as spelled, which fails closed (#5, R1-4)
- What the guard allows it also approves (`permissionDecision: allow`), so a role never meets a permission prompt for a vetted command and the shared `settings.json` carries no git write rule
- Every change to the guard adds or changes a row in `tests/guard-cases.tsv` in the same commit, with the `agent_type` Claude Code sends, beside a row for the neighbouring decision that must not change (`allow Write REPO/scripts/redline-guard.sh` in an ordinary repository, next to the self-hosted `deny`)
- An agent's prompt tells it the shape of a command the guard accepts: no `$`, no backticks, no process substitution, one command per call, redirection only into the temp directory. When a prompt and the table disagree, the table wins and the prompt is fixed
- A Redline role is identified by `agent_type` alone (`redline:redline-<role>`, or `redline-<role>` for a copy under `.claude/agents/`); anything else, the main session included, leaves the guard inert with no output, with one exception: a Bash call that is one of the plugin's own scripts by real path (`redline-gh.sh`'s read subcommands, `redline-prefs.sh`, `redline-gate.sh check`, `redline-setup.sh version`), the repository's `checks.sh`, or read-only git, each as the bare command word (nothing in front of it: no wrapper, `env`, `timeout` or `xargs`; a `cd` to the repository root before it is fine), is approved for any session, so the shared allow list carries no `Bash(/*/scripts/…)` rule that a script of the same name at any path an agent could write would match, and anything else from such a session, a builtin, `sed` or `find` included, is inert, never a deny, so the permission prompt decides (#50; #54, R2-1; #80, R2-5)
- A guard denial is a sentence a person can act on: which file or command, which rule, and for the self-hosted files, who changes them
- A repository's ask rules (`askRules[].when.paths` in `.claude/redline.json`, #49) add to the refused set for every role: the guard reads the file at each call, refuses a write under a rule's globs naming the rule and its reason, refuses a write to a directory that holds a rule's root (`rm -rf config`, or a pattern whose literal prefix is the root or above it), resolves the target through symlinks first (always, a missing parent included, so a link under the temp directory that points into a match is refused), and fails closed on a malformed list, refusing every write until a person fixes the file. The glob dialect (`**` across segments, `*` and `?` inside one, a slashless pattern at any depth, a leading slash anchoring, a trailing slash taking the directory) is one function in the guard and one in the workflow, pinned by the same cases on both sides; `tests/guard-test.sh` prepares the fixture repositories the rows need under `~/.cache/redline/` on every run
- A Bash write target holding `*`, `?`, `[` or `{` is refused for every role unless it is under the temp directory: the guard checks paths, not patterns, and expanding the pattern at check time is not a fix, since a pattern that matches nothing when the hook runs can match a file an earlier command in the same call creates. The literal prefix still goes through the protected and ask-rule checks first, so the specific reason wins where it applies, and the refusal names the protected file or rule the pattern could reach. A tool's `file_path` is literal and never cut (#53, closing #52 R1-1)
- Read-only git is vetted by flag, for every role and the main session: `--output`, `-O`/`--open-files-in-pager` and `--ext-diff` on a read subcommand, every `-c`/`--config-env` (a configuration key can name a program: `diff.external`, `core.pager`, `core.fsmonitor`, `gpg.program`, `filter.*.clean`), `--exec-path`, and every environment prefix (`GIT_*` and `PAGER` first, since #54 every name but the exempt ones, below) are refused outright; no key list is kept, since nothing legitimate uses them and a list would need keeping (#50). A flag is read as git's parser reads it: `-O` anywhere in a short-flag bundle (`-lO<pager>`) and any `--op…` abbreviation of the long form are refused too (#54, R2-7). And git runs only with the repository root as its working directory, after `-C` and any `cd`, for every subcommand: the repository git runs in can name a program in its config, and a role can write one under the temp directory or nested inside the repository (#54, R2-8)
- Every route that sets a variable for a child is refused for every role: `export`, `declare`, `typeset`, `set`, `readonly` and `local` as commands, every `env` option, and a `NAME=value` prefix on any command, bare or through `env`, a bare assignment with no command included (an exported name such as `PATH` keeps its export when reassigned), except `REDLINE_OCTANE` and the `env` names of the repository's `checks.json` `vars`, whose value must be a plain word (letters, digits, `_`, `.`, `/`, `-`). The guard reads `checks.json` at each call as it reads the ask rules, and a file it cannot read declares nothing (#54, R2-6)
- `!` and the shell keywords are refused as a command word: the word after one would never be read, and a role runs plain pipelines, `a && b` in place of `if a; then b; fi` (#54, R2-5)
- A sed script is never a write target, in every spelling of `-e` and `-f` (detached, attached, bundled as `-ne`, the long forms), and every script a call carries is read as sed reads it: a `w`, `W` or `e` command, or a `w` or `e` flag on `s`, is refused for every role, the file after `-f` is read from disk, and a script the reader cannot place is refused, which is the default. find's file-writing predicates (`-fprint`, `-fprint0`, `-fprintf`, `-fls`) are refused the same way (#54, R2-1, R2-2)
- A pattern under the temp directory is admitted only when the wildcard is in its last segment and no segment is `..`: the text after the cut is never resolved (#54, R2-3). `git add` of a path holding a pattern character is checked as the literal path when a file of exactly that name exists, else as a pattern; git's own pathspec matching may then stage a modified sibling (`i.php` for `[id].php`), which is harmless, since the role could stage it by name and the checker's allowed list catches a file the plan did not name (#54, R2-4)
- The guard does not see a skill fork: a `Skill` call from a Redline role runs the skill's commands with no Redline `agent_type`, so `gh`, `$(...)` and loops the role's row refuses go through unvetted (spike #72). A pass built on a skill is therefore a plain workflow agent, never a role, and its safety is the skill's own read-only recipe and the session's permission mode, except where the fork's Bash call meets #50's main-session approvals: a fork is a non-role session to the guard, so one of the plugin's scripts by real path (of `redline-gh.sh`, only its read subcommands), the repository's `checks.sh` and read-only git are approved for it with no prompt, and a `redline-gh.sh` write (a review, a reply, a comment, an issue, a thread resolve) is inert, never a deny, so the session's permission prompt decides; `tests/guard-cases.tsv` pins the write as `inert` beside a read row that stays `allow`, and the README's Known limits, `docs/running.md` and `docs/guard.md` say the same (#80, R2-5, R4-2). In bypass-permissions that prompt does not exist, so wherever Redline offers that mode it says the mode removes the pass's prompt, the one check the guard cannot provide, and that a fresh launch with `coverage off` runs without the pass: the launch skill's Inline session paragraph, `docs/running.md`, `CONTRIBUTING.md` and the README's Known limits (#83, R1-6)

## process/docs-gate

# Docs gate

Every spec names the README, `docs/` and template changes it needs, so a public reader is never behind the code.

- Gate step 10 in `.claude/commands/agent-os/shape-spec.md`: for each file added or altered under `scripts/`, `skills/`, `agents/`, `templates/`, `workflows/`, `hooks/` or `.claude-plugin/`, and for each new config key, subcommand, allow rule or exit code, the plan names the README section, or the `docs/` file and section (and template, if any), and either the commit that updated it or "no reader-facing change" with the reason
- A plan that cannot name the section adds one; the entry then names the new section
- The entries are written at shaping time, one per touched file, in `plan.md`: in the task that touches the file (as point 7 of the unattended section has a Redline shaper write them) or together under one Docs entries heading (as the #13 spec did); either placement meets this rule, and the gate confirms each names its commit or its reason (#51, R1-2)
- No commit exists at shaping time: a plan's entry names the README section, or the `docs/` file and section (and template), its task updates, or the reason there is no reader-facing change, and its commit is that task's own, named in `plan.md`'s As built when it lands and confirmed at the gate. The plan approver checks the section or the reason only: its check 8 first asked for the commit too, which no reshape could supply, so a plan written as point 7 says could be bounced until the run ran out of adjustments (#51, R1-3)

- A prose step whose text holds a backticked span is inside the stamp: adding this step moved the hash, and the restamp went in the same commit (#13)
- Point 7 of the unattended section keeps its "Steps … stay as written" sentence first on its line and says "gate step" in lower case after it: `redline-setup.sh unattended` reads the fill-ins back by leftmost match, so an earlier capital "Step" on that line would be read as the fill-in (#13)
- A section the setup template or the workflow names by heading (`Git rules for Redline agents`, named by `templates/claude-md-git-sentence.md` and the run line in `workflows/redline-loop.js`; `Known limits`, linked by the handoff comment) stays in the README under that heading: moving it is a template change, a minor bump and a rerun of setup in every repository. The `checks.sh` header's "See README.md for the output contract" is the same kind, written by `redline-setup.sh checks` and read back by `read-checks`, and is kept until the next `checks-template.sh` bump; `docs/contract.md` opens by saying it is the contract that sentence means (#14)
- A new launch word lands, in the same commit, in the skill's grammar table, its `argument-hint` and its `description`, and in the alias template's `argument-hint` with this checkout's copy, so the slash-command hint never omits a word a run's own message tells the person to type (#80, R1-1)
- A change to the run's done rule rewords every statement of it a reader meets, found by searching for the old rule's words, not only in the file the change touched: the README's opening paragraph and its Known limits ("What a clean run means", which the handoff links), `docs/`, the skills' descriptions, both `.claude-plugin/` descriptions and `agent-os/product/mission.md`, whose "Honest about its reach" cites the README's Known limits and says what a clean run checked in the same words. A clean run is stated as what the run checked, never as a promise that no correctness bug remains, since the reviewer verifies the coverage pass's candidates and a decided finding it still reproduces is listed under For the person. #79 reworded the skill's description and the README's loop paragraph and left the README's opening line, both plugin descriptions and the mission on the old rule until round 5 (#80, R5-1)
- A change to `docs/` is reader-facing by nature and needs no Docs entry of its own. `docs/scripts.md` quotes every script's header verbatim, so a change under `scripts/` that touches a header names `docs/scripts.md` in its entry and updates it in the same commit (#14)
- A cost a spec's renderer Evidence records (a link that breaks, an entity that shows) is named in README Known limits in the same PR, each Evidence row read against the costs list before the docs are written: the #87 follow-up spec recorded an inline link's href taking the joiner, and Known limits named only the bare URL until #89, R3-1

## process/release

# Release

The plugin's version is the manifest's, every PR moves it, and a release is a person's tag and changelog entry after the merge (#16).

- Every PR bumps `version` in `.claude-plugin/plugin.json`, and the marketplace entry in `.claude-plugin/marketplace.json` carries the same string: minor when the change alters what a setup rerun writes (`scripts/checks-template.sh` below its header, a file under `templates/`, an allow entry, the unattended section's body), with the template markers it touches bumped in the same PR; major for a contract change a rerun cannot carry; patch otherwise. The gate's Version step says so, and the Redline reviewer reports a missing bump as a nit (`agents/redline-reviewer.md`, the Version bullet), except in a PR whose spec keeps the version on purpose, as #16 keeps `0.1.0` (#65, R1-1)
- The two versions are kept equal, never one without the other: Claude Code reads the manifest's first and ignores the entry's when both are set, `claude plugin validate` warns on a disagreement and `claude plugin tag` refuses one; `tests/setup-test.sh`'s last cases prove they agree and are semver
- The tag is a person's step, never CI's: on `main`, clean, from the plugin root, `claude plugin tag --dry-run .` then `claude plugin tag --push`, which validates the manifest, requires the two versions to agree, a clean tree and no `redline--v<version>` tag yet, and pushes the annotated tag. CI runs the gate and nothing of a release
- `CHANGELOG.md` is written at tag time, dated and committed on `main` before `claude plugin tag`, so the tag names a commit that carries its own entry (#65, R1-2): one heading per tagged version, newest first, one line per merged PR since the previous tag, in three groups (Features; Fixes; Setup and templates, the ones a rerun of `/redline:setup` carries); a PR merged between tags goes under the next tagged version. A line under Setup and templates says what a rerun writes, read off the subcommand's own header: `redline-setup.sh config` keeps an existing `redline.json` as the person's and lists a changed template value under differs without writing it, so a key the template gains reaches a repository by hand or by `--force`, and the line says which (#80, R2-4)
- Claude Code moves an install on the manifest's `version`, not on the tag: an install from the GitHub marketplace stays on its version until `claude plugin update redline@redline` or auto-update, which is off by default for a marketplace that is not Anthropic's. The tag names the release commit and is what a dependency's version range resolves against (plugin loading reference, "How Claude Code computes the version"). A version can be installed from the moment it merges, tag or no tag: an install that updated from that merge stays on those files while later PRs keep the version string, since `claude plugin update` finds nothing to move to, so being untagged is no reason for a PR to keep a merged version (#83, R2-1)
- A marketplace is registered once per user, so the machine's `redline` marketplace is the GitHub one and development loads the checkout with `claude --plugin-dir <checkout>`, which replaces the installed copy by name for that session with its hooks and `CLAUDE_PLUGIN_ROOT` from the checkout; the local-directory marketplace would put every repository on the machine on the checked-out branch
- A script the skill runs by `${CLAUDE_PLUGIN_ROOT}` knows which copy the session loaded from its own path, so it takes no flag for it: `redline-setup.sh version <repoRoot>` reports a self-hosted root that is not the loaded copy (`plugin: {self, inPlace, pluginRoot}`) and the launch precheck warns with the `claude --plugin-dir` line, never stops
- Under `claude --plugin-dir` a subagent's `Write` is refused in auto mode with no verdict, and in accept-edits it prompts despite a matching allow rule; an installed release is clean. The probe, on Claude Code 2.1.319: a project subagent with `tools: Write` asked to write one word, same checkout, same mode, refused under `--plugin-dir` and written under plain `claude`. ## process/standards-retrospective

# Standards retrospective

Every spec ends by asking what it taught, mechanically, and the answer lands in a standard or is recorded as "no changes".

- Gate step 12 in `.claude/commands/agent-os/shape-spec.md`: list every Decision in `shape.md`, every deviation in `plan.md`'s As built, and every check that went red and was fixed by learning something; classify each as already in a standard, missing, or contradicting one
- Approved edits land in their own commit, separate from the spec's code. Code that enforces a new rule (a guard-cases row, a loop-test check) follows in its own commit with the case proving a violation fails
- In a Redline run the shaper proposes the edits under `## Standards retrospective (proposed)` in `shape.md`, the standards approver approves the list, and the implementer applies it in one commit
- When nothing changes, `shape.md` records "Standards retrospective: no changes" under Decisions, so the absence is deliberate and visible
- A round a person finishes by hand, outside the run (a pending decision applied, a deferred full fix made), still owes its record in the same PR: the round's `shape.md` records the decision with its owner and commit, its proposed retrospective lands or reads 'Standards retrospective: no changes', and every standard that named the change pending says what landed, not only the README and `docs/`: `6ef58a9` applied R3-4 with neither record, and `a70c243` narrowed the guard while `scripts/guard.md` still called it pending, until the next round found both (#80, R4-1, R4-2)
- A standards edit keeps the file's headings: they diff empty against `main` unless the spec names the section it adds, renames or removes
- `index.yml` lists every standard and nothing else; a new file is added to it in the same commit, alphabetised by folder and file

## process/internal-notes

# Internal notes

This is the public repository: it carries the tool and its operating documentation, never the design record.

- Step notes, spike notes, API notes and the design document live in the private sibling repository `redline-internal` (`DESIGN.md`, `docs/`). A spec here may cite one by file name; it never copies the text in
- `README.md`, `docs/` and `CONTRIBUTING.md` are the long-form documents here: the README for installation and use (what it is, requirements, install, quick start, the dials, the Files table, the git rules for agents, Known limits), `docs/` for the reference (setup, contract, running, guard, upgrading, scripts), `CONTRIBUTING.md` for developing, CI, the Docs step and releases. A rationale goes to the internal repository; a rule goes to a standard (#14)
- Seed PRs and their answer keys live outside this repository, so a reviewer cannot read the answers
- `agent-os/specs/` holds the specs of changes to this repository, including the rounds Redline runs on itself. They are public and carry no attribution and no private detail (no token, no cost figure, no person's name beyond a GitHub login where a decision names its owner)
- A baseline for a PR whose head has moved is measured on a throwaway draft PR at the old SHA, since the precheck requires HEAD equal to the PR head and a run on the real PR would see later comments in the known-finding check; the body is the original's with `Closes` changed so nothing is linked, and the PR is closed and its branch deleted afterwards. Once the original PR is merged, `main` contains the old SHA and a draft PR against `main` diffs the wrong history, so the base is the branch's last merged `main` commit (the second parent of its last merge of `main`), pushed as a second throwaway branch and deleted with the first; while the original is open, `main` stays the base (#79). Once the original PR has merged, its review-round spec folders are on the default branch too, and a coverage pass that follows the repository's own check-before-reporting rule reads them: the #817 rerun's pass read the merged PR's round decisions at call 91 of 112 (`SPIKE-72-NOTES.md` §10). So measure before the original merges, or audit what the pass read, by call index, from the fork's transcript. The fork's thinking is empty in the transcript, so the call order is the only evidence: count as independent only what it found before the first such read; an item whose file the fork first names after the read is not independent even when the whole-diff read came before it, and is recorded as open, not as found (#85). Probe scripts, runbooks and run-record copies live beside the spike note in `redline-internal/docs/` (spike #72)

## prompts/attribution

# Attribution

Redline labels its own work as Redline and never as a model or a vendor.

- `Redline round N` review titles, the `redline:` commit prefix, the `Redline handoff` comment and `decided by: redline` are a tool's name and are allowed everywhere
- No `Co-Authored-By`, no "Generated with", no model or vendor name in a commit message, PR body, review, reply, issue, spec file or standard. The guard refuses a commit message that carries one (`ATTRIBUTION` in `scripts/redline-guard.sh`), after stripping path spellings such as `.claude/` and `CLAUDE.md`
- A repository's CLAUDE.md gets the paragraph from `templates/claude-md-git-sentence.md`, so a model reading its no-attribution rule does not take Redline's label for attribution
- This repository's own commits, issues and specs follow the same rule; the plugin manifest names its author, who is a person
- An agent prompt never says which model is running; a role is named by what it does (reviewer, shaper, checker)
