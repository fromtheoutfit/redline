# Show a decided call to the plan approver and the implementer by what the resolve agent stated it ends in

In a Redline round, `effectiveDispositions` in `workflows/redline-loop.js` builds the dispositions the plan approver and the implementer are shown for each finding. For a judgment call the person or the autopilot answered, the decision names no disposition. So the call is shown with the shaper's disposition (`ask`), or with whatever a reshape after a bounced plan re-sorted it to. It is never shown with what the resolve agent stated the decision ends in (`stated`: `fix`, `defer` or `accept`), although `isDeferral`, `needCommits` and the hold after each reshape all read that. Take a reshape that re-sorts a call stated as a fix to `decline`, against its prompt. The implementer is shown `decline` beside the line that a declined finding has no task and no commit, while `needCommits` still demands the call's commit. An implementer that follows the shown disposition rather than the plan and the decision beside it skips the task. The check then fails, the repair runs, and the round stops at stage `check`, whose resume starts at the build and cannot replan. The #99 spec left this view to #106 (its decision 14), and #106 settled only the files shown beside it.

- **Where:** `workflows/redline-loop.js:3968`
- **Why it is not fixed in #114:** The line that builds the shown disposition predates the pull request it was found in, which changed only the files shown beside it. The full fix changes what the plan approver and the implementer are shown in every round with an answered call, so how they handle a shown `accept` or `defer` on a call has to be checked first. That is a change of its own, beyond that pull request's task list.
- **Proposed fix:** In `effectiveDispositions`, show a call the round tracks whose decision names no disposition by its stated end (the decision's own disposition when it names one, else `stated` for the call). Check that the first branch of `needCommits` still leaves stated calls out, and that `outcomesFor` still reads a decided call by its decision. Read the plan approver's and the implementer's agent files for how they treat a shown `accept`. Add loop cases: a call stated as a fix that a reshape re-sorts to `decline` is shown `fix` to the implementer and built, a call stated as accepted is shown `accept`, and a round with no answered call keeps its prompts byte for byte.
