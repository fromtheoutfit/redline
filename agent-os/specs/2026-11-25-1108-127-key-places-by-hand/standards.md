## workflow/agents

One role per file under `agents/`, loaded as `redline:redline-<role>`, with its model and its denied tools in the frontmatter.

- Frontmatter carries `model` (overridden per call from `.claude/redline.json`) and `disallowedTools` as whole tools. Per-command limits are the guard's job: `Bash(git push *)` in `disallowedTools` would remove all of Bash, and a plugin agent's own `hooks` are ignored
- A prompt opens with "This is a Redline agent run on pull request #N" and names the plugin's README path for the git rules. The agent file holds the role; the workflow's prompt holds the round's inputs
- The reviewer, the shaper, both approvers and the checker return JSON, not prose, and the workflow reads fields, never text (the coverage pass's relay of a skill's text is the one exception, below). The checker's pass or fail comes from `checks.sh`'s JSON: each check's `exit` against the baseline, the exit code and the git block (`unexpected_files`, `uncommitted`, `commits`), never `ok` and never the checker's error text (#37, R1-3)
- An agent file's return block is one JSON object with each key once. A key two operations fill with different types (the GitHub agent's `skipped`: post-review's `already posted` string, resolve-threads' `[{id, reason}]` list) appears once, and a sentence under the block says what each operation puts there. Each call's schema in the workflow carries the type that call accepts (#45, R1-1)
- The shaper decides, and a person is asked in named cases only (#93): the verifier states what is true and the shaper sorts every finding into `fix`, `decline` (with the reason a teammate reads), `defer` or `ask`. Since #95 these are four endings, and `defer` is its own: an item of any kind that is worth doing and not in this pull request, with a mitigation only when a cheap one exists inside it, and always with a drafted issue (a title, what was found, why it is not fixed here, the fix proposed) that the run files; `decline` is for what is not worth doing (the claim is wrong, the conditions will not occur, the spec chose otherwise, or it could not be confirmed) and never points at follow-up work, so the proportionality rule and a refactor that fails a small-refactor test end in `defer`. It returns an `ask`, with a story, options and a recommendation, in five cases (the options differ in what the product does or a user sees; the fix changes an assumption, the approach or the architecture the spec agreed; it reaches outside the pull request; two options are defensible with no clear pick; the finding is still unconfirmed after the shaper's second look and serious if true), beside a repository ask rule and a finding on one of Redline's own files. Everything else it decides, a decline included, as `decided by: redline` with its reason. The rule is cases, never a confidence figure, and the workflow checks it: a judgment call whose `why_human` is outside the round's list is refused by the shaper's own output schema, and one that reaches the workflow anyway stops the run at `shape`. The person decides a call in their session, or autopilot takes the recommendation and says so, except for a finding a repository ask rule covers or one on Redline's own files, which autopilot leaves to the person with the rule, or Redline's own files, as its reason (#49; #94, R8-4). No other role decides a pending call or reopens a decision made, except where its job is to: a disposition override is the person's decision and replaces the shaper's, a decline included, and the plan approver checks the shaper's own dispositions and a bounce sends one back to the shaper to decide again, so the resolve and plan approver prompts carry rules of their own and not the implementer's 'never reopened' (#94, R4-4, R4-5)

R2-4, R3-3, R4-6, R4-7 in the harness's git) until the round cap ended the run with both open, and the sweep made by hand then found two more ways in that no round had named (`GIT_ATTR_SOURCE`, the per-user ignore file); #114, R1-1); and each thing a row says is shown is traced to what it is read from, one by one: the draft view's row gave the list as the source of the mitigation's words beside `files` and `ships`, and the words are read from the decision's entry, which no reshape replaces (#114, R1-7); and since #75 the rule is a step with fields: every fix the shaper sorts states `cause` (where the cause lives, and `one-place`, `sweep` with what the sweep covered, or `instance`), the verifier states `sameClassAs` in a review that is shown earlier findings, the workflow keeps a link only to a finding its record shows as fixed, and an `instance` fix under a link that stands stops the round at shape; - A finding a repository ask rule covers (#49) has its own outcome kind, `left`: never `fixed` or `deferred`, so no commit is demanded, its thread stays open for the person unless they defer it to an issue (below), a human pass's refusal of `defer` is never tripped, and its reply opens `left to the author under repository rule <id>`, which `redline-gh.sh prior-findings` reads as the disposition `left`. Any other answer, and autopilot, leave the finding as before; a check of a left call that only the shaper's own drafting could satisfy spares a draftless defer option of a call `forceAskRules` relabelled from a reason that does not mark a left call (neither a `repository rule` nor `redline's own file`, the two the shaper is told to draft for), which keeps its options as written and, on a pick, has the resolve agent write the draft; it holds every defer option of a call the shaper wrote as left to its draft, and every draft a left call does carry complete, since the picked option's draft is the one filed and a short one would stop the round at `resolve` on every resume (#127, R1-4)
- Every decision carries its owner, in `shape.md`, in each finding's reply and in the handoff comment: `decided by: redline`, `decided by: @<login>` (the login `redline-gh.sh login` prints), `decided by: redline (autopilot)`, or `decided by: @<reviewer login>` for a change a teammate's review asked for and a human review pass made as asked (#36). An `accept` that keeps a decline changes nothing Redline does: it is the person's decision, listed under Put to with their reason, never an overrule (#94, R2-10). A posted line names the person running Redline by login, never by role or as "you" (`left to @<login> under repository rule <id>`, `### Put to @<login>`), since on a teammate's pull request that person is not its author; with no login the words are "the person running Redline", and `redline-gh.sh prior-findings` reads the older wording too
- A human review pass (`/redline:redline-revise <pr> review <selector>`) sorts a teammate's comment into `fix` (theirs: the shaper returns `decidedBy: "reviewer"` and the workflow maps it to their login), `ask` (the author's) or `none` (asks for nothing), never `defer` and never `decline`: nothing a teammate asked for is deferred or declined by Redline on its own, and the author chooses a mitigation at the hand-off if they want one. The workflow refuses the other pass's values at `shape`. Every label, reply file, title and log line of a pass comes from one descriptor (`passOf` in `workflows/redline-loop.js`), so a Redline round's prompts stay byte-identical to what they were before human passes existed, and the loop test proves it (#36). The pass is unchanged by #93: its prompts keep "Judgment calls are returned, never decided", its lines say "the author", and a run that is a human review pass keeps that as its no-login fallback. The round its final nit pass runs as is a Redline round, whose shaper may decline, so the pass's summary counts what the nit pass found and what a commit fixed, and never says fixed of an item that was not; its final nit pass runs when the pass committed a fix (`fixed`), as the main loop's does, never on a new head alone, since the spec folder's own commit is no fix diff (#94, R4-12)
- A role's prompt names only the commands the guard allows it, in the exact spelling the guard accepts (`<plugin>/scripts/redline-gh.sh diff <pr>`, `vendor/bin/pest <file>`)
- A message the run shows the person names a plugin file by its absolute path from `pluginRoot`, as a prompt names a plugin script (`${pluginRoot}/scripts/redline-gh.sh`): the person reads it from the repository under review, where a path relative to the plugin does not exist (#37, R1-2)

- Every agent's `error` is normalized once, as `run()` returns the result: `""`, `''` and `null` are empty and the text is trimmed, so a call site reads `.error` as it is, and a new call cannot stop a run on `'""'` as Losers League #790 did at Finish. The checker's `error` is text and never a verdict input: the verdict comes from each check's `exit` against the baseline, the git block and the gate's exit code, and the text is a warning on a round that passes (a round whose only failing checks were failing at baseline included) or detail added to a failure the data already established; `""`, `''` and `null` as its text are empty, by the normalization in the bullet above (#9; #34 round 2; #37, R1-3). ## process/release

The plugin's version is the manifest's, every PR moves it, and a release is a person's tag and changelog entry after the merge (#16).

- Every PR bumps `version` in `.claude-plugin/plugin.json`, and the marketplace entry in `.claude-plugin/marketplace.json` carries the same string: minor when the change alters what a setup rerun writes (`scripts/checks-template.sh` below its header, a file under `templates/`, an allow entry, the unattended section's body), with the template markers it touches bumped in the same PR; major for a contract change a rerun cannot carry; patch otherwise. The gate's Version step says so, and the Redline reviewer reports a missing bump as a nit (`agents/redline-reviewer.md`, the Version bullet), except in a PR whose spec keeps the version on purpose, as #16 keeps `0.1.0` (#65, R1-1)
- The two versions are kept equal, never one without the other: Claude Code reads the manifest's first and ignores the entry's when both are set, `claude plugin validate` warns on a disagreement and `claude plugin tag` refuses one; `tests/setup-test.sh`'s last cases prove they agree and are semver
- The tag is a person's step, never CI's: on `main`, clean, from the plugin root, `claude plugin tag --dry-run .` then `claude plugin tag --push`, which validates the manifest, requires the two versions to agree, a clean tree and no `redline--v<version>` tag yet, and pushes the annotated tag. CI runs the gate and nothing of a release
- `CHANGELOG.md` is written at tag time, dated and committed on `main` before `claude plugin tag`, so the tag names a commit that carries its own entry (#65, R1-2): one heading per tagged version, newest first, one line per merged PR since the previous tag, in three groups (Features; Fixes; Setup and templates, the ones a rerun of `/redline:setup` carries); a PR merged between tags goes under the next tagged version. A line under Setup and templates says what a rerun writes, read off the subcommand's own header: `redline-setup.sh config` keeps an existing `redline.json` as the person's and lists a changed template value under differs without writing it, so a key the template gains reaches a repository by hand or by `--force`, and the line says which (#80, R2-4)
- Claude Code moves an install on the manifest's `version`, not on the tag: an install from the GitHub marketplace stays on its version until `claude plugin update redline@redline` or auto-update, which is off by default for a marketplace that is not Anthropic's. The tag names the release commit and is what a dependency's version range resolves against (plugin loading reference, "How Claude Code computes the version"). A version can be installed from the moment it merges, tag or no tag: an install that updated from that merge stays on those files while later PRs keep the version string, since `claude plugin update` finds nothing to move to, so being untagged is no reason for a PR to keep a merged version (#83, R2-1)
- A marketplace is registered once per user, so the machine's `redline` marketplace is the GitHub one and development loads the checkout with `claude --plugin-dir <checkout>`, which replaces the installed copy by name for that session with its hooks and `CLAUDE_PLUGIN_ROOT` from the checkout; the local-directory marketplace would put every repository on the machine on the checked-out branch
- A script the skill runs by `${CLAUDE_PLUGIN_ROOT}` knows which copy the session loaded from its own path, so it takes no flag for it: `redline-setup.sh version <repoRoot>` reports a self-hosted root that is not the loaded copy (`plugin: {self, inPlace, pluginRoot}`) and the launch precheck warns with the `claude --plugin-dir` line, never stops

## scripts/bash-conventions

Every script under `scripts/` is its own documentation and talks to the workflow in JSON.

- Every script starts `#!/usr/bin/env bash` and `set -euo pipefail` (`redline-gh.sh`, `redline-guard.sh`, `redline-prefs.sh`, `redline-gate.sh`, `redline-setup.sh`, `checks-template.sh`). The test harnesses use `set -uo pipefail` instead, because one failing case must not stop the table
- A script a workflow reads emits exactly one JSON object on stdout and everything else on stderr: `checks.sh` logs through `log()` to stderr and prints the envelope last; `redline-prefs.sh resolve` and every `redline-gh.sh` read subcommand whose header says JSON print JSON and nothing else; a subcommand a role reads as text says what it prints instead (`diff` a unified diff, `pr-comments` and `issues-search` text), and one whose answer is yes or no (`has-review`) prints nothing and answers by exit code (#71, R1-6)
- `bash -n` reads its first file and treats the rest as arguments; check several with `ls <glob> | xargs -n1 bash -n` (#5, R1-3)
- Usage errors exit 2 with a one-line reason on stderr. A check that fails exits 1. A script whose exit code is an answer (`redline-gh.sh has-review`: 0, 1 or 2) says so in its header. Under `set -e` a command substitution that fails exits with its command's own status, so a documented exit code holds only where each such call is guarded (`found="$(gh issue list …)" || { echo '…' >&2; exit 1; }`): `defer` exited 4 on a gh that needed a login, while its header said 1, until #97, R4-1. A function run inside `$(...)` runs with `-e` off (bash clears it there outside POSIX mode, and no script here sets `inherit_errexit`), so a failing command inside it does not stop it and its last command's status is the substitution's: what it printed is checked before it is used. `post-review` posted a review of one newline when the jq inside `place_comments` failed, until #112, R1-9. A check of what it printed cannot see a step that failed and left the last one a well-formed result to print, so such a function returns non-zero when a step fails and its caller reads the status as well: an empty kinds file made `place_comments` print every comment under 'The file is not in this pull request:', and `post-review` posted it and exited 0, until #112, R4-5. A documented exit code for an input the script cannot read holds only when the input's whole shape is checked before any jq reads a field of it, each element of a list included: `post-review` checked only that `comments` was an array, so a number in it reached the jq in `wanted_files`, which a plain function call under `set -e` turned into jq's exit 5 and message while the header promised one line and exit 2 (#112, R3-2); line 24 is the same rule for a validator
- A wrapper that runs another script for a role (`redline-background.sh` around `checks.sh`) passes the wrapped script's stdout and stderr through unchanged, and its documented exit codes (0, 1 and 2 for `checks.sh`), so the role reads the result as it would the script's own, and takes the codes above them for its own answers (3 still running, 4 past the limit, 5 no result), stated in its header. Any other code the wrapped script exits with (a command failing under its `set -e`, a signal) is the wrapper's no-result answer with a line naming the code, never passed through: a passed-through 3 reads as still running and loops the role (#41, R1-3). A result the wrapper keeps under a label the workflow reuses is read once: the wait that returns it removes the label's files, so a wait that runs before the next start has cleared them cannot return the earlier run's result (#41, R1-2). It runs one fixed script, never a command it is given, so the guard admits it by subcommand (#40)
- The header comment is the documentation, in this order: what the script is, usage, environment variables, the output contract, the exit codes. `docs/scripts.md` quotes it verbatim and `docs/contract.md` carries the output contract, so a header change updates `docs/scripts.md` in the same commit (#14). A field added to `checks.sh`'s JSON, or a limit changed in it (`run_check` in `scripts/checks-template.sh`), updates `docs/contract.md`'s output contract in the same change, and a flag that reports a cut is set by every limit that can cut (#7, R1-14). `checks.sh`'s whole JSON stays bounded however many checks fail: the failing checks share one output budget, split evenly among them in a final pass after every check has run, never consumed in run order, because the checker may not Read a result that spills to a file (#7, R1-13). It is bounded whatever the pull request's size and the run's length as well (#68): stdout carries what the workflow reads and no more (a passing check's name, exit code and `recorded`, counts for the lists nothing reads, the round's own commits), stderr counts toward what the Bash tool shows, the budget is written out as arithmetic in the template's comment and run at its stated scale in `tests/setup-test.sh`, and what stdout leaves out is in the kept result, which `checks.sh --verdict` reads
- A change to what a subcommand selects or prints rewords every description of it in the same commit, found by searching for the old phrase across `README.md`, `docs/`, `skills/` and `agents/` rather than by editing only the `redline-gh.sh` table row that quotes the header: R1-3 changed which review body `human-review` takes and updated the header, the README's `redline-gh.sh` row and the revise skill, and left the README's paragraph on `/redline:redline-revise <pr> review` describing the old selection (#38, R2-1)
- A subcommand added to `redline-gh.sh` or `redline-prefs.sh` is added to the guard's groups in the same change (`GH_READ` for a read subcommand; `gh-all` already covers a write one), and the agent or skill that calls it names the exact spelling; a subcommand removed (`issue-create`, replaced by `defer`) takes its callers with it in the same commit: the skill section that ran it, the agent operation, its guard rows and `docs/scripts.md` (#95); and every sentence that describes what it did, found by searching the README and `docs/` for its words: `docs/guard.md` still named the after-run filing as the main session's one prompt until #97, R1-1
- A record a subcommand keeps beside what it writes is merged into as the file stands when the entry is written, never into the copy read when the subcommand began, and the temp file it writes beside the record is removed on every way out that does not end in its `mv`, through one `EXIT` trap that names every temp file the subcommand makes: `redline-gh.sh defer` read the round's record before a lookup and a create on GitHub and wrote that copy back, so an entry recorded in between would be lost, and left `.redline-deferred.*` behind on a failed write, where the run-record commit stages every untracked file (#97, R1-2, R1-3); and every step of the record's write that can fail after the create (the folder, the read, the temp file, the move) exits through one function that names the entry it could not record, since under `set -e` a tool's own message alone loses the issue just opened (#97, R2-1)
- A subcommand that makes temp files, directly or through the functions it calls, makes them in one `mktemp -d` directory its `EXIT` trap removes (`place` and `post-review` point `TMPDIR` at it), made before the subcommand's first call that makes one, the listing's read in `pr_files` included (#112, R2-3), so a failure or an interrupt leaves nothing in the temp directory: a function that removes its own files on return leaves them behind when the subcommand stops inside it (#112, R1-2)
- A script only a skill calls (`redline-prefs.sh`, `redline-gate.sh`, `redline-setup.sh`) needs no guard group: the guard's default deny refuses it to every role, and `tests/guard-cases.tsv` rows pin it as the skill's (#6); when one of its subcommands is reserved for a person, its rule in the shared allow list (`templates/settings.allow.json`, and the repository's `.claude/settings.json`) names only the subcommand the skill runs unprompted (`Bash(/*/scripts/redline-gate.sh check *)`), so the reserved one stays behind the permission prompt (#7, R1-9); `redline-setup.sh`'s writing subcommands have no allow-list rule, and the permission prompt is the person's confirmation (#6), while `version`, which writes nothing and which `/redline:redline`'s precheck runs at every launch, once had the one narrow rule, `Bash(/*/scripts/redline-setup.sh version *)`, on the pattern of `redline-gate.sh check`'s (#12, R1-8); since #50 the allow list carries no script path rule at all (a `Bash(/*/scripts/…)` rule matched a script of that name at any path an agent could write), and the guard approves the one unprompted subcommand (`redline-gate.sh check`, `redline-setup.sh version`) for the main session by real path, so the reserved ones stay behind the permission prompt
- A value the skill passes into `args` from the run marker is computed by `redline-prefs.sh run` and copied as printed, so its rule has a prefs case where skill prose would have none: `run check`'s `hand`, with the label's earlier entry merged in (#10), and `run drift`'s `drift`, whose agent list an error or stopped marker keeps as its own args passed it (#91, R1-1)
- A saved launch setting added later is asked once of a saved file that lacks it, beside the confirm, and a setting that does not apply to a run (the deferral settings under `review only`, `deferAt` under `autopilot`) is neither asked nor written by it, so the next run it applies to asks. `redline-prefs.sh save` takes every setting and keeps the inapplicable ones out itself, so the skill always passes what `resolve` printed (#95)
- A generator that writes a file from a template (`redline-setup.sh checks` from `checks-template.sh`) splices by anchor lines and exits 1 naming a missing one, so the template and the generator cannot drift apart silently, and its output is deterministic: the same input gives the same bytes, and nothing is written when they are unchanged (#6). It validates every input field it writes, not only the commands: a field that lands in a comment is a single line, and one that lands inside quotes holds no character that would end or expand them, so a bad `checks.json` exits 2 rather than writing a `checks.sh` that runs a stray line (#12, R1-6)
- A script that edits a person's file (`.gitignore`, `shape-spec.md`, `settings.json`) preserves the file's line endings and a byte-order mark (`settings.json` refuses a byte-order mark instead, exit 2, as its header says), writes only when the bytes change and reports `changed: false` otherwise, so a rerun can say nothing drifted; a JSON file is compared with `jq -S`, since a CLI that rewrites it (`claude plugin install`) reorders keys and that is not drift (#6)
- A merge into a person's JSON file keeps every value already there, adds only what is missing, and reports each kept value that differs from the template (`conflicts`) rather than overwriting it (#12, R1-3, R1-4); every subcommand that writes takes `--dry-run`, which prints the same JSON with `written: false` and creates nothing, not even the target's directory (#12, R1-2)
- A rerun over a file the script wrote earlier changes only the values the script derives from its inputs (`config` updates `checker` and `checkerStallMs` in place, keeping the file's formatting) and keeps every other value as the person's, the ones the person chose at setup included (`reviewer`), listing each that differs from the template under `differs` without changing it; `--force` is the full reset to the template (#12, R1-5)
- A rerun's `differs` lists drift from the template, never the person's own additions: `config_differs` ignores a key only the person writes (`askRules`), so a rerun does not report the rules as values to reset (#49)
- A config key that says where an outward write goes (`deferTo` in `redline.json`: a GitHub issue, or a file) is refused when it is not one of its words, with a line naming the key, the file and the value, and is never defaulted; a key that only bounds the run (`maxRounds`) falls back to its default (#95)
- A validator that shares its messages with another (`ask_rules_fault` in `redline-setup.sh`, `rule_fault` in the guard, the workflow's launch check) shares its tests too: a key's presence (`has("paths")`), never a non-null value, so `{"paths": null}` gets the shared message instead of passing, and a list's elements are filtered to objects (`objects`) before a field of each is read, so a non-object element gets `not an object` and exit 2 instead of jq's own error and exit 5 under `set -e` (#52, R1-2), and a pattern is matched against the whole string, `\A...\z` in jq: jq's `$` also matches before a final newline, so `^[a-z][a-z0-9-]*$` passed the id `"a\n"`, which the guard's `fullmatch` and the workflow's `/^...$/` refuse, and setup wrote a list that then stopped every run (#52, R2-1)
- A flag that replaces a list a rerun otherwise keeps (`config --ask-rules`) clears it with `[]`, and the skill that calls it passes `[]` when the person removes every entry: without the flag the old list stays, so "with none, omit the flag" left a removed list enforced (#52, R1-3)
- A jq program that holds a quote goes in a quoted heredoc (`prog="$(cat <<'JQ' ... JQ)"`, then `jq "$prog"`), never in a bash single-quoted string: `ask_rules_fault` first wrote `'\($r.id)'` inside `jq -r '...'`, which ended the bash string at the first quote and failed `bash -n` (#49)
- Python inside a script is `python3 -I -c "$PYTHON"` with the standard library only, fed on stdin; it writes no file beside the script
- A path the script receives is made absolute once (`cd "$(dirname "$path")" && pwd`) and used as is; the repository is `git rev-parse --show-toplevel`, never a walk from `$PWD`
