# Agents

One role per file under `agents/`, loaded as `redline:redline-<role>`, with its model and its denied tools in the frontmatter.

- Frontmatter carries `model` (overridden per call from `.claude/redline.json`) and `disallowedTools` as whole tools. Per-command limits are the guard's job: `Bash(git push *)` in `disallowedTools` would remove all of Bash, and a plugin agent's own `hooks` are ignored
- A prompt opens with "This is a Redline agent run on pull request #N" and names the plugin's README path for the git rules. The agent file holds the role; the workflow's prompt holds the round's inputs
- The reviewer, the shaper, both approvers and the checker return JSON, not prose, and the workflow reads fields, never text (the coverage pass's relay of a skill's text is the one exception, below). The checker's pass or fail comes from `checks.sh`'s JSON: each check's `exit` against the baseline, the exit code and the git block (`unexpected_files`, `uncommitted`, `commits`), never `ok` and never the checker's error text (#37, R1-3)
- An agent file's return block is one JSON object with each key once. A key two operations fill with different types (the GitHub agent's `skipped`: post-review's `already posted` string, resolve-threads' `[{id, reason}]` list) appears once, and a sentence under the block says what each operation puts there. Each call's schema in the workflow carries the type that call accepts (#45, R1-1)
- The shaper decides, and a person is asked in named cases only (#93): the verifier states what is true and the shaper sorts every finding into `fix`, `decline` (with the reason a teammate reads), `defer` or `ask`. It returns an `ask`, with a story, options and a recommendation, in five cases (the options differ in what the product does or a user sees; the fix changes an assumption, the approach or the architecture the spec agreed; it reaches outside the pull request; two options are defensible with no clear pick; the finding is still unconfirmed after the shaper's second look and serious if true), beside a repository ask rule and a finding on one of Redline's own files. Everything else it decides, a decline included, as `decided by: redline` with its reason. The rule is cases, never a confidence figure, and the workflow checks it: a judgment call whose `why_human` is outside the round's list is refused by the shaper's own output schema, and one that reaches the workflow anyway stops the run at `shape`. The person decides a call in their session, or autopilot takes the recommendation and says so, except for a finding a repository ask rule covers, which autopilot leaves to the person with the rule as its reason (#49). No other role decides a pending call or reopens a decision made
- A finding a repository ask rule covers (#49) has its own outcome kind, `left`: never `fixed` or `deferred`, so no commit is demanded, its thread stays open for the person, a human pass's refusal of `defer` is never tripped, and its reply opens `left to the author under repository rule <id>`, which `redline-gh.sh prior-findings` reads as the disposition `left`. One function in the workflow (`forceAskRules`) applies the rules after every shape and reshape, whatever `fix`, `defer` or `ask` the shaper returned (a human pass's `none`, a comment that asks for nothing, is left as it is, since there is no change to leave to the person; #52, R1-4): a paths rule on the finding's file and on the `files` the shaper lists for its task, a prose rule by the shaper's `askRule` tag; the reviewer's tag is advisory and only marks the review. A later numeric limit (#25) forces there too
- Every decision carries its owner, in `shape.md`, in each finding's reply and in the handoff comment: `decided by: redline`, `decided by: @<login>` (the login `redline-gh.sh login` prints), `decided by: redline (autopilot)`, or `decided by: @<reviewer login>` for a change a teammate's review asked for and a human review pass made as asked (#36). A decision Redline makes alone carries its reason beside its owner, in the thread and in the handoff, so the person can audit it and overrule it without a new stop: a typed line at a stop the run already makes in that round, or a reply in the thread and a human review pass over their own login (#93). A posted line names the person running Redline by login, never by role or as "you" (`left to @<login> under repository rule <id>`, `### Put to @<login>`), since on a teammate's pull request that person is not its author; with no login the words are "the person running Redline", and `redline-gh.sh prior-findings` reads the older wording too
- A human review pass (`/redline:redline-revise <pr> review <selector>`) sorts a teammate's comment into `fix` (theirs: the shaper returns `decidedBy: "reviewer"` and the workflow maps it to their login), `ask` (the author's) or `none` (asks for nothing), never `defer` and never `decline`: nothing a teammate asked for is deferred or declined by Redline on its own, and the author chooses a mitigation at the hand-off if they want one. The workflow refuses the other pass's values at `shape`. Every label, reply file, title and log line of a pass comes from one descriptor (`passOf` in `workflows/redline-loop.js`), so a Redline round's prompts stay byte-identical to what they were before human passes existed, and the loop test proves it (#36). The pass is unchanged by #93: its prompts keep "Judgment calls are returned, never decided", its lines say "the author", and a run that is a human review pass keeps that as its no-login fallback. The round its final nit pass runs as is a Redline round, whose shaper may decline, so the pass's summary counts what the nit pass found and what a commit fixed, and never says fixed of an item that was not
- A role's prompt names only the commands the guard allows it, in the exact spelling the guard accepts (`<plugin>/scripts/redline-gh.sh diff <pr>`, `vendor/bin/pest <file>`)
- A message the run shows the person names a plugin file by its absolute path from `pluginRoot`, as a prompt names a plugin script (`${pluginRoot}/scripts/redline-gh.sh`): the person reads it from the repository under review, where a path relative to the plugin does not exist (#37, R1-2)
- A message the run shows the person says when it fires in the words of the decision behind it, so a fix that widens or narrows the condition rewords the message and the loop checks that pin it in the same commit: R1-3 let the checker-text warning fire on a round whose gate exited 1, and it still said 'on a passing gate' next to 'still failing, as at baseline' (#37, R2-1)
- A decision that changes a rule a prompt states is applied everywhere the prompt and the role's agent file state the old rule, found by searching both for the rule's own words (`never re-raise`, the example values), not only in the sentence the finding quoted, and every other wording of the same rule (`not raised again`, `raises it again`): #93's decline reopening reached the candidates block and the handled-list header and left the agent file's "is not raised again", the history header, the README's Known limits and `docs/running.md` unconditional until #94, R1-1: R2-1's reopen changed the candidates block and two paragraphs of the agent file but left the handled-list header and the `knownAs` example saying a fixed match is never re-raised (#80, R3-3); and a prompt sentence that invites more text into a field the workflow parses (a coverage ref) is checked, in the same change, against every parse of that field, so the prompt keeps the text out of the field or after the parsed token and the parse reads past it: R1-4 kept a partly tracked candidate's issue out of a `finding` ref, which the workflow matches by id alone, and R4-1 had a `duplicate` ref open with the index or the id, a note after it, and widened the target parse, anchored at both ends, to read a leading index token (#86, R1-4, R4-1)
- An agent whose words reach GitHub in a comment or a reply says so in its file. The reviewer, the shaper, the resolve agent and the implementer each carry the sentence: 'An identifier that begins with `@` (a decorator, a directive, a docblock tag) is always written in backticks, because a bare `@word` notifies a GitHub account.' The loop test pins it in each file. The workflow neutralises the finder's and the verifier's short fields itself, but a comment's description, a reply, a mitigation or a commit subject is posted as written. The GitHub agent writes none of its own text, so its file does not carry the sentence. A new role whose text is posted gains it too (#87).
- A body the GitHub agent writes with the Write tool, byte for byte, holds no invisible character the post depends on: nothing compares the file it writes with the workflow's text, so a character it drops goes unseen. Such a character is written as a numeric character reference GitHub decodes, as `postedText` writes the word joiner as `&#8288;`, and the loop test checks that the post and handoff prompts hold no raw joiner (the #87 follow-up spec)
- Haiku for the roles that move files and post (github, checker); Opus for the ones that read code (reviewer, plan approver); the revise model is picked at launch and saved per person
- A role that finds a problem with its own instructions (a command the guard refuses, a file that does not exist) reports it in its JSON rather than working around it
- A sentence that says what keeps a change out of a run, in the README, `CLAUDE.md`, a standard or a prompt, credits a role only with a check its prompt carries, read in that prompt before the sentence is written: #65's R1-3 correction credited the plan approver with keeping the guard and hook files out of a cached-mode plan, while its file-scope check names the loaded plugin's directory, which is then the cache, and the claim reached four files before R2-1 removed it (#65, R2-1)
- A degraded result is data, not an error: the GitHub agent returns a posted review with no inline comment as `posted` true with every finding in `movedToBody`, the workflow records a warning, and `error` is reserved for an operation that failed. The workflow does not take an agent's `error` on trust in either direction: an `error` on a review that is posted, has a review id and accounts for every finding (inline or in `movedToBody`) is recorded as a warning and the run continues, while one on a result that fails that check still stops the run (#33: a review with every finding in the body ended the run at `post`; #34, R1-8; #9)
- Every agent's `error` is normalized once, as `run()` returns the result: `""`, `''` and `null` are empty and the text is trimmed, so a call site reads `.error` as it is, and a new call cannot stop a run on `'""'` as Losers League #790 did at Finish. The run record's `detail.checker` keeps the normalized text, beside the status, reason and partial result #9 keeps it for (#42; #43, R1-1)
- An agent that could not read what it was asked to relay returns a distinct status (the checker's `result_unreadable`, with a reason from a fixed set) and whatever it did get, never a partial object that looks like a failing result. The workflow stops on that status, and on any result the implementer cannot change (no result, exit 2, no git block), naming the cause and the fix; it sends to repair only failing checks and git-block findings. The checker's `error` is text and never a verdict input: the verdict comes from each check's `exit` against the baseline, the git block and the gate's exit code, and the text is a warning on a round that passes (a round whose only failing checks were failing at baseline included) or detail added to a failure the data already established; `""`, `''` and `null` as its text are empty, by the normalization in the bullet above (#9; #34 round 2; #37, R1-3). A usage error (exit 2) prints no JSON, so the checker's instructions and `stopReason()` test it before the unreadable status it would otherwise fall under: a specific case comes before the general rule, in the agent's steps and in the workflow's check order (#37, R1-1). Two causes with two different fixes are two reasons, since the message is what the person acts on: a foreground run the Bash tool moved to the background is `backgrounded` (re-record the baseline), not `spilled` (cap the output) (#40). A reason that claims something the workflow can check from the JSON it holds (`not_json`, `no_git_block`) is checked: when the result is one object with a `checks` array and a `git` key, the workflow reads it and records the misread as a warning naming the reason, since a Haiku checker read `git: null` as a missing key and stopped #54 at baseline. A reason about where the output went (`spilled`, `backgrounded`, `no_result`) stops as before: the JSON cannot refute it (#55). The run record's `detail.checker` then holds the copy the workflow read (`status` `read`, `reason` empty), and the warning is where the checker's own reason is kept; a change that rewrites a result before a call site stores it rewords every sentence that says what the record keeps, as #55 left the README saying `detail.checker` kept whatever the checker returned (#56, R1-1)
- A role never ends its turn to wait on a background task: a subagent's background task is killed when the agent gives its final response, and Claude Code blocks a long foreground `sleep`. A gate the recorded baseline says will not fit in one foreground Bash call (over 480 s of `args.baselineSeconds`, or none recorded) runs through `redline-background.sh`: `start` with `run_in_background`, then `wait` in the foreground, again while it exits 3, each call under the tool's 600 s cap and the stall window. The stall watchdog restarts only a silent agent and every wait is activity, so the wait's own `--limit` (the stall window in seconds) is what bounds a hung gate (#40)
- A check that something was already posted looks for text only that post carries. `redline-gh.sh pr-comments` prints review bodies and issue comments together, so a body finding's marker, which the review body also holds, proves nothing; the reply's own `from the Redline round N review body` line does; and it prints no URL or id, so a prompt whose duplicate check finds the post asks the agent to report it posted (`posted` true) with an empty `comment_url`, never for a field the script cannot give: a request for one leaves the agent to report the post missing or set `error` (#34, R1-1; #59, R2-1)
- A reply names what it answers, in a line only that reply carries: a human review pass's thread reply ends with a hidden `<!-- redline:answers <ids> -->` listing its findings' comment ids, and `redline-gh.sh human-review` counts a comment as answered only when a Redline reply in its thread names it. A Redline reply without the line (a Redline round's, or a human-pass reply posted before the line existed) answers every comment before it in its thread, the fallback that keeps older replies valid. Counting by thread alone lost a second teammate's comment and a follow-up left in a shared thread (#38, R1-1)
- A finding an earlier round recorded is not one it dispositioned. The evidence of a disposition is the Redline reply answering the finding (`fixed`, `declined`, `deferred`, `decided`, `dropped`, `left`, or `carried` by a later round; a reply opening `declined: ` is Redline's own decision not to act, #93; a later run's `resolved; first reported as` reply reads as `fixed`, since it is Redline's own claim that the code no longer has the bug, not a decision a person made, so a coverage candidate that still reproduces it reopens it as one that still reproduces a fixed finding does, #80, R4-3), never `shape.md`, which a hand-off never relaunched leaves reading `Decided by: redline` on fixes never made; a finding with no reply, or a `not changed` one, is carried forward: a finding of the current round with `carriedFrom`, re-verified against the head and never copied, listed under its own heading in the review body, replied to in its earlier thread and swept with it, and named in the handoff. The reviewer accounts for every carry-forward id as carried or resolved, and the workflow carries what it did not account for, with a warning, rather than dropping it. The duplicate check for a reply is a reply opening with this pass's title, so an earlier round's reply in a carried finding's thread is not one (#35). Only the run's first round carries: a `carriedFrom` on any review with no carry-forward list (a re-review, a final nit pass, a first round with no earlier findings) is cleared with a warning, since the history block shows later reviewers the carried ids (#46, R1-1). An earlier thread is swept on its own reply when the finding that carries it sits in the review body, which has no thread to reply in (#46, R1-4). The handoff names an earlier finding by its disposition before its reply text: one a later round's line already carried reads `carried forward as R2-2 in round 2`, whatever its own thread's last reply says (#46, R1-5). A carried finding is never known by a Redline id: a `knownAs` naming one is cleared with a warning and the finding is carried. One naming an issue or a teammate's comment keeps the author's choice to track it there: the finding stays under Already tracked with `first reported as R1-2` on its line, unshaped, and its earlier thread is answered `carried forward as R2-1; already tracked in #41 · decided by: redline` and left open as `already tracked`. That reply is what the next run reads as carried, so the finding is neither set aside unanswered nor raised again (#46, R1-2)
- An id the workflow mints beside the reviewer's is numbered after the highest in use, never by count: a reviewer's ids can skip a number, and every record of a run (comment ids, dispositions, outcomes, reply ids, the carried map) is keyed by id (#46, R1-3). When the workflow renames an id the reviewer returned, every ref to it in the same result (a coverage `finding` or `duplicate` entry) is renamed with it before anything reads the refs, or the entry looks like one naming no finding (#80, R2-3)
- An answered review body is found the same way: a human review pass's body reply is an issue comment whose header line names the review (`**H<n>-<k>** · from review <id> by @<login>`), and `redline-gh.sh human-review` reads the PR's issue comments back and never takes a body whose review such a comment names, so a repeat pass over an answered review stops with nothing to revise. A pass still takes one body, the newest of the selection's that is not yet answered, so an older note comes up on the next pass (#38, R1-3)
- A reply's route comes from whether a review is on GitHub, never from a missing thread id alone: a thread id replies in the thread, a body finding of a posted review gets an issue comment behind its marker, and a dry run or an unposted review writes the reply file and posts nothing (#34, R1-7). A dry run routes every reply file-only whatever threads exist, since a teammate's threads are real even then (#36)
- A thread gets one reply per pass. In a human review pass two open comments of one thread (a teammate's comment and their own follow-up) are two findings with one thread root, so their replies merge into one that opens with the pass's title and gives each finding's outcome on its own `**H<n>-<k>**:` line; the GitHub agent never replies twice in one thread (#38, R1-4)
- Finish resolves the threads Redline opened for the findings it settled, and never a human's (#39). The workflow picks, the GitHub agent calls, as with the run-record commit: the workflow lists each settled finding's inline comment id and reply id (`record.commentIds`, and `record.replyIds` kept from the agent's `replies[].reply_id`, which the loop dropped before), the agent runs the one `resolve-threads` line it is given, and the script resolves only a thread every comment of which is in the list, so a thread a teammate opened or commented in, wherever the comment sits, is skipped with a reason, which is a result and not an error (#45, R1-2). Redline posts from the author's login, so its comments are told by id, never by author. Settled is fixed, deferred, declined or decided with the reply posted, one list (`SETTLED_KINDS`) read for the round's own threads and for the earlier threads it carried (#93); a dropped finding stays open as the person's pick, and a body finding has no thread. The sweep runs after the PR description and before the handoff comment or the human summary, so the comment reports it (`Resolved n threads; m left open: <ids and why>`). A thread already resolved when the sweep runs (resolved by hand before Finish) is in neither count, since the line reports what this sweep resolved and what is still open (#45, R1-3). A capped run, a dry run and a `no push` run sweep nothing, and the line is absent when no Redline thread exists
- A count a skill or prompt needs comes from a command that prints the number (`git diff --shortstat`, `jq length`), never from counting printed lines by eye (#34, R1-5)
- An error result names the agent label that caused the stop (`resumeFrom`), and the skill writes a marker through `redline-prefs.sh run save`; a resume is the person's choice at the next launch, never a retry by the skill or the workflow, and a `gather` error is not resumable (#10)
- The workflow checks a result before it acts on it: the shaper's spec folder is listed by the GitHub agent's read-only `spec-status` operation, an `ask` must have its judgment call, except, on a reshape, one the round already decided, since the reshape returns only the calls still pending or newly raised (#61, R1-2), a `decline` must carry its reason, and on a Redline round a judgment call's `why_human` must be one of the round's cases (#93): the shaper's output schema is built per pass, so its enum is that pass's reasons and the rule reasons and a value from the other pass is refused in the shaper's own run, which then decides the finding or asks again with an allowed reason; the workflow's test is the second layer, run after `forceAskRules`, so a call a repository rule covers is judged by the reason the rule gives it (#94, R1-5, R1-12, R1-13), and an unusable result is a stage error with `resumeFrom` naming the agent to rerun, never a synthetic judgment call; the one call the workflow writes is the repository-rule ask (#57)
- A workflow subagent never has the Agent tool (`agent()` has no `tools` option and the default workflow agent denies it), so a skill it invokes runs its recipe without a fan-out. The skill runs as a foreground fork with the caller's tools and output contract: a `schema` on the agent that calls the Skill tool, role or not, can make the fork call StructuredOutput itself and leave the caller with `Skill execution completed` (spike #72's reviewer-role probe, then #79's second corpus run on a default agent after the same script got through on the first; it is not deterministic), and the run record counts the calling agent only (two tool calls), so a skill pass is a plain workflow agent with no schema, measured from the fork's transcript under `subagents/` (spike #72, #79). Its text is the one thing the workflow reads as text: the skill's own documented contract, one fenced json array of findings; an array none of whose entries carries the contract's fields is not that contract, and stops the round as recipe drift rather than passing as blank candidates (#80, R1-3), and two fixed marker lines the prompt asks for (`coverage: skill denied`, `coverage: skill absent`), each read at the start of any line with leading backticks or quotes allowed, since an agent copies the prompt's formatting, and only when no fenced list in the skill's shape was found, so a skill result that quotes a marker is still the list (#80, R2-2), each a cause the workflow turns into a stage error at the pass's own label; anything else in the text is ignored. The effort word is always passed, since without one the skill reuses the level typed last on the machine (#79)
- The coverage pass is the finder and the reviewer the verifier (#79): the built-in `code-review` skill runs over the whole pull request at the round's head on every whole-PR and fix-diff round, since it is stochastic and attends to what moved, so each pass is a sample and the manual loop it replaces ran one per round. The reviewer verifies its candidates and runs no discovery pass of its own over the PR; it keeps the checks its prompt names by rule (scheduled and queued overlap, the Docs nit, the Version nit) and the fix-diff recheck. Since #93 the verifier states facts only and the shaper decides: each candidate is accounted for with one of six outcomes, three facts (`verified`, reproduced or traced with the lines cited; `unconfirmed`, the narrow case of a claim the repository cannot show, with one line on what would confirm it; `refuted`) and three collapses (`duplicate`, `settled`, `known`). A verified or unconfirmed candidate is a finding of the round, with an id and a thread; there is no outcome for "true, not worth acting on" and no list for the person. What used to end the matter is a fact the finding states: a cause outside the diff (`outsideDiff`), the conditions a failure needs, a guard the pull request removed. The kind is a fact too, and it is what keeps a run going: `correctness` is wrong behaviour reachable in practice, a security hole, a privacy leak, data loss, a broken contract, or a promise the pull request makes that the code does not keep; everything else is `nit`. The done rule is the workflow's, read off the shaper's decisions (#93): a round is bought by what it finds, not by what it commits; a new correctness finding the shaper fixes, defers or asks about, or a decline the person overrules to a fix, buys the next round whatever the answer and with or without a commit; every other round ends the run, at the handoff when no commit names a finding and after one final nit pass over the fixes when one does; `maxRounds` is unchanged, and with `coverage off` a bought round that changed no code ends the run, since there is no pass to rerun. The finder never returns an empty list, so the prompt defines new (not collapsed into a finding already reported, settled in an earlier round, carried, or tracked elsewhere), and two outcomes reopen a settled finding as a new one of this round, the earlier id named in its description and `knownAs` empty: one marked `fixed` that the verifier still reproduces or traces at the round's head, so a fix that did not fully land keeps the run going (#80, R2-1), and one declined for want of confirmation that the verifier now confirms (#93); every sentence the verifier reads states the reopen rules, the handled-list header of an earlier run's findings included, which names the exceptions only when the pass ran (#80, R3-3). A `decided` finding stays settled whatever its commits, since an applied decision is often a deliberate keep or mitigation: a candidate that still reproduces one is accounted for as `settled`, its ref naming the earlier id and saying so, and the set-aside block shows it (#80, R3-4; #93). A candidate the verifier left out, gave an unknown outcome, or accounted for with a ref that names no finding becomes a finding of the round as reported (a new id, `correctness`, `unconfirmed`), with a warning, the mirror of carry-forward, so nothing is dropped and nothing is parked; a carried finding the verifier left out is carried as `unconfirmed` for the same reason. The verifier is shown the PR's earlier runs' handled findings on every round that ran a coverage pass, not only on the whole-PR round, since the pass samples the whole PR at every head and can re-sample a finding an earlier run deferred, declined or decided; the carry-forward list stays on the first round (#80, R1-2). The count sentence counts a candidate where the round puts it: an entry is counted by its finding's own confidence, and a finding listed under Already tracked is `known`. Under `correctness only` the workflow declines what is not a correctness finding with the scope as its reason: the finding stays in the round's record, so a later round collapses a repeat, and is listed once in the review body and the handoff with an id that is not bold, no thread and no reply, so `redline-gh.sh prior-findings` never reads it back and a later run without the scope sees it fresh. The findings file keeps the candidate list beside the accounting its indexes point into (#80, R1-4, R1-5)
- The verifier's rules from the #817 rerun (#85). An issue or a teammate's comment that tracks only part of a candidate leaves the remainder to be judged as its own candidate: one caused in the diff is a finding naming the issue, `knownAs` empty, accounted for as `verified`, unless another rule puts it elsewhere as it would any candidate (a collapse or a refutation), so a neighbouring issue never decides where a remainder goes (#86, R2-1); a partly tracked candidate is accounted for by what its remainder became, with the issue named in the finding's description or another outcome's ref, never in a `verified` or `unconfirmed` ref, which the workflow matches by id alone (#86, R1-4), `known` being for one tracked whole; two candidates are not one because one issue's title fits both. A refutation answers the candidate's claim, and its ref states that claim and the evidence against it; evidence for a neighbouring claim, or a comment or docblock stating intent, does not refute, and such a candidate is verified or could not be confirmed on its own claim (#93). A guard this pull request removed is a fact the finding states, naming the removed line, never a reason to drop it. Every candidate that is not a finding of the round is listed after the findings and the closing sentence in the set-aside block, under its own heading `### Candidates set aside (N)` (in the handoff, `### Candidates set aside in round <n> (N)`), a collapsed `<details>` whose summary is `Refuted, collapsed or already tracked`, by one rule (`LISTED_ELSEWHERE`), never a list of outcomes, so an outcome added later is listed too, and the rule reads the accounting after `accountCoverage`, which accounts for a candidate behind an Already tracked finding as `known`, so that candidate is in the block too, its ref the finding's id and the issue (#86, R5-3); the summary's three groups are the count sentence's (`refuted`; `duplicate` and `settled`; `known`) and add up to the heading's count. One line each, with the candidate's own file, line and summary, whole, so a refutation that answers another claim shows as a mismatch, then the outcome and the ref (`no reason given`, with a warning, when none): a `known` line names the issue, and a `duplicate` of another candidate's index also gives that candidate's place and outcome, and the finding's id when that candidate became a finding, which the block does not list (#86, R5-4), so a duplicate of a refuted or tracked candidate cannot hide: the accounting sentence, in the verify prompt and the agent file, has a duplicate's ref open with the index of the candidate or the id of the finding it collapses into, anything meant for the reader after it, and the workflow reads the target from a leading index token (`3`, `candidate 3` or `index 3`, any case) whatever follows it, so a note after the index keeps the target (#86, R4-1); nothing set aside, no block. Every finder and verifier field the review body and the handoff post (the block's lines; finding lines and the line under one saying what would confirm it; scope-declined, Already tracked and Resolved lines; the summary; the handoff's lines by outcome and its Earlier rounds lines), and an inline comment's title, go through one function, `postedText`, with fields that share a line read as one text. Outside code spans, `&` then `<` are escaped, and `&#8288;`, the word joiner (U+2060) as a numeric character reference, follows each `@` before an ASCII letter or digit, so no tag ends the block or bolds the body and no `@word` notifies; GitHub decodes it, and outside a code span it shows nothing (the #87 follow-up spec). Spans are read as GitHub pairs backtick runs and left as written, unless the text holds `](`, `][`, `://`, `www.` (any case), a backslash before a backtick, a carriage return or a newline; such a text is escaped whole, and a backslash anywhere else, as in a namespace, changes no pairing and is no trigger (#89, R3-3).
