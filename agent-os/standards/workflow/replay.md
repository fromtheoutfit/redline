# Replay

A relaunch replays every agent before the stopping point from cache, so every prompt before that point is byte-identical between the first launch and the relaunch.

- Nothing before a stopping point reads the clock: the launch timestamp is `args.launchedAt`, the spec folder name is derived from it, and `Date.now()` and `new Date()` do not appear in `workflows/redline-loop.js`
- Decisions, approved plans, selected findings and the answers to deferred drafts enter the workflow only after the prompt they answer (`args.decisions` after shaping, `args.approvedPlans` for the plan dial, `args.selected` for the review dial, `args.deferrals` at a stop check, at filing and in the text posted after it); a prompt before that point never mentions them; and a stop takes only a decision whose prompt comes after it, so a disposition override, which the round's first resolve applies, is taken only at a stop the round reaches before that resolve: a later stop of the round (a reshape after a bounced plan, a draft the resolve agent wrote) takes none and lists no declines (#94, R3-7, stated then as no plan approver having run; #95); and an answer to a call that carries a disposition (the typed `<id>: defer.` for a finding left to the person, #126) is marked as a call's answer (`"call": true`), so no reader before the round's first resolve takes it as an override: a typed defer at a reshape's stop was read on the relaunch as a plan-dial override and set off a first resolve the launch had not run, until #127, R3-4
- An answer to something an agent wrote names the version it saw, and the workflow counts the version over the agent's text, never over the answer: a deferred draft's version rises when a reshape or the resolve agent changes the draft as written, a changed draft is raised again, and an answer to a later version covers the earlier ones, so the round's first stop still passes on a relaunch after its second (#95)
- A plan approval is keyed by the pass, not by a bare round number: `passOf(record).planKey` is a Redline round's number, or `h<n>` for a human review pass, since a human pass and its final nit pass can carry the same number (#38, R1-5)
- The skill relaunches with byte-identical `args` plus only what the stop asked for, and `resumeFromRunId` set to the run id it recorded at launch. A run the harness stopped is relaunched the same way with nothing added
- Every item a stop hands back is one the skill asks about and counts in `decisionsNeeded`: an override the resolve agent could not apply comes back as `overridesUnresolved` with its why, for the person to restate, since a stop with nothing to ask relaunches with the same args and replays the same refusal every time (#94, R4-8); a field a stop adds to the result is named in `relaunch.how` in the same commit, with what the relaunch passes for it, since a session reading the note would otherwise send the refused decision back unchanged (#94, R5-4); and the skill section that presents and records the new field lands in that commit too, since a stop the skill cannot answer relaunches into itself (#95, `drafts` and `draftsNeeded`); and `relaunch.how` gives each kind of answer the shape the skill records for it: its plan clause gave an ask the changed-disposition shape until #108, R3-2, which since #99 would let a guessed disposition decide a call
- A prompt names its inputs by path (`<specFolder>/redline/round-1-findings.json`), not by content, wherever the content can change between launches
- The GitHub agent never posts a round-N review when one already exists on the PR (`redline-gh.sh has-review`), so a fresh run after a lost session cannot double-post
- The first round number enters through `args.firstRound`: the skill reads the highest posted round with `redline-gh.sh last-round` before the launch and passes the next one, and the workflow never asks GitHub for it, since the answer changes as soon as the run posts (#33; #10, round numbering). A human review pass's number enters the same way, through `args.revise.n` from `redline-gh.sh last-human-review`, with the ingested comments as `args.revise.findings` (#36)
- The findings of the PR's earlier Redline rounds and their dispositions enter through `args.priorFindings`: the skill reads them with `redline-gh.sh prior-findings` after `last-round` and passes the list, and the workflow never reads the threads itself, since the run's own carried-forward replies change them (#35)
- Finish asks GitHub for state that changes as the run posts in two places, the read of the highest posted round (#81) and the thread sweep (which threads are open, and who spoke last in them, #39); both sit after every stopping point, so no prompt a relaunch replays depends on either. A stop at the end of the run (the deferred drafts held for it, #95) makes no agent call and is checked before Finish's first one; what it held is filed and replied to inside Finish, after the read of the highest posted round, so nothing is posted once that read refuses. What a round holds for it is recorded at round time from the setting alone, never from an answer, so no later round's prompt depends on one
- A per-repository list the prompts need (`askRules`, #49) enters through `args` at launch, read by the skill from `.claude/redline.json`, and is injected by appending to an existing interpolation, empty when there is none, so a repository without one keeps byte-identical prompts; the loop test proves it by comparing every prompt of a run with no key against one with `[]`
- A dial that turns a pass off leaves that pass's call and its block out of every prompt: `coverage off` reaches the workflow as `models.coverage` null, and the coverage call, the candidates block and its rules exist only when a pass ran. The loop test proves it per rule, each key phrase of the block being absent from a `coverage off` prompt (#79). Since #93 the off run follows the same model as the covered one, the reviewer finding and verifying alone, so its prompts are no longer those of the run before the pass existed
- `tests/loop-test.mjs` proves the rule: its relaunch scenarios assert that the prompts before the stopping point equal the first launch's, and a change that breaks that fails there before it reaches a PR
- A resume after an error changes exactly one prompt: `run()` appends a resume line to the agent label the error result's `resumeFrom` names (`args.resume`), so every prompt before it replays and that agent and all after rerun; a cached result the script rejected replays unchanged on a plain relaunch, which is why the line exists. A hand commit's paths join `approvedPaths` at that label, never at startup, so the cached snapshot prompt stays byte-identical (#10). A call the workflow makes because of a resumed step's answer (the verdict after a spilled check) carries that step's attempt number in its prompt, so the resume asks again and never replays what the earlier attempt was told. What a prompt before a resume point is built from changes only when a step completes: the snapshot's `round_sha` comes from `commitsAll`, which a round's commits join once its check has passed, so the snapshot of a resumed round is byte-identical and the commits a failed attempt made are still listed (#68); and a step whose stop is the workflow's own check of what that step returned is told so in its resume line, as the shaper is told to rewrite its folder: the resolve agent's rerun after a resolve-time stop was told only that the person had fixed the cause by hand, beside a `plan.md` its first attempt had already decided, until #108, R3-4; and that sentence is chosen by the stop, never by the agent alone: the resolve agent's was appended to every resume of a resolve, the autopilot stop raised from its own `unresolved` list included, whose rule keeps an unclear decision pending, until #108, R4-4; and the shaper's own sentence, rewrite the folder from scratch, is the wrong one beside entries the resolve agent decided: a reshape stopped by the workflow's check of the task it left a decided finding is told to correct the task and keep them, chosen by the stop (#106); a reshape resumed after any other stop kept the shaper's sentence until #117, which settled the class: no resumed reshape is told to rewrite, whatever stopped it, since its folder can hold decided entries and its own prompt says to correct the four files in place. A reshape is known by its label, and its sentence goes by what its stop was: after the workflow's own check of what it returned, correct what the error names; after any other stop (a missing spec file, a call that returned nothing), restore what is missing; and after either, never write from memory a decided entry the folder no longer holds (#120, R2-3). The from-scratch sentence stays for a round's first shape, which no decision of the person or the autopilot can precede in a round folder its own launch created, as the #117 spec measured over every scenario of the loop test; a revise-only pass over a round an earlier run shaped and resolved (`/redline:redline-revise <pr> round <N>`) shapes in that run's folder, so a resume of its first shape rewrites that run's decided entries, as it always has (#120, R1-1), and that run's spec commit keeps them in git history only once that run reached its implement step, since one that stopped before it left them uncommitted (#120, R2-2); and a first shape resumed after the workflow's own check is told so too, before that sentence, so the line and the skill's report agree: until #117 its line said only that the person had fixed the cause by hand, beside a skill that now says nothing needs fixing; and a stop says what it is where it is raised, so that sentence is chosen by the field the stop set (`ownCheck`), never by the words of its error: the error result returns the field, the run marker carries it and the skill copies it into the resume entry, which is also how the skill tells the person that nothing needs fixing by hand, and an entry without it is an ordinary stop, with no fallback to the wording. Until #116 `resumeLine` read how the error opened (`the resolve agent `, `the reshape left `), so a check worded another way got the wrong sentence, and the skill told the person to fix the cause by hand after every resumable stop; and a stop whose resume line tells the rerun to correct what the error names names every failure of its check in one error, since each one it leaves out is one more relaunch: the hold after a reshape named only the fixes left with no task when the same reshape also gave an accepted finding one, until #114, R4-6; and a check added beside one that already names every failure follows it: `checkCauses` and `checkOptions`, new in #127, threw at their first fault until #127, R1-5, and the older `checkCalls`, `checkWhy` and `checkDrafts` are a drafted issue; and a resume sentence that states an exception restates the rule it leaves standing: the correct-in-place sentence left out the from-scratch sentence's ban on touching `redline/`, until #114, R4-1; and a resume clause that tells the rerun to keep what the step's own prompt may change says which instruction wins: the restore clause told a resumed reshape to keep each decided entry's task, beside a reshape prompt that applies each adjustment and a run that follows the plan as reshaped (#106), until #120, R1-2; and a ban one clause of a step carries for a reason that holds after every stop of that step is carried by each of its clauses: the restore clause banned writing a lost decided entry back from memory, since the reshape prompt names each decided finding and its end and never the person's words, and the clause after the workflow's own check, given beside the same prompt to a reshape that may have dropped the same entry, did not, until #120, R2-3; and a clause given after several stops opens with what is true after each: the restore clause said the spec folder already holds the plan, and the spec check's `no plan.md` stop is one it follows, until #120, R3-5
- A fact about a stop that the rerun must act on crosses the relaunch by one road: the error result, the harness's record of the run, the run marker (`redline-prefs.sh run save`, which copies named keys and nothing else), the skill, and `args.resume[label]`. A field the skill alone reads needs only the result; a field `resumeLine` reads needs every step of the road, the script, its quoted header in `docs/scripts.md` and its test included. A spec costs that road before it scopes its files: #117's brief kept `scripts/` untouched until `ownCheck` needed the marker to carry it (#116); and the fact is set by the check whose stop the person must act on, which runs before any check whose stop would hide it: the shaper's result checks ran before the spec check, so an attempt that left a file out, which a refused Write causes and a person fixes, and returned a result a check refused stopped with `ownCheck` true, and the skill said nothing needed fixing by hand, until #120, R1-3; and the check that sets the fact is stated with what it cannot see: the spec check lists the four files, so it sees a refused Write only where the Write would have created one, a round's first shape, and a reshape whose Writes were refused passes it while a check of its result still sets `ownCheck`, which the comment on `vetShape` and `docs/running.md` say (#120, R2-5, deferred); and a change to the order of two checks is weighed for every stop either raises, the first check's own failure included: R1-3 ran the spec check first, and a spec-status call that fails itself keeps its own label (#57), so its resume replays a shaper result a later check refuses and the run stops twice, which the comment on `vetShape` and `docs/running.md` say (#120, R3-6)
- `args.resume` keeps every earlier entry, and each entry's line is built again on every relaunch, so a change to what the line says for a stop a run may already have resumed from changes that run's recorded prompt: after an update the step and everything after it run again, a round already built included. A spec that rewords a resume sentence says which entries change, keeps byte for byte the ones it need not touch (a first shape's line for an entry with no `ownCheck`, which would otherwise be rerun from scratch over its round's decisions), pins that with a case and the sweep, and says the rest in `docs/upgrading.md`. A fallback for the older entries is weighed against the runs in flight: #117 kept none, since none was (#116, #117)
- On an interactive relaunch the harness relays the person's last typed message to every agent with precedence over its task; an `AskUserQuestion` pick is not relayed and a headless session relays nothing. The skill relaunches only from `relaunch` typed alone or a line holding only a Redline command, a namespaced form (`/redline:redline`, `/redline:redline-review`, `/redline:redline-revise`) or a short alias (`/redline`, `/redline-revise`) a repository's `.claude/commands/` provides, and `RUN_LINE` names both lines and every form (#60, #44; #63, R1-4)
- A relaunch runs the script the run launched with, or it does not run, on every repository (`redline-prefs.sh run drift --plugin <the session's copy>`). By name while the session's copy's `workflows/redline-loop.js` equals the copy the harness persisted; from that copy (as `scriptPath`) once it differs, since a checkout loaded in place can change while it reviews any repository; and, with no persisted copy (a launch by the `scriptPath` fallback ran the file itself), by name while the file's blob id is the launch's and refused once it is not. The harness's copy holds what the launch ran, which in a live session is the workflow it loaded even after the file on disk changed, so it is compared with the live file, never with the blob the launch recorded from disk. Replay follows the prompt sequence: script path, script text outside the prompts, an agent's label and the agent file's body are not in the key. The `Workflow(<name>)` allow rule does not cover a `scriptPath` launch: it runs with no prompt in auto and bypass-permissions, asks once per relaunch in manual and accept-edits, and is denied in don't-ask and in a headless session outside auto and bypass. Measured on 2.1.332, interactive and headless (#135); first headless under `--plugin-dir` on 2.1.322 (#81)
- A run never relaunches under another version. The skill records the version it starts under and its workflow file's blob id as `args.launch`, once, at launch; `run check` and `run drift` refuse a resume or a relaunch when the session's copy holds another version, or the marker holds no launch; and the workflow refuses at startup when its `REDLINE_VERSION` is not `args.launch.version`, before any agent and before every other args check, so args an older skill built get the version line rather than a throw about a field this build requires. Only the script that runs can see a switch: a session runs the install listed first among those it sees, another process's install or update reorders the list, a reload or a reopen resolves the name afresh, agents with it, and the skill's text already in the conversation keeps the root it was expanded with. `args.launch` is read at startup only, never in a prompt, and the sweep proves no prompt changed (#135, Losers League #839)
- What changed since launch enters as `args.drift` on a relaunch and is read only at startup and at Finish; the loop test proves every prompt before Finish equals the run without it. Finish's own prompts replay on a resume past them, and the handoff comment names `drift.agents`, so an error or stopped resume passes the agent list its marker's args held (`redline-prefs.sh run drift` prints it so), only a hand-off or a `reviewed` relaunch reads it afresh, and the loop test proves every prompt through the comment replays on a record-commit resume with the held list (#91, R1-1). A run never finishes from a round below the highest posted: that stop is not resumable (#81)
