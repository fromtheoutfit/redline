# Release

The plugin's version is the manifest's, every PR moves it, and a release is a person's tag and changelog entry after the merge (#16).

- Every PR bumps `version` in `.claude-plugin/plugin.json`, and the marketplace entry in `.claude-plugin/marketplace.json` and `REDLINE_VERSION` at the top of `workflows/redline-loop.js` carry the same string: minor when the change alters what a setup rerun writes (`scripts/checks-template.sh` below its header, a file under `templates/`, an allow entry, the unattended section's body), with the template markers it touches bumped in the same PR; major for a contract change a rerun cannot carry; patch otherwise. The gate's Version step says so, and the Redline reviewer reports a missing bump as a nit (`agents/redline-reviewer.md`, the Version bullet), except in a PR whose spec keeps the version on purpose, as #16 keeps `0.1.0` (#65, R1-1)
- The three are kept equal, never one without the others: Claude Code reads the manifest's first and ignores the entry's when both are set, `claude plugin validate` warns on a disagreement and `claude plugin tag` refuses one, and the workflow refuses a relaunch whose `args.launch.version` is not its constant (#135); `tests/setup-test.sh`'s last cases prove the three agree and are semver
- The tag is a person's step, never CI's: on `main`, clean, from the plugin root, `claude plugin tag --dry-run .` then `claude plugin tag --push`, which validates the manifest, requires the two versions to agree, a clean tree and no `redline--v<version>` tag yet, and pushes the annotated tag. CI runs the gate and nothing of a release
- `CHANGELOG.md` is written at tag time, dated and committed on `main` before `claude plugin tag`, so the tag names a commit that carries its own entry (#65, R1-2): one heading per tagged version, newest first, one line per merged PR since the previous tag, in three groups (Features; Fixes; Setup and templates, the ones a rerun of `/redline:setup` carries); a PR merged between tags goes under the next tagged version. A line under Setup and templates says what a rerun writes, read off the subcommand's own header: `redline-setup.sh config` keeps an existing `redline.json` as the person's and lists a changed template value under differs without writing it, so a key the template gains reaches a repository by hand or by `--force`, and the line says which (#80, R2-4)
- Claude Code moves an install on the manifest's `version`, not on the tag: an install from the GitHub marketplace stays on its version until `claude plugin update redline@redline` or auto-update, which is off by default for a marketplace that is not Anthropic's. The tag names the release commit and is what a dependency's version range resolves against (plugin loading reference, "How Claude Code computes the version"). A version can be installed from the moment it merges, tag or no tag: an install that updated from that merge stays on those files while later PRs keep the version string, since `claude plugin update` finds nothing to move to, so being untagged is no reason for a PR to keep a merged version (#83, R2-1)
- A marketplace is registered once per user, so the machine's `redline` marketplace is the GitHub one and development loads the checkout with `claude --plugin-dir <checkout>`, which replaces the installed copy by name for that session with its hooks and `CLAUDE_PLUGIN_ROOT` from the checkout; the local-directory marketplace would put every repository on the machine on the checked-out branch
- A script the skill runs by `${CLAUDE_PLUGIN_ROOT}` knows which copy the session loaded from its own path, so it takes no flag for it, except `redline-prefs.sh run check` and `run drift`, which take that copy as `--plugin` (#81; required since #135): `redline-setup.sh version <repoRoot>` reports a self-hosted root that is not the loaded copy (`plugin: {self, inPlace, pluginRoot, version, workflow}`, the last two what a run records as `args.launch`, #135) and the launch precheck warns with the `claude --plugin-dir` line, never stops
- A session runs the install listed first among those it sees (user scope, and project or local scope for its directory), whatever their scopes; another process's install or update reorders the list, and an update leaves the older version's directory in the plugin cache. So `redline-setup.sh version <repoRoot>` also lists those installs from `claude plugin list --json` (`installs`, this session's found by `installPath` among them), and the launch precheck warns when their versions differ, with `claude plugin update <id> --scope <scope>` for each older one, a project or local one run from the repository root: run from elsewhere, the command picked another repository's install of the same scope and reported it already up to date. Measured on 2.1.332 with a throwaway plugin at two scopes (#135)
- Under `claude --plugin-dir` a subagent's `Write` is refused in auto mode with no verdict, and in accept-edits it prompts despite a matching allow rule; an installed release is clean. The probe, on Claude Code 2.1.319: a project subagent with `tools: Write` asked to write one word, same checkout, same mode, refused under `--plugin-dir` and written under plain `claude`. The main session's own Writes passed in both, and allow rules are not consulted for a subagent's write in either mode. Bypass-permissions is confirmed as a remedy by PR #83 round 1, an inline session in that mode on 2026-11-09, whose review posted with no prompt and no refusal (#83, R1-6). One launcher Write of `snapshot-start.json` was refused in an inline session on Nov 6, unexplained, so a run fails at its first file write, normally its first post. The launch skill says so when `${CLAUDE_PLUGIN_ROOT}` is outside `/plugins/cache/`, on a fresh launch and, before the Resume or Start fresh question, on a resume, since an `error` or `stopped` resume relaunches in that same turn (#83, R1-4); a warning and never a stop since a skill cannot read the permission mode (#76)
- A change to the unattended template's body is dry-run against this checkout's own section before the body is final (`redline-setup.sh unattended ... --merge --dry-run`): a point a repository added by hand beside a line the template changes conflicts in the merge, the person says how that hunk is resolved, and `docs/upgrading.md` names the lines that moved and the resolution, for the repositories that will meet the same hunk (#105: the sentence under point 10's example, beside this repository's point 11); and a body change bumps the marker even while the version it would change is unmerged: at an equal marker `redline-setup.sh unattended` compares the fill-ins only, so a rerun writes nothing to a checkout that already took that version, this one included, and the body's pin fails the change (the follow-up of #127 set out to keep v6, measured both, and went to v7 with the plugin's version kept); and a point put back after the template's side is taken is found by its opening words, never by its number, since the file holds another list with the same number (the Verification Gate's)
