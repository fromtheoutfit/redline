# Bash scripts

Every script under `scripts/` is its own documentation and talks to the workflow in JSON.

- Every script starts `#!/usr/bin/env bash` and `set -euo pipefail` (`redline-gh.sh`, `redline-guard.sh`, `redline-prefs.sh`, `redline-gate.sh`, `redline-setup.sh`, `checks-template.sh`). The test harnesses use `set -uo pipefail` instead, because one failing case must not stop the table
- A script a workflow reads emits exactly one JSON object on stdout and everything else on stderr: `checks.sh` logs through `log()` to stderr and prints the envelope last; `redline-prefs.sh resolve` and every `redline-gh.sh` read subcommand whose header says JSON print JSON and nothing else; a subcommand a role reads as text says what it prints instead (`diff` a unified diff, `pr-comments` and `issues-search` text), and one whose answer is yes or no (`has-review`) prints nothing and answers by exit code (#71, R1-6)
- `bash -n` reads its first file and treats the rest as arguments; check several with `ls <glob> | xargs -n1 bash -n` (#5, R1-3)
- Usage errors exit 2 with a one-line reason on stderr. A check that fails exits 1. A script whose exit code is an answer (`redline-gh.sh has-review`: 0, 1 or 2) says so in its header. Under `set -e` a command substitution that fails exits with its command's own status, so a documented exit code holds only where each such call is guarded (`found="$(gh issue list …)" || { echo '…' >&2; exit 1; }`): `defer` exited 4 on a gh that needed a login, while its header said 1, until #97, R4-1. A function run inside `$(...)` runs with `-e` off (bash clears it there outside POSIX mode, and no script here sets `inherit_errexit`), so a failing command inside it does not stop it and its last command's status is the substitution's: what it printed is checked before it is used. `post-review` posted a review of one newline when the jq inside `place_comments` failed, until #112, R1-9. A check of what it printed cannot see a step that failed and left the last one a well-formed result to print, so such a function returns non-zero when a step fails and its caller reads the status as well: an empty kinds file made `place_comments` print every comment under 'The file is not in this pull request:', and `post-review` posted it and exited 0, until #112, R4-5. A documented exit code for an input the script cannot read holds only when the input's whole shape is checked before any jq reads a field of it, each element of a list included: `post-review` checked only that `comments` was an array, so a number in it reached the jq in `wanted_files`, which a plain function call under `set -e` turned into jq's exit 5 and message while the header promised one line and exit 2 (#112, R3-2); line 24 is the same rule for a validator; `version_installs` read `claude plugin list --json` with no fallback for its own jq, so a version or a path of another type printed nothing, and `cmd_version`'s `--argjson` of that empty output exited 2, which the launch precheck reads as not set up, where the header promised a warning that never stops (#137, R1-4). A check that a program printed one JSON value reads the whole stream (`jq -se 'length == 1 and (.[0] | type == "array")'`), since `jq -e` answers for the last value only: two lists in one output passed `jq -e 'type == "array"'`, and `--argjson` refused the two arrays the program then printed (#137, R1-4). A jq program that reads another program's JSON hands a string builtin only text (`tostring` first), since jq's versions differ on a non-string: from jq 1.8, `rtrimstr` fails on one, while jq 1.7, the jq of CI's legs, returns it unchanged. A setup case that leaned on that failure was red before the fix and green after under this machine's jq 1.8.2, and would have been green before and red after on CI, until the plan approver of #137's round 1 bounced it. So a case expects only what both versions give, and a spec names the jq version of each red it records
- A wrapper that runs another script for a role (`redline-background.sh` around `checks.sh`) passes the wrapped script's stdout and stderr through unchanged, and its documented exit codes (0, 1 and 2 for `checks.sh`), so the role reads the result as it would the script's own, and takes the codes above them for its own answers (3 still running, 4 past the limit, 5 no result), stated in its header. Any other code the wrapped script exits with (a command failing under its `set -e`, a signal) is the wrapper's no-result answer with a line naming the code, never passed through: a passed-through 3 reads as still running and loops the role (#41, R1-3). A result the wrapper keeps under a label the workflow reuses is read once: the wait that returns it removes the label's files, so a wait that runs before the next start has cleared them cannot return the earlier run's result (#41, R1-2). It runs one fixed script, never a command it is given, so the guard admits it by subcommand (#40)
- The header comment is the documentation, in this order: what the script is, usage, environment variables, the output contract, the exit codes. `docs/scripts.md` quotes it verbatim and `docs/contract.md` carries the output contract, so a header change updates `docs/scripts.md` in the same commit (#14). A field added to `checks.sh`'s JSON, or a limit changed in it (`run_check` in `scripts/checks-template.sh`), updates `docs/contract.md`'s output contract in the same change, and a flag that reports a cut is set by every limit that can cut (#7, R1-14). `checks.sh`'s whole JSON stays bounded however many checks fail: the failing checks share one output budget, split evenly among them in a final pass after every check has run, never consumed in run order, because the checker may not Read a result that spills to a file (#7, R1-13). It is bounded whatever the pull request's size and the run's length as well (#68): stdout carries what the workflow reads and no more (a passing check's name, exit code and `recorded`, counts for the lists nothing reads, the round's own commits), stderr counts toward what the Bash tool shows, the budget is written out as arithmetic in the template's comment and run at its stated scale in `tests/setup-test.sh`, and what stdout leaves out is in the kept result, which `checks.sh --verdict` reads
- A change to what a subcommand selects or prints rewords every description of it in the same commit, found by searching for the old phrase across `README.md`, `docs/`, `skills/` and `agents/` rather than by editing only the `redline-gh.sh` table row that quotes the header: R1-3 changed which review body `human-review` takes and updated the header, the README's `redline-gh.sh` row and the revise skill, and left the README's paragraph on `/redline:redline-revise <pr> review` describing the old selection (#38, R2-1)
- A subcommand added to `redline-gh.sh` or `redline-prefs.sh` is added to the guard's groups in the same change (`GH_READ` for a read subcommand; `gh-all` already covers a write one), and the agent or skill that calls it names the exact spelling; a subcommand removed (`issue-create`, replaced by `defer`) takes its callers with it in the same commit: the skill section that ran it, the agent operation, its guard rows and `docs/scripts.md` (#95); and every sentence that describes what it did, found by searching the README and `docs/` for its words: `docs/guard.md` still named the after-run filing as the main session's one prompt until #97, R1-1
- A record a subcommand keeps beside what it writes is merged into as the file stands when the entry is written, never into the copy read when the subcommand began, and the temp file it writes beside the record is removed on every way out that does not end in its `mv`, through one `EXIT` trap that names every temp file the subcommand makes: `redline-gh.sh defer` read the round's record before a lookup and a create on GitHub and wrote that copy back, so an entry recorded in between would be lost, and left `.redline-deferred.*` behind on a failed write, where the run-record commit stages every untracked file (#97, R1-2, R1-3); and every step of the record's write that can fail after the create (the folder, the read, the temp file, the move) exits through one function that names the entry it could not record, since under `set -e` a tool's own message alone loses the issue just opened (#97, R2-1)
- A subcommand that makes temp files, directly or through the functions it calls, makes them in one `mktemp -d` directory its `EXIT` trap removes (`place` and `post-review` point `TMPDIR` at it), made before the subcommand's first call that makes one, the listing's read in `pr_files` included (#112, R2-3), so a failure or an interrupt leaves nothing in the temp directory: a function that removes its own files on return leaves them behind when the subcommand stops inside it (#112, R1-2)
- A script only a skill calls (`redline-prefs.sh`, `redline-gate.sh`, `redline-setup.sh`) needs no guard group: the guard's default deny refuses it to every role, and `tests/guard-cases.tsv` rows pin it as the skill's (#6); when one of its subcommands is reserved for a person, its rule in the shared allow list (`templates/settings.allow.json`, and the repository's `.claude/settings.json`) names only the subcommand the skill runs unprompted (`Bash(/*/scripts/redline-gate.sh check *)`), so the reserved one stays behind the permission prompt (#7, R1-9); `redline-setup.sh`'s writing subcommands have no allow-list rule, and the permission prompt is the person's confirmation (#6), while `version`, which writes nothing and which `/redline:redline`'s precheck runs at every launch, once had the one narrow rule, `Bash(/*/scripts/redline-setup.sh version *)`, on the pattern of `redline-gate.sh check`'s (#12, R1-8); since #50 the allow list carries no script path rule at all (a `Bash(/*/scripts/…)` rule matched a script of that name at any path an agent could write), and the guard approves the one unprompted subcommand (`redline-gate.sh check`, `redline-setup.sh version`) for the main session by real path, so the reserved ones stay behind the permission prompt
- A value the skill passes into `args` from the run marker is computed by `redline-prefs.sh run` and copied as printed, so its rule has a prefs case where skill prose would have none: `run check`'s `hand`, with the label's earlier entry merged in (#10), and `run drift`'s `drift`, whose agent list an error or stopped marker keeps as its own args passed it (#91, R1-1)
- A saved launch setting added later is asked once of a saved file that lacks it, beside the confirm, and a setting that does not apply to a run (the deferral settings under `review only`, `deferAt` under `autopilot`) is neither asked nor written by it, so the next run it applies to asks. `redline-prefs.sh save` takes every setting and keeps the inapplicable ones out itself, so the skill always passes what `resolve` printed (#95)
- A generator that writes a file from a template (`redline-setup.sh checks` from `checks-template.sh`) splices by anchor lines and exits 1 naming a missing one, so the template and the generator cannot drift apart silently, and its output is deterministic: the same input gives the same bytes, and nothing is written when they are unchanged (#6). It validates every input field it writes, not only the commands: a field that lands in a comment is a single line, and one that lands inside quotes holds no character that would end or expand them, so a bad `checks.json` exits 2 rather than writing a `checks.sh` that runs a stray line (#12, R1-6)
- A script that edits a person's file (`.gitignore`, `shape-spec.md`, `settings.json`) preserves the file's line endings and a byte-order mark (`settings.json` refuses a byte-order mark instead, exit 2, as its header says), writes only when the bytes change and reports `changed: false` otherwise, so a rerun can say nothing drifted; a JSON file is compared with `jq -S`, since a CLI that rewrites it (`claude plugin install`) reorders keys and that is not drift (#6)
- A merge into a person's JSON file keeps every value already there, adds only what is missing, and reports each kept value that differs from the template (`conflicts`) rather than overwriting it (#12, R1-3, R1-4); every subcommand that writes takes `--dry-run`, which prints the same JSON with `written: false` and creates nothing, not even the target's directory (#12, R1-2)
- A rerun over a file the script wrote earlier changes only the values the script derives from its inputs (`config` updates `checker` and `checkerStallMs` in place, keeping the file's formatting) and keeps every other value as the person's, the ones the person chose at setup included (`reviewer`), listing each that differs from the template under `differs` without changing it; `--force` is the full reset to the template (#12, R1-5)
- A rerun's `differs` lists drift from the template, never the person's own additions: `config_differs` ignores a key only the person writes (`askRules`), so a rerun does not report the rules as values to reset (#49)
- A config key that says where an outward write goes (`deferTo` in `redline.json`: a GitHub issue, or a file) is refused when it is not one of its words, with a line naming the key, the file and the value, and is never defaulted; a key that only bounds the run (`maxRounds`) falls back to its default (#95)
- A validator that shares its messages with another (`ask_rules_fault` in `redline-setup.sh`, `rule_fault` in the guard, the workflow's launch check) shares its tests too: a key's presence (`has("paths")`), never a non-null value, so `{"paths": null}` gets the shared message instead of passing, and a list's elements are filtered to objects (`objects`) before a field of each is read, so a non-object element gets `not an object` and exit 2 instead of jq's own error and exit 5 under `set -e` (#52, R1-2), and a pattern is matched against the whole string, `\A...\z` in jq: jq's `$` also matches before a final newline, so `^[a-z][a-z0-9-]*$` passed the id `"a\n"`, which the guard's `fullmatch` and the workflow's `/^...$/` refuse, and setup wrote a list that then stopped every run (#52, R2-1)
- A flag that replaces a list a rerun otherwise keeps (`config --ask-rules`) clears it with `[]`, and the skill that calls it passes `[]` when the person removes every entry: without the flag the old list stays, so "with none, omit the flag" left a removed list enforced (#52, R1-3)
- A jq program that holds a quote goes in a quoted heredoc (`prog="$(cat <<'JQ' ... JQ)"`, then `jq "$prog"`), never in a bash single-quoted string: `ask_rules_fault` first wrote `'\($r.id)'` inside `jq -r '...'`, which ended the bash string at the first quote and failed `bash -n` (#49)
- Python inside a script is `python3 -I -c "$PYTHON"` with the standard library only, fed on stdin; it writes no file beside the script
- A path the script receives is made absolute once (`cd "$(dirname "$path")" && pwd`) and used as is; the repository is `git rev-parse --show-toplevel`, never a walk from `$PWD`
- A path compared with `git rev-parse --show-toplevel` is made physical first (`pwd -P`): git prints the physical path, and on macOS `/var` is `/private/var`, so a logical path never matches its prefix (#6)
- A header printed by `-h|--help` is printed with `sed -n '2,/^$/p'`, never a numeric range, which rots on every header edit (#6)
- A script that chooses which part of a file to hash refuses when more than one part qualifies, naming each by line, rather than taking the first: a silent switch moves the hash onto the wrong text and every later check passes against it (#7, R1-6)
- Never print a token, a header or an environment dump; `redline-gh.sh` leaves authentication to `gh`
- `jq` reads and writes every JSON value; no hand-built JSON strings in bash
- A jq lookup keyed by a field that may be absent reads the key as `(.f // "")`: an object indexed with null is an error, and in jq 1.8 `//` does not catch it, so `$kind[.path] // "absent"` crashed on a comment with no path, which the base had moved into the body (#112, R1-8)
- A JSON value that grows with the pull request (the anchor positions of `place`, megabytes on a 336-file PR) reaches `jq` through `--slurpfile` or `--rawfile` from a temp file, never `--argjson`, which puts it on the command line and fails with "Argument list too long" (#33)

For such a file, and only when a comment names one, `place` reads the whole-PR diff through `gh api` under the diff media type on a PR of 300 files or fewer, then the clone; a refused read is never an error, the file only stays without hunks (#96)
- What GitHub's files listing says about a missing patch: `patch` null with `changes` 0 is a binary file, or with status renamed a rename with nothing changed, and has no hunks; `patch` null with `changes` above 0 is a text file whose patch is past about 100 KiB, and GitHub still takes a comment on its lines. A `git diff` that stands in for GitHub's hunks is the merge base against the head, never the base tip, with its flags pinned (`--diff-algorithm=myers -U3 --inter-hunk-context=0 --indent-heuristic -M`, the `a/` and `b/` prefixes, no external diff, no textconv, no order file (`-O/dev/null`), since git ends a diff whose `diff.orderFile` it cannot read and reads a relative one against the repository root (#112, R4-4), every file read as text (`--text`), since the listing counts the file's changed lines and git's own binary test follows attributes (`.git/info/attributes`, `core.attributesFile`) and `core.bigFileThreshold`, none of which GitHub sees (#112, R2-2), `core.quotepath=off`) and its paths literal, and it runs with `GIT_DIFF_OPTS` unset (`env -u GIT_DIFF_OPTS git ...`), since git lets that variable override `-U` whatever the command line says (#112, R1-4), and with every other global pathspec setting unset (`GIT_GLOB_PATHSPECS`, `GIT_NOGLOB_PATHSPECS`, `GIT_ICASE_PATHSPECS`), since git refuses `--literal-pathspecs` beside glob or icase and exits 128, which left every wanted file without hunks and its comments under the could-not-be-had line (#112, R3-1), and with `GIT_ATTR_SOURCE` unset, since a tree it names that the repository does not hold ends the diff while every other git call the script makes passes (#112, the round 4 spec's sweep). What this covers is measured, not promised: every `diff.*` and `core.*` key git-config(1) lists, every attribute source and every variable git(1) lists was set against the call on git 2.54, and none moves a position or ends it (the table in `agent-os/specs/2026-11-20-1057-112-review-round-4-by-hand/shape.md`); a flag joins the call with the row that shows the need, and a key a later git adds is outside the table. Shutting the global and system files out of the call is not the way: the repository's own configuration still applies, so no flag could go, and `safe.directory` and a partial clone's fetch settings live in those files; plain `diff -U3` gives other hunks, and the compare endpoint takes no path and drops more patches than the listing (#96, measured on #97 and #111)
- A file of diff text (the hunk stream `diff_sections` writes) is read as text by every tool that reads it, `grep -a` for grep: grep takes a file that holds a NUL for binary and prints no matching line (GNU grep from the buffer that holds the NUL on; BSD grep when the NUL sits in the file's first 32 KiB, and it then prints `Binary file ... matches` in its place, which `cut -f2` passed on as a path), and GNU awk keeps a NUL that macOS's awk drops, so one NUL past the first 8,000 bytes of a text file, where git's binary test stops looking, moved every patch-less file's comments under the could-not-be-had line on a Linux runner until #112, R2-1

Such a line is written another way (the assignment unquoted, with a comment saying why), and the round-trip cases in `tests/setup-test.sh` are what prove it (#68)
