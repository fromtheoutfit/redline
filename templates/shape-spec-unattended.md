## Unattended mode (Redline)
<!-- redline-unattended: v7 -->

This section applies only when the invoking prompt declares a Redline run, with the sentence **"This is a Redline run; follow shape-spec in unattended mode."** A person running this command by hand never sees any difference: every step, the gate and the output structure below stay exactly as written, and this section only says what changes when no person is present.

In a Redline run you are the **shaper**: a subagent shaping one review round of a pull request. The invoking prompt gives you the PR number (or a spike name), the round number, the launch timestamp, and the round's findings. Each finding has an ID like `R1-4`, a file and line, a kind (`correctness` or `nit`), a severity, whether the verifier confirmed it (`confirmed`, or `unconfirmed` with one line on what would confirm it), a description and, usually, a proposed fix. A finding may also carry `sameClassAs`: the ids of earlier findings that were fixed and whose cause the verifier judges to be one class with this finding's (point 5). The verifier states what is true; what to do about each finding is yours to decide.

**What changes:**

1. **Plan mode.** Skip the plan-mode check above. You cannot enter plan mode, and nothing below depends on it.
2. **No questions.** `AskUserQuestion` is not available to you, and no person is watching. For every question Steps 1 to 5 would put to a person (scope, visuals, references, product context, standards), answer it yourself from the findings and the code, and record the answer **and its evidence** (the file, line, spec or standard you read) in `shape.md` under a heading `## Unattended answers`. Never invent a citation: cite only files, issues and specs you opened. A question the PR description, the original spec or the code's own docblock already answers is answered from that evidence (quote the line) and recorded here, never escalated as a judgment call, even when a finding asks it: the author has answered it. Where the code disagrees with that answer, the disagreement is the finding to fix (a name, a docblock, a test that pins the stated behaviour).
3. **You decide, and the person is asked in five cases only.** A finding becomes a judgment call when one of these holds, and only then:
   - the options differ in what the product does or in what a user sees;
   - the fix changes an assumption, the approach or the architecture the original feature spec agreed;
   - the fix reaches outside what the pull request set out to do;
   - two options are both defensible and neither is the clear pick;
   - the finding is still unconfirmed after your second look (point 5) and its harm would be serious if it were true: security, privacy, data loss or money.

   A finding the invoking prompt's repository ask rules cover is asked as well (point 4). In every other case you take your own recommendation, a decision to decline included, and record it with its reason: never return a question you can answer. The rule is these cases, never a degree of confidence: "I am not sure" is not one of them. A judgment call is a *pending* entry under `## Decisions` in `shape.md`, a task marked `pending decision <id>` in `plan.md`, and an object in the `judgmentCalls` array you return, its `why_human` naming the case. Every option of a call states what choosing it ends in, in `ends`: `fix` (a change in this pull request that leaves nothing to track elsewhere), `defer` (the work goes to an issue, with or without a mitigation now) or `accept` (no change); the pending entry lists each option with its end. The call names the option you recommend in `recommended`, by its label as written. The person is shown each option with its end, and a decision that picks an option ends in what that option states, so state the end the option really has: one that ships a guard now and leaves the full fix to an issue ends in `defer`, and one that keeps the behaviour and still ships something, a code comment say, ends in `fix`. For a call you do not pick an option, do not implement a default, and do not resolve it by reading a past spec and treating the matter as closed. The person decides; a later agent applies the decision.
   **Every decision names its owner.** Each decided entry under `## Decisions` (a `fix`, a `decline`, a `defer`, an unattended answer) ends with the line `Decided by: redline`. A pending entry has no owner line; the agent that applies the decision adds `Decided by: @<login>` (the person) or `Decided by: redline (autopilot)` (the run took your recommendation on autopilot).
4. **Dispositions.** Sort every finding, of any kind (a bug, a nit, a small refactor, a test gap, a cost, a doc), into exactly one of:
   - `fix`: the change is clear and its cost is in proportion. It becomes a plan task. A small refactor (below) is a `fix`, done without asking.
   - `decline`: the item is not worth doing, and Redline says why in one sentence a teammate can read: the `reason`, which is posted in the finding's thread, where the person can overrule it. Reasons that stand: the claim is wrong (your second look refuted it; give the evidence); the failure needs conditions that will not occur (name them); the pull request's own spec decided the point (cite the decision); or your second look could not confirm it (`could not confirm: needs <what would confirm it>`). A decline never points at follow-up work (another pull request, an issue, a later change): an item worth doing somewhere is a `defer`. A declined finding is listed under `## Declined` in `shape.md` with its reason and has no plan task.
   - `defer`: the item is worth doing, and not in this pull request: a gap that predates it, a cause in code it did not change, a refactor that is large or reaches well outside it, a full fix out of proportion here. Any kind of finding can be deferred, not only a bug. Deferring is your decision, never a question: point 3's third case is for a fix this pull request needs and that reaches outside it, not for work that belongs elsewhere. A mitigation is optional: when a cheap one exists inside the pull request (a guard, a clear error, a log line, a code comment naming the finding) it becomes a plan task, and otherwise the finding has no task. Every deferred finding carries a drafted issue that stands on its own, listed under `## Deferred` in `shape.md` and returned in `deferred`: a `title`; `found`, what was found, written for a reader who has not seen this pull request; `why`, why it is not fixed here; and `fullFix`, the fix proposed. Redline adds the file and line, the pull request and the finding id, and files the draft where the repository tracks work. Never write a model name, a vendor name or an AI-assistant marker in a draft.
   - `ask`: a judgment call, in one of point 3's cases. A finding the invoking prompt's repository ask rules cover (a `paths` rule on its file or on a file its task would touch, or a `prose` rule's sentence) is `ask` with `why_human: "repository rule <id>"`, never `fix`, `decline` or `defer`; the person acts on it outside the run. Its options are the person's to carry out: make the change by hand after the run, which ends in `fix`, or accept it as it is, which ends in `accept`. When the item is worth doing and you would have deferred it, offer as well an option that ends in `defer` and carries its drafted issue in `draft` (`title`, `found`, `why`, `fullFix`, written as a deferral's are), listed under that option in the pending entry: the person may defer what is theirs to change, and Redline then files that draft, plans no task and writes nothing under the rule. A `draft` is read on that option alone.
   **Proportionality rule.** Before choosing `fix` for a correctness finding, record two things in `shape.md`: how likely and visible the failure is (observed? reachable by a normal user? what happens when it fires?) and what the fix costs (files touched, especially outside the PR's diff; new dependencies, services or abstractions; rough size). When the cost is out of proportion to the likelihood and impact, the full fix is not the answer: it is `defer`, with a mitigation when a cheap one exists and none otherwise, or `ask` when one of point 3's cases holds. A guard the base branch had and this pull request removed weighs toward `fix`: putting it back is cheap.
   **A small refactor is done without asking.** A refactor is small when all four hold: behaviour is unchanged (no existing test's expectation is edited, though tests may be added or follow a rename, and nothing outside the code depends on what moves: a route, a response shape, a config key, a command's output, a column); it stays inside the pull request (every file it changes is one the pull request already changed, or a new file holding code moved out of those, or their tests); it reworks code this pull request wrote (the lines it rewrites are lines the pull request added or changed, plus the call sites of what it extracts in those same files); and it is one idea, smaller than the pull request (one extraction, rename, inlining or removal, with a diff smaller than the pull request's own). A refactor that fails one of the four is `defer`, its drafted issue saying which test it fails, or asked about when one of point 3's cases holds. One that would undo a choice the pull request's own spec records as deliberate is never asked about: point 2 answers it from the spec, and it is declined with that decision cited.
5. **Investigate before you sort.** Read the code a finding names and its callers and tests. A finding the verifier marked `unconfirmed` gets your second look first: try what its line says would confirm it, and return what you found as `secondLook`. Confirmed, it is sorted like any other finding. Refuted, it is `decline` with the evidence as the reason. Still unconfirmed, it is `fix` when a cheap guard is right whether or not the claim holds, and otherwise `decline` with `could not confirm: needs <what would confirm it>`, unless its harm would be serious if it were true (security, privacy, data loss, money): then it is `ask`, the story saying what you tried and what would confirm it, and it is never declined on your own say. Never mark a finding `fix` on trust, and never drop one.
   **Instance or class.** Before you sort a finding as `fix`, say where its cause lives and whether the finding is one instance of that cause or the cause is a class: a function that reads its input one way too few, a rule applied at one call site and not at its siblings, a list kept in two places. Ask what else reaches the same cause: other inputs, other callers, other entries. The fix is then one of three, recorded with its reason in the finding's entry in `shape.md` and returned as `cause` (`where`, a path in the repository; `outcome`; `why`, one sentence). `one-place`, the fix is made where the cause lives, so every instance is closed at once: the answer when that is inside the proportionality rule (point 4), and `where` is one of the task's files. `sweep`, the fix is this instance and a sweep of the class: every member measured by running it, never by reading the code, with the table written into `shape.md` under a heading that names the finding and returned inside `cause`, as `cause.swept`, never on the finding beside it: a list, one entry a member, `member` and `found`: `holds` when you measured it and the code as it stands already handles it, so nothing changes for it, and `fixed` when you measured it exposed and this task's change closes it. `instance`, the fix is this instance alone, with why the cause is not a class. A member the sweep finds exposed that this task does not close fits neither value, and then the outcome is not a sweep: the finding is `defer`, its mitigation the instance fix with whatever members it does close and its drafted issue naming the members left exposed, or `ask` when one of point 3's cases holds. A finding that carries `sameClassAs` has the question answered, whatever an earlier round decided: a cause fixed once and found again is a class, so its fix is `one-place` or `sweep`, never `instance`, and when closing the class does not belong in this pull request the finding is `defer` or `ask`, as above.
6. **Scope and folder name.** Scope is the round's findings, nothing more. The spec folder is `agent-os/specs/YYYY-MM-DD-HHMM-<pr>-review-round-<n>/`, where the timestamp is the launch timestamp **from the invoking prompt**, never the clock, so a relaunch names the same folder. Step 6's slug rule does not apply.
7. **The plan.** Task 1 is "Save spec documentation", as always. Then one task per `fix` finding and per `defer` finding that ships a mitigation, in finding order, each naming the file, the change and the test that proves it. Then one task per `ask` finding, titled `Pending decision <id>: <title>`, holding the options rather than a change. The final task is the Verification Gate, whose command steps (gate steps 1 to 7) read, in a Redline run: **run `.claude/redline/checks.sh <snapshot>` until it exits 0; its JSON is the evidence.** The script is a transcription of those steps, so the gate text stays the source. Steps 8 and 9 stay as written. You do not run the gate; the implementer and checker do. Every command the plan gives the implementer to run, in a task or in the gate, is a plain pipeline: no `$`, backticks, process substitution (`<(`, `>(`) or interpreter (`python3`, `node`, `php -r`). Those are the Bash rules Redline's agents follow, and the implementer's guard refuses a command that breaks them.
8. **Standards retrospective.** Gate step 8's edits are proposed, not applied. Write the proposed edit list (file, line, the drafted wording, or "no changes") under `## Standards retrospective (proposed)` in `shape.md`. An item whose wording depends on a pending decision is listed as `Held for <id>` with what it would record; the resolve agent drafts it once the person has decided, before the standards approver runs. The standards approver approves the list and the implementer applies it in its own commit. `standards.md` still records each applied standard as it reads at shaping time.
9. **You write only the spec folder.** Create it with Write. Do not edit source files and do not run `gh`. Read-only `git` (`status`, `diff`, `log`, `show`, `blame`) is fine; never stage, commit, check out, stash or create branches. If a referenced file does not exist, say so in `shape.md` rather than creating it.
10. **What you return.** Your final output is JSON, not prose:

    ```json
    {
      "specFolder": "agent-os/specs/2026-10-18-0912-21-review-round-1",
      "findings": [
        {"id": "R1-1", "disposition": "fix", "decidedBy": "redline", "recommendation": "Reject a status outside the enum in the request rules; a feature test proves it.", "files": ["app/Http/Requests/StoreOrderRequest.php", "tests/Feature/Orders/StoreOrderTest.php"], "cause": {"where": "app/Http/Requests/StoreOrderRequest.php", "outcome": "one-place", "why": "The request rules are the one place a status is validated, so every caller is covered there."}},
        {"id": "R1-2", "disposition": "ask", "decidedBy": "pending", "recommendation": "Accept, no change.", "files": []},
        {"id": "R1-3", "disposition": "decline", "decidedBy": "redline", "recommendation": "Decline; the pull request's spec settled it.", "reason": "the pull request's spec keeps the name on purpose (decision 4 in its shape.md)", "files": []},
        {"id": "R1-4", "disposition": "defer", "decidedBy": "redline", "recommendation": "Defer the queue client's retry policy; log the retry count now.", "files": ["app/Jobs/SyncOrders.php"]},
        {"id": "R1-5", "disposition": "fix", "decidedBy": "redline", "recommendation": "Read the status through the enum in the export, the one reader of three that compared the raw string; a test for each reader proves it.", "files": ["app/Exports/OrdersExport.php", "tests/Feature/Orders/OrdersExportTest.php"], "cause": {"where": "app/Exports/OrdersExport.php", "outcome": "sweep", "why": "Each reader of an order's status compares it itself, so every reader was run with a lower-case status.", "swept": [{"member": "OrdersExport::query", "found": "fixed"}, {"member": "OrderPolicy::update", "found": "holds"}, {"member": "SyncOrders::handle", "found": "holds"}]}}
      ],
      "deferred": [{
        "id": "R1-4",
        "mitigation": "Log the retry count when the queue is down.",
        "title": "Back off retries in the queue client when the queue is down",
        "found": "`SyncOrders` retries at once and without limit when the queue connection drops, so one outage becomes a retry storm.",
        "why": "The retry policy lives in the queue client, which this pull request does not touch.",
        "fullFix": "Give the client a capped exponential backoff and have `SyncOrders` use it."
      }],
      "judgmentCalls": [{
        "id": "R1-2",
        "title": "Short summary",
        "story": "A user opens the app, does X, Y happens, which is bad because Z.",
        "why_human": "product decision | spec assumption | outside the pull request | no clear pick | unconfirmed, serious if true | redline's own file | repository rule <id>",
        "options": [{"label": "Full fix", "cost": "...", "effect": "...", "ends": "fix"}, {"label": "Mitigate", "cost": "...", "effect": "...", "ends": "defer"}, {"label": "Accept", "cost": "...", "effect": "...", "ends": "accept"}],
        "recommended": "Accept",
        "recommendation": "Accept, no change.",
        "dependsOn": []
      }]
    }
    ```

    The story is plain language about the real-world effect, written for the person who will decide, not a restatement of the finding. Every finding carries `decidedBy` (`"redline"` for a `fix`, a `decline` or a `defer`, `"pending"` for an `ask`) and `recommendation`, one sentence a person can act on without opening the spec: the change the plan makes for a `fix`, the decision for a `decline`, the mitigation for a `defer` (or that nothing ships now), the option you recommend for an `ask`. Every finding also carries `files`, the paths its task creates or changes, an empty list when it has no task: for a `defer`, a task listed here is what says a mitigation is planned, whatever the words of `mitigation` say, and for an `ask` they are the paths its recommended change would touch. A `fix` also carries `cause` (point 5), an object holding `where`, `outcome` (`one-place`, `sweep` or `instance`) and `why`, and for a `sweep` also `swept`, inside `cause` beside them and never on the finding itself: a list of each member the sweep measured as `{"member", "found"}` with `found` `holds` or `fixed`. A `decline` also carries `reason`, the sentence posted in the finding's thread, and a finding the verifier could not confirm also carries `secondLook` (`confirmed`, `refuted` or `unconfirmed`). Every `defer` finding has exactly one entry in `deferred`: its `mitigation` (an empty string when nothing ships now) and its drafted issue (`title`, `found`, `why`, `fullFix`); no other finding has one. Every `ask` finding has exactly one entry in `judgmentCalls`, whose `why_human` names its case in point 3's order (`product decision`, `spec assumption`, `outside the pull request`, `no clear pick`, `unconfirmed, serious if true`), its repository rule, or `redline's own file` for a finding on one of Redline's own files, which no Redline role may change; `fix`, `decline` and `defer` findings have none. Each option of a call carries `ends` (`fix`, `defer` or `accept`), and the call carries `recommended`, the label of the option your `recommendation` describes; an option that ends in `defer`, on a call for a finding left to the person (point 4), also carries `draft`, and no other option does. List the calls in the order the person should answer them: a call whose options or recommendation turn on another call's answer comes after it and names it in `dependsOn` (`[]` when it stands alone). The person is asked in exactly that order.
11. **The PR description.** When the round's spec redrafts a stale PR description as `pr-body.md` (per the repository's standard for agent-written PR descriptions), the person's go is the Redline run itself: Redline's Finish phase posts the newest round's `pr-body.md` before it requests review.

Everything not named above is unchanged: the file layout under Output Structure, the `shape.md`, `standards.md` and `references.md` content sections, the Verification Gate text, and the Tips.
