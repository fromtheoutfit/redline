# Upgrading

How a plugin update reaches a repository, and what a rerun of `/redline:setup` carries that an update alone does not. Where a command below names `<plugin>`, it is the directory `claude plugin list` prints as `Read from:` for `redline@redline`.

## Updating the plugin

**Updating the plugin.** `claude plugin update redline@redline` in a terminal, or **Enable auto-update** for the `redline` marketplace under `/plugin` → Marketplaces (auto-update is off by default for a marketplace that is not Anthropic's), then restart or `/reload-plugins`. An update replaces the plugin's files only. The per-repository contract (the `checks.sh` template version, the unattended section of `shape-spec.md`, the allow list in `settings.json`, the alias command files) is carried by a rerun of `/redline:setup`, and the launch precheck names which part is behind, as the paragraphs below describe. `CHANGELOG.md` says what each version changed and which changes need the rerun.

## The gate stamp, on a repository set up before it existed

A launch now refuses a `checks.sh` that carries no gate stamp (see "Gate stamp" in [contract.md](contract.md)). A repository set up before the stamp existed is stamped once, by hand, from its root:

```bash
<plugin>/scripts/redline-gate.sh stamp .claude/commands/agent-os/shape-spec.md .claude/redline/checks.sh
```

It prints the line it wrote. Change the `-h|--help` line of `checks.sh` from its numeric `sed -n '2,NNp'` range to `sed -n '2,/^$/p'` at the same time (the inserted line shifts the header, and `stamp` warns when it does), then commit both. A PR branch cut before that commit reached its base carries no stamp, and a launch on it stops with the same line: merge the base into the branch, or stamp it on the branch and commit and push, before launching on it. Or run `/redline:setup` from the repository's root (see [setup.md](setup.md)): on a repository whose `checks.sh` was written by hand it bootstraps `.claude/redline/checks.json` from the file (`redline-setup.sh read-checks`), regenerates `checks.sh` from the current template, which brings the version line and the template's current functions with it, shows you the diff to accept, and stamps it.

## Allow-list entries retired by #50

**Allow-list entries retired by #50.** `templates/settings.allow.json` no longer carries `Bash(/*/scripts/redline-gh.sh *)`, `Bash(/*/scripts/redline-prefs.sh *)`, `Bash(/*/scripts/redline-gate.sh check *)`, `Bash(/*/scripts/redline-setup.sh version *)`, `Bash(/*/.claude/redline/checks.sh *)`, `Bash(REDLINE_OCTANE=1 /*/.claude/redline/checks.sh *)`, `Edit(//tmp/redlinerepro/**)`, `Bash(git diff:*)`, `Bash(git log:*)` or `Bash(git show:*)`: a script of that name at any path an agent could write ran unprompted, and `git diff --output=<file>` writes a file. The guard now approves the plugin's own scripts, the repository's `checks.sh` and read-only git by real path for any session (see [guard.md](guard.md)), so nothing replaces them. A repository set up before this still carries them in `.claude/settings.json`: rerun `/redline:setup`, which reports them as `stale` and removes them on a yes (`redline-setup.sh settings . --remove-stale`), or delete the lines by hand. The checks template moved to v2 at the same time (`checks.sh` exited without its JSON when an untracked file could not be read, such as a symlink to a directory): a launch on a repository whose `checks.sh` carries v1 warns and says to rerun `/redline:setup`, which regenerates it. Since #15 the launch's precheck reads all of this in one call, `redline-setup.sh version .`, and warns about the missing and the retired entries by name.

## Unattended section versions (#15)

**Unattended section versions (#15).** `templates/shape-spec-unattended.md`, the section `/redline:setup` pastes into `shape-spec.md`, has had three bodies: v1 at the extraction (2026-10-20), v2 the same day with the owner line on every decision and `decidedBy` and `recommendation` on every finding, and v3 on 2026-10-30 with the repository ask rules of #49. Until #15 a rerun patched only the fill-ins, so a section made from an older body kept it, and no launch said so: Chalkboard's section was at v1 and two more at v2. The body now opens with a version marker, `<!-- redline-unattended: v3 -->`, the older bodies are frozen under `templates/history/`, and a launch on a section whose marker is older or missing warns, never stops: `the unattended section in shape-spec.md was made from template v1; the plugin ships v3. Run /redline:setup to see the change`. The rerun shows the three-way view (what the template changed since that version, what the repository changed from it, and the merged section) and, on a yes, merges the template's changes in while keeping the hand edits (`redline-setup.sh unattended ... --merge`), asking per conflicting line; or marks the section current as it stands (`--keep`); or leaves it, in which case every launch keeps warning. A section with no marker is matched to the nearest frozen body and the match is reported as guessed; read the diff before the merge, since a section whose hand deletions are exactly a version's additions is guessed older than it is.

## What a template bump means

The plugin's version is semver in `.claude-plugin/plugin.json` ([CONTRIBUTING.md](../CONTRIBUTING.md), Releases). A **patch** bump changes the plugin's files only: an update, or auto-update, is the whole upgrade. A **minor** bump means the change alters what a setup rerun writes into a repository: `scripts/checks-template.sh` below its header (the generated `checks.sh`), a file under `templates/` (the allow list, the unattended section, the alias commands, the CLAUDE.md sentence, `redline.json.example`), or an allow entry. Such a change bumps the template marker it touches in the same PR (`# redline-template: checks-template.sh vN` in `checks.sh`'s header, `<!-- redline-unattended: vN -->` as the unattended section's first line), and the launch precheck (`redline-setup.sh version <repoRoot>`, run at every `/redline:redline`) compares each marker and the allow list with the plugin's and warns, never stops, naming the part that is behind and saying to rerun `/redline:setup`. The rerun shows every diff before writing and carries only what moved: it regenerates `checks.sh` from the repository's `checks.json`, merges the template's section changes three ways, adds the missing allow entries and offers to remove the retired ones, and compares the alias files byte for byte. A **major** bump is a contract change a rerun cannot carry, and `CHANGELOG.md` says what to do by hand. `CHANGELOG.md`'s third group, "Setup and templates", lists every change a rerun carries.

`tests/setup-test.sh` pins the version comparisons (`version <checks.sh>`, `unattended --version`, `version <repoRoot>`), the three-way merge and the frozen bodies under `templates/history/`.

See also: [setup.md](setup.md) for the rerun step by step, [contract.md](contract.md) for the stamp and the version line.
