# Upgrading

How a plugin update reaches a repository, and what a rerun of `/redline:setup` carries that an update alone does not. Where a command below names `<plugin>`, it is the directory `claude plugin list` prints as `Read from:` for `redline@redline`.

## Updating the plugin

`claude plugin update redline@redline` in a terminal, or **Enable auto-update** for the `redline` marketplace under `/plugin` → Marketplaces (auto-update is off by default for a marketplace that is not Anthropic's), then restart or `/reload-plugins`. Update every scope that holds Redline for a repository, user and the repository's project or local install alike: a session runs whichever is listed first, so installs at different versions can switch a session mid-run, and the launch warns when they differ (see "A stopped run across a version change" below). An update replaces the plugin's files only. The per-repository contract (the `checks.sh` template version, the unattended section of `shape-spec.md`, the allow list in `settings.json`, the alias command files) is carried by a rerun of `/redline:setup`, and the launch precheck names which part is behind, as the paragraphs below describe. `CHANGELOG.md` says what each version changed and which changes need the rerun.

## The gate stamp, on a repository set up before it existed

A launch now refuses a `checks.sh` that carries no gate stamp (see "Gate stamp" in [contract.md](contract.md)). A repository set up before the stamp existed is stamped once, by hand, from its root:

```bash
<plugin>/scripts/redline-gate.sh stamp .claude/commands/agent-os/shape-spec.md .claude/redline/checks.sh
```

It prints the line it wrote. Change the `-h|--help` line of `checks.sh` from its numeric `sed -n '2,NNp'` range to `sed -n '2,/^$/p'` at the same time (the inserted line shifts the header, and `stamp` warns when it does), then commit both. A PR branch cut before that commit reached its base carries no stamp, and a launch on it stops with the same line: merge the base into the branch, or stamp it on the branch and commit and push, before launching on it. Or run `/redline:setup` from the repository's root (see [setup.md](setup.md)): on a repository whose `checks.sh` was written by hand it bootstraps `.claude/redline/checks.json` from the file (`redline-setup.sh read-checks`), regenerates `checks.sh` from the current template, which brings the version line and the template's current functions with it, shows you the diff to accept, and stamps it.

## Allow-list entries retired by #50

`templates/settings.allow.json` no longer carries `Bash(/*/scripts/redline-gh.sh *)`, `Bash(/*/scripts/redline-prefs.sh *)`, `Bash(/*/scripts/redline-gate.sh check *)`, `Bash(/*/scripts/redline-setup.sh version *)`, `Bash(/*/.claude/redline/checks.sh *)`, `Bash(REDLINE_OCTANE=1 /*/.claude/redline/checks.sh *)`, `Edit(//tmp/redlinerepro/**)`, `Bash(git diff:*)`, `Bash(git log:*)` or `Bash(git show:*)`: a script of that name at any path an agent could write ran unprompted, and `git diff --output=<file>` writes a file. The guard now approves the plugin's own scripts, the repository's `checks.sh` and read-only git by real path for any session (see [guard.md](guard.md)), so nothing replaces them. A repository set up before this still carries them in `.claude/settings.json`: rerun `/redline:setup`, which reports them as `stale` and removes them on a yes (`redline-setup.sh settings . --remove-stale`), or delete the lines by hand. The checks template moved to v2 at the same time (`checks.sh` exited without its JSON when an untracked file could not be read, such as a symlink to a directory): a launch on a repository whose `checks.sh` carries v1 warns and says to rerun `/redline:setup`, which regenerates it. Since #15 the launch's precheck reads all of this in one call, `redline-setup.sh version .`, and warns about the missing and the retired entries by name.

## The checks template, v3 (#68)

`scripts/checks-template.sh` moved to v3 with #68. Until then `checks.sh` printed the allowed list, the changed files and every commit since the run started, with twenty lines of each passing check's output, so its result grew with the pull request and with the run: on a medium pull request three rounds were enough to pass what the Bash tool shows inline, and the run stopped at `check` on a gate that had passed. A v3 `checks.sh` prints counts for those lists, the round's own commits, no output for a check that passed, and keeps its full result in a file under the temp directory ([contract.md](contract.md), "Output contract"). It also takes `--verdict`, which the workflow asks for when a result still cannot be shown.

A launch on a repository whose `checks.sh` carries v2 warns and says to rerun `/redline:setup`, which regenerates it from the repository's `checks.json`; nothing else in the repository changes. Until the rerun the v2 file keeps working: it ignores the snapshot's new `round_sha` and lists every commit, and the workflow reads its result as before. It can still spill on a long run, and it has no `--verdict` (`checks.sh: unknown flag --verdict`, exit 2), so the run then stops as it did, naming the rerun. A teammate on a plugin older than this one, running against a v3 `checks.sh`, gets the smaller result too, with every commit since the start listed, since that plugin writes no `round_sha`.

## Unattended section versions (#15)

`templates/shape-spec-unattended.md`, the section `/redline:setup` pastes into `shape-spec.md`, has had seven bodies: v1 at the extraction (2026-10-20), v2 the same day with the owner line on every decision and `decidedBy` and `recommendation` on every finding, v3 on 2026-10-30 with the repository ask rules of #49, v4 on 2026-11-13 with #93: the shaper decides every finding, `decline` is a disposition with a reason, a person is asked in five cases only, and a small refactor is done without asking; v5 on 2026-11-16 with #95: `defer` is for any item worth doing outside the pull request, with or without a mitigation, it carries a drafted issue, and a decline never points at follow-up work; v6 on 2026-11-24 with #105, #75 and #126: point 10's example and the sentence under it show `files` on every finding, every option of a judgment call states what it ends in (`ends`) and the call names its recommended option (`recommended`), a fix says where its cause lives and whether it is an instance or a class (`cause`, the step "Instance or class" in point 5), and a call for a finding left to the person may offer an option that ends in `defer` and carries its drafted issue; and v7 on 2026-11-25 with the follow-up of #127: point 5 and the sentence under point 10's example say that a sweep's list sits inside `cause`, as `cause.swept`, and never on the finding beside it, the example shows a sweep, and its judgment call recommends "Accept, no change." where it recommended an option that ends in `accept` together with a comment (#127, R2-2). Until #15 a rerun patched only the fill-ins, so a section made from an older body kept it, and no launch said so: Chalkboard's section was at v1 and two more at v2. The body now opens with a version marker, `<!-- redline-unattended: v7 -->`, the older bodies are frozen under `templates/history/`, and a launch on a section whose marker is older or missing warns, never stops: `the unattended section in shape-spec.md was made from template v1; the plugin ships v7. Run /redline:setup to see the change`. The rerun shows the three-way view (what the template changed since that version, what the repository changed from it, and the merged section) and, on a yes, merges the template's changes in while keeping the hand edits (`redline-setup.sh unattended ... --merge`), asking per conflicting line; or marks the section current as it stands (`--keep`); or leaves it, in which case every launch keeps warning. A section still at v3 tells the shaper to put a finding it cannot confirm to the person as `unsure`, which a Redline round no longer takes: the shaper's own output schema refuses the value, so the shaper either decides the finding (fix, decline or defer) or asks under one of the five cases, and the round goes on; the rerun brings the section's wording in line. From v3 to v4 the merge is clean unless the section was edited by hand on a line the template changed (points 3, 4, 5 and 10, and the sentence after the JSON example) or on the line beside one: a conflicting hunk is shown, and picking the section's side for it means carrying the template's wording into that hunk by hand. A section still at v4 describes the old `defer` (a real bug behind a cheap mitigation) and has the shaper decline what belongs elsewhere, while the plugin's shaper file and the round's own prompt describe the new one and ask for the drafted issue. The launch warns, as for any older section, and the workflow stops a round at shaping on a deferral that carries no draft, where a resume reruns the shaper; the rerun of `/redline:setup` brings the section's wording in line. From v4 to v5 the merge is clean unless the section was edited by hand on a line the template changed (points 4, 7 and 10, the JSON example and the sentence after it) or on the line beside one. A section still at v5 is one release behind in its wording only: its example shows no `files`, no `ends`, no `recommended` and no `cause`, and it has no instance-or-class step. The launch warns and goes on, and nothing the workflow reads depends on the section's version: the plugin's shaper file and each round's own prompt ask for every one of those fields, and the shaper's output schema requires `ends` and `recommended`, so a round under a v5 section returns them, and the workflow stops a round at shaping on a fix with no `cause`, where a resume reruns the shaper. There is no fallback for a section that is behind, and no launch is refused for one; the rerun of `/redline:setup` brings the wording in line. From v5 to v6 the merge is clean unless the section was edited by hand on a line the template changed (the paragraph that opens the section, points 3, 4, 5 and 10, the JSON example and the sentence after it) or on the line beside one: a repository that added a point of its own right after point 10 has it beside that sentence, so the hunk conflicts; take the template's side for it and put the added point back, or keep the section's side and carry the template's sentence in by hand. A section still at v6 tells the shaper that a sweep's list is returned "as `swept`" and names no place for it: a shaper read that as a key of the finding, beside `cause`, and the round stopped at shaping twice. The plugin's shaper file and each round's own prompt now say `cause.swept`, and the stop names that place and says where it found the list, so a round under a v6 section is told both; the rerun of `/redline:setup` brings the section's wording in line. From v6 to v7 the merge is clean unless the section was edited by hand on a line the template changed (point 5, the JSON example and the sentence after it) or on the line beside one: a point a repository added right after point 10 conflicts as it did from v5 to v6, with the same two ways out. A section with no marker is matched to the nearest frozen body and the match is reported as guessed; read the diff before the merge, since a section whose hand deletions are exactly a version's additions is guessed older than it is.

## Two Redline versions on one pull request (0.3.0)

From 0.3.0 a review body writes `unconfirmed` as a finding's confidence word, and the tail of a finding a repository ask rule covers names the person by login (` · left to @<login> under rule <id>`). The `redline-gh.sh prior-findings` of an older release reads neither. It gives no line for an unconfirmed finding, so such a finding is neither carried nor settled, and a decline of one can be raised again as new. It also keeps the new rule tail in the finding's title and reads the rule reply as decided. Continue a pull request that a 0.3.0 run reviewed with 0.3.0 or later; 0.3.0 reads the older forms too.

## A stopped run across 0.4.5 (#116, #117)

From 0.4.5 an error result says whether the stop was the workflow's own check of what an agent returned (`ownCheck`). The run marker keeps it, and what a resumed step is told is chosen by it, no longer by how the error is worded ([running.md](running.md), "Run markers and resume"). A marker an older release wrote holds no `ownCheck`, so it resumes as an ordinary stop: the rerun is told the cause was fixed by hand, and a resolve agent stopped by a check of its own result is not told to correct what it wrote. A resumed reshape keeps the folder and restores what is missing, whatever stopped it.

A run also keeps every earlier resume in its args, and each one's line is built again on every relaunch. So a run that had already resumed at a resolve check or at a reshape under an older release, stopped again later, and is relaunched under 0.4.5 builds a different line for that step, and the step and everything after it run again, a round already built included. Finish or restart a stopped run before updating across 0.4.5. A run that never resumed at one of those steps, and is not stopped at one now, is not affected.

## A stopped run across 0.5.0 (#105, #75, #126)

0.5.0 changes what the shaper is asked and what it returns: every option of a judgment call states what it ends in, the call names its recommended option, and a fix states its cause. The shaper's output schema requires the new keys and refuses a key it does not name on the result, a finding, `cause`, an entry of `swept`, a call, an option and its `draft`; a deferred entry stays open, and the workflow's draft check holds it. The schema of a review that is asked for class links refuses one on the result and on a finding. So every shape prompt changed, and its schema with it. On a pull request where no earlier Redline run replied to a finding with anything other than "not changed in this round" (a finding with no reply counts as unanswered), a stopped run relaunched after the update replays only what came before its first shape. A run stopped at the review dial, before any shaping, replays whole and goes on. A run stopped anywhere later (a hand-off for decisions or for a plan, a stop for a draft, an error at a check, at push and reply or at the handoff comment, the end-of-run stop for drafts) replays its gather, review and post and then runs again from the first round's shape: a round that was already built and pushed is shaped and built again over its own commits. A human review pass stopped at a hand-off runs again from its shape the same way.

On a pull request where an earlier Redline run replied to at least one finding with anything other than "not changed in this round", the run's first review is also asked whether each finding is one class with an earlier fixed one (`sameClassAs`), so its prompt changed too. There a stopped run replays only what came before that review, whatever stopped it, the review dial included: the review runs again, and so does the post, which finds the round already posted and posts nothing, but writes the round's `round-<n>-review.json` and `round-<n>-findings.json` again from the rerun's findings, which need not be the findings GitHub shows under the same ids. In both cases, finish or restart a stopped run before updating across 0.5.0, a run stopped at the review dial on such a pull request included; a decision you had already given is kept in the run's arguments and applied again, as an answer in your own words.

The workflow has no fallback for a shape made under an older release, because none can reach it: a shape result from before 0.5.0 never replays under a changed shape prompt. On the plugin's own repository a relaunch runs the script the run launched with (#81), so a run in flight there is not affected. From 0.5.1 a stopped run is not relaunched under another version at all, on any repository: it is refused and started fresh (see the next section).

## A stopped run across a version change (#135)

From 0.5.1 a run records the version it starts under, the one in `.claude-plugin/plugin.json`, and the git blob id of the workflow file it starts with, as `args.launch`; a relaunch or a resume under another version is refused, never run ([running.md](running.md), "Hand-off and relaunch"). Before 0.5.1 a relaunch ran whatever the workflow's name resolved to. A session runs the install listed first among those it sees (user scope, and project or local scope for its directory), an install or update in another process reorders that list, and a session that reloads or is reopened resolves the name afresh, so on Losers League #839 a run launched from 0.4.3 relaunched under 0.4.5: 9 of 26 recorded steps replayed, and the run went back to round 1's shape with that round already pushed.

Two layers refuse it. Before every relaunch and every resume, `redline-prefs.sh run drift` and `run check` compare the version the run recorded with the copy of Redline the session loaded. At startup, before any agent, the workflow compares it with its own version: when the session switched after the skill was expanded, only the script that runs can see it. Either refusal names both versions, says nothing on GitHub is lost, and leads to a fresh run, whose first round carries the open findings forward; nothing needs fixing by hand.

A run stopped under a release before 0.5.1 holds no `args.launch`, so its marker is refused like any version change. The line names the version from the manifest of the release the run was launched from (an update leaves the older version's directory in the plugin cache), or says a build before 0.5.1 when it was launched from a checkout, whose manifest may have moved on since. Finish a stopped run before updating to 0.5.1, or start it fresh after.

The check lives in the new workflow, so it closes the gap in one direction only until every install a session sees is 0.5.1 or later. A session that launched under 0.5.1 and then reloads, or is reopened, onto an install from before 0.5.1 runs that build's workflow, which has no check: the relaunch goes ahead and replays only up to that build's first changed prompt, as before; typing the command again runs that build's skill, which has no check either. No code can close it, since the older build's files are what run: bring the older install up to date.

That is what the launch warning is for. At every fresh launch `redline-setup.sh version` reads `claude plugin list --json` and, when the installs this repository sees are at different versions, says so in one line and gives the update for each older one:

```bash
claude plugin update redline@redline --scope <user|project|local>
```

A project or local update is run from the repository's root: run from elsewhere, the command can pick another repository's install of the same scope and report it already up to date (measured on Claude Code 2.1.332). Then restart the session or run `/reload-plugins`. The warning never stops a launch, and it says nothing when the session loads Redline from a checkout (`--plugin-dir` hides every install) or when the `claude` CLI is missing or fails.

A checkout loaded in place carries the plugin's version too. Its workflow can change during a run without the version changing, and a relaunch then runs the launch's copy of the script, on any repository. A commit that changes its version ends a run at the next relaunch, like any version change, and a fresh launch in a session that loaded the checkout before such a commit is refused until the session is reopened.

## What a template bump means

The plugin's version is semver in `.claude-plugin/plugin.json` ([CONTRIBUTING.md](../CONTRIBUTING.md), Releases). A **patch** bump changes the plugin's files only: an update, or auto-update, is the whole upgrade. A **minor** bump means the change alters what a setup rerun writes into a repository: `scripts/checks-template.sh` below its header (the generated `checks.sh`), a file under `templates/` (the allow list, the unattended section, the alias commands, the CLAUDE.md sentence, `redline.json.example`), or an allow entry. Such a change bumps the template marker it touches in the same PR (`# redline-template: checks-template.sh vN` in `checks.sh`'s header, `<!-- redline-unattended: vN -->` as the unattended section's first line), and the launch precheck (`redline-setup.sh version <repoRoot>`, run at every `/redline:redline`) compares each marker and the allow list with the plugin's and warns, never stops, naming the part that is behind and saying to rerun `/redline:setup`. The rerun shows every diff before writing and carries only what moved: it regenerates `checks.sh` from the repository's `checks.json`, merges the template's section changes three ways, adds the missing allow entries and offers to remove the retired ones, and compares the alias files byte for byte. The rerun keeps `redline.json` as yours, so a key a newer `templates/redline.json.example` adds is not written into an existing file: 0.4.0's `deferTo` (#95, where a deferred item's draft goes) shows under `differs`, and until someone adds it by hand the built-in default holds, a GitHub issue per deferred item. A **major** bump is a contract change a rerun cannot carry, and `CHANGELOG.md` says what to do by hand. `CHANGELOG.md`'s third group, "Setup and templates", lists every change a rerun carries.

`tests/setup-test.sh` pins the version comparisons (`version <checks.sh>`, `unattended --version`, `version <repoRoot>`), the three-way merge and the frozen bodies under `templates/history/`.

See also: [setup.md](setup.md) for the rerun step by step, [contract.md](contract.md) for the stamp and the version line.
