# A run, start to finish

What happens between typing `/redline <pr>` and the handoff comment: the precheck, the rounds, how each finding is decided, how you overrule a decision, where the run stops for you and how it relaunches, what it posts, and what it leaves in the repository. The dials themselves (interrupt, scope, rounds, models) and their defaults are in the README; the files a run reads are in [contract.md](contract.md).

## Launching a run

Check out the PR's branch, clean, at the pushed head, and type the command from a message that holds only the command:

```
/redline 21
/redline-revise 21 review @sam
/redline:redline 21
/redline:redline 21 max 2 rounds
/redline:redline 21 revise fable no push
/redline:redline 21 reviewer @sam
/redline:redline 21 autopilot
/redline:redline 21 plan correctness only
/redline:redline 21 defer at end defer to spec
/redline:redline 21 review
/redline:redline 21 dry run review only
/redline:redline 21 coverage off
/redline:redline-revise 21 review @sam
```

The short forms are two project command files, `.claude/commands/redline.md` and `.claude/commands/redline-revise.md`, that `/redline:setup` writes from the plugin's `templates/command-redline.md` and `templates/command-redline-revise.md` (its step 12, default yes; a rerun shows a changed one as a diff and asks, and leaves a file of that name that is not Redline's alone); each is a one-line command that invokes the namespaced skill with the arguments typed, so the namespaced form always works, and `/redline:redline-review` has no short form (#44). The words can come in any order. `dry run` posts and pushes nothing: every body is written under the round's spec folder instead, and the PR may be closed (a seed). Its commits stay on the local branch, unpushed: the round's spec commit, one per finding, and the run-record commit, so a `dry run review only` leaves exactly one commit, the record, and nothing on GitHub. Those commits put HEAD ahead of the PR's head, so the next launch stops at the precheck (`pull or push so HEAD matches the PR`) until they are gone. Do not push them: copy the round's spec folder outside the repository if the review is worth keeping, then drop them with `git reset --hard origin/<branch>`. Because nothing was posted, the next `/redline:redline <pr>` then finds no Redline round on the PR (`redline-gh.sh last-round` reads the posted reviews) and starts at round 1 with no carried findings: a dry run's review is a record, kept only where you copied its spec folder, not a round the next run continues. The first launch in a repository asks for the settings it was not given on the command line, and later launches confirm the remembered ones in one question; see "Saved launch settings" below. `/redline:redline-review` and `/redline:redline-revise` are the two halves on their own, for debugging. `review only`, read the review, then `/redline:redline <pr>` is the expected path: the review-only run commits its record, so the tree is clean for the next launch, and the full run's first round carries every finding of the review-only round that has no disposition (see "Earlier rounds" below; a posted round only, never a dry run's), so no separate revise launch is needed; `/redline:redline-revise <pr> round <n>` over that round stays as the manual path.

## Precheck

`/redline:redline <pr>` is typed in an interactive session whose working directory is the repository root: the guard approves git only there, for the roles and the session alike (#54). The workflow runs in the background and the session waits for it. The precheck prints the PR's file count from GitHub and warns when the local diff against the base counts differently; above 300 files it warns that GitHub's whole-PR diff is unavailable there (Redline reads per-file patches instead, and takes the hunks of a text file whose patch GitHub omits from the clone when it holds the PR's base and head commits, so inline anchoring still works there, except in a binary file and in one whose diff GitHub takes no comment on), and above `maxFiles` in `redline.json` it refuses. A PR that already carries posted Redline rounds gets its next number: the precheck reads the highest posted round (`redline-gh.sh last-round`) and the run starts after it, so every finding of the new run gets its own review and threads instead of being skipped as already posted; it then reads what those rounds posted and how each finding was answered (`redline-gh.sh prior-findings`), so a finding with no disposition is carried into the new run's first round instead of being skipped as already known (see "Earlier rounds"). A headless session (`claude -p`) stops background tasks ten minutes after its last turn, which kills a run mid-phase, so it is started with `CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS=0`. A run the harness stopped is resumed from the session that launched it: the skill relaunches with byte-identical `args`, no new `decisions`, and `resumeFromRunId` set to the run id; finished agents replay from cache and the interrupted one reruns. A hand-off relaunch works the same way, adding only what the stop asked for (`decisions`; `approvedPlans` for the plan dial; `selected` for the review dial; `deferrals` for a stop that raised deferred drafts), so every prompt before the stopping point replays from cache.

Before any of that, the precheck runs `redline-gate.sh check` (the gate stamp in `checks.sh` still matches the repository's Verification Gate; a moved gate or a missing stamp stops the launch with the script's one line) and `redline-setup.sh version` (the contract's versions: `checks.sh`'s template line, the unattended section's marker, `settings.json` against the allow-list template, and whether a self-hosted run loads in place; warnings only, each saying to rerun `/redline:setup` or to start the session with `claude --plugin-dir`), checks `gh`'s version and login, and writes the start snapshot ([contract.md](contract.md), "Snapshot file"). A session that loads the plugin from a directory, as `claude --plugin-dir` does for the plugin's own self-review, gets one more warning, on a fresh launch and on a resume, and never a stop: in auto mode Claude Code refuses the Redline agents' file writes with no verdict, and the run fails at its first file write, normally its first post; run such a session in accept-edits and approve each prompt, or in bypass-permissions (#76). Bypass-permissions also removes the coverage pass's permission prompt, the one check the guard cannot provide; a fresh launch with `coverage off` runs without the pass.

## Rounds

Each round is one pass of the loop, numbered from the highest round already posted on the PR plus one:

1. **Review.** Every round but a final nit pass opens with the **coverage pass**, the finder: the built-in `code-review` skill, run from a plain workflow agent over the whole pull request at the round's head, at the configured effort with every finding reported (see "The coverage pass" below). The **reviewer** is the verifier. For each candidate it establishes one thing, whether the claim is true, and says so as one of three facts: verified, could not confirm, or refuted. Or it collapses the candidate into something already reported, settled or tracked. It does not decide what to do about a true claim: no candidate is held back because it is small, costly to fix, unlikely, or caused outside the diff. On a later round it still rechecks the previous round's fix diff. It returns findings, each with an id (`R1-4`), a file and line, a kind (`correctness` or `nit`), a severity, whether it was confirmed (`confirmed`, or `unconfirmed` with one line on what would confirm it), a description and usually a proposed fix; on a round that rechecks a fix diff, each also says whether its cause is in those fixes (`inFixDiff`; see step 7). A finding an open issue or a teammate's comment already tracks in full is reported as `already tracked`, never fixed; when one tracks only part of a candidate, the part it lacks is judged on its own (#85; #86, R2-1). With `coverage off` the reviewer alone reads the whole diff in round 1 and the fix diff after, under the same contract; a final nit pass is always the reviewer alone. The GitHub agent posts one review per round (`Redline round N`, the `COMMENT` event): one inline comment per finding on a line of the PR diff, and a body that lists the findings by kind (`### Correctness`, `### Other items`, `### Could not confirm`, each unconfirmed one with what would confirm it) and then, folded under its own heading, every candidate the verifier set aside. A finding GitHub cannot anchor (a binary file, a line outside the diff, a file the pull request does not change, a diff too large for GitHub to take a comment on, among others) goes in the body behind a marker, under one line saying why (see "How the review is posted").
2. **Shape.** The shaper runs the repository's `/agent-os:shape-spec` in unattended mode ([contract.md](contract.md), "The unattended section") and writes a spec folder, `agent-os/specs/<launch stamp>-<pr>-review-round-<n>/`: `plan.md` (one task per finding), `shape.md` (every decision with its owner, the proportionality notes, the proposed standards edits), `standards.md` and `references.md`. It decides every finding (see "Dispositions"): fix it here, defer it to a drafted issue (with a mitigation in this pull request when a cheap one exists), decline it with a reason, or ask. It returns the judgment calls, the few findings it may not decide.
3. **Approve.** The plan approver reads the plan against the findings, the repository's standards and the ask rules, and passes it or sends it back with reasons; a bounced plan is reshaped, up to `maxPlanAdjustments` times, then the run stops at stage `approve`. That count is the only bound on bounces, and when a reshape changed the task of a finding you or the autopilot decided, the stop's `detail` lists it under `reshaped`: the finding, who decided it, and its task's files as first planned and after each reshape that changed them ("Deferred items", "A reshape after your decision"). The standards approver approves the proposed standards edits. The GitHub agent then writes the round snapshot with every approved path ([contract.md](contract.md), "Snapshot file").
4. **Implement.** The implementer makes the changes in the plan's order, one commit per finding (the README, "Git rules for Redline agents"), runs the gate through `checks.sh` after each, and applies the approved standards edits in their own commit.
5. **Check.** The checker runs `checks.sh` with the round's snapshot (the whole gate, or only its git block when `checker` is `git-only`) and returns the JSON. The workflow decides pass or fail from the data: each check's exit against the baseline the run took before its first implement step ("tests pass" means no failure the baseline did not already have), the git block (no file changed outside the approved plan, nothing uncommitted outside `agent-os/specs/`) and the exit code. A failing round goes back to the implementer with the failing checks and git-block findings; a result the implementer cannot change (unreadable, exit 2, no git block) stops the run at stage `check` naming the cause and the fix. One unreadable result is asked for again first: when the gate's output was too large for the Bash tool to show, the checker runs `checks.sh --verdict`, which prints the verdict the script kept for that run, and the round goes on from it ([contract.md](contract.md), "Exit code").
6. **Push and reply.** When the round deferred anything, the GitHub agent first files each deferred item's drafted issue (see "Deferred items"), so the replies can say where each went. It then pushes once (when `push` is on) and replies in each finding's thread with what became of it and its owner (see "Decided by"): `fixed in <sha> (...)`, `deferred to #<n>` or `deferred; the issue draft is at <path>` (then `Mitigated in <sha> (...)` when a mitigation shipped), `declined: <reason>` for a finding Redline decided not to act on, `not acted on in this run.` for a finding you dropped on the review dial, `not changed in this round.` for a fix that did not land, `left to @<login> under repository rule <id> (...)`.
7. **Re-review, or the end.** A round is bought by what it finds, not by what it commits.
   - **What buys the next round.** The round's review held a new correctness finding that the shaper fixed (in full, or by a deferral's mitigation) or put to you. The next round then runs the coverage pass again over the whole PR at the new head, and the reviewer rechecks the fix diff beside the candidates. This holds whatever you answered and whether or not a commit resulted: after a round you answered with "no change", the next round has no fix diff to recheck, says so, and verifies the pass's candidates at the same head. A decline you overruled to a fix counts the same. A deferral buys a round only through a commit of its own, since that is the new code: a planned mitigation the build left out buys nothing, and neither does a deferral you changed to no change. One correctness finding does not buy a round: a small bug in the previous round's fixes, below.
   - **A small bug in the last fixes.** A new correctness finding that is low severity and whose cause is in the previous round's fix diff is fixed like a nit (#95). It is shaped, fixed and answered in its thread with the round's other findings, it buys no round, and when nothing else in the round buys one, the round ends in the final nit pass over its fixes. A finding in the pull request's own code, or of medium severity or above, still buys a round, and so does a low one the verifier does not place in the fix diff. Severity says how bad the failure is when it happens, not how likely it is. The verifier states the place as a fact on each finding of a round that rechecks a fix diff (`inFixDiff`), and the workflow honours it only where it can be true: on a round that read a fix diff, for a file the previous round's plan named. A claim it cannot honour is cleared with a warning in the run's result, and the finding buys a round as any other does. The run's result lists each round's findings of this kind under `minor`.
   - **What ends the run.** Every other round. Nothing new, or everything new declined by Redline on its own, and no fix committed: the handoff. Fixes committed, none of them for a correctness finding that buys a round (nits, small refactors, tests, docs, costs, a small bug in the last fixes): one **final nit pass**, in which the reviewer alone reads those fixes and reports only correctness bugs they introduced. Its review and the handoff call what it read the nit fixes, or `round <n>'s fixes` when that round fixed a small bug in the fixes before it. A nit it reports anyway is declined with the pass's scope as its reason, listed once in that round's review body and in the handoff, with no thread, and is never shaped. What it finds goes through the shaper once more, and then the run ends, whatever that pass did.
   - **Why it does not chase nits.** Only such a correctness finding buys a round. The final nit pass reads the fixes only, never the whole PR, and reports no nits. A finding Redline declined is settled, so no later round raises it again, unless it was declined because it could not be confirmed and a later round's verifier confirms it from a coverage candidate; with `coverage off` there is no candidate, and it stays settled.
   - **What counts as correctness.** Wrong behaviour reachable in practice, a security hole, a privacy leak, data loss, a broken contract, or a promise the pull request makes (in its title, its description or its spec) that the code does not keep. Everything else is a `nit`: naming, clarity, a docblock, a small refactor, a test gap, a cost, a doc. The verifier states the kind, since the kind is what keeps a run going.
   - **What counts as new.** Not collapsed into a finding already reported, settled in an earlier round, carried forward or tracked elsewhere in full (the part an issue or a teammate's comment does not track is judged on its own, #85). Two things reopen a settled finding, each reported as new with the earlier id named: a candidate that matches a finding marked fixed but still reproduces at the new head, and one that matches a finding declined because it could not be confirmed, which the verifier now confirms. A decided finding stays settled whatever its commits, since an applied decision is often a deliberate keep or mitigation: a candidate that still reproduces one is accounted for as settled, shown in the set-aside block with the earlier id, and buys nothing (#80, R3-4).
   - **The scope and the pass.** With `correctness only`, anything the verifier reports that is not a correctness finding is declined with the scope as its reason, listed under `scoped` in the round's findings file, apart from its `findings`, so `/redline:redline-revise <pr> round <n>` never shapes it, and there is no final nit pass, with one exception: a round whose fixes are for small bugs in the last fixes gets one, since those fixes are code no round has read. With `coverage off` there is no pass to run again: a round that fixed a correctness finding is followed by a review of the fix diff, and a bought round that changed no code ends the run.

The round cap (`maxRounds`, default 3) counts this run's revise rounds. The review after the last of them still runs. A new correctness finding in it that would buy a round, confirmed or not, ends the run with the **cap-hit comment** ("Redline stopped at the round cap": it reached its cap of N revise rounds with correctness findings still open in the latest review, so it has not requested a review; `@<login>` will pick these up, each listed under "Still open", followed by the handoff's `### Deferred` section when the run deferred anything, since no handoff follows). The run then makes the run-record commit and ends with no handoff and no review request. A round past the cap that holds only nits, or only nits and small bugs in the last fixes (low severity, caused in the previous round's fix diff), is still fixed and gets its final nit pass; the cap-hit comment of a capped run lists every open correctness finding, those included. `tests/loop-test.mjs` pins the phases, the done rule, the final nit pass, the cap and every dial level with scripted agents.

## The coverage pass

Every whole-PR and fix-diff round opens with the coverage pass, the finder: a plain workflow agent (`coverage r<n>`, the default agent type, no Redline role and no output schema) invokes the built-in `code-review` skill over the head branch at the round's head, at the effort `models.coverage` names, with `--max-findings all`, and relays the skill's text. The workflow reads from it only the skill's own fenced JSON array of candidates (file, line, summary, failure scenario) and hands the list to the reviewer, which verifies rather than discovers.

**Three facts, and the collapses.** The verifier accounts for every candidate with one of six outcomes:

- `verified`: it reproduced the claim, or traced it through the code to the result the candidate claims, with the lines cited. The candidate is a finding of the round, `confirmed`.
- `unconfirmed`: the claim turns on something the repository cannot show (production data, an external service, timing between processes, a browser). This is the narrow case: a claim that reading the code or running a test can settle is verified or refuted. The candidate is a finding of the round with one line on what would confirm it, and the shaper takes a second look (see "Dispositions").
- `refuted`: it holds evidence against the claim the candidate makes, and its ref states that claim and the evidence. A refutation answers the candidate's claim: evidence for a neighbouring claim does not refute it, and neither does a comment or docblock that states intent (#85).
- `duplicate`, `settled`, `known`: the candidate collapses, by cause and never by line or file, into another candidate or finding of the round, a finding of an earlier round (of this run or an earlier one on the PR), or an issue or a teammate's comment that tracks it in full.

What used to end the matter is now a fact the finding states, for the shaper to weigh: a cause in code this pull request did not change, the conditions a failure needs, and a guard the base branch had and this pull request removed (naming the removed line). There is no outcome for "true, not worth acting on" and no list for the person: whether a fix is worth its cost is the shaper's question.

An issue or a teammate's comment that covers only part of a candidate leaves the remainder to be judged as its own candidate: a remainder whose cause is in this PR's diff is a finding that names the issue in its description, with no `knownAs`, unless it collapses or is refuted like any other; and two candidates are not one because one issue's title fits both (#85; #86, R2-1). A candidate the verifier anchored outside the diff keeps its place, and the post moves its comment into the review body.

**What is posted.** The round's findings file holds each candidate, by index, beside its outcome and its ref. The review body counts them in one sentence (`15 candidates: 12 verified, 1 could not be confirmed, 1 refuted, 0 collapsed into items already reported or settled, 1 already tracked`; a finding the round lists under Already tracked counts as already tracked). After the findings, under the heading `### Candidates set aside (N)`, it lists in a folded `<details>` block, the set-aside block, every candidate that is not a finding of the round (`refuted`, `duplicate`, `settled` or `known`; its summary line, `Refuted, collapsed or already tracked`, names the count sentence's three groups, which add up to N). There is one line each: the candidate's file and line, its own summary as the finder wrote it, then the outcome and the verifier's ref (`no reason given`, with a warning in the run, when it gave none). A `known` line names the issue or comment, and a `duplicate` line names what it collapsed into, its ref opening with the candidate's index or the finding's id and anything meant for the reader after it, plus, when it opens with another candidate's index (`3`, `candidate 3` or `index 3`), that candidate's place and outcome, and the finding's id when that candidate became a finding, so a duplicate of a refuted or tracked candidate cannot hide (#86, R4-1, R5-4). Each line's summary, outcome and ref are escaped and their mentions neutralised as one text, as "How the review is posted" says, so no tag in a summary or a ref can end the block or open another and no `@word` in one notifies anyone (#85; #86; #87). The block is there so you can overrule a refutation, a collapse or a match to an issue without opening the round folder; a round that set nothing aside has no block.

**Nothing leaves quietly.** A candidate the reviewer left out, gave an outcome the workflow does not know, accounted for with a ref that names no finding of the round, or collapsed with a ref that names nothing it collapses into (a `duplicate` of itself, of an index past the round's last candidate, or of a duplicate that leads back to it, or a `duplicate` or `settled` ref whose leading id no finding of the round, of the run or of the PR's earlier runs has; #94, R8-2), becomes a finding of the round as reported: a new id, `correctness`, `unconfirmed`, with a warning in the run. The shaper's second look then decides it. A ref that opens with a finding's id and adds a note after it names that finding, with a warning. A collapse whose ref opens with neither an index nor an id, a note in words, names something and is shown as written in the set-aside block. A candidate that names no file is kept at `(no file)`, line 0, so a later run reads its line back. One with neither a summary nor a failure scenario is kept with a title and a description that say so.

**Why every round.** The skill is stochastic and attends to what moved, so each pass is a sample. The manual loop Redline replaces ran a pass per round and stopped when one confirmed nothing new; a single sample on round 1 is why a hand-run pass after a Redline run could still find something. So the pass runs again at every head, the reviewer still rechecks the previous round's fix diff beside the candidates, and the done rule follows the manual loop's: the run goes on while a round finds a new correctness item to fix or ask about, under `maxRounds`. The skill never returns an empty list, so what ends a run is never the skill: it is the shaper's decision on what the verifier found. A round whose new items are all declined, deferred with nothing shipped, nits, or low-severity bugs in the previous round's fixes ends it, after one final nit pass when the round committed fixes. The cost is about one skill pass per round, what the manual loop paid.

`models.coverage` in `redline.json` picks the pass's model and effort ([contract.md](contract.md)); absent, the first-round reviewer's. `coverage off` on the command line, or `"coverage": null` in the file, runs every round with the reviewer alone, under the same model (it finds and verifies, reports what it confirmed and what it could not, and the shaper decides): the fallback when the skill is absent on this Claude Code or its recipe has drifted, never the default; the word is per-run and never saved. The effort word is one of `low`, `medium`, `high`, `xhigh` or `max`; `max` runs as a single pass, since a workflow subagent has no Agent tool for the skill's fan-out, and `xhigh` on the opus-5 family is the recipe validated on Claude Code 2.1.318.

A pass that yields nothing usable stops the round at stage `review`, resumable at `coverage r<n>` (see "Run markers and resume"), with one of three causes in the error, each with its fix: the Skill tool was denied (allow it in the session's permission mode or allow list), the skill is absent on this Claude Code (`claude --version`; upgrade), or the pass's text holds no fenced JSON array of findings in the skill's shape (the recipe drifted; check the version). Each message also names the alternative, a fresh launch with `coverage off`. An empty array the skill returned on purpose is zero candidates, not an error: the reviewer runs no discovery pass of its own; it runs the scheduled-and-queued, Docs and Version checks, the recheck of the previous round's fix diff on a later round, and the carry-forward list on a first round that has one.

**What the guard does not vet.** The skill runs as a fork of the coverage agent, and the fork carries no Redline `agent_type`, so the fork is a non-role session to the guard: it is inert for every call but one shape. A Bash call that is one of the plugin's own scripts by real path, the repository's `checks.sh` or read-only git is approved for the fork exactly as for the main session (#50), with no prompt; of `redline-gh.sh`, only the read subcommands are (#80, R2-5). A subcommand that posts a review, replies, comments, creates an issue or resolves threads is left to the session's permission prompt, never refused, as is the rest of what the fork runs beyond its allow list; the coverage prompt also tells the agent not to post anything. A Redline role could not host the pass either, since the fork would escape the role's row the same way and a role's output schema can make the fork return nothing. In the spike and the second corpus run the fork ran read-only git (`log`, `diff`, `show`, `grep`), `cat` and `grep`, and `gh` reads of the PR and the issues; the guard approves the read-only git as it does for any session, and the rest meets the session's allow list or permission prompt, so a default-mode session may be asked once by the fork. See "Known limits" in the README.

## Dispositions

The verifier says what is true; the shaper decides what to do about it. It sorts every finding, of any kind (a bug, a nit, a small refactor, a test gap, a cost, a doc), into exactly one of:

- **`fix`**: the change is clear and its cost is in proportion. It becomes a plan task and a commit. `decided by: redline`.
- **`decline`**: the item is not worth doing, and Redline says why in one sentence a teammate can read. The reason is posted in the finding's thread as `declined: <reason>` and listed in the handoff. Reasons that stand: the claim is wrong (the shaper's second look refuted it); the failure needs conditions that will not occur; the pull request's own spec decided the point; or the second look could not confirm it. A decline never points at follow-up work: an item worth doing somewhere is a `defer`, the run warns when a decline's reason says otherwise, and the plan approver sends such a decline back. No task and no commit. `decided by: redline`, and you can overrule it (see "Overruling a decline").
- **`defer`**: the item is worth doing, and not in this pull request: a gap that predates it, a cause in code it did not change, a refactor that is large or reaches well outside it, a full fix out of proportion here. Any kind of finding can be deferred, not only a bug. A mitigation is optional: when a cheap one exists inside the pull request (a guard, a clear error, a log line, a comment naming the finding) it becomes the task and the commit, and a deferral that ships nothing has no task and no commit. What it shipped is read from the round's record, never from the words written for it (see "Deferred items", Whether a mitigation shipped). Every deferred item carries a drafted issue that stands on its own (a title, what was found, why it is not fixed here, the fix proposed), listed under Deferred in `shape.md` and filed by the run (see "Deferred items"); a deferral without one stops the run at shaping. `decided by: redline`.
- **`ask`**: a judgment call, returned to you and never decided by Redline: a pending entry in `shape.md`, a `Pending decision` task in the plan, and a judgment call in the run's result with a plain-language story, the options with their cost and effect, and the shaper's recommendation. On `guided` the run stops for it (see "Hand-off and relaunch"); on `autopilot` the recommendation becomes the decision, `decided by: redline (autopilot)`. The shaper asks in five cases only:
  1. the options differ in what the product does or in what a user sees;
  2. the fix changes an assumption, the approach or the architecture the original spec agreed;
  3. the fix reaches outside what the pull request set out to do;
  4. two options are both defensible and neither is the clear pick;
  5. the finding is still unconfirmed after the shaper's second look, and its harm would be serious if it were true (security, privacy, data loss, money).
- **Left to you**: a finding a repository ask rule covers ([contract.md](contract.md), "Ask rules") is always the person's, whatever the shaper returned: it comes back as a judgment call naming the rule, with options you carry out outside the run, and Redline makes no change for it; on autopilot, where nobody answers, its line under Left to in the handoff also says what Redline would have done. It is no deferral: it has no drafted issue. A finding on one of Redline's own files in the repository (`.claude/redline/`, `.claude/redline*.json`, `.claude/settings*.json`) is put to you the same way, since no Redline role may write them. Its reply reads `left to @<login> under the rule on Redline's own files`, its thread stays open whatever you answer, and on autopilot its Left to line says what Redline would have done (#94, R8-4).

In every other case the shaper takes its own recommendation, a decision to decline included, and records it with its reason. The rule is the cases, never a degree of confidence, and the workflow holds the shaper to it: a judgment call for any other reason stops the run at shaping, before it reaches you. Every decision, in `shape.md`, in the thread reply and in the handoff comment, ends with its owner.

**Proportion.** Before choosing `fix` for a correctness finding, the shaper records how likely and visible the failure is and what the fix costs (files touched outside the PR's diff, new dependencies, rough size). When the cost is out of proportion, the full fix is not the answer: it is `defer`, with a mitigation when a cheap one exists and none otherwise, or `ask` when one of the five cases holds. It is never a decline for its cost alone. A guard the base branch had and this pull request removed weighs toward `fix`.

**A small refactor is done without asking.** A refactor is small when all four hold:

1. Behaviour is unchanged: no existing test's expectation is edited (tests may be added, or follow a rename), and nothing outside the code depends on what moves (a route, a response shape, a config key, a command's output, a column).
2. It stays inside the pull request: every file it changes is one the pull request already changed, or a new file holding code moved out of those, or their tests.
3. It reworks code this pull request wrote: the lines it rewrites are lines the pull request added or changed, plus the call sites of what it extracts in those same files.
4. It is one idea, smaller than the pull request: one extraction, rename, inlining or removal, with a diff smaller than the pull request's own.

A refactor that fails one of the four is deferred, its drafted issue saying which test it fails, or asked about when one of the five cases holds. One that would undo a choice the pull request's own spec records as deliberate is never asked about: the shaper answers it from the spec and declines it with that decision cited.

**A finding the verifier could not confirm** gets the shaper's second look first: it tries what the verifier said would confirm it. Confirmed, the finding is decided like any other. Refuted, it is declined with the evidence. Still unconfirmed, it is fixed when a cheap guard is right whether or not the claim holds, and otherwise declined with `could not confirm: needs <what>`, unless its harm would be serious if it were true: then it is put to you (case 5), with what was tried and what would confirm it, and never declined on Redline's own say. The shaper returns what it found as `secondLook`; the run warns when a finding the verifier could not confirm has none, or when a decline gives `could not confirm` as its reason though the second look refuted or confirmed the claim.

### Overruling a decline

A decline is Redline's judgment, posted with its reason so you can audit it. Overruling one never adds a stop to a run. There are two doors:

- **At a stop the run already makes in that round.** On `guided`, when a round stops for a judgment call, the skill lists what the shaper declined in that round, each with its reason, after the calls. A typed line `<id>: fix. <reason>` (or `<id>: defer. <reason>`) overrules one before you type `relaunch`. This holds at a stop the round reaches before its first resolve has run. A later stop of the round (for the draft of a deferral you chose at the first one, or after the approver bounced the plan: the reshape raised a new call or changed a draft, or its resolve could not apply an answer) lists no declines: the skill says in one line that the round's declines are overruled after the run, by the second door, since an overrule is applied at the round's first resolve, which ran before that stop, and the relaunch could otherwise lose your other answer. On the `plan` dial the list shows every disposition, and a decline can be changed to fix or defer there. Either way the decision is recorded as yours, `decided by: @<login>`, and a correctness finding you overrule to a fix buys the next round. A round with declines and no judgment call does not stop.
- **After the run, or for an earlier round.** Reply in the decline's thread on the pull request, saying what you want, or, for a finding in the review body, which has no thread, submit a pull request review whose body names its id and says what you want (an issue comment is not read), then run `/redline:redline-revise <pr> review @<login>` (or the short `/redline-revise` where the repository has the alias; the handoff comment names the namespaced form, which always works). The human review pass takes your reply as an instruction and makes the change, decided by you. A teammate overrules the same way from their own review, with their own login: the handoff comment's line says the login is whoever replied. Use `review @<login>`: `review latest` leaves out the comments of the person running Redline.

When a run finishes, the session's closing summary lists what Redline fixed and then what it declined on its own, each with its id and reason, with one line on how to overrule one, so you do not have to open GitHub to learn what was declined; under `correctness only` it also names, in one line, what the scope declined. The handoff comment carries the same list under `### Declined by Redline`. A later full run still reads the thread's `declined:` reply as settled, which is right once the pass has fixed it. Finish resolved that thread when the run handed off, so your reply may sit in a resolved thread; the human review pass reads it all the same, since it does not read whether a thread is resolved.

## Deferred items

A deferred item is worth doing and not in this pull request, so it ends in a drafted issue, and the run files it (#95).

- **The draft.** The shaper (or, for a deferral you chose at a stop, the resolve agent) writes a title, what was found, why it is not fixed here and the fix proposed. The workflow composes the issue from those: the title on the first line, then the body, to which it adds the file and line, when the finding names a file, and a last line naming the pull request, the round and the finding (`Deferred from pull request #94 by Redline (round 2, finding R2-3).`). The mitigation is not in the issue; the thread reply carries it. No model or vendor name is in a draft. A deferral you chose comes back from the resolve agent with its draft: one that comes back without it, or with no entry at all, stops the run at stage `resolve`, resumable there.
- **Whether a mitigation shipped.** A mitigation is optional, so no commit is demanded of a deferral: the check never fails for one, and a deferral never stops a round. What shipped is read from the round's record, never from the words of the mitigation, which are shown only beside a mitigation that ships (#100), except in the plan dial's list of the shaper's dispositions, where the shaper's words stand as written beside the files it listed, and the files say whether a task is planned. Before the build the record is the plan: a task with files, listed by the shaper for its own deferral or planned by the resolve agent for one you chose (and, after a bounced plan, as the reshape left that task: "A reshape after your decision" below), and a stop shows a draft with those files. After the build it is the commit: a mitigation shipped when a commit of the finding's own landed, one the implementer reported for the finding or whose subject opens `redline: <id>`; a commit that only mentions the id is not one. With such a commit the reply reads `deferred to #<n>. Mitigated in <sha> (...)` and the commit is reviewed like any fix; without one it reads `deferred to #<n>.`, and the issue is filed all the same. Two warnings in the run's result say when the plan and the commits disagree: `R1-4 planned a mitigation in <files> and no commit of its own landed; posted as shipping nothing` (the task was skipped, or its commit went in under another subject), and `R1-4 has a commit of its own (<sha>) and the shaper listed no files for its task; posted as its mitigation`; for a deferral you or the autopilot chose, it reads `R1-4 has a commit of its own (<sha>) and the resolve agent planned no task with files for it; posted with its decision`. A commit that is not counted is pushed with the round, named in no reply and read by no Redline pass unless something else in the round earns a final nit pass or a next round, whose review range holds it. A mitigation the build left out is not retried: the repair pass runs for a failing check or a fix with no commit, never for a deferral.
- **A deferral you chose at a call.** An answer to a judgment call, yours at a stop or the recommendation autopilot took, names no disposition: it is an option's label or your own words. The resolve agent, which applies it, states what it ends in, one of three: `fix`, a change in this pull request whose commit the check demands, whatever its size (keeping the behaviour and adding a comment is a fix); `defer`, an issue, with a mitigation now or with none; or `accept`, no change. Redline reads the answer's disposition from that statement and from nothing else (#99): an answer stated as a deferral is filed and never has a commit demanded of it, whatever the words of its mitigation say, and one stated as a fix is demanded and files nothing. The statement is checked against what the same resolve planned, before anything is built, filed or posted. One its own plan cannot support stops the run at stage `resolve`, resumable at the resolve step that ran (`resolve r<n>`, `resolve r<n> #<k>` for a call a reshape raised, or `resolve h<n>` in a human review pass), where the resolve agent runs again, told that the stop was the check the workflow runs on what it returned and asked to correct what it wrote, so nothing needs fixing by hand first, and nothing is posted: a deferral with no deferred entry, a fix with no task of its own that names files (one task planned for two calls counts for the call it names), an accept beside a task that names files, or a call with no statement at all. A deferred entry beside a fix or an accept is dropped, so no draft is raised for it and no issue is opened, on any dial, with a warning in the run's result: `the resolve agent listed R1-4 as deferred and stated its decision as fix; the entry is dropped, since the statement decides`. The entry is dropped from the run's list only: the round's `shape.md`, which the resolve agent wrote, can still list the finding under `## Deferred` with its draft, as it can beside a disposition override to fix or accept, so the run's warning and the finding's reply are the record of what the round did (#108, R4-7). A second statement for one call is dropped too: `the resolve agent stated a disposition for R1-4 more than once; the first is kept`. The first is kept whatever it holds: a statement outside `fix`, `defer` and `accept` is no statement, so a first one like that stops the run at stage `resolve`, as a call with no statement does, even when a valid second one follows it. A disposition you changed yourself (`<id>: <fix|defer|accept>. <reason>`) names its own and needs no statement. What it names is checked the same way before anything is built (#108): a fix with no task of its own that names files, or an accept beside a task that names files, stops the run at stage `resolve` as a statement does, and so does a deferral with no deferred entry, unless the round already holds the shaper's own entry for it. One resolve is not held to the fix half: the one a reshape's call sets off for a finding whose disposition you had already changed to a fix. The round reads that finding's task from the plan as the reshape left it, which the stop after that reshape has checked ("A reshape after your decision" below), so that resolve need not plan the task again; a task that names files, planned there for a finding you accepted, still stops the run at that resolve (#114, R4-5).
- **A reshape after your decision.** When the plan approver sends a plan back, the shaper reshapes it, and that can change the task of a finding you or the autopilot decided, a fix or an accepted finding as well as a deferral: move it to other files, add one, or remove a deferral's mitigation. The decision stands, since a reshape's disposition or deferred entry for a decided finding is dropped, but the task is the plan's, so the run follows the plan as reshaped (#106). The reshape is asked for the files of each decided finding's task as `plan.md` now holds it, and the plan approver's next pass and the implementer are shown those files, and so, for a deferral, are a draft at the end-of-run stop and the two warnings above. Before #106 a finding you or the autopilot decided was shown its task as first planned whenever it was shown as a deferral, whether its decision named one (`<id>: defer. <reason>`) or a reshape had re-sorted it to one, and otherwise the shaper's list from before the decision, then the reshape's own. A reshape that lists the same files changes nothing. The mitigation's words beside a draft and in the run's deferred list stay as the resolve agent wrote them for your decision, since the reshape's entry is dropped: when a reshape moves the task, its files and the finding's own commit say what ships. Each change is a warning in the run's result: `the reshape changed the files of R1-4's task, a finding decided by @<login>, from app/x.php to none`. A commit beside a task a reshape emptied is warned about as `R1-4 has a commit of its own (<sha>) and the reshape left its task with no files; posted with its decision`. The reshape is told, as the resolve agent is, that a fix you decided keeps a task of its own and that a task counts only for the finding it names, since the workflow holds the decision to the files the reshape lists for that finding and a reshape returns no list of tasks. The decision is held to its task after each reshape, as it is when the resolve agent first plans it: a reshape that leaves a fix you decided with no task that names files, or gives a finding you accepted one, stops the run at stage `shape`, resumable at that reshape (`reshape r<n> #<k>`, or `reshape h<n> #<k>` in a human review pass), where the shaper runs again, told that the stop was the check the workflow runs on what it returned and asked to correct what the error names and keep the decided entries, so nothing needs fixing by hand first. A reshape resumed after any other stop keeps them too, and is never told to rewrite the folder ("Run markers and resume" below). A deferral is not held, since its mitigation is optional: a reshape that removes a mitigation you asked for is followed, with the warning, and the reply reads `No code change.` You are not asked about that deferral's draft again when only what ships changed, since a draft's version counts its issue text ("A draft that changes is shown again"). A finding left to you under a repository rule is outside all of this: no task writes anything for it.
- **Filing.** After the round's gate has passed and before its push and replies (or, with deferred items raised at the end of the run, when the run finishes), the GitHub agent writes each draft to `<round folder>/redline/issue-<id>.md` and runs `redline-gh.sh defer` for it, which, when the drafts go to GitHub, opens a plain issue with no labels and writes its number into the round's record, `redline/round-<n>-deferred.json`. With the spec folder or print it records the draft's path and opens nothing, and so does a dry run, whatever the setting.
- **Where a draft goes.** One of three places, a launch setting ("Saved launch settings" below): `defer to github`, a GitHub issue, which Redline opens, one per deferred item; `defer to spec`, the round's spec folder, where the draft file is the whole outcome and opening an issue from it is yours; or `defer to print`, the same file, with its title and body printed in the session when the run ends, to paste into another tracker. The draft file is written in every case. `defer to github` needs GitHub Issues turned on in the repository: a repository with Issues off, or one that tracks its work in another tracker, uses `spec` or `print`. Redline does nothing about a project board: a repository that routes new issues onto a board gets a card for each issue Redline opens, which the launch question and the stop both say, and on autopilot those issues are opened with no question. A team that does not want that sets `"deferTo": "spec"` in `.claude/redline.json` ([contract.md](contract.md), "`redline.json`"): it is the option each person is offered first and what a headless run uses.
- **Safe to repeat.** The script opens an issue only when the record holds none for the finding and GitHub holds no issue carrying the draft's last line. A relaunch, a resumed round or a round that ran again is given the number already recorded, so one finding never gets two issues. The lookup on GitHub is the second layer, for a run that died between opening an issue and recording it; GitHub's search can lag by seconds, so it is best effort, and the record is what makes a repeat safe. A filing that fails stops the run at stage `defer`, resumable at `file deferred r<n>`.
- **When you are asked.** On every dial but autopilot you see each draft before it is filed, and say which go ahead. When is a launch setting too (`defer each round`, `defer at end`). With deferred items raised **each round** (the default), the drafts come at the round's stop after shaping, after the judgment calls and the round's declines: one stop for both, and a round with only deferred items stops too. That is the stop this setting adds to a guided run. With deferred items raised at the **end of the run** there is no stop inside the rounds and one stop before the handoff, only when the run deferred something: until then a deferred item's thread has no reply, later rounds are shown the item as deferred from its round's record, so it is not raised again and buys no round, and the handoff and the review request wait for your answer. A run that reaches the round cap stops the same way before its cap-hit comment, and a revise-only pass before its record commit. A human review pass raises its drafts in the pass at either setting, since its threads take one reply per pass. Autopilot asks nothing: each draft is filed as drafted, in its round.
- **What you can do with a draft.** Go ahead: it is filed as drafted and stays `decided by: redline`. A title of your own (`<id>: title. <new title>`): filed under it, the body unchanged. Drop it (`<id>: drop. <reason>`): nothing is filed and nothing else changes, so a planned mitigation still ships; it is posted as your decision (`<your reason> No issue was opened. · decided by: @<login>`) and listed under Overruled in the handoff. A draft of a deferral you chose at a call keeps that decision and its commit first: `<your decision> Applied in <sha> (...). <your reason> No issue was opened.` Make it a fix (`<id>: fix. <reason>`): the existing disposition override, planned and built in the same round as your decision; it is offered at the round's stop after shaping and on the plan dial, where nothing is built yet. At a later stop of the round and at the end-of-run stop a fix can no longer be built: reply in the finding's thread after the run and use `/redline:redline-revise <pr> review @<login>`. With more than three drafts the skill lists them all first, shows every body, and asks once whether to file all as drafted or walk them one at a time; typed lines still name the exceptions.
- **A draft that changes is shown again.** Each draft has a version. An answer stands for the version you saw, so a reshape after a bounced plan that rewrites an answered draft stops the round once more for it, and a deferral you choose at a stop (`<id>: defer. <reason>`), which is drafted after that stop, is shown before it is filed. A stop the round reaches after its first resolve takes no disposition change and lists no declines, as a stop after a bounced plan does.
- **The trail.** The thread reply and the handoff say where the item went, and a later run reads a reply that opens `deferred` as settled (`redline-gh.sh prior-findings`). The draft file and the record reach the branch with the run-record commit, at the end of the run, and stay local with `no push`, as the run's commits do.

## Hand-off and relaunch

The interrupt dial (the README, "Dials") says where the run stops for you. Each level is a stopping point the loop already has:

- **`guided`** (default) stops when the shaper returns a judgment call and, with deferred items raised each round (the default), when it defers an item: both at one stop, after shaping, and a round with only deferred items stops too (see "Deferred items"). The skill shows the calls one at a time, in the order the shaper gave (a call whose options turn on another's answer comes after it). Answer each with a pick from the options, or one line `<id>: <choice>. <reason>`. After the calls the skill lists what the shaper declined in that round, each with its reason, and a line `<id>: fix. <reason>` overrules one, at a stop before the round's plan approver has run (see "Overruling a decline"). Then type `relaunch` on its own. The run relaunches with the decisions in its arguments: every prompt before the stopping point replays from cache, the shaper applies the decisions, and the round goes on. Each decision is recorded and posted as `decided by: @<login>` with your reasoning restated in one sentence, never your typed text.
- **`plan`** stops after shaping, every round, showing every finding's disposition with the shaper's one-sentence recommendation. Approve as is, change a disposition to fix, defer or accept (a decline changed to fix or defer is overruled; a change to `fix` or `defer` for a finding under an ask rule is refused with a warning), answer an ask, or answer a deferred item's draft, which the list shows with the rest; then `relaunch`.
- **`review`** stops after the round 1 review is posted. Pick the findings to act on, then `relaunch`; each one not picked is dropped with a reason, posted in its thread. Later rounds stop as `guided` does.
- **`review only`** stops after the round 1 review; nothing is revised. The run still commits its record, so the tree is clean for the full run that usually follows.
- **`autopilot`** never stops. It files each deferred item's draft as drafted, in its round, with no question.

A disposition you changed (a decline overruled at a stop, or a change on the plan dial) that the run cannot turn into a task comes back at the next stop with the resolve agent's reason, as a decision the stop needs: restate it as `<id>: <fix|defer|accept>. <reason>`, saying what the reason asks for, then type `relaunch`. A relaunch with the same line would only replay the same refusal.

In an interactive session the harness hands the person's last typed message to every agent of a run, verbatim, with precedence over the agent's task; an `AskUserQuestion` pick is not relayed, and a headless session relays nothing. On PR #59 a hand-off answer typed as `Refuse it` reached the GitHub agent that way and it refused to write the snapshot, with the prompt's own sentence against it in hand. So the skill relaunches only from `relaunch` typed on its own (a hand-off, the review dial) or from a line holding only a Redline command (a launch, a resume; the namespaced form or the short alias, #44); a stopped run relaunched in its own session takes either, and the skill refuses any other last line; every agent's prompt names those two as conversational, with `args.decisions`, `args.selected`, `args.approvedPlans` and `args.deferrals` the only authority, as the second layer (#60). Hand-off answers are picks, or one line `<id>: <choice>. <reason>`, restated before anything is recorded.

**What `relaunch` runs on the plugin's own repository (#81).** A relaunch runs the workflow script the run launched with. On every other repository that is simply the installed workflow, which never changes during a run, and the relaunch is by name as it always was. When Redline reviews its own repository from the checkout (`claude --plugin-dir`), a round's commits can change `workflows/redline-loop.js` or an agent file. Replay follows the prompts, so a relaunch that ran the edited workflow would replay nothing after its first changed prompt and rerun rounds already posted (PR #80). So before every relaunch the skill runs `redline-prefs.sh run drift`:

- **The workflow file is as launched:** the relaunch is by name, as anywhere else.
- **The workflow file changed:** the relaunch runs the copy of the script the harness kept at launch (under the session's `workflows/scripts/`), passed as `scriptPath`, so every recorded step replays; the run reviews and fixes the new loop while running the one it started with. The allow rule covers the workflow by name only: in bypass-permissions, which is how the plugin reviews itself, the relaunch is expected to run with no prompt, and in any other mode Claude Code is expected to ask once per relaunch to review the script, but neither has been measured yet: only the headless denial below was (#81). A headless session cannot answer that prompt, so there the relaunch is denied and the skill says to relaunch from an interactive session or start fresh.
- **The workflow file changed and no copy was kept:** a first launch that fell back to `scriptPath` (the workflow's name was not found) ran the file itself. The relaunch is refused with a line naming the file, and the run is finished with a fresh one, whose first round carries the open findings forward.
- **An agent file changed:** agent files cannot be pinned, since an agent run from a copy has no role and so no guard. The relaunch goes on, the skill says `Agent files changed since this run launched (...): this run's remaining rounds may run under them, while the workflow's own prompts are the launch's.`, and the handoff comment says the same in the past tense, since it is posted after the last round (`Agent files changed during this run (...): the rounds after the change may have run under them, while the workflow's own prompts were the launch's.`), so the teammate knows the later rounds ran under instructions the run itself edited. The list the comment names is read at a hand-off or a review-dial stop, both before Finish. A resume after an error or a stopped run keeps the list the run already passed (`run drift` prints it so, and the skill's line still names every changed file), since such a resume can rerun Finish from a step after the comment posted: a changed list would change the comment, so it would be posted a second time and review requested again (#91, R1-1). Agent text is not part of what replay matches, so an edited agent file never makes a recorded step rerun.

Claude Code read the agent files and the named workflow once, at session start, when this was measured (headless, under `--plugin-dir`, 2.1.322), and read them again when the session was reopened with `claude --resume`; whether an interactive session reloads them mid-session was not measured, and nothing above depends on it.

## The handoff comment

When a round buys no further round (see "Rounds", step 7), the run finishes. With deferred items raised at the end of the run, it first stops once for the drafts it held, before anything below (see "Deferred items"); after the relaunch it goes on from here, and files those drafts and posts their replies right after the read of the highest posted round. First the GitHub agent reads the highest Redline round posted on the PR (`redline-gh.sh last-round`), and a run that is finishing from a lower round stops there with an error naming both rounds and saying to start a fresh run, before anything below is posted, since a round that re-ran can come back clean while later rounds are open (#81; the cap-hit comment and a human review pass's summary are held to the same read, and a dry run, which posted nothing, goes on). Then the PR description is redrafted when the repository has a standard for it (the previous one stays in the description's edit history, and a copy is kept under the round's `redline/` folder), the threads Redline opened for settled findings are resolved, the **Redline handoff** comment is posted, review is requested from the configured reviewer, and the run-record commit is made and pushed.

The comment opens with how the run ended, then groups every item of the run by what became of it. A heading with nothing under it is left out. In order:

- **The opening sentence.** How many rounds ran and how the last one ended: it verified no new correctness item to fix or ask about; or none beyond low-severity bugs in the previous round's fixes, which are handled like nits, and it committed no fix; or it was a final nit pass, with what that pass read named (the nit fixes, or a round's fixes) and what it found counted (how many correctness items, how many of them a commit fixed and so went unreviewed, how many were not changed), and never a word saying an item was fixed when it was declined. With the coverage pass, every round but a final nit pass reviewed the whole PR at its head; with `coverage off`, only round 1 did; a link to Known limits in the README says what that means.
- The threads line, the description note, the agent-files sentence when agent files changed during the run, and `@<reviewer>, over to you for the human review`.
- `### Rounds`: one line per round with what became of its items (`13 items: 8 fixed, 3 declined, 1 put to @<login>, 1 left to @<login>`), its commits, whether you approved the plan, and the spec folder.
- `### Put to @<login> (n)`: the judgment calls you answered, and a decline you kept on the plan dial with `accept` and your reason, each with your decision restated and whether it was applied. On autopilot the heading reads `### Asked, decided on autopilot (n)`.
- `### Overruled by @<login> (n)`: a disposition you changed at a stop, a decline you overruled included (an `accept` that keeps a decline is not an overrule).
- `### Declined by Redline (n)`: what Redline decided not to act on, each with its reason, under one line on how to overrule one. An item the verifier could not confirm has no heading of its own: it sits under what became of it, and a decline for want of confirmation reads `could not confirm: needs ...`.
- `### Declined under this run's scope (correctness only) (n)`: on a `correctness only` run, what the scope declined; on any other run, `### Declined under the final nit pass's scope (correctness only) (n)`: a nit the final nit pass's reviewer reported though that pass reports correctness only.
- `### Deferred (n)`: every item that ended in a drafted issue, with where it went (`deferred to #123; mitigated in <sha>`, or `deferred; the issue draft is at <path>`); a deferral you chose reads as your decision and ends `Deferred to #123.` Then `### Left to @<login> (repository rules)`, each line with the rule, its reason, your decision and, on autopilot, what Redline would have done; the heading reads `(Redline's own files)`, or `(repository rules and Redline's own files)`, when it lists findings on Redline's own files.
- `### Not picked by @<login> (n)` on the review dial, and `### Not changed (n)` for a fix that did not land.
- `### Fixed (n)`: folded, one line per item with the commits that fixed it (one item can have two, and two items can share one).
- `### Earlier rounds` (see below), the set-aside block of the last round that ran the coverage pass (the round before a final nit pass, else the last round), under `### Candidates set aside in round <n> (N)`, which names that round, since earlier rounds' blocks stay in their own review bodies (#85), and `### Commits`. With `push` off it says the commits are local only.

The person running Redline is named by login in every line, never by role: on a teammate's pull request the person running Redline is not its author. With no login, the lines say "the person running Redline".

The handoff comment lists every decision of the run, the ones Redline made alone included, and one line about the threads: `Resolved n threads; m left open: <finding ids and why>`. Redline resolves a thread it opened once its finding is settled (fixed, deferred with its drafted issue filed, declined by Redline with its reason, or decided by the person and applied) and its reply is posted; a thread a teammate opened or commented in, before or after Redline's reply, is theirs and stays open, as does a finding the person dropped. An earlier thread whose carried finding a `correctness only` run declined under its scope stays open too, named `declined under the scope`: it gets no reply, so a later run without the scope sees the finding fresh. A dry run or a `no push` run resolves nothing, and the line is absent. The shaper's JSON carries `decidedBy` per finding (`redline` or `pending`; `reviewer` for a fix in a human review pass); the workflow fills `@<login>` from `args.login` for the answers a person gave and `@<reviewer login>` for the teammate's instructions.

## Decided by

Every decision is posted with its owner. Each Decision in a round's `shape.md`, each reply in a finding's thread, and each item line the handoff comment lists under an outcome heading (Put to, Asked and decided on autopilot, Overruled by, Declined by Redline, Left to, Not picked, Not changed and Fixed; see "The handoff comment" above) ends with one of:

- `decided by: redline`: the shaper settled it from the evidence (a fix, a decline with its reason, a defer, an answer the PR description or the code already gave);
- `decided by: @<login>`: a person decided it at a hand-off (the login `redline-gh.sh login` prints), with their reasoning restated in one sentence. What they typed is a pick from the shaper's options or one line `<id>: <choice>. <reason>`, and the relaunch is the typed word `relaunch`; the restatement is what is recorded and posted, never the typed text;
- `decided by: redline (autopilot)`: the run took the shaper's recommendation on autopilot;
- `decided by: @<reviewer login>`: a teammate asked for the change in their review, and a human review pass (`/redline:redline-revise <pr> review ...`) made it as asked.

## Earlier rounds

A fresh run on a PR that already carries posted Redline rounds (a dry run posts none, so it is never an earlier round) reads every finding those rounds posted and its disposition before launching (`redline-gh.sh prior-findings`, passed as `args.priorFindings`), from the Redline reply in the finding's thread (or the issue comment behind its marker, for a finding in the review body): `fixed`, `declined` by Redline with its reason, `deferred`, `decided`, `dropped` by the person on the review dial, `left` to the person under a repository ask rule, or `carried` into a later round. A scope decline is none of these: it has no thread and no reply, so a later run without the scope sees the code fresh. A `resolved; first reported as` reply, which a later run posts on an earlier finding its reviewer found the code no longer has, reads as `fixed`: it is Redline's own claim that the bug is gone, the claim a fixed reply makes, not a decision a person made, so a coverage candidate that still reproduces it is new, as one that still reproduces a fixed finding is (#80, R4-3). A finding recorded is not one handled: a finding with no reply (a `review only` round, a run that stopped after posting, a hand-off never relaunched) or with a `not changed in this round` reply (a fix that never landed) has no disposition, and the new run's first round carries it forward. The reviewer re-verifies each one against the current head, never copies it, and either reports it as a finding of the new round, under `### Carried forward from earlier rounds` in the review body with `first reported as R1-2` on its line and in its inline comment, or lists it under `### Resolved from earlier rounds` when the code no longer has it. A finding the reviewer accounts for neither way is carried by the workflow as reported, with a warning, never dropped. A carried finding then goes through shape, approve and fix like any other; when it is settled, dropped or not changed, its earlier thread gets one reply from the new round (`Redline round 2: carried forward as R2-1; fixed in abc1234 (...) · decided by: redline`), as does a resolved one (`Redline round 2: resolved; first reported as R1-4 in Redline round 1. <why> · decided by: redline`), and Finish's sweep resolves that thread beside the new one. A finding with a disposition is matched into `knownAs` (`R1-1: fixed`) and never re-raised. A carried finding that an issue or a teammate's comment already tracks keeps the author's choice. It stays under `### Already tracked` with `first reported as R1-2` on its line and is not shaped. Its earlier thread gets `Redline round 2: carried forward as R2-1; already tracked in #41 · decided by: redline` and stays open as `already tracked`, and the next run reads that reply as carried. A `knownAs` naming a Redline id on a carried finding is cleared with a warning, and the finding is carried (#46, R1-2). The handoff comment's `### Earlier rounds` section says what became of each: `carried forward as R2-1: fixed in ...`, `resolved: ...`, `carried forward as R2-2 in round 2` for a finding an earlier run already carried (#46, R1-5), `carried forward as R2-1: already tracked in #41` for a carried finding an issue tracks (#46, R1-2), or `already handled in round 1: ...` (#35).

## Saved launch settings

`.claude/redline.local.json` in the repository (ignored by git, so per person per repository) remembers six settings: `interrupt`, `revise` (the model id), `maxRounds`, `scope`, and the two for deferred items, `deferAt` (when their drafts are raised with you: `round` or `end`) and `deferTo` (where a draft goes: `github`, `spec` or `print`) ([contract.md](contract.md), "`redline.local.json`"; what the two do is under "Deferred items" above).

- **No saved file.** The skill asks for every setting not typed on the command line, in two questions, since one takes four fields: first the dial, the revise model, the rounds and the scope, with the defaults first (guided, Opus 5.5, 3 rounds, all); then when deferred items are raised (each round first) and where their drafts go (the repository's `deferTo` first, marked as the repository's default; a GitHub issue when `redline.json` sets none). A `review only` run asks only for the scope, since no revise agent starts and nothing is deferred. An `autopilot` run is asked where the drafts go and never when, since it files each draft in its round and asks nothing.
- **A saved file.** One confirm question whose first option reads `Run with: <interrupt> · <model> · <N> rounds · <scope> · <deferred each round|deferred at the end> · <drafts to GitHub|drafts to the spec folder|drafts printed>` (a value typed on the command line overrides the saved one and is marked `(command line)`; a deferral setting that does not apply to the run is left out), and whose second option, "Change something", re-asks the fields that were not typed, in the same two questions. A file that lacks a deferral setting the run needs (it was saved before the two existed, or only by `review only` or `autopilot` runs) is asked for it beside the confirm, once: the confirm line then holds the settings the file has.
- **Whatever the run uses becomes the saved set**, however it was chosen, except `autopilot` and `review only`, which are never written: the previous saved interrupt stays. A deferral setting that did not apply to the run is not written either (both under `review only`, when under `autopilot`), so the next run it applies to asks for it.
- **The words.** `defer each round` and `defer at end` set when; `defer to github`, `defer to spec` and `defer to print` set where. Typed, they hold for the run and become the saved values, like any other setting. A headless run (`claude -p`) asks nothing: it takes the command line, then the saved file, then the defaults, which for `deferTo` is the repository's, else a GitHub issue. It still stops where its dial does: on every dial but `autopilot`, at a judgment call and at a round that defers anything (with `defer at end`, once before the handoff), since each draft is shown before it is filed, so a headless run that must not stop uses `autopilot`.
- **A hand-off relaunch asks nothing** beyond the calls themselves and the typed `relaunch`.

The merge rules live in `scripts/redline-prefs.sh` (`resolve` prints the effective settings, what to ask and the confirm line; `save` writes the file and keeps its other keys), and `tests/prefs-test.sh` is their unit test. The same file holds `runs`, one marker per PR for a run that stopped (see "Run markers and resume" below): `redline-prefs.sh run save <repoRoot> <pr> --run-id <id>` writes it from the harness's own record of the run, `run read` prints it, `run check [--plugin <dir>]` says whether the run can be resumed from here and why not, `run drift [--plugin <dir>]` says which script a relaunch runs and which agent files changed since launch (see "Hand-off and relaunch"), and `run clear` removes it. The file is one of Redline's own: the guard refuses it for every role, and only the skill writes it, through the script.

## Run markers and resume

Every stop leaves a marker under `runs` in `.claude/redline.local.json` (#10): a hand-off, the review dial, a run the harness stopped, and an error at a stage a rerun can recover from. The skill writes it with `redline-prefs.sh run save` from the harness's own record of the run (the run id, the session id, HEAD, the branch, the stage and agent label, the error, whether the stop was Redline's own check of what an agent returned, the spec folders and the args as launched). The next `/redline:redline <pr>` offers to resume it or start fresh, naming the stage and the error. It asks before anything else, and a resume keeps the run's original settings: the settings question is not asked, and words typed after the PR number are named and ignored. Resume runs `redline-prefs.sh run check` first and stops on its line when the marker's session is not this one (the harness replays only from the session that launched the run; the line prints `claude --resume <session id>`), the branch is not the PR's, HEAD is neither the run's last commit nor on top of it, the run stopped other than with an error and HEAD moved at all (only an error resume carries a hand commit into the workflow), the commits on top touch a path outside `.claude/` (a fix to the gate's `checks.json`, `redline.json` or `settings.json` is expected after an error; a fix to the code under review is a fresh run), the repository under review is the plugin itself and HEAD moved at all (a plugin fix changes what runs, so the next round carries the findings forward), or an untracked or modified path sits outside the run's spec folders (the folders its result lists and every folder its launch stamp names for the PR, so the start snapshot and a round not yet recorded count as the run's). Then it relaunches with the marker's args plus `resume`, one entry for the agent label the error named (`coverage r1`, `recheck r1`, `shape r1`, `handoff comment`), and the workflow appends one resume line to that agent's prompt: a cached result replays unchanged even when the workflow rejected it, so the prompt has to change, and everything before it still replays from cache while that agent and all after it rerun. A hand commit under `.claude/` rides along in the entry: the checker's verdict excuses its paths and its commit, and the next round's snapshot allows the paths. A second resume at the same step keeps the earlier resume's hand commits: `run check` prints the list with the label's earlier entry merged in. Some stops need no hand fix at all: the ones that are the workflow's own check of what the step's agent returned, which the step corrects when it runs again. They are the resolve agent's checks ("A deferral you chose at a call" above), the hold of a decided finding to its task after a reshape ("A reshape after your decision" above), and the shaper's checks of its own result: a finding without a disposition, an ask without a judgment call or a call for a finding sorted otherwise, a reason outside the cases a person is asked in, a decline with no reason, a deferral with no drafted issue, a value that belongs to the other kind of pass. The error result says so in `ownCheck`, and the skill then tells you that nothing needs fixing by hand and that `/redline:redline <pr>` resumes the step as it stands; for every other stop it says to fix the cause first. The marker carries the field into the resume entry, where the workflow reads it to choose what the rerun is told, and it never reads the error's words for that (#116). A missing `plan.md`, `shape.md` or Decisions section is not such a stop, since a file can be missing because a Write was refused, which is yours to fix. A marker written before the field existed holds none and resumes as an ordinary stop. A resume at the shape stage reruns the shaper, which never touches `redline/`. At a round's first shape (`shape r<n>`, `shape h<n>`) it rewrites the four spec files: nothing you or the autopilot decided can be in the folder yet. At a reshape after a bounced plan (`reshape r<n> #<k>`, `reshape h<n> #<k>`) it never rewrites them, since the folder can by then hold the entries and tasks written for your decisions (#117). After a stop that is the workflow's own check of what the reshape returned, the hold of a decided finding to its task ("A reshape after your decision" above) or a check of its result, it corrects what the error names and keeps the decided entries. After any other stop, a missing spec file or a call that returned nothing, it reads the four files as they stand, keeps the decided entries and their tasks, and writes again what is missing; an entry of yours the folder no longer holds is named in `shape.md` as lost, never written back from memory, since the reshape is told which findings you decided and what each decision ends in, not your words. After shaping, the GitHub agent's read-only `spec-status` operation lists the spec folder's four files and greps `shape.md` for its Decisions heading with two `git grep --no-index` lines; a missing `plan.md`, `shape.md` or Decisions section, a finding without a disposition, or an ask without a judgment call (on a reshape after a bounced plan, one the round has not already decided: the reshape returns only the calls still pending or newly raised) is an error at stage `shape` with `resumeFrom` the shaper's label, and no judgment call is invented for it: the run stops, the review stays posted, and a resume reruns the shaper (#57; the one call the workflow writes is the repository-rule ask). The record folder holds only what the run wrote: a note or a draft a person adds goes outside the repository, since the record commit and the resume's untracked-path check read the folder as the run's. A resume at the closing comment first looks for the comment an earlier attempt posted, and one at the record commit for the commit an earlier attempt made, so a request-review or a push that failed after them is retried without posting or committing twice. A `gather` error (the head moved since launch, the PR is not open, the branch is wrong) is not resumable: the error result says so and the next launch is fresh. `review only` and revise-only runs end with the run-record commit like a full run, so an error after one of them leaves nothing untracked.

## The run record

Everything a run writes into the repository sits under `agent-os/specs/`, inside every allowed list, and is committed as the run's record. Each round's spec folder (`<launch stamp>-<pr>-review-round-<n>/`, or `-human-review-<n>/` for a human review pass) holds the four spec files and a `redline/` subfolder with the round's review and findings as posted, the replies, each deferred item's drafted issue (`issue-<id>.md`) with the record of where each went (`round-<n>-deferred.json`), the round snapshot, and, in the first round's folder, the start snapshot ([contract.md](contract.md), "Snapshot file"). The round makes the spec commit, one commit per finding, the standards commit when there is one, and the as-built commit; a run that finishes makes one more, the run-record commit, which stages by name every file under the `redline/` folders that no commit holds yet (the replies, the closing comment, the description's backup, the ingested human review) and commits them as `redline: record the run's replies, reviews and handoff for PR #<pr> (#<issue>)`. A `dry run` writes every body under the round's folder, posts nothing and pushes nothing: its commits, the record included, stay on the local branch until you drop them before the next launch (see "Launching a run" above). The git rules the agents follow are in the README under "Git rules for Redline agents", the one section of it written for them.

## How the review is posted

The GitHub agent posts through `redline-gh.sh` ([scripts.md](scripts.md)), and follows these rules around it:

- Check `has-review <n> <round>` before `post-review`; a hit means the round is already posted and the post is skipped.
- Inline comments must sit on a line in the PR diff (an added, removed or context line of a hunk of that file's patch). GitHub answers `422 Unprocessable Entity` with `Line could not be resolved` and posts nothing, not even the valid comments, and the answer names no path or line. So `post-review` runs `place` first: every comment off a hunk is moved into `body` under "Not placed inline" behind `<!-- redline:<id> -->` before anything is sent, and the output's `moved` says which. The agent reports them as `movedToBody`. A file's hunks are its patch in the files listing. GitHub leaves that out of a text file whose patch is over about 100 KiB and still takes a comment on its lines, so for a file a comment names the hunks are then read from GitHub's whole-PR diff (one call, on a PR of 300 files or fewer) or, failing that, from a `git diff` of the merge base against the head in the clone (#96). The moved comments are grouped under one line per cause: the file is not in the pull request, the line is not in its diff, the file is binary, it was renamed with nothing changed, GitHub takes no comment on a diff this large, or the file's patch could not be had. The too-large cause is learned by posting: GitHub refuses the whole review with a 422 naming the file, and `post-review` moves that file's comments into the body and posts again, once per such file. Any other 422 on a review that placed a comment through the whole diff or the clone is answered once, by posting from the listing's patches only, with the rest in the body under GitHub's message. Both are a posted review and exit 0, with one line on stderr each; a refusal after that, or with no such comment, fails as before. A posted review with no inline comment at all is a degraded result the workflow records as a warning, never an error.
- A finding in the body has no thread, so its reply is an issue comment (`comment`) whose first line is the finding's marker, then `**<id>** · \`file:line\` · from the Redline round N review body`, then the reply, when the round's review is on GitHub; in a dry run, or a revise over a review that was never posted, the reply is written to its file and nothing is posted. One per finding, never twice. To check whether one is already posted, the agent looks for that second line in `pr-comments`, never for the marker, which the review body also carries.
- **What is escaped and neutralised (#87).** The finder's and the verifier's free text goes through one function where the workflow posts it:
  - a finding's title: on its line in the review body and the cap comment, in its inline comment, and on every handoff line that names it (each list by outcome, Deferred, Left to the person, Earlier rounds);
  - the review's summary;
  - the line saying what would confirm a finding the verifier could not confirm, in the review body and in its inline comment;
  - a scope-declined line's title;
  - Already tracked lines (title and `knownAs`);
  - Resolved from earlier rounds (title and why);
  - the `knownAs` and the why on Earlier rounds lines;
  - the set-aside block's lines;
  - the body of a deferred item's drafted issue, field by field (what was found, why it is not fixed here, the fix proposed), though those are the shaper's words: an issue is read by people who never saw the pull request, and a tag or an `@word` in it would land in a new place (#95). The shaper and the resolve agent are asked to write each of those fields as one paragraph with no line break, since a field with one is escaped whole, as below, and a code span in it would show the entity (#97, R3-3). Its title is the exception the other way: GitHub shows an issue title as plain text, decoding no entity and linking no `@word`, so the title is filed as written, made one line, with control characters removed and cut to 256 characters.

  Outside code spans, `&` becomes `&amp;`, then `<` becomes `&lt;`, and `&#8288;` goes after every `@` that comes before an ASCII letter or digit. That is the word joiner (U+2060) written as a numeric character reference: GitHub decodes it before it looks for mentions and shows the invisible joiner. So a tag reads as text, a `@click` or a `@param` mentions nobody, and the text reads as written. The reference is plain ASCII, so it survives the GitHub agent's copy of the body into a file with the Write tool; a raw joiner the agent dropped would make the mention live again with no sign. GitHub still links `\@x` and `&#64;x`, so neither is used.

  A code span is left as written, since GitHub shows a span literally. The exception is a text that holds `](`, `][`, `://`, `www.` (any case), a backslash before a backtick, a carriage return or a newline. There GitHub can read a backtick as part of a link, or as escaped, before it pairs spans, so the whole text is escaped, spans included, and a span holding `<`, `&` or `@x` then shows the entity (`&lt;`, `&amp;`, `@&#8288;x`). A summary with a newline is one such text. A backslash anywhere else, as in a namespace (`App\Models\User`), changes no pairing, so that text keeps its spans as written; outside a span, a backslash typed before `<` or `&` shows the entity text (`\<b>` reads `&lt;b>`). A bare URL holding `@x` shows `&#8288;` too, and its link breaks, though an `@` inside an autolink is never a mention. An inline link whose destination holds `@x` keeps its text, but its href gets the joiner after the `@` (`%E2%81%A0`), so the link looks right and leads to another page. Fields that share a line are read as one text.

  What the workflow writes is posted as written, so `@<reviewer>, over to you for the human review`, `decided by: @<login>` and the headings and lines that name the person by login still notify. So are:
  - the shaper's, the person's and the implementer's words (a mitigation, a full fix, a decision sentence, a commit subject);
  - an inline comment's description and proposed fix;
  - every reply.

  The reviewer, shaper, resolve and implementer agent files ask for every identifier that begins with `@` in backticks, since their text reaches GitHub in comments and replies (see Known limits in the README). A later run reads a title back through `prior-findings` as it was posted, and decodes it once at launch: the `&#8288;` after `@` is removed, then `&lt;` and `&amp;` are decoded. So the reviewer reads the title as written, a `@&#8288;` the finder typed included, and a carried title is escaped once, never twice.
- The `comments[].id` values printed by `post-review` are what `reply` takes; keep them in the round's record. The `id` each `reply` prints is kept too: Finish's sweep names a thread by that pair, and `resolve-threads` resolves nothing with a comment that is not one of them.
- The sweep is the workflow's selection and the agent's one call, as the run-record commit is: the workflow lists the settled findings' ids, the agent runs the one `resolve-threads` line it is given, and the script skips whatever a teammate opened or commented in. The handoff comment then says `Resolved n threads; m left open: <ids and why>`; a human review pass's summary says the same of its final nit pass's threads, and a capped run, a dry run and a `no push` run sweep nothing.
- **What a watcher is notified of.** A round's review is one notification, with every inline comment in it. Each reply is its own post, so each is its own notification, and since every finding Redline decides has a thread, a round with a dozen findings sends a dozen; a reply to a finding in the review body is an issue comment, one more each. The handoff comment and the review request are one each. An issue Redline opens for a deferred item is a new issue of the repository, so GitHub notifies whoever watches the repository's issues, as it does for any new issue, whether or not they follow the pull request. Anyone subscribed to the pull request receives them: the teammate once review is requested or once they comment, so on a later run or a human review pass, and someone watching the repository from round 1. GitHub's API can deliver a round's replies as one notification (a pending review that holds the replies, submitted once); Redline does not do that yet (see Known limits in the README).

## A human review pass

`/redline:redline-revise <pr> review <id | @login | latest>` is the pass after the hand-off: a teammate's review comments become the findings (`H<n>-<k>`, one pass per launch, numbered after the `Redline human review` passes already on the PR). `review @login` takes every inline comment by that login (matched in any case) that no Redline reply has answered yet, replies inside Redline threads included, plus the newest of their review bodies that no Redline human review comment has answered yet (one body per pass, so an older one comes up on the next pass); `review <id>` takes that review's unanswered comments and its body, unless a Redline human review comment has already answered it; `latest` is the newest review that is not Redline's, not the author's, and still has an unanswered comment or body. A clear instruction is fixed, `decided by: @<login>`; a question, a disagreement or a comment the shaper cannot turn into one change comes back to you as a judgment call with the comment quoted, and the reply says what you decided; a comment that asks for nothing gets "no change requested". Nothing a teammate asked for is deferred by Redline on its own; a deferral you choose at a hand-off there is filed like any other, into the pass's own record (`human-review-<n>-deferred.json`), and the summary line says where it went. After the fixes are pushed and every thread answered, the reviewer reads the fix diff once as the next `Redline round` when the pass committed a fix (a pass that committed only its spec folder has no fix diff, runs no such round, and its summary says so), what it finds goes through the round's shaper once more, and the pass ends with one summary line on the PR, which counts what that pass found and what a commit fixed, names each item it deferred with where it went, and never says an item was fixed when it was declined or deferred: no handoff comment, no review request, the teammate is already there. The interrupt dial applies; the scope does not.
