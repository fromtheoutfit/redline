# A run, start to finish

What happens between typing `/redline <pr>` and the handoff comment: the precheck, the rounds, how each finding is dispositioned, where the run stops for you and how it relaunches, what it posts, and what it leaves in the repository. The dials themselves (interrupt, scope, rounds, models) and their defaults are in the README; the files a run reads are in [contract.md](contract.md).

## Launching a run

Check out the PR's branch, clean, at the pushed head, and type the command from a message that holds only the command:

```
/redline 21
/redline-revise 21 review @sam
/redline:redline 21
/redline:redline 21 max 2 rounds
/redline:redline 21 revise fable no push
/redline:redline 21 reviewer @sam
/redline:redline 21 autopilot
/redline:redline 21 plan correctness only
/redline:redline 21 review
/redline:redline 21 dry run review only
/redline:redline 21 coverage off
/redline:redline-revise 21 review @sam
```

The short forms are two project command files, `.claude/commands/redline.md` and `.claude/commands/redline-revise.md`, that `/redline:setup` writes from the plugin's `templates/command-redline.md` and `templates/command-redline-revise.md` (its step 12, default yes; a rerun shows a changed one as a diff and asks, and leaves a file of that name that is not Redline's alone); each is a one-line command that invokes the namespaced skill with the arguments typed, so the namespaced form always works, and `/redline:redline-review` has no short form (#44). The words can come in any order. `dry run` posts and pushes nothing: every body is written under the round's spec folder instead, and the PR may be closed (a seed). Its commits stay on the local branch, unpushed: the round's spec commit, one per finding, and the run-record commit, so a `dry run review only` leaves exactly one commit, the record, and nothing on GitHub. Those commits put HEAD ahead of the PR's head, so the next launch stops at the precheck (`pull or push so HEAD matches the PR`) until they are gone. Do not push them: copy the round's spec folder outside the repository if the review is worth keeping, then drop them with `git reset --hard origin/<branch>`. Because nothing was posted, the next `/redline:redline <pr>` then finds no Redline round on the PR (`redline-gh.sh last-round` reads the posted reviews) and starts at round 1 with no carried findings: a dry run's review is a record, kept only where you copied its spec folder, not a round the next run continues. The first launch in a repository asks for the settings it was not given on the command line, and later launches confirm the remembered ones in one question; see "Saved launch settings" below. `/redline:redline-review` and `/redline:redline-revise` are the two halves on their own, for debugging. `review only`, read the review, then `/redline:redline <pr>` is the expected path: the review-only run commits its record, so the tree is clean for the next launch, and the full run's first round carries every finding of the review-only round that has no disposition (see "Earlier rounds" below; a posted round only, never a dry run's), so no separate revise launch is needed; `/redline:redline-revise <pr> round <n>` over that round stays as the manual path.

## Precheck

`/redline:redline <pr>` is typed in an interactive session whose working directory is the repository root: the guard approves git only there, for the roles and the session alike (#54). The workflow runs in the background and the session waits for it. The precheck prints the PR's file count from GitHub and warns when the local diff against the base counts differently; above 300 files it warns that GitHub's whole-PR diff is unavailable there (Redline reads per-file patches instead, so inline anchoring still works, except in a file whose patch GitHub omits), and above `maxFiles` in `redline.json` it refuses. A PR that already carries posted Redline rounds gets its next number: the precheck reads the highest posted round (`redline-gh.sh last-round`) and the run starts after it, so every finding of the new run gets its own review and threads instead of being skipped as already posted; it then reads what those rounds posted and how each finding was answered (`redline-gh.sh prior-findings`), so a finding with no disposition is carried into the new run's first round instead of being skipped as already known (see "Earlier rounds"). A headless session (`claude -p`) stops background tasks ten minutes after its last turn, which kills a run mid-phase, so it is started with `CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS=0`. A run the harness stopped is resumed from the session that launched it: the skill relaunches with byte-identical `args`, no new `decisions`, and `resumeFromRunId` set to the run id; finished agents replay from cache and the interrupted one reruns. A hand-off relaunch works the same way, adding only what the stop asked for (`decisions`; `approvedPlans` for the plan dial; `selected` for the review dial), so every prompt before the stopping point replays from cache.

Before any of that, the precheck runs `redline-gate.sh check` (the gate stamp in `checks.sh` still matches the repository's Verification Gate; a moved gate or a missing stamp stops the launch with the script's one line) and `redline-setup.sh version` (the contract's versions: `checks.sh`'s template line, the unattended section's marker, `settings.json` against the allow-list template, and whether a self-hosted run loads in place; warnings only, each saying to rerun `/redline:setup` or to start the session with `claude --plugin-dir`), checks `gh`'s version and login, and writes the start snapshot ([contract.md](contract.md), "Snapshot file"). A session that loads the plugin from a directory, as `claude --plugin-dir` does for the plugin's own self-review, gets one more warning, on a fresh launch and on a resume, and never a stop: in auto mode Claude Code refuses the Redline agents' file writes with no verdict, and the run fails at its first file write, normally its first post; run such a session in accept-edits and approve each prompt, or in bypass-permissions (#76). Bypass-permissions also removes the coverage pass's permission prompt, the one check the guard cannot provide; a fresh launch with `coverage off` runs without the pass.

## Rounds

Each round is one pass of the loop, numbered from the highest round already posted on the PR plus one:

1. **Review.** Every round but a final nit pass opens with the **coverage pass**, the finder: the built-in `code-review` skill, run from a plain workflow agent over the whole pull request at the round's head, at the configured effort with every finding reported (see "The coverage pass" below). The **reviewer** is the verifier: it applies its rules to each candidate (collapse by cause, the known-finding check, reproduction, a line inside the diff, the two guards), on a later round still rechecks the previous round's fix diff, and returns findings, each with an id (`R1-4`), a file and line, a category (`correctness` or `nit`), a severity, a confidence, a description and usually a proposed fix, plus `### For the person`: what it would not act on but the teammate should see, one line each, never shaped or fixed, and after it, under its own heading, a collapsed block listing every candidate it set aside (collapsed, already tracked or dropped), with its outcome and ref (see "The coverage pass" below). A finding an open issue or a teammate's comment already tracks in full is reported as `already tracked`, never fixed; when one tracks only part of a candidate, the part it lacks is judged on its own, and a part whose cause is in this PR's diff is a finding that names the issue unless another of the verifier's rules puts it elsewhere, as it would any candidate (#85; #86, R2-1). With `coverage off` the reviewer alone reads the whole diff in round 1 and the fix diff after, as before the pass existed; a final nit pass is always the reviewer alone. The GitHub agent posts one review per round (`Redline round N`, the `COMMENT` event): one inline comment per finding on a line of the PR diff, and a body that lists them; a finding in a file whose patch GitHub omits goes in the body behind a marker (see "How the review is posted").
2. **Shape.** The shaper runs the repository's `/agent-os:shape-spec` in unattended mode ([contract.md](contract.md), "The unattended section") and writes a spec folder, `agent-os/specs/<launch stamp>-<pr>-review-round-<n>/`: `plan.md` (one task per finding), `shape.md` (every decision with its owner, the proportionality notes, the proposed standards edits), `standards.md` and `references.md`. It sorts every finding (see "Dispositions") and returns the judgment calls it could not settle.
3. **Approve.** The plan approver reads the plan against the findings, the repository's standards and the ask rules, and passes it or sends it back with reasons; a bounced plan is reshaped, up to `maxPlanAdjustments` times, then the run stops. The standards approver approves the proposed standards edits. The GitHub agent then writes the round snapshot with every approved path ([contract.md](contract.md), "Snapshot file").
4. **Implement.** The implementer makes the changes in the plan's order, one commit per finding (the README, "Git rules for Redline agents"), runs the gate through `checks.sh` after each, and applies the approved standards edits in their own commit.
5. **Check.** The checker runs `checks.sh` with the round's snapshot (the whole gate, or only its git block when `checker` is `git-only`) and returns the JSON. The workflow decides pass or fail from the data: each check's exit against the baseline the run took before its first implement step ("tests pass" means no failure the baseline did not already have), the git block (no file changed outside the approved plan, nothing uncommitted outside `agent-os/specs/`) and the exit code. A failing round goes back to the implementer with the failing checks and git-block findings; a result the implementer cannot change (unreadable, exit 2, no git block) stops the run at stage `check` naming the cause and the fix.
6. **Push and reply.** The GitHub agent pushes once (when `push` is on), then replies in each finding's thread with what became of it and its owner (see "Decided by"): `fixed in <sha> (...)`, `mitigated ...; the full fix is deferred and listed in the Redline handoff`, `not acted on in this run.` for a finding you dropped on the review dial, `not changed in this round.` for a fix that did not land, `left to the author under repository rule <id> (...)`.
7. **Re-review.** The next round runs the coverage pass again over the whole PR at the new head, and the reviewer rechecks the fix diff beside the candidates. A round whose verifier confirms no new correctness finding is the last, where new means not collapsed into a finding already reported, settled in an earlier round, carried forward or tracked elsewhere in full (the part an issue or a teammate's comment does not track is judged on its own, #85); a candidate that matches a finding marked fixed but still reproduces at the new head is new, reported with the earlier id named, so a fix that did not fully land runs one more round under `maxRounds`. A decided finding stays settled whatever its commits, since an applied decision is often a deliberate keep or mitigation: a candidate that still reproduces one is listed under For the person, naming the earlier id, in the review and the handoff, and the run still ends (#80, R3-4). With scope `all`, a round that fixed only nits ends in one final nit pass over the nit fixes; with `correctness only`, a round with nothing new is done. With `coverage off` the next round reviews the fix diff only and a round whose review finds no correctness bug is the last.

The round cap (`maxRounds`, default 3) counts this run's revise rounds. At the cap with correctness findings still open, the run posts the **cap-hit comment** ("Redline stopped at the round cap": it reached its cap of N revise rounds with correctness findings still open in the latest review, so it has not requested a review; the author will pick these up, each listed under "Still open"), makes the run-record commit, and ends with no handoff and no review request. `tests/loop-test.mjs` pins the phases, the done rule, the final nit pass, the cap and every dial level with scripted agents.

## The coverage pass

Every whole-PR and fix-diff round opens with the coverage pass, the finder: a plain workflow agent (`coverage r<n>`, the default agent type, no Redline role and no output schema) invokes the built-in `code-review` skill over the head branch at the round's head, at the effort `models.coverage` names, with `--max-findings all`, and relays the skill's text. The workflow reads from it only the skill's own fenced JSON array of candidates (file, line, summary, failure scenario) and hands the list to the reviewer, which verifies rather than discovers: it collapses each candidate by cause into what the round, the earlier rounds of this run or of an earlier run on the PR, the carry-forward list or an issue already holds (a finding marked fixed is the one exception: a candidate that still reproduces it at the head is new, named with the earlier id, while one the fix did close no longer reproduces and settles; a decided finding stays settled whatever its commits, and a candidate that still reproduces one goes under For the person, naming the earlier id), runs the known-finding check, reproduces a correctness candidate where that is cheap, anchors it on a line inside the diff, and gives it the contract a finding has. An issue or a teammate's comment that covers only part of a candidate leaves the remainder to be judged as its own candidate: a remainder whose cause is in this PR's diff is a finding that names the issue in its description, with no `knownAs`, unless another of these rules puts it elsewhere as it would any candidate (a collapse, a refutation, the disproportionate guard, or For the person for a removed guard or a candidate plausible but not reproduced), never a note saying what the issue lacks, and two candidates are not one because one issue's title fits both (#85; #86, R2-1). Two guards: a candidate anchored outside the diff is never a finding (re-anchored when its cause is in the diff, else For the person or dropped with the reason); a candidate that is technically true but needs implausible conditions to bite is disproportionate and is dropped with that word, never shaped, unless the base branch handled it and this PR stopped handling it: a removed guard goes under For the person, naming the removed line. A refutation answers the candidate's claim: evidence for a neighbouring claim does not refute it, and neither does a comment or docblock that states intent; such a candidate goes under For the person (#85). The round's findings file holds each candidate, by index, beside its outcome, one of eight (`finding`, `forThePerson`, `duplicate`, `settled`, `known`, `refuted`, `outside`, `disproportionate`), and its ref: for `refuted`, the claim it disproves and the evidence against that claim (until #85, one sentence why). The review body counts them in one sentence (a finding the round lists under Already tracked counts as already tracked, and under `correctness only` a nit the reviewer reported from a candidate is listed under For the person) and, after For the person, under the heading `### Candidates set aside (N)`, lists in a collapsed `<details>` block, the set-aside block, every candidate that is neither a finding nor a For the person entry (`duplicate`, `settled`, `known`, `refuted`, `outside` or `disproportionate`; its summary line, `Collapsed, already tracked or dropped`, names the count sentence's three groups, which add up to N). The heading keeps the block apart from the section before it when a round has no For the person entries (#87). There is one line each: the candidate's file and line, its own summary as the finder wrote it, then the outcome and the verifier's ref (`no reason given`, with a warning in the run, when it gave none). A `known` line names the issue or comment, and a `duplicate` line names what it collapsed into, its ref opening with the candidate's index or the finding's id and anything meant for the reader after it, plus, when it opens with another candidate's index (`3`, `candidate 3` or `index 3`), that candidate's place and outcome, and the finding's id when that candidate became a finding, so a duplicate of a dropped or tracked candidate cannot hide (#86, R4-1, R5-4). Each line's summary, outcome and ref are escaped and their mentions neutralised as one text, as "How the review is posted" says, so no tag in a summary or a ref can end the block or open another and no `@word` in one notifies anyone (#85; #86; #87). The block is there so you can overrule a drop, a collapse or a match to an issue without opening the round folder; a round that set nothing aside has no block. A candidate the reviewer left out, or accounted for as a finding the round does not have, is listed under `### For the person` as reported, with a warning in the run.

**Why every round.** The skill is stochastic and attends to what moved, so each pass is a sample. The manual loop Redline replaces ran a pass per round and stopped when one confirmed nothing new; a single sample on round 1 is why a hand-run pass after a Redline run could still find something. So the pass runs again at every head, the reviewer still rechecks the previous round's fix diff beside the candidates, and the done rule is the manual loop's: the run finishes when a round's verifier confirms no new correctness finding, under `maxRounds`. The skill never returns an empty list, so the stop rule is the verifier's collapse, never the skill's. The cost is about one skill pass per round, what the manual loop paid.

`models.coverage` in `redline.json` picks the pass's model and effort ([contract.md](contract.md)); absent, the first-round reviewer's. `coverage off` on the command line, or `"coverage": null` in the file, runs every round with the reviewer alone under the done rule from before the pass existed: the fallback when the skill is absent on this Claude Code or its recipe has drifted, never the default; the word is per-run and never saved. The effort word is one of `low`, `medium`, `high`, `xhigh` or `max`; `max` runs as a single pass, since a workflow subagent has no Agent tool for the skill's fan-out, and `xhigh` on the opus-5 family is the recipe validated on Claude Code 2.1.318.

A pass that yields nothing usable stops the round at stage `review`, resumable at `coverage r<n>` (see "Run markers and resume"), with one of three causes in the error, each with its fix: the Skill tool was denied (allow it in the session's permission mode or allow list), the skill is absent on this Claude Code (`claude --version`; upgrade), or the pass's text holds no fenced JSON array of findings in the skill's shape (the recipe drifted; check the version). Each message also names the alternative, a fresh launch with `coverage off`. An empty array the skill returned on purpose is zero candidates, not an error: the reviewer runs no discovery pass of its own; it runs the scheduled-and-queued, Docs and Version checks, the recheck of the previous round's fix diff on a later round, and the carry-forward list on a first round that has one.

**What the guard does not vet.** The skill runs as a fork of the coverage agent, and the fork carries no Redline `agent_type`, so the fork is a non-role session to the guard: it is inert for every call but one shape. A Bash call that is one of the plugin's own scripts by real path, the repository's `checks.sh` or read-only git is approved for the fork exactly as for the main session (#50), with no prompt; of `redline-gh.sh`, only the read subcommands are (#80, R2-5). A subcommand that posts a review, replies, comments, creates an issue or resolves threads is left to the session's permission prompt, never refused, as is the rest of what the fork runs beyond its allow list; the coverage prompt also tells the agent not to post anything. A Redline role could not host the pass either, since the fork would escape the role's row the same way and a role's output schema can make the fork return nothing. In the spike and the second corpus run the fork ran read-only git (`log`, `diff`, `show`, `grep`), `cat` and `grep`, and `gh` reads of the PR and the issues; the guard approves the read-only git as it does for any session, and the rest meets the session's allow list or permission prompt, so a default-mode session may be asked once by the fork. See "Known limits" in the README.

## Dispositions

The shaper sorts every finding into exactly one of:

- **`fix`**: a clear correctness bug or nit with a proportionate fix. It becomes a plan task and a commit. `decided by: redline`.
- **`defer`**: a real bug whose full fix is out of proportion to its likelihood and impact, where a cheap mitigation exists (a guard, a clear error, a log line, a comment naming the finding). The mitigation becomes the task and the commit; the full fix is listed under Deferred in `shape.md` and in the handoff comment, for you to triage after the run. `decided by: redline`.
- **`ask`**: a judgment call. A question that depends on product intent, on an assumption in the original spec, on a standard the codebase does not follow yet, on a fix out of proportion with no cheap mitigation, or on anything the shaper cannot settle after reading the code and its tests is returned to you, never decided: a pending entry in `shape.md`, a `Pending decision` task in the plan, and a judgment call in the run's result with a plain-language story, the options with their cost and effect, and the shaper's recommendation. On `guided` the run stops for it (see "Hand-off and relaunch"); on `autopilot` the recommendation becomes the decision, `decided by: redline (autopilot)`.
- **Left to you**: a finding a repository ask rule covers ([contract.md](contract.md), "Ask rules") is always the person's, whatever the shaper returned: it comes back as a judgment call naming the rule, with options you carry out outside the run, and Redline makes no change for it; on autopilot it is listed under Deferred with no mitigation.

Before choosing `fix` for a correctness finding, the shaper records how likely and visible the failure is and what the fix costs (files touched outside the PR's diff, new dependencies, rough size); when the cost is out of proportion, the full fix is not its to choose. A finding it can neither confirm nor refute is `ask`, never dropped and never fixed on trust. Every decision, in `shape.md`, in the thread reply and in the handoff comment, ends with its owner.

## Hand-off and relaunch

The interrupt dial (the README, "Dials") says where the run stops for you. Each level is a stopping point the loop already has:

- **`guided`** (default) stops only when the shaper returns a judgment call. The skill shows the calls one at a time, in the order the shaper gave (a call whose options turn on another's answer comes after it). Answer each with a pick from the options, or one line `<id>: <choice>. <reason>`; then type `relaunch` on its own. The run relaunches with the decisions in its arguments: every prompt before the stopping point replays from cache, the shaper applies the decisions, and the round goes on. Each decision is recorded and posted as `decided by: @<login>` with your reasoning restated in one sentence, never your typed text.
- **`plan`** stops after shaping, every round, showing every finding's disposition with the shaper's one-sentence recommendation. Approve as is, change a disposition to fix, defer or accept (a change to `fix` or `defer` for a finding under an ask rule is refused with a warning), or answer an ask; then `relaunch`.
- **`review`** stops after the round 1 review is posted. Pick the findings to act on, then `relaunch`; each one not picked is dropped with a reason, posted in its thread. Later rounds stop as `guided` does.
- **`review only`** stops after the round 1 review; nothing is revised. The run still commits its record, so the tree is clean for the full run that usually follows.
- **`autopilot`** never stops.

In an interactive session the harness hands the person's last typed message to every agent of a run, verbatim, with precedence over the agent's task; an `AskUserQuestion` pick is not relayed, and a headless session relays nothing. On PR #59 a hand-off answer typed as `Refuse it` reached the GitHub agent that way and it refused to write the snapshot, with the prompt's own sentence against it in hand. So the skill relaunches only from `relaunch` typed on its own (a hand-off, the review dial) or from a line holding only a Redline command (a launch, a resume; the namespaced form or the short alias, #44); a stopped run relaunched in its own session takes either, and the skill refuses any other last line; every agent's prompt names those two as conversational, with `args.decisions`, `args.selected` and `args.approvedPlans` the only authority, as the second layer (#60). Hand-off answers are picks, or one line `<id>: <choice>. <reason>`, restated before anything is recorded.

## The handoff comment

When a round's verifier confirms no new correctness finding (with `coverage off`, when a round's review finds no correctness bug), the run finishes: the PR description is redrafted when the repository has a standard for it (the previous one stays in the description's edit history, and a copy is kept under the round's `redline/` folder), the threads Redline opened for settled findings are resolved, the **Redline handoff** comment is posted, review is requested from the configured reviewer, and the run-record commit is made and pushed. The comment says how many rounds ran and what the last one reviewed (with the coverage pass, every round but a final nit pass reviewed the whole PR at its head; with `coverage off`, only round 1 did; a final nit pass reviewed the fix diff only; with a link to Known limits in the README), the threads line, the description note, `@<reviewer>, over to you for the human review`, then one line per round under `### Rounds` (correctness and nit counts, commits, the spec folder, whether you approved the plan or picked the findings), `### Earlier rounds` (see below), `### Decisions` (every decision of the run with its owner, not only the human ones), `### Deferred (mitigated now, full fix left open)` (`shipped <mitigation>; open: <full fix>`), `### Left to you (repository rules)`, `### For the person` (every round's entries, verbatim from the review bodies: what the reviewer would not act on but you should see, never shaped or fixed), the set-aside block of the last round that ran the coverage pass (the round before a final nit pass, else the last round), under `### Candidates set aside in round <n> (N)`, which names that round, since earlier rounds' blocks stay in their own review bodies (#85), and `### Commits`. With `push` off it says the commits are local only.

The handoff comment lists every decision of the run, not only the human ones, and one line about the threads: `Resolved n threads; m left open: <finding ids and why>`. Redline resolves a thread it opened once its finding is settled (fixed, deferred with the mitigation committed, or decided by the person and applied) and its reply is posted; a thread a teammate opened or commented in, before or after Redline's reply, is theirs and stays open, as does a finding the person dropped. A dry run or a `no push` run resolves nothing, and the line is absent. The shaper's JSON carries `decidedBy` per finding (`redline` or `pending`; `reviewer` for a fix in a human review pass); the workflow fills `@<login>` from `args.login` for the answers a person gave and `@<reviewer login>` for the teammate's instructions.

## Decided by

Every decision is posted with its owner. Each Decision in a round's `shape.md`, each reply in a finding's thread, and each line of the handoff comment's Decisions list ends with one of:

- `decided by: redline`: the shaper settled it from the evidence (a fix, a defer, an answer the PR description or the code already gave);
- `decided by: @<login>`: a person decided it at a hand-off (the login `redline-gh.sh login` prints), with their reasoning restated in one sentence. What they typed is a pick from the shaper's options or one line `<id>: <choice>. <reason>`, and the relaunch is the typed word `relaunch`; the restatement is what is recorded and posted, never the typed text;
- `decided by: redline (autopilot)`: the run took the shaper's recommendation on autopilot;
- `decided by: @<reviewer login>`: a teammate asked for the change in their review, and a human review pass (`/redline:redline-revise <pr> review ...`) made it as asked.

## Earlier rounds

A fresh run on a PR that already carries posted Redline rounds (a dry run posts none, so it is never an earlier round) reads every finding those rounds posted and its disposition before launching (`redline-gh.sh prior-findings`, passed as `args.priorFindings`), from the Redline reply in the finding's thread (or the issue comment behind its marker, for a finding in the review body): `fixed`, `deferred`, `decided`, `dropped` by the person on the review dial, `left` to the person under a repository ask rule, or `carried` into a later round. A `resolved; first reported as` reply, which a later run posts on an earlier finding its reviewer found the code no longer has, reads as `fixed`: it is Redline's own claim that the bug is gone, the claim a fixed reply makes, not a decision a person made, so a coverage candidate that still reproduces it is new, as one that still reproduces a fixed finding is (#80, R4-3). A finding recorded is not one handled: a finding with no reply (a `review only` round, a run that stopped after posting, a hand-off never relaunched) or with a `not changed in this round` reply (a fix that never landed) has no disposition, and the new run's first round carries it forward. The reviewer re-verifies each one against the current head, never copies it, and either reports it as a finding of the new round, under `### Carried forward from earlier rounds` in the review body with `first reported as R1-2` on its line and in its inline comment, or lists it under `### Resolved from earlier rounds` when the code no longer has it. A finding the reviewer accounts for neither way is carried by the workflow as reported, with a warning, never dropped. A carried finding then goes through shape, approve and fix like any other; when it is settled, dropped or not changed, its earlier thread gets one reply from the new round (`Redline round 2: carried forward as R2-1; fixed in abc1234 (...) · decided by: redline`), as does a resolved one (`Redline round 2: resolved; first reported as R1-4 in Redline round 1. <why> · decided by: redline`), and Finish's sweep resolves that thread beside the new one. A finding with a disposition is matched into `knownAs` (`R1-1: fixed`) and never re-raised. A carried finding that an issue or a teammate's comment already tracks keeps the author's choice. It stays under `### Already tracked` with `first reported as R1-2` on its line and is not shaped. Its earlier thread gets `Redline round 2: carried forward as R2-1; already tracked in #41 · decided by: redline` and stays open as `already tracked`, and the next run reads that reply as carried. A `knownAs` naming a Redline id on a carried finding is cleared with a warning, and the finding is carried (#46, R1-2). The handoff comment's `### Earlier rounds` section says what became of each: `carried forward as R2-1: fixed in ...`, `resolved: ...`, `carried forward as R2-2 in round 2` for a finding an earlier run already carried (#46, R1-5), `carried forward as R2-1: already tracked in #41` for a carried finding an issue tracks (#46, R1-2), or `already handled in round 1: ...` (#35).

## Saved launch settings

`.claude/redline.local.json` in the repository (ignored by git, so per person per repository) remembers `interrupt`, `revise` (the model id), `maxRounds` and `scope` ([contract.md](contract.md), "`redline.local.json`").

- **No saved file.** The skill asks one `AskUserQuestion` for every setting not typed on the command line (up to four fields), with the defaults first: guided, Opus 5.5, 3 rounds, all. A `review only` run asks only for the scope, since no revise agent starts.
- **A saved file.** One confirm question whose first option reads `Run with: <interrupt> · <model> · <N> rounds · <scope>` (a value typed on the command line overrides the saved one and is marked `(command line)`), and whose second option, "Change something", re-asks the fields that were not typed.
- **Whatever the run uses becomes the saved set**, however it was chosen, except `autopilot` and `review only`, which are never written: the previous saved interrupt stays.
- **A hand-off relaunch asks nothing** beyond the calls themselves and the typed `relaunch`.

The merge rules live in `scripts/redline-prefs.sh` (`resolve` prints the effective settings, what to ask and the confirm line; `save` writes the file and keeps its other keys), and `tests/prefs-test.sh` is their unit test. The same file holds `runs`, one marker per PR for a run that stopped (see "Run markers and resume" below): `redline-prefs.sh run save <repoRoot> <pr> --run-id <id>` writes it from the harness's own record of the run, `run read` prints it, `run check [--plugin <dir>]` says whether the run can be resumed from here and why not, and `run clear` removes it. The file is one of Redline's own: the guard refuses it for every role, and only the skill writes it, through the script.

## Run markers and resume

Every stop leaves a marker under `runs` in `.claude/redline.local.json` (#10): a hand-off, the review dial, a run the harness stopped, and an error at a stage a rerun can recover from. The skill writes it with `redline-prefs.sh run save` from the harness's own record of the run (the run id, the session id, HEAD, the branch, the stage and agent label, the error, the spec folders and the args as launched). The next `/redline:redline <pr>` offers to resume it or start fresh, naming the stage and the error. It asks before anything else, and a resume keeps the run's original settings: the settings question is not asked, and words typed after the PR number are named and ignored. Resume runs `redline-prefs.sh run check` first and stops on its line when the marker's session is not this one (the harness replays only from the session that launched the run; the line prints `claude --resume <session id>`), the branch is not the PR's, HEAD is neither the run's last commit nor on top of it, the run stopped other than with an error and HEAD moved at all (only an error resume carries a hand commit into the workflow), the commits on top touch a path outside `.claude/` (a fix to the gate's `checks.json`, `redline.json` or `settings.json` is expected after an error; a fix to the code under review is a fresh run), the repository under review is the plugin itself and HEAD moved at all (a plugin fix changes what runs, so the next round carries the findings forward), or an untracked or modified path sits outside the run's spec folders (the folders its result lists and every folder its launch stamp names for the PR, so the start snapshot and a round not yet recorded count as the run's). Then it relaunches with the marker's args plus `resume`, one entry for the agent label the error named (`coverage r1`, `recheck r1`, `shape r1`, `handoff comment`), and the workflow appends one resume line to that agent's prompt: a cached result replays unchanged even when the workflow rejected it, so the prompt has to change, and everything before it still replays from cache while that agent and all after it rerun. A hand commit under `.claude/` rides along in the entry: the checker's verdict excuses its paths and its commit, and the next round's snapshot allows the paths. A second resume at the same step keeps the earlier resume's hand commits: `run check` prints the list with the label's earlier entry merged in. A resume at the shape stage reruns the shaper, which rewrites the four spec files and never touches `redline/`. After shaping, the GitHub agent's read-only `spec-status` operation lists the spec folder's four files and greps `shape.md` for its Decisions heading with two `git grep --no-index` lines; a missing `plan.md`, `shape.md` or Decisions section, a finding without a disposition, or an ask without a judgment call (on a reshape after a bounced plan, one the round has not already decided: the reshape returns only the calls still pending or newly raised) is an error at stage `shape` with `resumeFrom` the shaper's label, and no judgment call is invented for it: the run stops, the review stays posted, and a resume reruns the shaper (#57; the one call the workflow writes is the repository-rule ask). The record folder holds only what the run wrote: a note or a draft a person adds goes outside the repository, since the record commit and the resume's untracked-path check read the folder as the run's. A resume at the closing comment first looks for the comment an earlier attempt posted, and one at the record commit for the commit an earlier attempt made, so a request-review or a push that failed after them is retried without posting or committing twice. A `gather` error (the head moved since launch, the PR is not open, the branch is wrong) is not resumable: the error result says so and the next launch is fresh. `review only` and revise-only runs end with the run-record commit like a full run, so an error after one of them leaves nothing untracked.

## The run record

Everything a run writes into the repository sits under `agent-os/specs/`, inside every allowed list, and is committed as the run's record. Each round's spec folder (`<launch stamp>-<pr>-review-round-<n>/`, or `-human-review-<n>/` for a human review pass) holds the four spec files and a `redline/` subfolder with the round's review and findings as posted, the replies, the round snapshot, and, in the first round's folder, the start snapshot ([contract.md](contract.md), "Snapshot file"). The round makes the spec commit, one commit per finding, the standards commit when there is one, and the as-built commit; a run that finishes makes one more, the run-record commit, which stages by name every file under the `redline/` folders that no commit holds yet (the replies, the closing comment, the description's backup, the ingested human review) and commits them as `redline: record the run's replies, reviews and handoff for PR #<pr> (#<issue>)`. A `dry run` writes every body under the round's folder, posts nothing and pushes nothing: its commits, the record included, stay on the local branch until you drop them before the next launch (see "Launching a run" above). The git rules the agents follow are in the README under "Git rules for Redline agents", the one section of it written for them.

## How the review is posted

The GitHub agent posts through `redline-gh.sh` ([scripts.md](scripts.md)), and follows these rules around it:

- Check `has-review <n> <round>` before `post-review`; a hit means the round is already posted and the post is skipped.
- Inline comments must sit on a line in the PR diff (an added, removed or context line of a hunk of that file's patch). GitHub answers `422 Unprocessable Entity` with `Line could not be resolved` and posts nothing, not even the valid comments, and the answer names no path or line. So `post-review` runs `place` first: every comment off a hunk, and every comment in a file whose patch GitHub omits, is moved into `body` under "Not placed inline" behind `<!-- redline:<id> -->` before anything is sent, and the output's `moved` says which. The agent reports them as `movedToBody`. A posted review with no inline comment at all is a degraded result the workflow records as a warning, never an error.
- A finding in the body has no thread, so its reply is an issue comment (`comment`) whose first line is the finding's marker, then `**<id>** · \`file:line\` · from the Redline round N review body`, then the reply, when the round's review is on GitHub; in a dry run, or a revise over a review that was never posted, the reply is written to its file and nothing is posted. One per finding, never twice. To check whether one is already posted, the agent looks for that second line in `pr-comments`, never for the marker, which the review body also carries.
- **What is escaped and neutralised (#87).** The finder's and the verifier's free text goes through one function where the workflow posts it:
  - a finding's title: on its line in the review body and the cap comment, in its inline comment, and on every handoff line that names it (Decisions, Deferred, Left to you, Earlier rounds);
  - the review's summary;
  - For the person lines;
  - Already tracked lines (title and `knownAs`);
  - Resolved from earlier rounds (title and why);
  - the `knownAs` and the why on Earlier rounds lines;
  - the set-aside block's lines.

  Outside code spans, `&` becomes `&amp;`, then `<` becomes `&lt;`, and a word joiner (U+2060, invisible) goes after every `@` that comes before an ASCII letter or digit. So a tag reads as text, a `@click` or a `@param` mentions nobody, and the text reads as written. GitHub still links `\@x` and `&#64;x`, so neither is used.

  A code span is left as written, since GitHub shows a span literally. The exception is a text that holds `](`, `][`, `://`, `www.` (any case), a backslash, a carriage return or a newline. There GitHub can read a backtick as part of a link before it pairs spans, so the whole text is escaped, spans included, and a span holding `<` or `&` then shows the entity. A summary with a newline is one such text. Fields that share a line are read as one text.

  What the workflow writes is posted as written, so `@<reviewer>, over to you for the human review` and `decided by: @<login>` still notify. So are:
  - the shaper's, the person's and the implementer's words (a mitigation, a full fix, a decision sentence, a commit subject);
  - an inline comment's description and proposed fix;
  - every reply.

  The reviewer, shaper, resolve and implementer agent files ask for every identifier that begins with `@` in backticks, since their text reaches GitHub in comments and replies (see Known limits in the README). A later run reads a title back through `prior-findings` as it was posted, and decodes it once at launch: the joiner after `@` is removed, then `&lt;` and `&amp;` are decoded. So the reviewer reads the title as written, and a carried title is escaped once, never twice.
- The `comments[].id` values printed by `post-review` are what `reply` takes; keep them in the round's record. The `id` each `reply` prints is kept too: Finish's sweep names a thread by that pair, and `resolve-threads` resolves nothing with a comment that is not one of them.
- The sweep is the workflow's selection and the agent's one call, as the run-record commit is: the workflow lists the settled findings' ids, the agent runs the one `resolve-threads` line it is given, and the script skips whatever a teammate opened or commented in. The handoff comment then says `Resolved n threads; m left open: <ids and why>`; a human review pass's summary says the same of its final nit pass's threads, and a capped run, a dry run and a `no push` run sweep nothing.

## A human review pass

`/redline:redline-revise <pr> review <id | @login | latest>` is the pass after the hand-off: a teammate's review comments become the findings (`H<n>-<k>`, one pass per launch, numbered after the `Redline human review` passes already on the PR). `review @login` takes every inline comment by that login (matched in any case) that no Redline reply has answered yet, replies inside Redline threads included, plus the newest of their review bodies that no Redline human review comment has answered yet (one body per pass, so an older one comes up on the next pass); `review <id>` takes that review's unanswered comments and its body, unless a Redline human review comment has already answered it; `latest` is the newest review that is not Redline's, not the author's, and still has an unanswered comment or body. A clear instruction is fixed, `decided by: @<login>`; a question, a disagreement or a comment the shaper cannot turn into one change comes back to you as a judgment call with the comment quoted, and the reply says what you decided; a comment that asks for nothing gets "no change requested". Nothing a teammate asked for is deferred by Redline on its own. After the fixes are pushed and every thread answered, the reviewer reads the fix diff once as the next `Redline round`, a correctness bug it finds gets one more fix pass, and the pass ends with one summary line on the PR: no handoff comment, no review request, the teammate is already there. The interrupt dial applies; the scope does not.
