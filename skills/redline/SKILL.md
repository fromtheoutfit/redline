# /redline:redline

You are the only part of Redline that can talk to the person. You parse what they typed, settle the run's settings (asked once, then remembered in `.claude/redline.local.json`), check the checkout, write the start snapshot, launch the plugin's `redline:redline-loop` workflow, and handle what it returns: a hand-off (judgment calls to decide, or a plan to approve), a posted review to pick findings from, a finished run (what was fixed, deferred and where each draft went, and declined, to report), a capped run, or an error. Every stop leaves a run marker in the same file (`redline-prefs.sh run save`), so the next `/redline:redline <pr>` can offer to resume it, from the session that launched it (#10). The workflow, the agents and the scripts do everything else; see `${CLAUDE_PLUGIN_ROOT}/README.md` and `${CLAUDE_PLUGIN_ROOT}/docs/`.

Arguments: `$ARGUMENTS`

## 1. Resolve the repository

Run `git rev-parse --show-toplevel`. That absolute path is `repoRoot`; every path below is absolute from it. Read `<repoRoot>/.claude/redline.json` (the per-repo config). If it does not exist, stop with one line: this repository is not set up for Redline yet (see `${CLAUDE_PLUGIN_ROOT}/docs/setup.md`).

The plugin's root is `${CLAUDE_PLUGIN_ROOT}`: its scripts, workflow, README and `docs/` are there. Everything per repository (`checks.sh`, `redline.json`, the spec folders) is under `repoRoot`.

## 2. Parse the arguments

The grammar, in any order, case-insensitive:

| Typed | Meaning | Default (from `redline.json`, then built in) |
| --- | --- | --- |
| `<n>` or `#<n>` | PR number. **Required.** | none: stop with "Usage: /redline:redline <pr> [...]" |
| `autopilot`, `guided`, `plan`, `review`, `review only` | `interrupt`: the dial, where the run stops for the person (see "The interrupt dial" below). `review only` also sets `reviewOnly = true`: stop after the first round's review is posted (or written, in a dry run) | saved, else `guided` (step 3) |
| `correctness only` | `scope = "correctness"`: the reviewer runs no nit checks of its own, a nit it verifies is declined with the scope as its reason, and a round without a correctness finding is done, with no final nit pass (the one final nit pass this scope has follows a round that fixed a low-severity bug in the previous round's fixes) | saved, else `all` (step 3) |
| `max <N> rounds`, `max <N> round`, `max <N>` | `maxRounds = N` (revise rounds allowed while correctness bugs remain) | saved, else `maxRounds` in `redline.json`, else 3 (step 3) |
| `revise fable`, `revise opus` | `models.revise.model`: `claude-fable-5-1` or `claude-opus-5-5` | saved, else ask (step 3) |
| `defer each round`, `defer at end` | `deferAt`: when a deferred item's drafted issue is raised with the person: `round`, at the round's stop after shaping, with its judgment calls, or `end`, once before the run finishes ("The round's deferred drafts", section 7). It does not apply to `autopilot`, which files each draft as drafted in its round, or to `review only`, which revises nothing | saved, else ask (step 3) |
| `defer to github`, `defer to spec`, `defer to print` | `deferTo`: where a deferred item's draft goes: `github`, Redline opens an issue for it; `spec`, the draft stays a file in the round's spec folder; `print`, the same, and its title and body are printed when the run ends. It does not apply to `review only` | saved, else ask with `deferTo` in `redline.json` first (step 3) |
| `reviewer @handle` | `reviewer = handle` (the `@` is dropped) | `reviewer` |
| `no push` | `push = false` (commit locally only) | `push`, else true |
| `dry run` | `postToGitHub = false` and `push = false`: every body is written under the spec folder's `redline/`, nothing reaches GitHub | `postToGitHub = true` |
| `coverage off` | `models.coverage = null` in `args`: every round runs the reviewer alone, with no coverage pass and the done rule from before the pass existed. The fallback when the built-in `code-review` skill is absent on this Claude Code or its recipe has drifted, never the default; a per-run word, never saved | `models.coverage` from `redline.json` (absent: on, at `reviewerFirstRound`'s model and effort) |

A word that fits none of these stops the launch with one line naming it. Do not guess. A deferral word typed with a dial it does not apply to (`defer at end` with `autopilot`, either with `review only`) does not stop the launch: say in one line that it does not apply to this run, and go on.

**The interrupt dial.** Five levels, each a stopping point the loop already has:

- `autopilot`: never asks. At a judgment call the shaper's recommendation becomes the decision and the run goes on; each such decision is attributed `redline (autopilot)` in the spec, the thread and the handoff comment.
- `guided` (the default): the run ends only when the shaper returns a judgment call (`ask`), which it does in five cases only, beside the repository's ask rules and Redline's own files; everything else it decides itself, a decision to decline included, and the run does not stop for it; you present the calls, record the answers and relaunch.
- `plan`: after shaping, every round, the run ends with the full disposition list; you present it, the person approves it as-is or changes a disposition or answers an ask, and you relaunch.
- `review`: the run ends after the first round's review is posted; you present the findings, the person picks which to act on (and drops the rest, each with a reason), and you relaunch. Later rounds behave as `guided`.
- `review only`: stop after the first round's review; nothing is revised.

In a headless session (`claude -p`), resume when the check below passes, else start fresh, and say which in one line.

On exit 1, say its `line` verbatim and stop: for `session` the line carries `claude --resume <id>` (the harness replays a run only from the session that launched it, so the person reopens that session and types the command again there); for `branch`, `head-moved`, `plugin` and `untracked` it says what to do (any hand commit after a stop that was not an error, a fix outside `.claude/` after an error, or any hand commit when this repository is the plugin, means a fresh run, whose first round carries the findings forward). For `version` (#135) the run started under another version of Redline than this session loads, or under a build before 0.5.1, which records none: a relaunch would rerun steps already recorded. For either, nothing needs fixing by hand. Say the line, then ask one `AskUserQuestion`, **Start fresh** first and **Stop** second; Start fresh is the bullet below, and Stop leaves the marker. In a headless session, start fresh, as above. On exit 2, say the script's stderr line and stop, and leave the marker: it could not read what it checks, a `--plugin` whose manifest holds no version, the saved file or the repository (#137, R2-5). On exit 0, skip sections 3, 4 and 5, and say in one line that the run resumes with its original settings: the marker's `args.interrupt`, its revise model (`args.models.revise.model`), `args.maxRounds`, `args.scope` and, where the marker's args hold them, `args.deferAt` and `args.deferTo` (when deferred items are raised and where their drafts go). When words were typed after the PR number (`dry run`, `no push`, `autopilot` and the rest), name each one in that line as ignored, since a resume keeps the run's args; when none were typed, say nothing about them. Save the run record copy as section 7 says ("Save the run record"). Then, by `kind`:
  - `error`: relaunch in this session with the marker's `args` exactly, plus `resume`: the marker's `args.resume` (or `{}`) with one entry added under the marker's `label`, `{"attempt": <marker.attempt>, "error": "<marker.error>", "hand": <the check's hand>, "ownCheck": <marker.ownCheck>}` (the script has already merged the label's earlier entry, so copy it as printed; `ownCheck` is the marker's, `false` when the marker holds none, and it is how the workflow knows the stop was its own check of what the step returned, which it never reads off the error's words, #116), and `resumeFromRunId` set to the marker's `runId`. The agents before that label replay from cache; that one reruns with one added line and everything after it runs again.
  - `handoff` or `reviewed`: read `result` from the marker's `record` file (the harness's own record of the run), run `run drift` before presenting anything, as section 7's "The script a relaunch runs" says for such a resume, and continue as that result's section below says: present the calls, the drafts or the findings, record the answers, confirm, relaunch with the marker's `args` plus what the stop asked for.
  - `stopped`: relaunch with the marker's `args` unchanged and `resumeFromRunId`, as "stopped before a result" says.
  Every relaunch here goes through "The script a relaunch runs" (section 7) first. Record the new `runId`. The next stop rewrites the marker; a run that finishes clears it. An `error` or `stopped` resume relaunches from the line holding only the command the person typed, which the relaunch rule (section 7) accepts; nothing else is typed first. A `handoff` or `reviewed` resume relaunches from the word, as its section says ("Relaunch only from the word"), since the person answers there first.
- **Start fresh.** Run `${CLAUDE_PLUGIN_ROOT}/scripts/redline-prefs.sh run clear <repoRoot> <n>`, then go on to section 3. When precheck step 4 (a clean tree) fails and the marker named spec folders, the one line names them: `commit or remove <folders>` (the earlier run's record; a hand-off or an error that was not resumed leaves it, since `review only` and revise-only runs commit their own).

## 3. Settle the settings (fresh launches only)

Skip this on a relaunch after a hand-off or a `reviewed` result, and on a resume (section 2, "A stopped run"): the settings were settled at the first launch and `args` is reused byte for byte. The only typed line a relaunch needs is `relaunch` (section 7, the relaunch rule).

Six settings are remembered per person per repository in `<repoRoot>/.claude/redline.local.json` (ignored by git): `interrupt`, `revise` (the model id), `maxRounds`, `scope`, and the two for deferred items (#95), `deferAt` (when their drafts are raised with the person: `round` or `end`) and `deferTo` (where a draft goes: `github`, `spec` or `print`). The merge rules live in one script; run it once with the words from the command line (only the ones typed; `defer each round` is `--defer-at round`, `defer at end` is `--defer-at end`, `defer to <word>` is `--defer-to <word>`), and read its JSON:

```
${CLAUDE_PLUGIN_ROOT}/scripts/redline-prefs.sh resolve <repoRoot> [--interrupt <word>] [--revise fable|opus] [--max-rounds <N>] [--scope all|correctness] [--defer-at round|end] [--defer-to github|spec|print]
```

It prints `effective` (command line over saved file over defaults: `guided`, `claude-opus-5-5`, `redline.json`'s `maxRounds` or 3, `all`, `round`, `redline.json`'s `deferTo` or `github`), `sources` (where each came from), `repository` (what `redline.json` supplies as a default; `repository.deferTo` is null when the file does not set one), `applies` (the fields that apply to this run), `ask`, `confirm` and `summary`. On exit 2, stop the launch with its one stderr line: a bad word, or a `deferTo` in `redline.json` that is not `github`, `spec` or `print`, which a person fixes in the file. Then:

- **`confirm` is false (no saved file).** Ask one field per name in `ask`, each with the sensible default first, in two `AskUserQuestion`s, since one takes four fields: the first with the names among the first four, the second with the names among `deferAt` and `deferTo`. A question none of whose fields is in `ask` is not asked (a `review only` run asks only for the scope, since no revise agent starts and nothing is deferred).
  - "Where should the run stop for you?" **Guided (Recommended)** · Autopilot · Plan · Review, with one line each from the dial above.
  - "Which model should revise this PR (shape, resolve, implement)?" **Opus 5.5** (`claude-opus-5-5`; never spends Fable budget by accident) · **Fable 5.1** (`claude-fable-5-1`; the better result when the budget allows).
  - "How many revise rounds at most?" **3** · 2 · 1 · 5.
  - "What should the reviewer look for?" **Everything** (`all`: correctness bugs and nits) · **Correctness only** (no nits; a final nit pass only after a round that fixed a low-severity bug in the previous round's fixes).
  - "When should deferred items be raised with you?" **Each round (Recommended)** (`round`): with the round's judgment calls, after shaping; a round with only deferred items stops too. **End of the run** (`end`): no stop inside the rounds; one stop before the handoff, only when the run deferred something. Leave this field out when the first question's answer was Autopilot: autopilot files each draft as drafted and asks nothing, so the setting does not apply and is not saved.
  - "Where should a deferred item's draft go?" **GitHub issue** (`github`): Redline opens one issue per deferred item; a project board that takes new issues gets a card for each. **Spec folder** (`spec`): the draft is written into the round's spec folder. **Print** (`print`): the draft is written there, and its title and body are printed when the run ends, for you to paste. When `repository.deferTo` is not null, that option comes first with "(this repository's default)" after its label; otherwise GitHub issue comes first.
- **`confirm` is true (a saved file).** Ask one `AskUserQuestion`: "Settings for this run?" whose first option is the script's `summary` verbatim (`Run with: <interrupt> · <model> · <N> rounds · <scope> · <deferred each round|deferred at the end> · <drafts to GitHub|drafts to the spec folder|drafts printed>`, with `(command line)` after each value typed in the command, which overrides the saved one; a deferral setting that does not apply to the run, or that is asked beside it, is not in the line), and whose second option is **Change something**. When `ask` is not empty, the saved file lacks a deferral setting this run needs (it was saved before the two existed, or by runs they did not apply to): ask each name in `ask` as a field of the same `AskUserQuestion`, with the options above, so the file is asked for them once. On "Change something", ask the first four fields in `applies` that were not typed on the command line, with the saved values as the first options, then, in a second question, the deferral fields in `applies` that were neither typed nor just answered, the saved value first and the repository's default marked as above (no `deferAt` when the dial is now Autopilot).

A headless session (`claude -p`) has no `AskUserQuestion`: there, take the script's `effective` values without asking (the command line, the saved file and the defaults, in that order; for `deferTo` the default is the repository's, else `github`) and say so in one line. When the dial is not `autopilot`, say in that line too that the run still stops at a judgment call and at a deferred item's draft, so a headless run that must not stop uses `autopilot`. Pass every setting on the command line when a headless run must not rely on the saved file.

Whatever the run uses is the new saved set, however it was chosen: run `redline-prefs.sh save <repoRoot> --interrupt <word> --revise <model id> --max-rounds <N> --scope <word> --defer-at <round|end> --defer-to <github|spec|print>` with the six effective values before launching (for a deferral setting that was not asked because it does not apply, the value `resolve` printed). The script itself keeps `autopilot` and `review only` out of the file (they are per-run verbs; the previous saved interrupt stays), and keeps a deferral setting the run did not settle out of it too (both under `review only`, `deferAt` under `autopilot`), so the next run it applies to is asked; always pass what the run uses. The saved file is one of Redline's own: no Redline role may write it, and you write it only through the script.

The revise model holds for every round of the run and every relaunch. A `review only` run never starts a revise agent; its `models.revise.model` is whatever was settled, as a placeholder.

A warning, never a stop, and said in every permission mode, since the skill cannot read the mode. A Start fresh (section 2) has said it already, so it is not said twice.
2. `${CLAUDE_PLUGIN_ROOT}/scripts/redline-gh.sh pr <n>`: the PR must be `OPEN`, except in a `dry run`, which posts and pushes nothing and so may read a closed PR (a seed for a recall test). Keep `headRefName`, `headRefOid`, `baseRefName`, `title`.
3. `git rev-parse --abbrev-ref HEAD` must equal `headRefName`.
4. `git status --porcelain` must print nothing.
5. `git rev-parse HEAD` must equal `headRefOid`.

Run the git commands plainly, from the session's working directory, which section 1 established is inside the checkout: the shared allow rules are `Bash(git status:*)` and `Bash(git rev-parse:*)`, and a `git -C <path> ...` spelling matches neither, so it asks the person before running.
6. `${CLAUDE_PLUGIN_ROOT}/scripts/redline-gh.sh login` prints the login Redline posts as: keep it as `login` (every decision the person makes is attributed `@<login>`). When `reviewer` is set, it must not equal `reviewer` (GitHub ignores a review request to the PR's own author).
7. `${CLAUDE_PLUGIN_ROOT}/scripts/redline-gh.sh files <n>` prints every changed path as a JSON array (every page of GitHub's files endpoint, where `gh pr view` stops at 100); keep it as `files` for the snapshot in section 5. On exit 2, stop with its one stderr line verbatim (a `gh` older than 2.48.0 does not know `--slurp`). Say the count in one line, `<N> files on GitHub`. Above 300 files, warn: `over 300 files: GitHub's whole-PR diff is unavailable, so Redline reads per-file patches, and the hunks of a text file whose patch GitHub omits come from this clone when it holds the PR's base and head commits; a finding in a binary file, or in a file whose diff GitHub takes no comment on, goes in the review body behind a marker`. When `redline.json` sets `maxFiles` and the count exceeds it, stop: `<N> files is over maxFiles (<M>) in .claude/redline.json; split the PR`.
8. `${CLAUDE_PLUGIN_ROOT}/scripts/redline-gh.sh last-round <n>` prints the highest Redline round already posted on the PR, `0` when none (exit 2 stops the launch with its line). `firstRound` is that number plus one: a PR that already carries rounds 1 and 2 from an earlier run gets round 3 from this one, so every finding of this run gets its own review and threads, and nothing is skipped as already posted (#10). Say it in one line when it is not 1: `rounds 1 to 2 are already posted; this run starts at round 3`.
9. When `firstRound` is not 1: `${CLAUDE_PLUGIN_ROOT}/scripts/redline-gh.sh prior-findings <n>` prints every finding those rounds posted with its disposition, read from the Redline reply in its thread (exit 2 stops the launch with its line); keep the JSON array as `priorFindings`. A finding with no reply, or a `not changed` one, has no disposition and is carried into this run's first round, where the reviewer re-verifies it; the rest (`fixed`, `declined`, `deferred`, `decided`, `dropped`, `carried`, or `left` to the person under a repository ask rule) are tracked and never re-raised (#35). Say it in one line: `3 earlier findings have no disposition and are carried into round 3: R1-2, R1-5, R2-1`, or `every earlier finding has a disposition`. When `firstRound` is 1, `priorFindings` is `[]` and nothing runs.
10. The repository's **ask rules** (#49): `askRules` in `redline.json`, read in section 1, is a list of `{id, when, reason}`, or absent. Check each rule by reading it: `id` matches `[a-z][a-z0-9-]*` and is unique; `when` holds exactly one of `paths` (a non-empty list of non-empty strings, none holding `!` or `[`) or `prose` (a non-empty string); `reason` is one non-empty line. A rule that fails stops the launch with one line naming it (`askRules[2]: rule 'billing': reason must be one non-empty line; fix .claude/redline.json`): the guard refuses every write by a Redline role while the list is malformed, so the run could not build anything. Keep the list as `askRules` (`[]` when the key is absent or empty) and say in one line how many apply and their ids (`2 ask rules: craft-project-config, billing`); say nothing when there are none. A finding a rule covers comes back as a judgment call naming the rule, is never fixed, declined or deferred by Redline, and is listed as the person's in the handoff.

Any failure stops the launch with one line saying which check failed and what to do (the gate script's own line, `check out <branch>`, `commit or stash your changes`, `pull or push so HEAD matches the PR`, `pick another reviewer`, `split the PR`, the gh version line). Never fix the checkout yourself, and never stamp or edit `checks.sh`: a person does that.

## 5. Write the start snapshot and assemble `args`

1. `launchedAt`: run `date +%Y-%m-%dT%H:%M:%S%z` once and keep the output (for example `2026-10-18T09:30:00-0400`). The workflow derives the spec-folder timestamp `YYYY-MM-DD-HHMM` from it, so the same value must be reused on every relaunch.
2. `files`: the JSON array from precheck step 7.
3. `issue`: the issue number in the head branch (`feature/42-...` gives 42), else the `(#N)` in the PR title, else the PR number.
4. Write the start snapshot with the Write tool to `<repoRoot>/agent-os/specs/<YYYY-MM-DD-HHMM>-<n>-review-round-<firstRound>/redline/snapshot-start.json` (`firstRound` from precheck step 8; `1` on a PR with no posted Redline round):


## 6. Launch

Call `Workflow({name: "redline:redline-loop", args})`. If the name is not found (a session started before the plugin was installed or updated does not list its workflow), call `Workflow({scriptPath: "${CLAUDE_PLUGIN_ROOT}/workflows/redline-loop.js", args})` instead. **Record the `runId`** from the result; a relaunch needs it. The result also names the script the run launched with (a copy the harness keeps under the session's `workflows/scripts/` when the launch went by name); the harness writes that path into the run's record, which is where a relaunch finds it ("The script a relaunch runs", section 7). Keep `args` exactly as sent. In a headless session (`claude -p`) the harness stops background tasks ten minutes after the session's last turn, which kills a run mid-phase: such a session is started with `CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS=0` so it waits for the workflow (step 7).

Tell the person in one or two lines that the run has started, what it will do (the dial, the scope, dry run, rounds, revise model, reviewer, when deferred items are raised with them and where the drafts go, each where it applies, and `coverage off` when it was typed), and that they can watch it in `/workflows`. Then wait for the workflow's completion notification; never predict its result.

## 7. Handle the result

The workflow returns `{status, rounds, judgmentCalls, drafts, deferred, openFindings, decided, commits, specFolders, warnings, ...}`. Every decision in `decided`, in the spec folder's `shape.md`, in each finding's thread and in the handoff comment names its owner: `decided by: redline` (the shaper settled it from the evidence), `decided by: @<login>` (the person, at a hand-off, with the restated reasoning), or `decided by: redline (autopilot)`.

At every stop that waits for the person (a hand-off of any kind, a `reviewed` result), write the marker and run `run drift` as soon as the stop is reported, before presenting anything ("Write the marker" and "The script a relaunch runs", in the `decisions` hand-off below), so a relaunch that cannot run is said before any question and no answer is lost to it (#137, R2-6).

### `review-only`

Run `${CLAUDE_PLUGIN_ROOT}/scripts/redline-prefs.sh run clear <repoRoot> <n>` first. Summarise the first round's review (round `firstRound`) in a few lines: how many findings by category, not counting the round's `scoped` items (declined under the scope, `correctness only`), which you name in one line with their IDs, the correctness ones by title (a finding with `carriedFrom` as "first reported as <that id>"), how many of them the verifier could not confirm (`confidence` `unconfirmed`, each with what would confirm it, its `wouldConfirm`) and, when the round ran the coverage pass (`rounds[0].coverage` not null), how many candidates it returned and how many became findings (`coverage.candidates`; `coverage.counts.verified` plus `coverage.counts.unconfirmed`), where the review sits (`reviewFile`; in a dry run, say plainly that nothing was posted), and the run-record commit (`recordCommit`: the review-only run commits its review, findings and start snapshot like a full run, so the tree is clean for the next launch). Say in one line that a later `/redline:redline <pr>` carries these findings into its first round, so no separate revise launch is needed; in a dry run say instead that nothing reached GitHub and the record commit is local only: before the next launch, copy the round's spec folder outside the repository if the review is worth keeping and drop the commit (`git reset --hard origin/<branch>`), since the precheck stops while HEAD is ahead of the PR; a later run then starts at round 1 and carries nothing, and the review is the record under the round's spec folder until then. Stop.

### stopped before a result

The workflow was stopped without returning (the harness's background-task ceiling in a headless session, or the person stopping it). Nothing was decided. Write the marker (`${CLAUDE_PLUGIN_ROOT}/scripts/redline-prefs.sh run save <repoRoot> <n> --run-id <runId>`, kind `stopped`) and save the run record (see "Save the run record" below), then relaunch **in this session** with the same `args`, no new `decisions`, and `resumeFromRunId` set to the recorded `runId`, under the relaunch rule (section 7: when the last typed line is neither `relaunch` nor a line holding only a Redline command, ask for `relaunch` first) and after "The script a relaunch runs" below: the agents that finished replay from cache, the interrupted one reruns (a shaper completes the folder it started), and the run id is kept. Then handle the new result as below. If this session ends first, the marker is the way back: `/redline:redline <n>` in the reopened session (`claude --resume <session id>`, which `run check` prints) offers to resume it.

### `handoff` with `handoffKind: "plan"` (the `plan` dial)

The run stopped after shaping round `handoffRound`, as the dial asks, with the round's whole disposition list in `plan`: one entry per finding with `finding` (ID, file, line, title, category), `disposition` (`fix`, `decline`, `defer` or `ask`), `recommendation` (one sentence: the change planned, the decision to decline, the mitigation chosen for a defer or that nothing ships now, or the option recommended), for a decline its `reason` (the sentence Redline will post in the finding's thread), `decidedBy` (`redline` for a fix, a decline or a defer; empty for an ask, which is still pending) and `files` (the paths its task touches, empty when it has no task; for an ask, the paths its recommended change would touch; for a defer, a task listed here is what says a mitigation is planned, whatever its words say) and, for a fix its `cause`: where the cause lives (`where`), whether the fix is made there (`one-place`), is this instance with a sweep of the class (`sweep`, with what the sweep covered inside it, in `swept`) or is this instance alone (`instance`), and `why`. `deferredPlanned` holds each defer's mitigation as the shaper wrote it, possibly empty, which never says whether one ships (the entry's `files` in `plan` say whether a mitigation is planned), and its drafted issue (`title`, `found`, `why`, `fullFix`); `judgmentCalls` the asks, each with its story, its options (each with what it ends in, `ends`), the label of the recommended option (`recommended`) and the recommendation, in answering order.

Present the list, one line per finding (ID, title, disposition, recommendation, for a decline its reason, and for a fix what its cause was taken to be: one place, a sweep of a class, or this instance alone), then ask one `AskUserQuestion`, "Approve the plan as-is?", with **Approve as-is** first and **Change a disposition** second; then the asks as in the `decisions` hand-off below, one at a time. The person may:

- **approve as-is**: nothing to record beyond the asks' answers;
- **change a disposition** of a fix, decline or defer finding to `fix`, `defer` or `accept` (no change, with a reason); changing a decline to `fix` or `defer` overrules it, and Redline then builds it as the person's decision: on "Change a disposition", say that each change is one line in the answer form, `<id>: <fix|defer|accept>. <reason>`, in the Other field or typed; record each under its ID as `{"choice": "<fix|defer|accept>", "notes": "<the restatement>", "date": "<today>", "disposition": "<fix|defer|accept>"}`. The restatement rule below applies; for a `defer` it names the mitigation the person wants, or says that nothing ships now; for an `accept` the reason the behaviour stands. Say each back in one line, then ask "Approve the plan as-is?" again;
- **answer the drafts** (`drafts`, when the round deferred anything and drafts are raised each round): present them and record the answers as "The round's deferred drafts" below says. `canFix` is true for every draft at this stop, so a draft can be turned back into a fix here: that is a changed disposition, recorded as above;
- **answer an ask**: record it as in the `decisions` hand-off below. An entry whose `forced` is not null is a finding a repository ask rule covers (`forced.rule`, `forced.reason`), or, when `forced.own` is true, one on Redline's own files, which no Redline role may write: it is always an ask, and it cannot be changed to `fix` (the workflow drops the override and the guard refuses the write): say so when the person tries, and record their answer as an ask's. It can be deferred to an issue, by a pick of its option that ends in `defer` or by `<id>: defer. <reason>`, as the `decisions` hand-off below says.

Every ask and every draft in `draftsNeeded` must be answered before the relaunch (an approved round whose ask or draft is still open stops again as a `decisions` hand-off); the drafts' answers go in `args.deferrals`. When everything is answered, list the approvals and changes one line each, ask for the word as below ("Relaunch only from the word"), save the run record, and relaunch with `args.approvedPlans` set to `approveWith.approvedPlans` from the result (every pass approved so far, this one added: a Redline round by its number, a human review pass as `h<n>`; pass the list exactly as given) and `args.decisions` holding every decision so far plus the new ones. The plan dial stops again after the next round's shaping; repeat.

### `reviewed` (the `review` dial)

The run stopped after posting the first round's review (`reviewedRound`; `reviewFile`, in a dry run written only). `findings` holds every open finding in full (ID, file, line, category, severity, confidence, title, description, proposed fix, `wouldConfirm` for one the verifier could not confirm, and `carriedFrom`, the earlier round's id it carries forward, or empty); `known` the ones already tracked, which need nothing.

Summarise the review as in `review-only`, then present the findings one at a time, in prose (a carried one as "first reported as <id>"), and ask which to act on with `AskUserQuestion`, multiSelect, "Which findings does this run act on?": up to four findings per question, in review order (the label the ID and title, the description the proposed fix), as many questions as the review needs. Every finding not picked is dropped **with a reason**, one standalone sentence in the restatement style below (it is posted in the finding's thread and listed in the handoff comment as `decided by: @<login>`): "Not selected for this run." unless the person gives one as a line `<id>: drop. <reason>` (Other or typed); say each back in one line. Then list the selection one line each, ask for the word as in the `decisions` hand-off ("Relaunch only from the word"), save the run record, and relaunch with `args.selected` set to `{"act": ["R1-1", ...], "dropped": {"R1-2": "<reason>", ...}}`. The loop shapes only the selected findings; later rounds hand off their judgment calls as `guided` does.

### `handoff` with `handoffKind: "decisions"` (the `guided` dial, and the others when an ask is open)

The run stopped because the shaper returned judgment calls. Present them **in the order `judgmentCalls` lists them** (the shaper orders them so that a call whose options turn on another's answer comes after it, and names that call in `dependsOn`), **one at a time**, each in prose first and then as one `AskUserQuestion`:

- the finding (ID, file, line, title) in one line;
- when `dependsOn` is not empty, which earlier answer this one builds on, and what that answer means for these options;
- the story, in plain language: who does what, what happens, why it matters;
- each option with its cost and effect, and what it ends in (`ends`: `fix`, a change in this pull request; `defer`, an issue, with or without a mitigation now; `accept`, no change);
- the shaper's recommendation and why.

A call whose `forced` is not null (its `why_human` reads `repository rule <id>`, or `redline's own file` when `forced.own` is true) is a finding the repository's ask rules, or Redline's own files, leave to the person: say which rule and quote its reason (`forced.reason`), or say that no Redline role may write Redline's own files, and say that Redline makes no change for it whatever the answer: the options are the person's to carry out outside the run (make the change by hand after the run, or accept it as it is; each states an end like any other option's, and for this call the end says what the person's own action amounts to, never something Redline does), and the answer is recorded and posted in the finding's thread as `left to @<login> under repository rule <id>` (`left to @<login> under the rule on Redline's own files` for one with `forced.own`).

**Deferring a finding left to the person (#126).** Such a call may offer an option that ends in `defer` and carries a drafted issue (`draft`: `title`, `found`, `why`, `fullFix`): the shaper's own, or the one the workflow kept when the shaper had deferred the finding. It is shown with its draft's title, and picking it has Redline file that draft: no change is made, and the reply still says the change is the person's under the rule, then names the issue. `<id>: defer. <reason>` typed for such a finding is recorded with `"disposition": "defer"` (`{"choice": "defer", "notes": "<the restatement>", "date": "<YYYY-MM-DD today>", "disposition": "defer", "call": true}`), at every stop: the `"call": true` key marks it as an answer to a call, so a defer typed at a stop the round reaches after its first resolve (a reshape's after a bounced plan) is applied by the resolve that call sets off and is never read as a disposition changed on the plan dial. It defers the finding the same way, with the draft of the call's one drafted option or, when the call offered none or more than one, one the resolve agent writes; when it offered more than one, say so when you say the answer back, and that picking one of those options would file its draft. Either way the draft is shown before it is filed ("The round's deferred drafts" below), with `canFix` false: at a stop of the round, or, when deferred items are raised at the end of the run, at the end-of-run stop. Only those two defer it. Any other answer leaves the finding to the person, a fix typed for it and words such as "file an issue for this" included: when you say such an answer back, say that it is recorded as left to them, that nothing is filed for it, and that picking the option that ends in an issue, or typing `<id>: defer. <reason>`, would file one. On autopilot nothing is deferred: the finding is left, and its line in the handoff names the recommended option.

Then ask one `AskUserQuestion` for the call: the question names the finding (ID and title); the options are the shaper's labels in its order, the recommended one (`recommended`, the label of one option) first with "(Recommended)" appended, each description its cost and effect and then what it ends in (`Ends in a fix.`, `Ends in an issue.` or `Ends in no change.`); a call with more than four options shows the recommended one and the next three and says the rest are answered through Other.

**The round's declines.** `declined` lists what the shaper declined on its own in this round, each with its `reason` (empty when it declined nothing). At a stop the round reaches after its first resolve has run (the stop for a draft the resolve agent wrote, or a reshape's after a bounced plan), `declined` is empty and `declinedAfterRun` lists the IDs of the round's declines: when it is not empty, say in one line that those declines are overruled after the run, by a reply in the decline's thread and the human review pass (`/redline:redline-revise <pr> review @<login>`), and record no typed overrule of one at this stop, since the round's first resolve, which ran before it, is where an overrule is applied. After the last call, list them in prose, one line each (ID, title, reason), and say that a line in the answer form, `<id>: fix. <reason>` or `<id>: defer. <reason>`, overrules one before the relaunch, and that a decline nobody overrules is posted with its reason when the round goes on. This is a list, not a question: ask nothing about it, since the run never stops for a decline. Record an overrule under its ID as `{"choice": "<fix|defer>", "notes": "<the restatement>", "date": "<YYYY-MM-DD today>", "disposition": "<fix|defer>"}`, say it back in one line as any answer, and pass it in `args.decisions` with the answers. A decline of an earlier round is already posted: it is overruled on GitHub, as the `done` section says.

**The round's deferred drafts (#95).** A deferred item is worth doing and not in this pull request, and it ends in a drafted issue. On every dial but autopilot the person sees each draft before it is filed. `drafts` lists the ones not yet answered, and `draftsNeeded` their ids; both are empty when nothing was deferred, and, when deferred items are raised at the end of the run, at every stop but that one. Each entry has `id`, `round`, `finding` (file, line, title), `ships` (whether a mitigation ships in the round, read off the round's record and never off the words: before the build a task planned with files, at the end-of-run stop a commit of the finding's own), `mitigation` (the words for it as written, empty when nothing ships), `files` (the paths the planned task touches), `goesTo` (`github`: Redline opens an issue; `spec`: the draft stays in the round's spec folder; `print`: the same, and you print it when the run ends), `dryRun`, `title` and `body` (the issue exactly as it will be filed), `draft` (its version, which the answer names) and `canFix`. A stop can carry drafts and no call: a round with only deferred items stops too. After the calls and the declines:

- **Say where they go, once.** Before the first question, say how many drafts there are and where each goes (`2 drafts, each to a GitHub issue`). When `goesTo` is `github` and `dryRun` is false, add that each draft that goes ahead opens an issue on GitHub, and that a project board that takes new issues gets a card for each.
- **Three drafts or fewer: one at a time.** Show the draft in prose: the finding (ID, file and line, title), what ships in this round, from `ships`, whatever the words say (true: "a planned change" at a round's stop, or "a change in its own commit" at the end-of-run stop, where the record is the commit, with the files it touches, then the words as written, labelled as its words, when they are not empty, since they are not checked and can say that nothing ships, as in `a planned change in app/Jobs/SyncOrders.php (its words: "none")`; false: nothing ships), where the draft goes, then its title and its whole body, exactly as given. Then ask one `AskUserQuestion`, "What should happen with the draft for <ID>?", with **Go ahead (Recommended)** first (filed as drafted; it stays `decided by: redline`), then **Drop it** (not filed, and nothing else changes: a mitigation still ships; posted as the person's decision, with their reason) and, only when `canFix` is true, **Make it a fix** (the item is planned and built in this round, as the person's decision).
- **More than three: the list first, then one question.** List them all, one line each (ID, title, where it goes). Then show every draft's title and whole body under its ID, so each body is seen before anything is filed. Then ask one `AskUserQuestion`, "File all <n> as drafted, or walk them one at a time?", with **File all as drafted** first and **Walk them one at a time** second. On "Walk them", go on as for three or fewer. On "File all", every draft a typed line did not name goes ahead as drafted.
- **Typed lines** work at either question, in the Other field or as a chat line, for the exceptions: `<id>: title. <new title>` (goes ahead under that title, the body unchanged), `<id>: drop. <reason>`, and, when `canFix` is true, `<id>: fix. <reason>` or `<id>: accept. <reason>` (no change at all, a mitigation included). Any other typed line is a question or pushback, as for a call: answer it from the spec folder and ask again.
- **Where a fix can no longer be built.** `canFix` is false at a stop the round reaches after its first resolve (a draft the resolve agent wrote for a deferral the person chose, or one a reshape wrote or changed) and at the end-of-run stop below. Offer no fix there, record none, and when the person asks for one, say that it is done after the run: a reply in the finding's thread, then `/redline-revise <pr> review @<login>` (the namespaced `/redline:redline-revise` where the repository has no alias).
- **Record** each answer under its id in `args.deferrals`: `{"action": "file" | "drop", "title": "<the person's title, or an empty string>", "notes": "<for a drop, the restatement; else an empty string>", "date": "<YYYY-MM-DD today>", "draft": <the entry's `draft` number, exactly as given>}`. The restatement of a drop is one standalone sentence, as for a decision: what the person decided and why, with no quoted chat ("@sam does not want this tracked: the client is replaced next quarter."); it is posted in the finding's thread and listed in the handoff as `decided by: @<login>`. A fix or an accept is not a `deferrals` entry: it is a changed disposition, recorded under its id in `args.decisions` as `{"choice": "<fix|accept>", "notes": "<the restatement>", "date": "<today>", "disposition": "<fix|accept>"}`. Say each answer back in one line. `args.deferrals` holds every answer so far, unchanged, plus the new ones, on every later relaunch.

A draft the person answered is asked again only when it changed: a reshape after a bounced plan can rewrite one, and it then comes back with the next `draft` number and its new body. A `defer` the person types at a stop (`<id>: defer. <reason>`) is drafted after that stop, so its draft is shown before it is filed: at a later stop of the round, or at the end-of-run stop when deferred items are raised at the end of the run.

**An override the run could not apply.** `overridesUnresolved` lists each disposition the person changed (a decline overruled at a stop, or a disposition changed on the plan dial) that the resolve agent could not turn into a task, with the line as recorded (`disposition`, `notes`) and the agent's `why`; its ID is in `decisionsNeeded`. After the calls and the declines, show each in one line (ID, title, the line, the why) and ask the person to restate it in the answer form, `<id>: <fix|defer|accept>. <reason>`, with what the why asks for (`accept` on a decline makes no change, recorded as the person's decision). Record the restatement under its ID as `{"choice": "<fix|defer|accept>", "notes": "<the restatement>", "date": "<YYYY-MM-DD today>", "disposition": "<fix|defer|accept>"}`, say it back in one line as any answer, and pass it in `args.decisions`. The changed line is what lets the relaunch rerun the round's resolve; relaunching the same line replays the same refusal.

**The answer form.** An answer in the person's own words, or with their own reasoning, is one line, `<id>: <choice>. <reason>`: the choice an option label or their own words, the reason optional. It is accepted in the Other field (where the `<id>:` prefix may be omitted, since the question names the call) or as a typed chat line. A typed line not in the form is a question or pushback: answer it from the spec folder (`<repoRoot>/<specFolder>/shape.md`) and the code, never decide for them, and ask the call again. Nothing else is read as an answer.

**Record each answer** as `{"choice": "<option label or their words>", "notes": "<the restatement>", "date": "<YYYY-MM-DD today>"}` under its ID (the workflow adds `decidedBy: "@<login>"` from `args.login`; you never write an owner). When the answer picks one of the call's options (a pick in the question, or a form line whose choice is an option's label as written), add `"option": "<the option's label, exactly as given>"`: the workflow takes what the decision ends in from that option's `ends`, shows the finding by it, and holds the plan written for it to it. You never write a `disposition` for a call the person answered by picking an option, and never an `option` beside a `disposition`: the workflow refuses the two together. An answer in the person's own words carries no `option`, and the agent that applies it states what it ends in. The restatement is **one standalone sentence**: the choice and the person's reasoning, written so a reader who never saw the conversation understands what was decided and why, with no quoted chat, no "I'll take your recommendation", and no Redline role names. When the person gave no reason beyond agreeing, the reason is the recommendation's, stated as theirs ("The author keeps the current default so the list always agrees with the detail page."). Say the restatement back to the person in one line, with what it ends in for a pick ("Mitigate, which ends in an issue") or, for their own words, that the agent applying it will say what it ends in; then move to the next call. `notes` is the decision as it is recorded and published: the spec's Decisions entry, the reply in the finding's thread, and the handoff comment print it and nothing the person typed.

**Relaunch only from the word.** When every call in `decisionsNeeded` and every draft in `draftsNeeded` has an answer, list the restatements and the drafts' answers, one line per ID, and say: type `relaunch` to relaunch with these decisions, or a line in the answer form to change one. A form line is recorded again (a new restatement, said back) and the word is asked for again. The relaunch happens in the turn that starts with the word, under this rule:

**The relaunch rule.** `Workflow(...)` is called only when the person's last typed line is exactly `relaunch`, or, on a launch, a resume (section 2) or the in-session relaunch of a stopped run ("stopped before a result"), a line holding only a Redline command (`/redline:redline <n> ...` or a variant, or the short form a repository's `.claude/commands/redline.md` and `redline-revise.md` provide, `/redline <n> ...` and `/redline-revise <n> ...`, which `/redline:setup` writes; #44). The turn that relaunches need not be the person's (a stopped run is seen in the workflow's notification); the line that counts is still the last one they typed. The harness relays the person's last typed message verbatim to every agent of the run, with precedence over the agent's task; an `AskUserQuestion` pick is never relayed, and a headless session relays nothing. PR #59 showed that a typed answer (`Refuse it`) stops an agent whatever its prompt says, so the only lines Redline ever relaunches from are the word and the command line, and every agent's prompt names those two as conversational, with `args.decisions`, `args.selected`, `args.approvedPlans` and `args.deferrals` the only authority (#60). When the last typed line is anything else, do not relaunch: say in one line that the relaunch needs `relaunch` typed on its own, and wait.

**Save the run record** before the relaunch overwrites it: the harness keeps one record per run id, `<config>/projects/<project>/<session>/workflows/<runId>.json` (`<config>` is `~/.claude`, or, as expected but not measured, the directory `CLAUDE_CONFIG_DIR` names when the session sets it), and a relaunch with `resumeFromRunId` rewrites it. Its path is the marker's `record`: at a stop, the one `run save` printed when it wrote the marker (below), and on a resume, the marker's own. Copy it beside itself, into a `saved/` folder, as `<runId>.launch-<n>.json`, where `n` counts this run's launches so far (1 before the first relaunch): `mkdir -p <dir>/saved && cp <dir>/<runId>.json <dir>/saved/<runId>.launch-<n>.json`, `<dir>` being the record's folder. The copy stays outside the repository. On a resume, if the file at the marker's `record` is gone, say so in one line and go on: the copy is only a backup. `run drift` finds the launch's pinned script through that file, so with it gone it has no copy to compare, and answers `name` while the workflow file's blob is the one the launch recorded and `refuse` once it is not; the relaunch follows that answer, as below (#137, round 4). At a stop the path is the one `run save` printed, and a `run save` that finds no record stops the run (below), so nothing relaunches without one.

**Write the marker** at every stop that waits for the person (a `handoff` of any kind, a `reviewed` result, a run stopped before a result), as soon as the stop is reported, before anything is presented or asked, and so before saving the run record (#137, R2-6): run `${CLAUDE_PLUGIN_ROOT}/scripts/redline-prefs.sh run save <repoRoot> <n> --run-id <runId>`. It reads the run's args and result from the harness record, which it finds under the directory `CLAUDE_CONFIG_DIR` names when the session sets it and then under `~/.claude`, the session id from its own environment and HEAD from git, and writes them under `runs` in `.claude/redline.local.json`, and prints the marker, whose `record` is the path of that record, so a `/redline:redline <n>` typed later, in this session or the reopened one, offers to pick the stop up (section 2, "A stopped run"). If the script exits 2 (no record, no session id), say its line and stop, before any question: `run drift` reads the version the run launched under from the marker before every relaunch (#135), so without it the run is finished with a fresh one.

**The script a relaunch runs (#81, #135).** A relaunch runs the workflow script the run launched with, or it does not run, with one exception no check here can see: a session that switched onto an install older than 0.5.1 runs that build's workflow, which has no version check (the precheck's installs warning names such an install, #137, R4-3). Before every relaunch (a hand-off of any kind, a `reviewed` result, a stopped run, a resume), after the marker is written, run `${CLAUDE_PLUGIN_ROOT}/scripts/redline-prefs.sh run drift <repoRoot> <n> --plugin ${CLAUDE_PLUGIN_ROOT}` and read its JSON, on every repository. Where the person is asked anything before the relaunch (a hand-off of any kind, a `reviewed` result, and a resume of a `handoff` or `reviewed` marker), run it twice (#137, R2-6). First before anything is presented: right after the marker is written, or, on such a resume, right after `run check` passes, since its marker is already written. Act there on `refuse` and on exit 2, as below, so the person answers nothing for a run that cannot relaunch, and say nothing yet for `name` or `scriptPath`. Then again in the relaunch turn, after the word: the relaunch follows that run's answer, its `launch`, `scriptPath`, `agents` and `drift`. A relaunch replays a run's recorded steps only while the script builds the same prompts, and another script can answer to the workflow's name: another version of Redline, since a session runs the install listed first and a reload or a reopen resolves the name afresh (loser #839); a checkout loaded in place whose workflow file changed during the run, on any repository; and, when this repository is the plugin itself, a round's commits to `workflows/redline-loop.js` or an agent file (PR #80). A relaunch under another script would replay nothing after its first changed prompt and rerun rounds already posted. So, by `launch`:

- `name`: the workflow file is as launched. Relaunch by name, as below.
- `scriptPath`: the workflow file changed since launch. Say in one line: "`workflows/redline-loop.js` changed since this run launched, so this relaunch runs the launch's script from `<scriptPath>`. In auto and bypass-permissions mode it runs with no prompt; in manual and accept-edits mode Claude Code asks once per relaunch whether to run the script, and approving it relaunches." Then call `Workflow({scriptPath: "<scriptPath>", args: {...}, resumeFromRunId: "<runId>"})` in place of the call by name, with the same `args` and run id. If the call is denied (in don't-ask mode, and in a headless session in any mode but auto and bypass-permissions), say so in one line and stop: the marker stays, so the person relaunches from an interactive session (`claude --resume <session id>`, then `/redline:redline <n>`) or starts fresh.
- `refuse` (exit 1): the run started under another version of Redline than this session loads, or under a build before 0.5.1, and `line` names both versions, says nothing on GitHub is lost and names the spec folders to commit or remove (#135); or the session loads another copy of Redline at that version than the one the run launched from (a checkout and an installed release, or two checkouts, or a launch copy that is gone), so the rest of the run would call the scripts of the copy it started from, which this session's guard refuses, under this copy's agents (#137, R1-3, R3-2); or the workflow file changed and the launch kept no pinned copy, since it went by the `scriptPath` fallback of section 6 and ran the file itself. Say `line` verbatim, run `${CLAUDE_PLUGIN_ROOT}/scripts/redline-prefs.sh run clear <repoRoot> <n>`, and stop, so the next `/redline:redline <n>` starts fresh. Do not launch.

When `agents` is not empty, agent files changed since launch. They cannot be pinned (an agent run from a copy has no role, so no guard), and they do not stop the relaunch: say `line` verbatim, the sentence naming them, and go on; the handoff comment carries the same sentence for the list in `drift`, for the teammate. When `drift` is not null, set `args.drift` to it exactly as printed, replacing the one an earlier relaunch set; when it is null, leave `args.drift` out. The workflow reads it only at startup and at Finish. Finish's prompts replay on a resume past them, and the handoff comment is the one that names the agent list, so on an `error` or `stopped` marker `run drift` prints `drift` with the list the marker's own args passed, while `agents` and `line` still name every changed file: a resume after the comment posted then replays it, or its duplicate check finds it, and it is never posted twice (#91, R1-1). Only a hand-off or a `reviewed` relaunch, both before Finish, reads the list afresh. On exit 2, say the script's line and stop. The line names the cause: no marker, or, on the plugin's own repository, a marker with no start commit, so the launch's script is unknown and the run is finished with a fresh one; or a `--plugin` whose manifest holds no version, so the version this session loads is unknown (#137, R2-5).

Then relaunch **in this session**:

```
Workflow({name: "redline:redline-loop", args: {...the same args, decisions: {...every decision so far, unchanged, plus the new ones}}, resumeFromRunId: "<the runId you recorded>"})
```

Change nothing else in `args` (a plan hand-off adds `approvedPlans`, a `reviewed` result adds `selected`, a stop that raised drafts adds `deferrals`, and a resume adds `resume`, as their sections say; all four are kept, unchanged but for what a later stop adds, on every later relaunch; `drift` is set or left out afresh at each relaunch, as "The script a relaunch runs" says): the cached agents (review, post, shape) replay only while every earlier prompt and option is identical, and a changed earlier decision would rerun a round that already committed. Record the new `runId`. Never relaunch from a session other than the one that launched the run: the harness has nothing to resume there. The marker (section 2, "A stopped run") and `claude --resume <session id>` are the way back when this session is gone; a fresh `/redline:redline` after the person commits or removes the uncommitted spec folder is the other path (the GitHub agent will not post a second review for a round that already has one).

### `handoff` with `handoffKind: "deferred"` (deferred items raised at the end of the run)

With deferred items raised at the end of the run, no round stops for a draft: each deferred item's reply waits, and when the rounds are done (also when the run reached the round cap) the run stops once, here, only if it deferred something. Nothing of Finish has run: no handoff comment (or cap-hit comment) is posted and no review is requested yet. Say so in one line, and that both follow the relaunch. `drafts` holds every draft the run held, by round, and `draftsNeeded` their ids; `judgmentCalls`, `declined` and `decisionsNeeded` are empty, and `canFix` is false for every draft, since the rounds are over. Present the drafts and record the answers as "The round's deferred drafts" above says, ask for the word ("Relaunch only from the word"), save the run record, and relaunch with `args.deferrals`. The marker was written, and `run drift` first run, before the first draft was presented ("Write the marker" and "The script a relaunch runs" above); as at any hand-off, run `run drift` again in the relaunch turn, after the word, and relaunch on that answer, since the workflow file can change while the drafts are answered (#137, R4-4). The run then files the drafts that go ahead, posts the replies the deferred items waited for, and finishes.

### `done`

Run `${CLAUDE_PLUGIN_ROOT}/scripts/redline-prefs.sh run clear <repoRoot> <n>` first: the run finished, so no marker waits. Then report in a few lines: rounds, commits, and the decisions (`decided`, one entry per item with its `kind`), grouped so the person does not have to open GitHub to learn what Redline decided alone: first what it fixed (`kind` `fixed`), one line each with the ID, the title and the commit; then what it declined on its own (`kind` `declined`), one line each with the ID, the title and the `reason`, followed by one line on how to overrule one: reply in its thread on the pull request (for one in the review body, which has no thread, a pull request review whose body names its id), then `/redline-revise <pr> review @<login>` (the namespaced `/redline:redline-revise` where the repository has no alias). When any round has `scoped` items (`rounds[].scoped`), one line names them, ID and title, as declined under this run's scope (correctness only), or, in a final nit pass's round, under that pass's scope, with no thread and no reply. When any round has `minor` ids (`rounds[].minor`), one line names them as low-severity bugs in the previous round's fixes, which were fixed like a nit and bought no further round; a `warnings` entry about a finding "placed in the fix diff" is one the workflow did not treat that way, and it is reported with the other warnings. After those, in a line each: what was put to the person (`kind` `decided`, `overruled` false; how many by `@<login>`, how many by `redline (autopilot)`), what the person overruled (`overruled` true), and what was deferred, not picked or not changed. Then the findings left to the person under a repository ask rule or on Redline's own files (`forced`: each with its rule id, or `own` true, and, for one nobody answered on autopilot, `open`, what Redline would have done or would have offered; their threads stay open and none is a deferral, except one the person deferred to an issue (#126): its `outcome` ends with where its draft went, it is listed among the deferred items below as well, and its thread is resolved once the draft is filed), whether the PR description was replaced (`prBody.file`, and the old body's `copy` in the round's `redline/` folder, or that no round wrote a `pr-body.md`), whether the handoff comment was posted and the review requested (or, in a dry run, where `handoff.md` was written), the threads (`threads`: how many Redline resolved and, for each left open, the finding and why; `null` when nothing was swept, as in a dry run or with `no push`), any `warnings`, and the run-record commit (`recordCommit`: its short SHA, how many files, whether it was pushed, or that nothing was left to commit). Then run `git status --porcelain`: a finished run leaves a clean tree, so name anything it prints. Then the deferred items (`deferred`), which the run has already filed where its setting says (`deferTo`: `github` opens an issue, `spec` and `print` leave the draft in the round's spec folder; a dry run writes every draft and opens nothing): one line each with the ID, the title, where it went (`deferred to #<number>`, with its `url`, or the draft's `path`) and what shipped, from `ships` and never from whether `mitigation` is empty (true: "a change in its own commit", then the words as written, labelled as its words, when they are not empty, since they are not checked and can say that nothing ships, as in `a change in its own commit (its words: "a log line")`; false: nothing). When `deferTo` is `print`, print each draft after the list as a block the person can paste into their own tracker: `draft.title` on a line of its own, then `draft.body` in a fenced block whose fence is one backtick longer than the longest run of backticks in the body, and at least three, both exactly as given. Nothing is asked here and nothing is opened: a deferred item's issue is filed during the run by the workflow's GitHub agent, through `redline-gh.sh defer`, which this skill never runs.

### `capped`

Run `${CLAUDE_PLUGIN_ROOT}/scripts/redline-prefs.sh run clear <repoRoot> <n>` first. The round cap was hit with correctness bugs open: the cap-hit comment was posted (or written), the run record was committed (`recordCommit`), and no review was requested. List `openFindings` one line each. Then the deferred items (`deferred`), as the `done` section lists them: one line each with the ID, the title, where it went (`deferred to #<number>`, with its `url`, or the draft's `path`) and what shipped, from `ships`, as that section says; when `deferTo` is `print`, print each draft after the list as that section says, `draft.title` on a line of its own, then `draft.body` in a fenced block whose fence is one backtick longer than the longest run of backticks in the body, and at least three, both exactly as given. Then stop. The person picks them up by hand or with another `/redline:redline`.

### `error`

Report `stage`, `error` and anything useful in `detail` (blocked tasks, the approver's adjustments, the checker's reasons), plus the commits made so far and `git status`. Then, when `resumeFrom` is not null (the agent label the run reruns from, and the attempt the relaunch would be): write the marker (`${CLAUDE_PLUGIN_ROOT}/scripts/redline-prefs.sh run save <repoRoot> <n> --run-id <runId>`) and save the run record, and say one line, chosen by the result's `ownCheck` (#116). When it is true, the stop is Redline's own check of what the step's agent returned: say that nothing needs fixing by hand, and that `/redline:redline <n>` offers to resume from `<label>` as it stands, where the step runs again and corrects what it returned, from this session or `claude --resume <session id>`. Otherwise say that once the cause is fixed by hand, `/redline:redline <n>` offers to resume from `<label>`, from this session or `claude --resume <session id>`; a hand fix that touches only `.claude/` files may be committed on top, anything else means a fresh run. When `resumeFrom` is null (a `gather` error, or no agent behind the stop, a relaunch the workflow refused at stage `relaunch`, because its file changed with no pinned copy, #81, or because the workflow running is another version than the run started under, #135, or a stop at stage `finish` because the run was finishing from a round below the highest one posted, #81), first run `${CLAUDE_PLUGIN_ROOT}/scripts/redline-prefs.sh run clear <repoRoot> <n>` (an earlier stop of the same run may have left a marker that no longer describes it), then say the run cannot be resumed and name the uncommitted spec folders to commit or remove before a fresh launch. When the workflow refused a fresh launch (section 6) for its version, this session runs another copy of the workflow than the one at `${CLAUDE_PLUGIN_ROOT}`: a session keeps the workflow it loaded, so in one that loads Redline in place, a commit changed the plugin's version after the session loaded it. The files at that root agree with each other, since the precheck stops a copy whose `plugin.json` and `REDLINE_VERSION` disagree before any launch (#137, R4-2), so a reopen loads one version. Say so, and that reopening the session with the checkout still loaded in place (`claude --plugin-dir <root> --resume <session id>`, `<root>` being `${CLAUDE_PLUGIN_ROOT}`) and typing the command again launches under the checkout's current files; a reopen without `--plugin-dir` runs the installed release instead (#137, R1-7). Do not retry and do not fix anything yourself.

## Rules

- Nothing here posts to GitHub except through the workflow's GitHub agent. A deferred item's issue is opened by that agent during the run, never by this skill.
- Never write a model name, vendor name or AI-assistant marker into anything that reaches the repository or GitHub. Redline labels its work as Redline.
- Outside the workflow, the repo's CLAUDE.md Git section stands: you never commit, push or stage.
- The run marker is written, read and cleared only through `redline-prefs.sh run`; on a resume, `args` come from the marker, never from memory.
- Relaunch only from `relaunch` typed on its own or a line holding only a Redline command, namespaced or the short alias (section 7, the relaunch rule); never from any other typed line.
